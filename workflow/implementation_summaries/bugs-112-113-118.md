## bug-112: the DuckDB instance cache {#bug-112}

**Measured (DuckDB 1.5.2).** Python `duckdb.connect(path)` reuses a cached database instance.
While any connection to `path` is open in the process, a new connect gets THAT database, even
after `os.replace` has put a new inode at the path.

- Read side: a second read-only connect read the old value. `ATTACH ... (READ_ONLY)` from
  `:memory:` read the new one.
- Write side (the ch-bsd 18.1 r1 B-1 sequence): two writers, close one, replace, reopen,
  INSERT + CHECKPOINT. The reopen served the OLD database, and a child process reading the file
  did not see the row. The write was lost silently.
- No in-process route to the new file exists while an old holder is open. A read-write ATTACH
  fails `Unique file handle conflict`, and so does a connect next to a read-only ATTACH of the
  old inode. The path only frees when every holder of the old inode is closed.

**Fix.** `backend.open_duckdb(path, read_only=)` is now the only file-backed opener in `src/`.
It covers Store, `replica_merge`, `migrate` and `cli` compact. An AST test fails on any other
`duckdb.connect(<file>)` call.

- A read-only open ATTACHes the file from a private `:memory:` instance and runs `USE`. It never
  shares an instance, so it always reads the file currently at the path. This covers
  `search.cached_replica`, `verbs.memory_partition`, and any second in-process reader.
- A write open first closes every registered connection still bound to a replaced inode at that
  path, and logs a warning. Those connections were writing into an unlinked file, and their
  owners now get a loud `Connection already closed`. If a holder cannot be closed, the open raises
  `StaleDuckDBInstanceError`.
- `DuckDBConnection.close` deregisters the connection through `release_duckdb`.

**Trade-off.** Each read-only open is now its own DuckDB instance, with its own buffer pool and
threads. Before, every reader of a path in the process shared one instance.

## bug-113: replica merge {#bug-113}

**Root cause: three defects.**

1. Schema lag. `duckdb_catalog.init_catalog` built `entities` without `vectors_partition`; only
   the Store added that column, by ALTER, on open. The merge's positional
   `INSERT ... SELECT ae.*` therefore failed with 13 vs 14 columns. The hand-listed newer-wins
   `UPDATE entities SET` also dropped the column.
2. The op never passed `dry_run` to `merge_slots`.
3. `merge_slots` left its connections open on error. While the op's `except ... as exc` kept that
   frame alive, the writer reopen failed `Unique file handle conflict` (measured in
   `bug113-measure.log`). The op then returned with the writer closed and unlocked.

**Fix.**

1. `duckdb_catalog.ENTITY_COLUMN_UPGRADES` and `upgrade_catalog()` now run inside `init_catalog`.
   The Store, the merge target and the sqlite migration share one schema, and the Store's inline
   ALTERs are removed. A parity test compares a Store-built catalog with `init_catalog` output.
2. Rows are copied `INSERT ... BY NAME`, and the UPDATE SET lists are built from the catalog's
   columns.
3. `dry_run` is passed through.
4. `merge_slots` and `audit_slots` close every connection on every path, and a half-built target
   is deleted.
5. Every op exit reopens the writer through one helper, `_reopen_writer_after_merge`: Store plus
   connection (the lock), then the replica link. If that reopen fails, the op reports it and
   `Daemon._writer_lost` exits for a supervisor respawn instead of serving unlocked.

## bug-118: blocking hooks that never blocked {#bug-118}

**Root cause.** `[ -x P ] && P || true` turns P's `exit 2` into 0.

**Fix.** One helper, `hooks._optional_project_hook`, renders `if [ -x P ]; then P; fi`. All three
sites route through it, and an AST test fails on a second `$CLAUDE_PROJECT_DIR/.claude/hooks`
literal. `.claude/settings.json` is regenerated (3 commands). The in-process `hooks.check` diff
now shows only the clone's path-prefix lines.

**Behaviour change.** `adr-gate.sh` no longer has `2>/dev/null`. The helper does not silence
stderr, because a gate's message is the point of the gate.
