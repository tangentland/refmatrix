## bug-112: the DuckDB instance cache {#bug-112}

**Measured (1.5.2, `bug112-measure.log`).** While any connection to a path is open in the process,
`duckdb.connect(path)` returns that database, even after `os.replace` has put a new file there.

- A second reader saw the old value.
- A reopened writer lost a CHECKPOINTed write (18.1 B-1).
- While an old holder is open, no in-process open can reach the new file ("Unique file handle
  conflict").

**Fix: one opener.** `backend.open_duckdb` handles every file-backed open, and
`backend.attach_file` handles every file ATTACH (mirror, merge, audit, sqlite migration/view).
AST tests refuse a second site of either.

- **Read-only opens** (r1 s-1): one private `:memory:` instance per (realpath, inode) attaches the
  file, and each open gets a cursor of it. A replaced file means a new inode, so the next open gets
  a new instance. The instance closes with its last cursor.
- **Write opens**:
  - Every registered holder of a replaced inode is interrupted, then closed (r1 s-2). The warning
    goes on `refmatrix.backend`, which the daemon routes to rmxd.log (r1 m-2).
  - The inode is checked before and after the connect, with a retry if it moved (r1 m-3).
  - A refused path, or a holder that cannot be closed, raises `StaleDuckDBInstanceError`, a
    `duckdb.ConnectionException`.

**s-1 measurement** (`s1-measure.log`): copy of the 828 MB snapshot, 8 concurrent readers.

| duckdb | path | 8-reader RSS | threads | ms per 3-query round |
|--------|------|-------------:|--------:|---------------------:|
| 1.5.3 | b381b6d raw connect | +6 MB | +0 | 37.9 |
| 1.5.3 | r1 instance per open | +732 MB | +120 | 42.4 |
| 1.5.3 | shared instance (now) | +5 MB | +0 | 41.6 |
| 1.5.2 | r1 instance per open | +148 MB | +120 | 57.1 |
| 1.5.2 | shared instance (now) | +8 MB | +0 | 53.1 |

Opening with one holder already open now takes 9.3 ms, against 20.3 ms in r1 and 8.9 ms at
b381b6d.

## bug-113: replica merge {#bug-113}

**Round 1:**
- one schema: `upgrade_catalog` runs inside `init_catalog`;
- rows are copied BY NAME, with SET lists generated from the catalogs;
- `dry_run` is passed through;
- every connection is closed on every path;
- one helper reopens the writer.

**r1 remedy:**
- **b-1 (THE exit, decision d9bw(d)):** `Daemon._writer_lost(reason)` logs one line, then calls
  `os._exit(2)` immediately while still holding `_store_lock`. It no longer uses a timer or `_stop`.
  The graceful path ends in `os._exit(0)`, which launchd does not respawn. The op's reply is lost.
  - `Daemon._reopen_writer()` asserts that `_store_lock` is held, opens the store through
    `open_duckdb`, and installs it via `_install_writer_store`.
  - `_reopen_writer_after_merge` delegates to both.
  - A real `serve_forever` child exits 2 with `RMX_DEGRADE_EXIT_S` at both 0.2 and 8.
- **b-2:** a swap failure reopens the writer. If A was already replaced, the partial B is removed
  so the rotation repair re-clones it, and A becomes the writer.
- **b-3:** a SET column that the winning source slot predates is set NULL. That is the row as the
  slot would read after the upgrade ALTER. The loser-redirect memory_content statements are
  generated the same way.
- **bug-123 (s-3):**
  - linkage_types merge by name, and B's ids are remapped in entity_links, linkage_evidence and
    `inverse_of`.
  - A partition identity clash is refused with `MergeRefused` before anything is written.
- **Fleet copies:** both directions of the global snapshot with its stale B, and of the refmatrix
  snapshot with its stale A, now merge on 1.5.2 and 1.5.3.
  - Dry runs: `r1-remedy-fleet-merge-dry.log`.
  - Real merges into littlebig scratch: 0 duplicate linkage names, 0 orphan link or evidence rows,
    0 duplicate (partition, kind, name) rows (`r1-remedy-fleet-merge-real.log`).

## ch-bsd r2 remedy (on 69ea55b) {#r2-remedy}

r2 closed every r1 finding and left 2 SKETCHY and 5 MEH items. The remedy commits are 30579e0
(the cherry-picked 0611d2f), 3cdc2cf and the drain test that follows.

### s-r2-1: stale-instance close crashed duckdb 1.5.2 {#r2-s1}

Closing a stale read-only instance while its cursors were mid-statement segfaulted duckdb 1.5.2.

- `_ROHandle` now counts calls in flight (execute, fetch*, ...). When `execute` returns the
  cursor, the call returns the handle instead, so a chained fetch is counted too.
- `shut` sets `closed`, after which new statements raise "file was replaced". It then interrupts
  the live cursors and waits up to 1 s for the count to reach 0 before it closes. If the count
  has not drained by then, the last statement to finish closes the instance.
- The stress child (8 readers plus a replacer) exits 0 on 1.5.2 and 1.5.3. Each was run 3×30 s;
  one recorded run per version made about 119k reads with 0 stale reads and 0 INTERNAL errors
  (`r2-stress-both.log`). At 69ea55b the same child failed on 1.5.2 with
  `INTERNAL Error: Attempted to dereference shared_ptr` (`r2-remedy-red.log`).
- A deterministic protocol test holds a statement in flight. It checks that the instance stays
  open, that a new statement is refused, and that the write open proceeds once the statement
  leaves.
- `.venv-eval` was not touched. Moving it to 1.5.3 is the user's call.

### d-1: enforce-rmx-grep stand-down on master {#r2-d1}

0611d2f is cherry-picked as 30579e0, so master gets the `learn.off` stand-down with the merge. A
test runs the generated command together with the real script, using a tmp HOME:
- with a decoy `learn.off`, it exits 0;
- without the marker, it exits 2.

### The MEH items {#r2-meh}

- **m-r2-1:** `_partition_clashes` is now the one comparison. `merge_slots` refuses on a clash.
  `audit_slots` and its sibling `audit_via_writer` report `partition_collisions` as drift.
- **m-r2-2:** `_drop_handle` discards the handle, so `shut` never interrupts a handle that has
  already closed. The stress run logged 0 such warnings.
- **m-r2-3:** `serve_forever` detaches the backend log handler in its shutdown. A child test shows
  the handler attached while serving and gone at the final exit.
- **m-r2-4:** new tests cover `inverse_of` by name (R2), the read-side inode retry (B1) and a stale
  writer mid-statement (B6). The ATTACH check also catches a string that starts with `ATTACH`
  (A1).
- **m-r2-5:** `_repair_missing_slot_locked` is now one body, shared by the startup asymmetric
  repair and the merge op's copy2-failure exit. That exit re-clones B under the same lock. A
  failed re-clone names the restart.

### Mutations {#r2-mutations}

- Broad run after the r2 remedy (66 files, isolated HOME): 714 passed, 6 skipped, 0 failed

## ch-bsd r3 remedy (on a2911a3) {#r3-remedy}

r3 found the batch mergeable and deployable, with 3 MEH items. All three are fixed.

- **m-r3-1:** the copy2 swap-failure exit now re-snapshots facts.log from the merged A once the
  writer is open on it, exactly as the success path does. The compaction runs after
  `_store_lock` is released, because it takes that lock itself. A failure is logged and appended
  to the op's error. Before this, a rebuild from the log would have dropped the rows the merge
  recovered.
- **m-r3-2:** the file-ATTACH AST check matches the head of an f-string in any case, which catches
  `f"attach {p!r} as x"`. Prose stays case-sensitive.
- **m-r3-3:** `_ROInstance.shut` returns whether it closed. `_close_stale_holders` logs "closed"
  or "close DEFERRED" to match. A failed `_repair_missing_slot_locked` raises `SlotRepairError`
  with `stage` set to "clone" or "reopen", and the merge error names the stage.

**Known limit: writer close.** The writer connection's undrained `interrupt()` + `close()` is
safe only because every writer statement runs under `_store_lock`. A future lock-free op on
`d._st()` would reopen the 1.5.2 close-under-a-running-statement crash.

## Open items {#open}

- `Daemon._install_writer_store` is used by the merge path only. The rotation repair and bootstrap
  still install their own Store; plan-23.1 R1.6 builds on this name.
- `_writer_lost` checks `_store_lock.locked()`, but `_FairLock` has no notion of an owner thread.
- Tables the merge does not copy (`derive_*`, `pagerank`, `coref_resolutions`, `pair_index`) are
  empty in a merged catalog. This is pre-existing.
