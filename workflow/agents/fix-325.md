# bug-325: deliver the successor, not the superseded memory {#root}

rel: implements -> [[bug_registry#registry]]
rel: depends-on -> [[orchestration#task]]

**The defect.** M4 (2026-11-25) measured on the logged product path: 4.7% of memory
deliveries were already superseded when delivered, 20.3% only amended, and 19.4% of
memory-delivering queries carried at least one superseded memory. No injection path reads the
`supersedes` edge (`brief.py` is the only reader). GMD says a superseded node is history: it is
loaded only as context for the node that replaces it. {#defect}

## The fix (Q88 = a) {#fix}

On the two hook channels that inject memories, scan-prompt and per-prompt memory recall (the
hook-invoked calls; find their memory legs with `scripts/rmx-master context` first):

1. A memory that is the target of a `supersedes` edge is replaced by its live successor. A
   chain is followed to its head (A ← B ← C delivers C). A cycle is a loud error counted once,
   and the original is delivered rather than nothing.
2. The successor is deduplicated against the payload: if it is already there, the superseded
   one is just dropped.
3. A memory that is the target of an `amends` edge is still delivered, with one line naming
   its amendment(s) by id.
4. Each substitution is counted in the call's `recall-events.jsonl` rows: the delivered row
   names the successor and carries the superseded id, so U1's and 21.1's readers still see what
   was retrieved. `v` stays 1; the change is additive.
5. Pull calls (`rmx context <name>`, `rmx memory get <name>`, MCP recall) are unchanged: an
   agent that asks for a memory by name gets that memory.
