## 1. The block -> memory tie {#tie}

A block node is `kind=concept`, `name = "<doc-id>#<anchor>"`, `meta.gmd_node = true`,
`meta.doc = <doc-id>`, `path` = the memory FILE (`ingest_gmd.py` `_entity_name`, pass 1). A
memory entity's `path` is NULL, so `path` ties nothing. The H1 `{#root}` anchor is a block
(`<id>#root`); only the synthetic `__root__` node (text before any heading) IS the memory entity.
`part-of` is stored `(concept_id = child, entity_id = parent)`.

| tie | live (583 memories) | LongMemEval (19,829 memories) |
|---|---|---|
| blocks whose name prefix is a memory name | 2,199 (on 404 memories) | 219,904 (on 19,829) |
| ... of those with `meta.doc` == the prefix | 2,199 / 2,199 | 219,904 / 219,904 |
| ... with `path` == the memory's path | 0 (memory path NULL) | 0 (memory path NULL) |
| ... whose `part-of` walk reaches its own memory | 2,194; **5 reach a FOREIGN memory** | 219,904 (depth 1: 19,958; 2: 199,850; 3: 96) |
| blocks with > 1 `part-of` parent | 208 part-of children overall; 10 memory blocks | 0 |
| memories with no block at all | 179 (focus summaries, heading-less) | 0 |

**Verdict: total by name prefix (= `meta.doc`), not by `part-of`.** `part-of` is not structural
only: a GMD `rel: part-of -> [[x]]` line writes the same linkage, so live has 4 blocks with a
direct `part-of` to another memory (`project_recall_state_cmd_mcp_shipped#engine` ->
`savestate_7fb3430f6091`, `project_bsd_five_round_arc_plan12#method` ->
`project_plan12_six_bugs_closed`, `project_concept_provenance_join#root` ->
`project_read_surface_rework`, `feedback_capture_reasoning_in_stm#root` ->
`project_session_0620_stm_forksafety`) and 10 `#root` blocks with two parents (the memory and the
doc `bsd-impressions`). LongMemEval happens to be clean on all three ties. {#tie-verdict}

**The join, chosen (lead's ruling, 2026-11-23: one of `meta.doc` / name prefix, never
`part-of`): the NAME PREFIX**, `split_part(b.name, '#', 1) = m.name AND m.kind = 'memory'` (same
partition, `b.kind = 'concept'`, `b.name` containing `#`). It equals `meta.doc` on every block of
both stores, and it is the cheaper side: `entities` carries a unique key on `(partition_id, kind,
name)`, so the memory lookup is indexed, while `meta` is a JSON `VARCHAR` that would be parsed per
block row. The tests pin the consequences, not the SQL: a `part-of` walk, a `LIKE` join and an
orphan block each have a planted case. {#join-choice}

Wrinkles, for GREEN and the lead:

- A SQL `b.name LIKE m.name || '#%'` is the wrong join: `_` is a LIKE wildcard and memory ids are
  full of it (`00020db3_1`, `feedback_lsof_the_stuck_process`). Use
  `split_part(b.name, '#', 1) = m.name` (or `meta.doc`) and require `m.kind = 'memory'` (doc
  blocks have the same name shape: 14,923 live gmd_node blocks belong to docs).
- 3 orphan blocks on live (`impression_bsd_isolation_drops_the_suite#root`,
  `#the-pythonpath-trap`, `#how-to-apply`): their memory entity and file are gone. They map to no
  memory, so (a) ignores them; they are stale graph state (the lead logs it as a separate bug).
  Under `kinds=["memory"]` they must not appear as hits (one planted case in the tests).
- Every block of every memory carries the tie, so the brief's stop condition did not fire; the
  lead was told so before the tests were written.
