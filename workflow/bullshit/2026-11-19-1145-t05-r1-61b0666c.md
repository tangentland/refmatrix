## Findings {#findings}

### BULLSHIT b-1: a compiling brief silently drops every unembedded memory {#b-1}

**File:** `src/refmatrix/daemon.py:5750` (the plan is built and its `stats` discarded); `src/refmatrix/consolidate.py:703` (`unclustered` covers embedded ids only); `src/refmatrix/brief.py:243-279` (`singleton` reads only `plan["unclustered"]`).

**What:** `compile_memories` clusters only rows that have a vector. Unembedded rows join no cluster and do not appear in `unclustered`. Its stats count them (`stats["unembedded"]`). The op's compiling branch keeps `plan` and throws its `stats` away, and `compile_briefs` never sees the count.

**Evidence:** probe P1 (`tests/test_bsd_t05_probes.py::test_p1_unembedded_rows_under_compile`, mini lane, `workflow/review-output/bsd-t05-probes.log:3-5,240`). It seeded the RED corpus (4 corroborating and 14 lone rows, all embedded) plus 3 memories with no vector, then ran `verbs.memory(root, "brief", compile=True)` on a real spawned daemon:

```
P1 stats: {"briefs": 15, "by_class": {"corroborated": 1, "singleton": 14}, "classes_not_run": {}, ..., "memories": 21, ..., "skipped": 0, "skipped_by": {}}
P1 unembedded seen in briefs: [] | 'unembedded' anywhere in reply: False
E  AssertionError: 3 unembedded memories are in stats.memories=21 but in no brief, no skip count and no reply field: skipped=0 skipped_by={}
```

So 21 memories go in and briefs cover 18, with `skipped: 0`. The CLI then prints "15 brief(s) over 21 memories" while 3 of them were seen by no plan-derived detector and counted nowhere.

It is also inconsistent inside `compile_memories`. When fewer than 2 rows are embedded, the early return (`consolidate.py:576`) puts EVERY row, unembedded ones included, in `unclustered`, so they become singletons. With 2 or more embedded rows they vanish.

**Why it's bullshit:**
- `brief.py` rule 3 (module docstring): "A row that cannot be read is counted and returned, never quietly dropped — `feedback_no_silent_failures` governs anything between a memory and the store, and a detector is on that path." `tests/test_brief_detectors.py:25` restates it for unembedded rows by name.
- CLAUDE.md #no-silent-failures is CRITICAL, and the before-commit gate says "no new silent failure on a memory path".
- The drop already existed on the CLI path (the old CLI discarded the plan's stats the same way, and r5's live `--compile` check missed it). This diff made the op the owner of the plan and opened the same drop to the verb and to MCP, which could not reach these classes before. For those surfaces it is new.
- If the lead rules that the brief is not a memory path, this is SKETCHY. I rank it BULLSHIT because the module names itself as on that path.

**Fix I'd accept:**
1. In `_op_memory_brief`'s compiling branch, carry the plan's `unembedded` (and the ids or names, so the count can be acted on) into the brief stats: `skipped += n`, `skipped_by["unembedded"] = n`. The CLI's existing "N row(s) skipped (…) — counted, not dropped" line then reports it. Or report them as their own class; but a count with a reason is the module's own convention.
2. Do the same in `compile_briefs` for a caller-supplied `plan`, so the two plan sources agree.
3. Test: extend `test_compile_reaches_the_plan_derived_classes_through_every_entry_point` (all three surfaces) with unembedded rows, asserting `skipped_by["unembedded"] == 3`.

Seen failing first: P1 is that test's RED.

**Pattern match:** YES. It is the r4 #s-2-r4 class (`skipped_by` incomplete, the CLI printed `(?)`): a skip total that does not cover every row a detector failed to see.
