## Findings {#findings}

### MEH m3-1: the whole-batch re-queue is unpinned, and it turns a deterministic batch crash into a permanent wedge of the queue {#m3-1}

**File:** `src/refmatrix/sync.py:150-155` (`except BaseException: if raws: enqueue(s.root, raws); raise`).
- Mutation RQ (`if raws:` → `if False:`) **survived**: 49/49 across `tests/test_sync*.py`
  (`26.2-bsd-r3-mut-RQ-batch-requeue-dropped.log`).
- **By reading, not probed:** a path that makes `_sync_paths` raise anything other than `MemoryOwnershipError` is
  now put back on every flush. Each new batch drains it together with every newly queued path, fails, and
  re-queues all of them, so nothing in the project syncs until that path is fixed.
- The failure is loud on each turn through the async record. At 90abc72 the batch was dropped and the next flush
  proceeded.
- **Fix:** a test that a raising batch re-queues its paths, plus a bound: retry a whole-batch failure once per
  path, then quarantine the path that fails alone, named on the record.
- **Lead note (measured, 2026-11-10):** across the 8 fleet stores' `rmxd.log`, 1 `async flush failed` line since
  2026-06 (cliquedb 2026-07-10, a DuckDB `FatalException` index drift, after which the daemon fast-exits and a
  re-queued batch is retried after the respawn) and none in the last 7 days. Follow-up row, not a merge blocker.

### MEH m3-2: implementer flag 1 — the foreground flush blocks Stop without a daemon or launchd, and the `--async` help is wrong {#m3-2}

- With no daemon answering and no launchd install, `--async` falls through to an in-process synchronous flush
  (`cli.py:8711-8716`). That flush now runs in the Stop / SubagentStop / SessionStart foreground.
- All 8 fleet stores are launchd-managed, so they take the `daemon down — queued` return; the latency lands only
  on unmanaged stores.
- The help still says "No-op without a running daemon".
- **Judgement:** acceptable for this merge. Fix the help. Optionally, on the no-daemon `--async` path, enqueue and
  print a loud "no daemon: queued, not flushed" instead of flushing in the hook.

### MEH m3-3: implementer flag 2 — a watch record can be sticky and can also be dropped, and the watcher never retries a refused path {#m3-3}

- The ACK carries every route's record, so a standing `watch` record fails each hook flush until a clean watch
  flush. That part is the intended loudness.
- But any clean watch flush clears it, including one over unrelated files
  (`daemon.py` `elif not cancelled: clear_sync_error("watch")`).
- The watcher has no queue: the refused path is retried only on its next fs event.
- So the refused path can stay unsynced after the record has been cleared.
- **Fix:** have the watcher put refused paths on `dirty.queue`, so the async route owns the retry and its record
  stays until that path is clean.

### MEH m3-4: implementer flag 3 — `rmx sync --stale` reports a refusal as a stopped daemon and exits 0 {#m3-4}

`cli._sync_stale._bail` handles an `ok:false` refusal reply this way:
- it prints a yellow "daemon stopped at N/M (…error…)" and returns exit 0;
- it re-enqueues the chunk's already committed healthy paths, which is harmless;
- its enqueue is wrapped in `except Exception: pass`, which is pre-existing.

**Fix:** tell a refusal apart from a dead daemon (ok:false with a reply versus a socket error), word it as a
refusal, exit 1, and count a failed enqueue.

### MEH m3-5: the refusal names no remedy {#m3-5}

- The refusal text (`refusal_summary` / `MemoryOwnershipError`) now prints every turn until the row is fixed.
- It says "cannot tell whether it owns the anchors" but does not say what to do.
- **Fix:** append the remedy, e.g. "repair the row's metadata or `rmx memory forget <name>`". The `forget` path
  now works, thanks to e47ddb8's `forget_memory` fix.
