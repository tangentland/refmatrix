## (2) `evidence_stale_drop` through `rebuild_index_from_log` {#b1-replay}

These cases replay correctly:
- **Normal stale row.** The drop at `T` deletes every copy appended at or before `T` with the same
  `row_key` + `detail`, and a re-ingest after `T` survives.
- **Legacy append** (no `c_kind`, a name logged as both `doc` and `concept`). The drop carries the
  kind `resolve_c_kind` gives, so the rebuild deletes the copy where it placed it (AC-10 legacy
  variant, mutation "key the drop on the catalog's kind").
- **No append at all** (`stale_drop_unlogged`). The rebuild never held the row.

**Double drop.** Step 3 (dead entity) and step 3b (both ends live) select disjoint catalog rows.
Two drop events can name one key only for a reborn name. Replay deletes are idempotent, so a second
delete finds nothing and loses nothing beyond what the catalog dropped.

**Not airtight, two edges:**
- the live-holder guard checks the CATALOG's keys while the rebuild places copies by RESOLVED keys
  (M2);
- in the guarded case the rebuild keeps a surplus copy (M2).

**`FOLD_OPS` is untested for the rule** (M1). 17.4's AST test catches a missing op. Nothing checks
that the fold agrees with the rebuild.

### SKETCHY S1: 22.6 AC-10 was only half converted, so it asserts the op it now forbids {#s1}

**File:** `task-22.6-removal-entry-points.md:823-824` and `:826-838`.

**What:**
- AC-10 still says "(a) is in step 3b's manifest and gone, with one `evidence_remove` event".
- The same AC's new mutation list says "log `evidence_remove` instead … FAILS".
- R10 (`:517`) now says step 3b "does NOT log 22.2 R3's `evidence_remove`".

A builder writing the assertion as worded writes a test that fails on correct code. A builder
writing the mutation writes the opposite assertion.

**Also, the legacy variant's live-holder mutation may be unable to fail.** "Drop a live holder's
key" (`:834-835`) fails only if (f)'s `evidence` append shares (e)'s `(linkage, file, line,
detail)` and end NAMES, because only then does R10's scan collect it. As written, (e) is a stale
row on doc `X` and (f) is a live row "under the same name" with a `c_kind: doc` append and its edge
present. If (f) is on doc `X` with the same target entity, the edge key is the same and (e) is not
stale. So (f) must differ in its target's kind (same name, other `e_kind`). The AC does not say so.
With an unrelated (f), the scan never sees its key and the mutation is vacuous.

**Fix:**
- Replace "with one `evidence_remove` event" with "with one `evidence_stale_drop` event (no
  `evidence_remove`)".
- Spell out (f) as: same `linkage`, `file`, `line` and `detail` as (e); same end names; `c_kind:
  doc`; target of another kind; its edge present.
- State the scan result the test asserts: keys {`concept X` dropped, `doc X` counted
  `stale_drop_live_holder`}.

**Pattern match:** YES (`imp-widening-fold-breaks-identity-clauses`: a fold that rewrote the
requirement and left the AC's sentence).

### SKETCHY S2: R2b reads `denotes`, but a concept that `memory_link` mints after its target exists gets none {#s2}

**File:** bug-218 R2b `:158-174`, AC-4b `:262-271`; bug-216 rev 6 `#r7-denotes`.

**What:**
- R2b's NAME path resolves doc, then memory, then concept (the concept only when no doc or memory
  has the name), and adds "every concept that `denotes` it … which is where a same-named
  `memory_link` concept lands".
- bug-216 creates `denotes` in two places only: (a) the one-time derive, now the verb `rmx derive
  denotes` (R14), and (b) "GMD ingest maintains it: ingesting a doc or memory with id X links every
  concept named X". Ingest skips unchanged files by content hash (bug-216 R10).

**Why it's sketchy:** the common order is that memory m5 exists first and a user later runs `rmx
memory link m6 reinforces m5`. `Store.memory_link` then calls `add_concept("m5")`, a new concept
with no `denotes`. `rmx memory score m5` resolves the memory, excludes the bare concept and finds
no `denotes`, so m6's statement is unreachable until m5's file changes or someone runs the derive.
AC-4b hides this, because its fixture runs "bug-216's derive" after the link. The S2 gap is closed
for the derive-after order only. Separately, AC-4b's 2.0 needs m6 created now, and the AC does not
say so.

**Fix (recommended):**
- `Store.memory_link` maintains `denotes` for the concept it resolves. It calls the same
  idempotent helper GMD ingest uses for "on ingest of X", linking the concept to a same-named
  doc/memory.
- AC-4b drops the explicit derive step, ingests m5 first and fixes m6's creation time.
- Add the mutation "`memory_link` maintains no `denotes`" (score reads 1.0, m6 missing).

**Alternative:** R2b's NAME path also adds the same-named concepts directly. That duplicates
`denotes`' job, so the helper is better.

**Pattern match:** YES (`imp-before-after-same-terms`: the fixture builds the state in the one
order the fix handles).

### MEH M2: the live-holder guard compares catalog keys, while the rebuild places copies by resolved keys {#m2}

**File:** `task-22.6-…:530-535`.

**What:** the guard skips a drop when "the catalog holds a NON-stale evidence row with the same
`row_key`". Two edge cases follow:
- **A live row whose own append is legacy.** Its catalog key (say `doc X`) can differ from where
  the rebuild put its copy (`concept X`). A stale row resolving to `concept X` then passes the guard
  and deletes the live row's only rebuilt copy.
- **The guarded case.** The catalog deletes the stale row but no drop is logged. The rebuild then
  holds one more copy at the live holder's key than the catalog does. That is a multiset divergence
  of the kind bug-216 AC-14 forbids. It is counted, not reconciled.

Both cases need a name logged under two kinds plus a coincident `(linkage, file, line, detail,
e)`, so they are rare.

**Fix:**
- Evaluate the guard against the RESOLVED keys of the live rows' own appends, which R5's one scan
  already collects.
- State the guarded case's rebuild surplus as accepted residue (counted `stale_drop_live_holder`),
  or give the op a `keep` count.

### MEH M4: R2b's concept leg does not say it keeps canonical-variant matching {#m4}

**File:** bug-218 R2b `:165-167`.

**What:** `rmx memory score` resolves today with `resolve_concept_ids(name, strict=False)`, which
matches every concept whose canonical form equals the name's (camelCase, dash and space variants;
`store.py:3305-3333`). R2b's NAME path says "the concept only when no doc or memory has the name"
and does not say whether that leg keeps the canonical match. A builder writing an exact-name lookup
regresses `memory score FooBar` for a `foo_bar` concept, and no AC catches it.

**Fix:** the concept leg is `resolve_concept_ids(name, strict=False)`. Add an AC-4b row with a
variant spelling.

### MEH M5: R0b cannot produce R4's candidate and `ambiguous` counts from a catalog copy alone {#m5}

**File:** bug-218 R0b `:110-130`, R4 candidates `:195-200`, AC-8 `:287-290`.

**What:** R4 separates candidates from `ambiguous` rows by a `rel:` `evidence` append in
`facts.log`. R0b's procedure copies only `catalog.read.duckdb`. AC-8 nevertheless requires "R4's
candidate and `ambiguous` counts".

There is also a cheaper discriminator. A GMD row whose evidence was lost has a node SOURCE
(`<doc>#<anchor>`, a name containing `#`), while a pre-R1 `memory_link` concept is
`add_concept(<name>)`. The `facts.log` test alone misclassifies a GMD row whenever its append is
missing (logging off at the time, or a compacted log).

**Fix:**
- R0b also copies `facts.log`, read-only, for that count.
- R4 lists every row whose concept side is a GMD node name (contains `#`) as `ambiguous`,
  regardless of the log.

### MEH M6: `--reinforce-orientation [--apply]` clashes with `repair-index`'s `--dry-run` convention {#m6}

**File:** bug-218 R4 `:191-194`; `cli.py:9800-9814`.

**What:** `repair-index` today applies by default and takes `--dry-run` for `--fragments`. With no
flag at all it STOPS the daemon and rebuilds an index. R4 adds a mode that is dry-run by default
with `--apply`. The spec does not say what `--reinforce-orientation --dry-run` or `--fragments
--apply` do, and does not say whether `--reinforce-orientation` can combine with `--entities` or
`--fragments`.

**Fix:** state the flag matrix. `--reinforce-orientation` is exclusive with the other modes,
rejects `--dry-run` (its default) and accepts `--apply` only with it. Add it to AC-9.
