## Findings {#findings}

### SKETCHY: the bug-135 fix took legacy-partition detection out of `memory_partition` on never-snapshotted stores — the MCP bootstrap now writes to `p` while the CLI writes to `memory-p` {#s-1}

**File:** `src/refmatrix/search.py:69-80` (`cached_replica` refuses the writer's primary
catalog); `src/refmatrix/verbs.py:354-366` (`memory_partition`: replica-first probe, then
`require_daemon` → absent → `return project`); `src/refmatrix/mcp.py:113`
(`_t_memory_add` bootstrap writes to `memory_partition(root)`).

**What:** `memory_partition` is "THE routing every memory verb must use". With no daemon, its
replica-first probe was the only thing that detected a legacy `memory-<project>` partition, and it
did so by reading the writer's primary catalog through the cache. bug-135 made the cache refuse
that file, so the probe now falls to absent, which returns the project partition. The CLI has its
own detector (`cli._legacy_memory_partition_exists`, a read-only open that is closed afterwards),
so the two bootstrap paths now disagree on the same store state:

| store: no daemon, no snapshot, legacy `memory-p` holds `legacy_row` | base 5787c6f | head 1081a05 |
|---|---|---|
| `verbs.memory_partition(root)` | `memory-p` | **`p`** |
| CLI `rmx memory add new_row` | crash (bug-135) | exit 0, lands in **`memory-p`** |
| MCP `rmx_memory_add mcp_row` (bootstrap) | crash (bug-135) | `{'id': 2}`, lands in **`p`** |

That is a split brain: the family `memory_partition` exists to prevent. Base failed loudly; head
writes to the wrong partition silently.

**Why SKETCHY:** exposure is narrow. It needs a legacy partition (a pre-merge store) and a store
that has never been snapshotted. Every store that has ever run a daemon has
`catalog.read.duckdb`, and then the probe reads the real replica (probe [B]: an up store returns
`memory-p`). But the change was not described: the registry row says "falls to its documented
bootstrap branch (no daemon → project partition)" and does not mention that the legacy check went
with it.

**Fix (about 6 lines):** in `memory_partition`, when `cached_replica` raises and
`require_daemon` says absent, check `partitions` for the legacy name with a read-only Store that
is CLOSED afterwards. That is the shape of `cli._legacy_memory_partition_exists`, and better still
is one shared helper so CLI and verb cannot drift. Then return the legacy name if it is present.
Pin it with this probe's MCP case.

**Pattern match:** YES. This is [[bsd-impressions#imp-read-fix-reaches-write-path]]: a read-cache
fix on a shared resolver reached its write-path caller.

### SKETCHY: the transport-wording guard covers one spelling; it passes eight evasions and already misses one live site {#s-2}

**File:** `tests/test_task3_6_r9_remedy.py:160-203` (`_DIAL_ATTRS`, `_DIAL_MODS`, `_WORDS`,
`_second_classifiers`); `src/refmatrix/cli.py:1336-1347` (`focus summarize --promote`:
`except (TimeoutError, socket.timeout, OSError)` around `_memory_daemon_call` →
`"daemon busy: promote not confirmed within …"`); `src/refmatrix/cli.py:10077-10090` (ingest-gmd:
the classifier is called and its words used, but nothing pins it).

**What:** I ran the test's own `_second_classifiers` against planted handlers. It flags only the
baseline (`raise RuntimeError(f"daemon busy ({e})")` around `daemon_mod.call`). It does NOT flag:

1. an f-string helper (`raise RuntimeError(_busy_msg(root, e))`);
2. a module constant (`BUSY_MSG % e`);
3. an unlisted module alias (`_daemon_mod2.call`);
4. a from-imported `call(...)`;
5. a dial through cli's wrapper `_memory_daemon_call`;
6. synonyms ("down", "wedged");
7. a "delegate" that calls the classifier on one branch and words its own error on another;
8. a handler that calls the classifier and then discards it. N8 shows this: ingest-gmd reverted to
   `"daemon busy (pid=…"` with `c` computed and unused, and it survives all 20 tests in the 3.6
   file.

A wider AST scan of src (any `try` around a `call` / `_call` / `_memory_daemon_call` / `rpc` /
`ping`) finds one store-daemon site the guard cannot see: `cli.py:1341`. It words ANY `OSError`
as "daemon busy", including a refused or missing socket after the status probe. That is r9 #s-1's
wording, one wrapper away. The other three hits are out of scope:

- `verbs.py:943` re-words an already-typed `VerbBusyError`.
- `reranker.py:449` is the model worker.
- `verbs.py:1395` is the hub.

**Why SKETCHY, not escalated:** `cli.py:1341` is reachable only in the race after
`daemon_status(...)` said up, and nothing opens a slot. But the user asked whether an f-string
helper fools the guard. It does, and so do seven other shapes. AC-5 claims "no src handler words a
store-daemon transport error itself", and that claim is false at `cli.py:1341`.

**Fix:**

- Route `cli.py:1341` through `classify_transport_error`, keeping its "may still complete" note
  for the timeout case.
- Widen the guard's dial set:
  - compute dial wrappers the same way delegates are computed (any function whose body dials,
    which covers `_memory_daemon_call`);
  - match from-imported `call` and any `*daemon*` alias.
- Have the word scan follow calls in the handler to module-level functions and constants.
- Treat a handler that calls the classifier but never uses its result as a second classifier.
- Plant a fixture for each shape so the guard is proven to FAIL on it.

**Pattern match:** YES. This is [[bsd-impressions#imp-ast-guard-one-spelling]], the fourth
guard-evasion finding across the bug-129 and plan-3 arcs.

## Answers to the coordinator's four questions {#answers}

1. **cached_replica's four callers, no daemon and no replica (real tmp store, head vs base).**
   - `_replica_bundle`, `_locate_one_project` and the federated fan-outs are reached only through
     `_live_roots`, which means an up daemon. An up daemon has a snapshot, so these are not
     user-facing for a no-daemon store.
   - With a snapshot deleted under an up daemon (an artificial case), head reports `no replica to
     read …` in `skipped`. Base read the writer's pre-rotation `catalog.duckdb` as if it were
     current. Head's behaviour is the honest one.
   - `rmx context`, `rmx query` and `rmx neighbors` use the CLI's own `_read_store`, not
     `cached_replica`, so they are unaffected.
   - **UI `replica_context`** on a never-daemoned store now returns `{"error": "replica
     unavailable: no replica catalog …"}`, where base returned the bundle. That is a real but
     narrow regression; the hub UI normally spawns or finds a daemon, which snapshots. It is an
     observation, not a finding.
   - **`memory_partition`** regressed in the way that matters: [[#s-1]].
2. **bug-135: is the fix at the cause?** At the measured cause, yes. The leak was the
   process-lifetime cache holding an `rmx_ro` attach of the WRITER's file. The other read-only
   opener (`_reader_store`) closes its handle and is harmless (measured in
   `bug135-measure.log`). Refusing to cache a non-replica is the right contract for a *replica*
   cache. The deeper enabler, `Store(read_only=True)` silently resolving to the writer's primary
   file, is untouched. That is acceptable, but it means any FUTURE long-lived read-only holder will
   reproduce bug-135. The one thing lost downstream is [[#s-1]].
3. **3.7 family table:** it anchors (#b-1 closed) but it is not a build spec yet; see [[#m-2]].
4. **Can an f-string helper fool the AST guard?** Yes, along with seven other shapes, and one live
   site already gets past it; see [[#s-2]].
