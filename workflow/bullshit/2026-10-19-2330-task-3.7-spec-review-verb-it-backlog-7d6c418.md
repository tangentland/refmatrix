## Findings {#findings}

### BULLSHIT: C3 names snapshot helpers that do not exist; the real ones open the writer or leak into MCP {#b-1}

**File:** task-3.7 spec #c3 and #fam-graph-read; src/refmatrix/cli.py:715, src/refmatrix/search.py:42, verbs.py:365
**What:** C3 says "the lock-free snapshot via the existing `read_store` / `read_with_fallback`
helpers".
**Why it's bullshit:** Neither helper exists at the verb layer.
- `_read_store` / `_replica_read` live in cli.py and raise `click.ClickException`.
- `_read_store` falls back to `_store()` → `_store_rw()`, a read-write open of the writer
  slot, when the daemon is absent.
- `_read_with_fallback` is daemon-internal.
- The helper verbs actually use is `search.cached_replica`, a process-lifetime cache. Inside
  `rmx mcp`, a long-lived process, that is the bug-136 hazard: a read-only open with no
  snapshot attaches the writer's file. bug-136 is open, as a rider on task 23.5.
An implementer will either import cli helpers into verbs (a layering inversion, plus
`ClickException` over MCP) or hand-roll an open.
**Fix:** Name ONE verb-layer reader, e.g. `verbs._snapshot_read(root, partition, fn)`:
- open per call and close after; never cache;
- refuse a non-replica file;
- daemon up with no snapshot → a read-worded `VerbBusyError`;
- in-process read-only only when `require_daemon` says absent;
- the result carries `source`.
Cite bug-136. Add a test that holds the MCP process across two calls.
**Pattern match:** YES (bug-135/136, r10 "where the success lands").

### BULLSHIT: `recall` routed through `memory_recall` silently changes what it ranks {#b-2}

**File:** spec #fam-graph-read (recall row); daemon.py:6256; cli.py:11180-11245; recall.py:64/120
**What:** The spec routes `recall` through the daemon `memory_recall` op and turns
`--concept` / `--symbolic` into a `candidate_ids` prefilter.
**Why it's bullshit:** The two paths rank differently.
- `memory_recall` runs `hybrid_memory_recall` (content_rank BM25 ⊕ dense). It defaults to
  `fuse=True`, auto concept-prefilters, and reranks under `_store_lock`.
- The CLI runs pure `dense_recall` by default, and `-s` is a caller-RANKED RRF input to
  `hybrid_recall`, not a filter.
- The CLI degrades to symbolic-only when dense is unavailable. The op returns `ok:false`.
So the spec breaks its own C2 ("options keep their meaning"), and an implementer gets a green
test over a different algorithm.
**Fix:** Add a project-recall op (or extend `ann_search`) that runs `dense_recall` /
`hybrid_recall(symbolic_hits=, candidate_ids=)` server-side, with `fuse` off by default. Keep the
symbolic-only branch. Pin rank order with a fixture whose order differs between the two
algorithms. The alternative is to record the semantic change as a decision.

### BULLSHIT: the curator-drain "atomic rename" closes no window; MCP gets drain without the snapshot read {#b-3}

**File:** spec #fam-refine-drain; gmd-curator.md:136-150; hooks.py:181/241; daemon.py:3113-3133
**What:** The spec says "the drain renames the queue file atomically before reading it".
**Why it's bullshit:**
- Drain reads nothing. Entries are lost between the agent's `curator status` snapshot and the
  drain (catalog-B #fam-refine 7), and a rename inside the drain does not touch that window.
- The generated hooks also run `curator status --drain` on every prompt.
- `curator status` (the snapshot) is classified `hook`, so an MCP agent can only drain blind.
  That breaks the template's own crash-safe order.
**Fix:** Build `rmx_curator(action=status|drain)`.
- `status` returns entries plus a token (byte size).
- `drain(token)` removes only that prefix, under a lock shared with the watcher's append.
- The no-drain `curator status` becomes the status twin; the hook keeps `--drain`.
- Test: an append between status and drain survives.

### SKETCHY: defaults parity cannot see dispatcher actions, and the actions' defaults conflict {#s-1}

**File:** tests/test_verb_parity.py:158 (PAIRING keyed by verb → CLI_MAP twin only)
**What:** C6 promises "PAIRING / defaults rows for every twin", but the parity mechanism cannot
hold one row per action twin.
**Why:** `CLI_ACTIONS` twins get no defaults check. Shared parameters conflict between actions:
- focus `top`: 20 (context) vs 60 (topics);

- `k`: 10 vs 40 (timeline);
- `linkage`: multiple/None vs `"mentions"`.
The `"ALL"` escape (`rmx_memory`) invites a vacuous gate for 41 of the 42 paths.
**Fix:** Use `X | None = None` resolved through an `ACTION_DEFAULTS[(verb, action)]` table. Add a
test that every `CLI_ACTIONS` twin's click defaults equal that table. Forbid `"ALL"` for the
eight new verbs. Name `_ACTIONS_SEED` and `CLI_ACTION_INVOKE` in C6.

### SKETCHY: a `project` filter parameter collides with the transport `project` {#s-2}
