## Findings {#findings}

### BULLSHIT: `queue_depth` counts the callers BEHIND you, after the queue has drained {#b-1}

**File:** `src/refmatrix/modelsrv.py:251-263` (`_augment_info`), `:471-487` (`_handle`)

**What:** `(1 + queue_depth) × docs × cost` is the arithmetic the whole task adds, and
`queue_depth` is called out by name as *"the term bug-019's fix was missing"*. `_handle`
increments `_pending[role]`, calls the worker, and decrements in a `finally:`. `_augment_info`
runs **after** that `finally`, reads `_pending`, and subtracts one more *"for the caller being
served"* — a caller the decrement already removed.

**Why it's bullshit:** the value is sampled at the one instant it is guaranteed not to describe
the caller's wait. Two probes against the real `_handle` over `socketpair`s:

```
# two rerank callers in flight/queued, info caller arrives THIRD
info answer: {'ok': True, ..., 'queue_depth': 0}
callers actually ahead of it when it queued: 2

# info caller goes FIRST, three reranks arrive BEHIND it
queue_depth reported: 2
```

So it reports `(callers who arrived after you) − 1`, and reads **0** in the single-contender case
— one other hook running — which is the exact condition bug-025 documents (9.26 / 14.08 / 3.72 s
for "the same" pool). With `queue_depth` pinned at 0 the estimate is off by the factor the term
exists to supply, and `RerankSkipped` will not fire when it must.

**Evidence:** `estimate_rerank_s` is unit-tested with `{"queue_depth": 2}` handed in by the test,
and `_augment_info` is unit-tested with `srv._pending["rerank"] = 3` set by the test. Neither
touches `_handle`. The live measurement
(`workflow/measurements/rerank-cost-budget-0916.md#live-private`) has one caller and records
`queue_depth: 0` — the only value the bug cannot distinguish from correct. Mutation A named in the
summary (*"`estimate_rerank_s` ignores `queue_depth`"*) mutates the arithmetic, never the producer.

**Fix:** snapshot the depth at ENQUEUE, not at completion — read `_pending` immediately after the
increment (`pending_before = pending - 1`, i.e. callers already in line) and carry that value into
`_augment_info`; delete the second `- 1`. One test that drives `_handle` with two clients closes
it for good.

**Pattern match:** YES — [[impression_bsd_existence_check_tests]] (a gate that populates the value
it then compares) and [[impression_bsd_tests_bypass_wiring]].

### BULLSHIT: the phase instrument names the wrong phase, and the measurement doc documents the shift instead of fixing it {#b-2}

**File:** `src/refmatrix/cli.py:40-56` (`render_phase_report`)

**What:** `phase_mark(name)` is documented as *"Record that `name` finished now"* and every call
site obeys that (`phase_mark("build_context")` sits immediately after the `build_context` call).
`render_phase_report` then labels interval `i` with `_PHASE_MARKS[i-1][0]` — the phase that ended
at the interval's **start** — and labels the trailing interval with `_PHASE_MARKS[-1][0]`, which
is the phase that had already finished.

**Why it's bullshit:** the task exists to ATTRIBUTE 8.5 unattributed seconds, and it attributes
them to the neighbour. A run whose costs I fixed in advance (2.0 s inside `build_context`, 0.5 s
after it):

```
rmx phases: import=0.012s entry=0.000s click-parse=0.000s context-import=0.000s
            dispatch=0.000s route-decision=0.000s store-bind=2.005s build_context=0.505s total=2.523s
ground truth: build_context cost 2.0 s; everything after it cost 0.5 s
```

`store-bind` is billed for `build_context`'s 2 s. `build_context` is billed for the render.

**Evidence that this was known and worked around rather than fixed:**
`workflow/measurements/cli-startup-gap-0916.md#instrument` says, in the document that publishes the
instrument's output, *"Each number is the time from that mark to the next, so `route-decision=…` is
`build_context` itself."* That is rule 10: the symptom was made survivable in prose instead of
fixed in the one function whose entire job is the label. The next reader of a `rmx phases:` line —
who will not have the measurement doc open — reads the wrong phase name.

The tests cannot see it: `test_every_phase_appears_exactly_once` checks that each name appears,
and `test_the_splits_sum_to_the_total` checks the sum. Neither asserts which interval carries
which label.

**Fix:** label interval `i` with `_PHASE_MARKS[i][0]`, keep `import` for the first, and give the
trailing interval its own name (`render`/`exit`) instead of reusing the last mark. Then delete the
compensating sentence from the measurement doc.

**Pattern match:** YES — [[impression_bsd_existence_check_tests]]; and this is the second
instrument in two rounds whose own doc carries the correction.

### MEH: the reranker's deadline is anchored AFTER the probe, so the leg can outlive the caller's budget {#m-1}

**File:** `src/refmatrix/reranker.py:297-304`, `:481-511`

`shared_reranker` probes (`client.info(timeout=probe_timeout)`, up to 1 s) and **then** constructs
`RemoteReranker(client, budget_s=timeout)`, which sets `_deadline = time.time() + timeout`. The
caller measured `rem = _l(30.0)` before the probe, so the reranker is handed a fresh `rem` seconds
starting after the probe consumed part of it, and `SharedWorkerClient`'s socket timeout is `rem`
too. Worst case the leg finishes ~1 s past the hook's own deadline, on a 5 s budget.

The `_budget_s` docstring claims the opposite: *"a 1 s `info` probe that ate 4 of 5 s must leave
1 s for the decision."* Construction order makes that false. (`score()`'s own `info()` is free —
`SharedWorkerClient.info` caches — so the second probe costs nothing; this is the first one only.)

**Fix:** pass an absolute deadline (`deadline=t0 + rem`) rather than a duration, computed before
the probe.
