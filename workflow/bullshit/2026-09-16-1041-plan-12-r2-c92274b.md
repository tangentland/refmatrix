## Findings {#findings}

### BULLSHIT: `ahead` is sampled after a blocking section, so the cold model load — the longest wait there is — still reports zero {#b-1-r2}

**File:** `src/refmatrix/modelsrv.py:481-487` (`_handle`), `:240-249` (`_worker`), `:290-315`
(`_check_worker_version`)

**What:** the fix moved the sample to `ahead = self._pending[role] - 1` immediately after the
increment. But the increment is still **after** `w = self._worker(role)`, and `_worker` holds
`self._lock` across `_check_worker_version(w)` → `w.info()`, which on first use of a role forces
the model load — **6.6 s measured** in this plan's own
`rerank-cost-budget-0916.md#live-private`. Every caller that arrives during that window blocks
inside `_worker`, uncounted, and increments only in whatever order the lock releases them.

**Why it's bullshit:** same rig as round 1, two arms:

```
warm  _worker (no load)     : queue_depth=2  (2 callers ahead)   <- the fix works
COLD  _worker (1.5s load)   : queue_depth=0  (2 callers ahead)   <- still wrong
```

The cold window is not an edge case: it is every hub start, and every `_drop_worker` (BrokenPipe,
version handshake, eviction) — the exact moments when the fleet's hooks pile up and a budgeted
caller most needs to know it is third in line. And it is silent in the same way as before:
`(1 + 0)` reads as "you are alone".

**Evidence that no test can see it:** `test_the_server_reports_the_callers_ahead_of_you`
monkeypatches `modelsrv.WorkerClient` to `_SlowWorker`, whose `info` returns instantly and carries
no `version` key, so `_check_worker_version` returns immediately and `_worker` never blocks. The
blocking section the bug lives in is stubbed out by the test that proves the fix.

**Fix:** sample on ARRIVAL, not after admission — increment and read `ahead` right after
`recv_frame` / role validation, before `self._worker(role)`, and keep the same `finally`.
Alternatively move `_check_worker_version` out from under `self._lock`. Either makes the two probe
arms agree.

**Pattern match:** YES — this is [[bsd-plan12-open-bugs-9494f1b#b-1]] one frame up the stack, and the third member of the
family this plan keeps producing: a value read outside the interval it claims to describe.
[[impression_bsd_counter_read_at_completion]].

### SKETCHY: the hot gate I recommended will make every store in the fleet hot within two days {#s-1-r2}

**File:** `src/refmatrix/hub.py:1092-1103` (`_queue_row_is_hot`)

**What:** the gate now fires on `derive_stale`, which is *stamped AND version-different*, with
exact inequality and no grace. That is my round-1 recommendation implemented faithfully, and I got
it wrong.

**Why:** measured on this machine —

- `discovery.discover_roots()` → **8 stores**. Six of them (`atldb`, `cliquedb`, `cliquet`,
  `orderly`, `viascope`, `thiquet`) are other projects, not edited during refmatrix work, so their
  watchers do not fire and they do not re-ingest.
- `git log --since=2026-09-06 -- src/refmatrix/__init__.py` → **34 version bumps in 10 days**
  (~3.4/day).

So the sequence is: plan-12 deploys, every store reads `derive_unstamped` and stays cold (correct,
and the point of the fix). Each store ingests once and is stamped at version X. The **next** bump
— hours later — makes every stamped store `derive_stale`, and the six idle ones stay that way
forever. Within about two days `global:queues` alerts on all 8 rows and keeps doing it several
times a day. That is precisely the outcome the comment three lines above the gate argues against
("an alert nobody reads again"), reached by a different route, and the signal-to-noise is roughly
1 in 34 because most bumps do not touch a derive pass.

**Fix:** gate on DISTANCE, not inequality. The table already stores `derived_at`; the cheapest
honest gate is "the stamp predates the newest mtime among the derive-pass sources
(`ingest.py`, `ingest_gmd.py`, `store.py`)", which fires only when the code that derives actually
changed. An age threshold (`derived_at` older than N days) is the cruder version. Either keeps the
`never_stamped`/`stale` split that is already right.

**Pattern match:** YES, and it is mine — [[impression_bsd_my_fix_needs_measuring]]. The remedy
implemented my one-line wording exactly; the wording was the defect.

### MEH: "dropped the in-process model" is logged before the model is dropped, and `worker_kinds` goes green with it {#m-2-r2}

**File:** `src/refmatrix/daemon.py:885-903`

Answering your question (3) directly: **the swap is safe.** Probe with a thread held inside
`Embedder.encode`:

```
adopted: ['embed']
log: ['embed: adopted hub-shared worker; dropped the in-process model']
```

surface reads `shared` and the RSS has not come back.
