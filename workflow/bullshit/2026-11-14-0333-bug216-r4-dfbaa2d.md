## Findings {#findings}

### BULLSHIT B1: `remap_a` is never applied to A's fragment rows, nor chained through the fresh-id move {#b1}

**File:** `src/refmatrix/replica_merge.py` `_merge_into`: the fresh-id loop (`fresh_b`, which
updates `remap_b` but never `remap_a`) and step 12 (A's rows are copied as they are).

**What:** two defects of the same class, bug-227's data loss, both reachable whenever B's copy of a
shared-name entity is the newer one.

**(a) A's fragment rows keep the loser's id.** Probe `probe_remap_a_bits.py`:
- A's `shared` (id 2) loses to B's newer `shared` (id 4), so `remap_a = {2: 4}`.
- B holds a different memory, `b1`, at id 2.
- After the merge, `entity_links` has the link remapped, but the bitmap under `b1` (2) holds
  `['topicx']` and the bitmap under `shared` (4) is empty.

A's bit now names B's unrelated entity. Without an entity at the old id, it would be a dead bit.

**(b) A loser's canonical id is not followed through the move.** Probe `probe_remap_a_chain.py`:
- A has `only-a` (3) and `shared` (4). B's newer `shared` is at 3, so `remap_a = {4: 3}`.
- B's `shared` (3) and A's `only-a` (3) are different entities sharing id 3, so the fresh loop
  moves B's `shared` 3→5.
- `remap_a` still says 4→3. The merged catalog has:

```
merged memories: [(3, 'only-a', 'SHARED A'), (5, 'shared', 'SHARED B (newer)')]
related-to links: [('only-a', 'topicx')]
```

A's `only-a` body "ONLY A" is overwritten by the loser's body (step 7c, as the loser's row is
newer). A's `shared` link is attributed to `only-a`. The bitmap under the dead id 4 still holds the
link, and `shared` (5) has none.

**Why it's bullshit:** L94 and L97 ruled that B2 and S1 are completed in this branch "because a
partial collision fix is still data loss". This is the same class on the A side:
- a memory body is overwritten, and its link lands on an unrelated memory;
- the shape is ordinary: in diverged slots both sides allocate the same next ids, so B's winning id
  is usually held by a different A entity.

The r3 S1 RED could not see it because both of its entities lost on the B side.

**Fix (a few lines, same kernels):**
- After the fresh loop, chain `remap_a` through the move:
  `remap_a = {k: fresh_b.get(v, v) for k, v in remap_a.items()}`, before the temp tables are
  filled.
- In step 12, pass A's rows through `remap_fragment(row, remap_a)` before the OR. `remap_a`'s keys
  are A's own loser ids, so unlike `remap_b` it is the correct map for A's rows.
- RED: both probes. `only-a` keeps "ONLY A" and has no `related-to` link; `shared` carries
  `topicx`; no bit sits on the old id. Both fail at `dfbaa2d`.

**Pattern match:** YES — `imp-collision-column-census` and `imp-moved-id-shared-rows`. Each round
has closed the side of the map the RED exercised.
