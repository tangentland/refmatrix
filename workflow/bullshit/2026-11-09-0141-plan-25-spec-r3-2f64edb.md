## Findings {#findings}

### SKETCHY S1: the moved replica leg keeps a hub-only embedder for every caller, while 3.7 makes `recall.shared_embedder` THE daemonless accessor {#s1}

**File:** [[task-25.1-recall-hook-byte-budget#r5]], d5, d6, d8, AC-4 (c); the 3.7 clone's
`recall.py:623` (`shared_embedder`), `verbs.py:2336,2361`; HEAD `cli.py:11372-11381`.

**What:**
- **HEAD.** `_replica_memory_recall` embeds only through the hub's shared worker
  (`modelsrv.shared_available` → `RemoteEmbedder(SharedWorkerClient)`) and returns None otherwise.
- **3.7, which merges first.** It introduces `recall.shared_embedder(root)`, whose docstring calls
  it "THE embedder accessor". A daemonless caller gets the hub worker, else a PRIVATE worker, else
  one cached in-process model (bug-171/173 remedies). 3.7's daemonless `graph_recall` and
  `ann_search` verbs answer through it.
- **25.1 as written.**
  - d5 puts the moved leg "beside `shared_embedder`" but never says it uses it.
  - d6 sends MCP and interactive recall through that leg.
  - d8 / AC-4 (c) assert that with no daemon and no hub the verb raises `VerbAbsentError`, for
    every caller.

**Result:** after both land, a daemonless `rmx_graph` answers through a private worker and a
daemonless `rmx_memory_recall` refuses. These are two daemonless embed policies in one package, the
"two ways to compute which rows" shape one level down. 25.1's `#overlap` row for `recall.py` says
"none textual", which hides this semantic overlap.

**Fix:** add a decision row and make AC-4 (c) follow it. Decided as the user would:
- Hook modes keep hub-only. A private-worker spawn or an in-process load (6-33 s) cannot fit the
  5 s per-prompt budget, and HEAD's leg says "never a locally spawned model".
- Interactive and MCP callers embed through `recall.shared_embedder(root)`, as 3.7's graph verbs do.
- AC-4 (c) becomes hook-mode only.
- A new AC-4 (g) covers no daemon and no hub, interactive: the answer comes from a private worker
  and `warnings` names it.
- A mutation for "hook mode spawns a private worker" (latency over budget) is added.

**Pattern match:** YES. This is the r2 impression "moving a leg into a shared verb changes every
other caller", extended to the code it is moved beside.

### SKETCHY S2: 25.4 keeps `\w`, `\b`, `\s` and `.` Unicode under `LC_ALL=C`, and AC-2 runs every row under `LC_ALL=C`; both greps answer differently there {#s2}

**File:** [[task-25.4-grep-bre-translation#r1]] (word anchors bullet), b9, AC-2; inherited by
[[task-25.5-substring-bre-metas#acceptance]] ("`LC_ALL` pinned as in 25.4"). Evidence is in
[[#probes]].

**What:** b9 makes POSIX classes follow the locale, but R1 keeps `\b \B \w \W \s \S` as Python's
Unicode classes "consistent with b9". Under C, b9 itself says ASCII. `.` matches one decoded
character in Python and one byte in grep under C. AC-2 runs every row "under
`LC_ALL=en_US.UTF-8` and under `LC_ALL=C`" on one fixture, and that fixture holds a `café` line for
the class row. Under C, both greps give:
- `\w\+ -o` → `caf`, while R1's translation gives `café`;
- `caf\b` → 1 match against 0;
- `-w` and `-x` with `.` on any non-ASCII line → different lines.

So spec-correct code fails AC-2's C column. The alternative is that someone cleans the fixture to
ASCII and the C column tests nothing. rg, which R4's fallback uses, is Unicode in every locale, so
no rmx leg reproduces grep's C-locale byte semantics.

**Fix:** decided as the user would, choosing the provable rule.
- Under a non-UTF-8 `LC_CTYPE`, every translated BRE is `UntranslatableBRE` and goes to the real
  grep (b5). The C column then exercises delegation.
- Add AC-2 rows `\w\+ -o`, `caf\b` and `-x .` on the `café` line under C.
- Add the mutation "translate under C".
- 25.5 states that it inherits the rule.

The workstation default is UTF-8, so the cost is nil in practice.

**Pattern match:** YES. This is r2 #s3's class (a rule written from the dialect docs, not the
oracle) and the third round on 25.4.
