## Findings {#findings}

### BULLSHIT: `_store_rw()` is not the one in-process write control point; the verbs layer has its own, and 6+ CLI commands, the MCP memory tool and `rmx init` still write a git-tracked catalog {#b-1}

**File:**
- src/refmatrix/cli.py:230-264 (`_store_rw`, its docstring);
- src/refmatrix/verbs.py:531-553 (`local_write`, whose docstring says "THE no-daemon writer");
- src/refmatrix/mcp.py:107-127 (`_t_memory_add`, direct `Store(root)`);
- src/refmatrix/handoff.py:380-386 (`_promote_digest`, direct `Store(root)`);
- src/refmatrix/verbs.py:1572-1576 (`change_subject`, direct `Store(root)`);
- src/refmatrix/cli.py:951-962 (`init`, `Store(target).init()`);
- docs/INTEGRATION.md#sync-tracked-catalog.

**What:** the lead's r2 decision put the refusal in `cli._store_rw()` because that was understood to be "the one in-process write control point". The code docstring says so: "`rmx sync`, `rmx ingest`, `rmx memory add`, the memory bridge and every other daemon-down writer reach it". The new INTEGRATION.md section says: "Every such open goes through one control point, `cli._store_rw()`, so the rule covers every writer".

**Why it's bullshit:** that premise is false, and nothing checked it. The verbs layer has its own no-daemon writer, `verbs.local_write()`. It opens `Store(root, partition=…)` read-write itself and never reaches `cli._store_rw()`. Every verb that writes through `_write_or_local` / `_matrix_write` goes there:
- `curate`: protect, unprotect, noise, unnoise, forget;
- `canon`;
- the matrix edits: add entity, add concept, link, and the rest.

The CLI commands are thin adapters over those verbs, and so are the MCP tools. Four more sites hand-roll the same in-process open:
- `mcp._t_memory_add`: the MCP `rmx_memory_add` fallback when no daemon runs;
- `handoff._promote_digest`: `rmx save-state` / MCP save-state promote with no daemon;
- `verbs.change_subject`: `rmx focus change-subject` with no daemon;
- `cli.init`: `s.init()` on an existing catalog.

None of these asks git.

**Evidence:**
- `tracked_repo`, both layouts, no daemon, on clean src at 67f55cb (`logs/probe-bypass-clean.log`): **10 of 10 writers wrote the committed catalog**:

| writer | slots layout | legacy layout |
|---|---|---|
| `rmx add concept` | ` M .refmatrix/catalog.A.duckdb` | ` M .refmatrix/catalog.duckdb` |
| `rmx add entity --kind doc` | same | same |
| `rmx add concept` + `rmx protect` | same | same |
| `rmx add concept` + `rmx noise` | same | same |
| MCP `rmx_memory_add` (`mcp._t_memory_add`) | exit 0, same | exit 0, same |
| `rmx init --no-hooks --no-agents` | exit 0, "initialized", ` M …catalog.A.duckdb` | ` M …catalog.duckdb` |

- The counter probe agrees: `ingest` and `sync --files` call `git_tracked_catalogs` once each, while `add concept` calls it **0** times and exits 0.
- None of these writers is in the RED set. `WRITERS = ["ingest", "memory-add", "bridge"]`, plus sync and the direct `_store_rw()` test, are exactly the paths that reach `_store_rw()`. The suite therefore proves the claim only for the writers it picked.
- What still holds: the b-1 incident path itself is closed. The generated hooks only run `rmx sync`, which reaches `_store_rw()`, and K1/K2/K5 and my X2 die. The open hole is the r2 scope, "every writer", which the docstring and INTEGRATION.md now claim.

**Fix:** converge the repeated shape into one function and add a bypass check (feedback_converge_repeated_shapes). This is small: about 30 lines of src plus tests.
1. Move the check to the store layer as one function: `store.refuse_tracked_in_process_open(root, db_path)`. It raises a typed `TrackedCatalogRefused(RuntimeError)` carrying today's exact wording. `cli._store_rw()` turns it into the `ClickException`. `verbs.local_write()` calls it before `Store(...)` opens and raises it as a `VerbError`, so the MCP and CLI adapters print one `Error:` line.
2. Route the hand-rolled opens through `verbs.local_write`: `mcp._t_memory_add`, `handoff._promote_digest` and `verbs.change_subject` are copies of it. `cli.init` calls the check before `s.init()` when a catalog file already exists. A fresh `init` has nothing tracked.
3. Bypass test: an AST scan of `src/refmatrix/` for read-write `Store(` constructions (no `read_only=True`). The allowlist is `cli._store_rw`, `verbs.local_write`, `daemon.py` (the a1/bug-214 accepted route), `hub._bootstrap_global_store` and `store.py`'s internal canon store. A new direct open fails the suite.
4. RED tests on `tracked_repo` for one verb-routed CLI writer (`rmx add concept`), MCP `rmx_memory_add`, and `rmx init`. Each expects one refusal line and unchanged bytes.

The alternative, the check inside `Store._connect()` for every non-`read_only` open with a daemon-only opt-out, would be a real single point. But it moves the refusal under every daemon open and needs the lead's ruling. Either way, the lead's "lives in `_store_rw()`" decision should be amended: its premise ("the one control point") is false.

**Pattern match:** YES, and this is the third occurrence, which triggers a PATTERN file:

- bug-212 r1 #s-1: the cwd guard covered the module the test touched;
- task 3.7 r6 (dae0f9e): "a module-wide claim needs a grep".

A docstring that says "every writer" is a census claim, and nobody ran the census.

### MEH: INTEGRATION.md's reader-file order is wrong when an `active` marker exists {#m-2}

**File:** docs/INTEGRATION.md#sync-tracked-catalog ("`catalog.read.duckdb`, then `read_only.duckdb`, then the inactive slot, then the legacy `catalog.duckdb`. Only when none of those exists … does a read fall to `_store_rw()`"), and cli.py:581-625 (`_replica_reader_path`).

**What:** `_replica_reader_path()` returns the inactive-slot NAME whenever `active` is A or B, whether that file exists or not. It never reaches the legacy file in that case.

**Evidence:** the DOCPROBE in `logs/probe-bypass-clean.log` used `active` = A, `catalog.A.duckdb` (tracked), the legacy `catalog.duckdb` present, and no B. `rmx pairs show` was refused (exit 1). The doc says the legacy file would serve that read. The red-r3 summary repeats the same order.

**Fix:** document the real rule: with an `active` marker, only the inactive slot is a reader fallback; the legacy file is a fallback only for stores without a marker. Do not change the code to read the legacy file: `_store_rw` documents it as frozen at bootstrap, so it holds stale data.

### MEH: the per-write cost is stated only in the summary, and the two git calls have no timeout {#m-3}

**File:** src/refmatrix/store.py:94-99 (`subprocess.run` ×2, no `timeout=`); docs/INTEGRATION.md#sync-tracked-catalog

**What:** measured on an untracked store in a repo, while a full suite ran beside it: one `git_tracked_catalogs` per `_store_rw()` call, **31 ms** (`sync --files`, 64 ms total) to **99 ms** (`ingest`, first call, 171 ms total). Daemon-routed writes pay nothing.

The cost appears in `#green-r2-flags` only. INTEGRATION.md and the `_store_rw` docstring do not mention it. Neither git call is bounded. A git that hangs (a stuck mount, an fsmonitor hook) now hangs every in-process writer, including the post-commit hook's backgrounded `rmx sync`, with no output.

**Fix:**
- one sentence in INTEGRATION.md#sync-tracked-catalog: "costs two git subprocesses (~30-100 ms) per in-process open; daemon writes pay nothing";
- `timeout=` on both calls (say 10 s), with a timeout raised as `TrackedCatalogCheckError`, which is fail-closed and loud like the ls-files failure.

### MEH: `git rev-parse` failure is read as "not in a repository" (fail-open), and its env strip is unpinned (mutation X3 survives) {#m-4}

**File:** src/refmatrix/store.py:94-97 (r1-remedy code, carried by this merge)

**What:**
- X3 keeps the hook's `GIT_*` env on the `rev-parse` call (ls-files stays stripped). It survives all 117 tests: the E1 fixture's `GIT_DIR` still answers "true" for `rev-parse`.
- Any `rev-parse` failure returns `[]`, which means "write". The docstring's contract ("unknown is treated as tracked") is applied only to `ls-files`.

**Evidence:** a repo that tracks `.refmatrix/catalog.duckdb`, then `.git/HEAD` overwritten with garbage. `rev-parse` exits 128 ("not a git repository"), and `git_tracked_catalogs` returns `[]` for a catalog that the index tracks. This is an edge case: git cannot commit in that state either.
