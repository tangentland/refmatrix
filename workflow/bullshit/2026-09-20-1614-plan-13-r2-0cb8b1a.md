**File:** `plan-13-cross-partition-sweep.md:142` (`#legs`), `task-13.1-sweep-verb.md:28`, `:93`

**What:** The leg table names three partitions: `project code+doc`, **`memory-<project>`**, and

> **Post-0.5.0 default: project partition (`default_partition_name`), NOT `memory-<project>`.** The
> split that existed for ADR-0001 Phase B → Phase C made **cross-partition wikilinks unresolvable**
> so memory→memory `rel:` edges from sync-disk silently dropped. Recall's existing `kind=memory`
> filter already separates memory results at query time, so the noise concern the split addressed is

On this repo's store — the store 13.0 names as the arbiter — there is no `memory-refmatrix`:

```
* 4  refmatrix                       repo

$ rmx stats                      # active partition = refmatrix

```

366 memory rows sit **in the project partition**. `verbs.memory_partition` returns the legacy name
only when that partition row exists (`verbs.py:270-271`), so it returns `refmatrix`. The maintenance

failing is the single most relevant piece of prior art this plan has, and it is uncited.

### BULLSHIT: the sessions partition is not a peer — no vectors, no pagerank, no typed edges — so the specified session leg is half a leg that reports itself healthy {#b-7}

3. If the answer is "embed the sessions partition", that is production work in the maintenance path

### BULLSHIT: the task that builds the question set is the task the question set judges, and +0.05 on 40-60 questions is 2-3 questions {#b-8}

**File:** `task-13.0-two-partition-kill-shot.md:32-40`, `:57`; `plan-13-cross-partition-sweep.md:249-250`

**What:** 13.0 owns building a 40-60 question known-item set AND owns the GO/STOP threshold measured
on it. The plan asserts "A set of ≤ 60 questions is enough to see a 0.05 effect".

**Why it's bullshit:** Two independent problems, and the second is the one that matters.

**Power.** hit@20 is a per-question binary. At n=60, a 0.05 absolute gain is **3 questions**; at
n=40 it is **2**. A binomial 95% interval around p̂=0.05 at n=60 spans roughly 0.010-0.139 — the
measurement cannot distinguish "0.05" from "0.00" or from "0.14". The plan states the sufficiency
claim with no power calculation and no interval. It is not unfalsifiable — the oracle union is
monotone (a set union can only add hits), so GO reduces to a deterministic count of questions
uniquely reached by a non-control condition, which is checkable — but it is an estimate whose
confidence interval is wider than the effect it is deciding on, presented as a threshold.

**Selection.** Worse: nothing pre-registers the SET'S COMPOSITION. The guard test
(`test_a_question_set_whose_golds_share_one_partition_is_rejected`) only rejects an all-one-partition
set; it says nothing about the MIX. The gain the oracle union shows is a direct function of how many
questions have session-partition golds — raise that share and GO arrives; lower it and STOP does.
13.0 builds the set with full knowledge of each gold's partition (it records the partition per
question, by requirement), after the threshold was written, and is the task the threshold judges.
A pre-registered number on a post-hoc set is not pre-registration.

There is also a supply constraint: the session partition holds **66 documents**. A set drawing
session-gold questions from 66 candidates, scored at hit@20, is retrieving up to 30% of the
partition per query.

**Fix:** Pre-register the composition — e.g. "20 session-gold, 20 memory-gold, 20 code/doc-gold,
sampled by a stated rule from `query.log`, frozen and hashed before any condition runs" — and report
the uniquely-reached COUNT with its interval rather than a bare hit@20 delta. If a defensible n is
unreachable from 66 session cards, say that and treat 13.0 as a screening measurement whose STOP is
strong and whose GO is provisional, rather than a gate with a threshold.

**Pattern match:** YES — [[impression_bsd_cost_measured_idle]] (a threshold whose measurement
conditions were chosen after the threshold).

### BULLSHIT: under the harness's own env, arm P's conditions read the wrong partition — the collapse would have a cause that is not the filter {#b-11}

**File:** `task-13.0-two-partition-kill-shot.md#reencode` conditions, against `eval/memaware/paths.py:59`

**What:** Arm P puts cards in `sessions-memaware`; the conditions are `rmx context`,

  so `rmx context` reads partition `memaware`.
- `cli._session_partition` (`cli.py:12067-12074`), whose docstring is literally *"Explicit -p /
  RMX_PARTITION wins; otherwise default to `sessions-<project>`"* — so `rmx session recall` pins
  `memaware`, not `sessions-memaware`, and `_session_call` (`cli.py:12077-12082`) sends that.

So on arm P every condition queries the partition that does NOT hold the P cards. `context` returns
≈nothing — and the spec has already written down what that means ("expected to collapse toward zero
— that collapse is the measurement"). It would be scored as the filter's cost when it is a partition
miss. `session recall` cannot answer arm P at all.

`cli.py:11674-11681` builds `sessions-` + `_root().resolve().parent.name`, and `paths.py:40-44` puts

`sessions-memaware` correctly. The pin does not break on the root basename; it never gets consulted,
because the env var short-circuits it.

**Fix:** Arm P's conditions run with `RMX_PARTITION` set to the arm's partition (or `-p`), and the

### MEH: arm P cannot measure the demotion, which is part of what the default costs {#m-7}

**File:** `context.py:1216-1240` (`_rank_entries`), against `#reencode`'s recovery test

`--include-sessions` restores MEMBERSHIP but not rank: `_rank_entries` sorts each KWIC linkage with
`1 if _is_session_card(e.entity.name) else 0` (`context.py:1237`) — *"durable docs before any session
cards that were opted back in"*.

On arm P this is a no-op, and that is the problem rather than a reprieve: every document in the
MemAware corpus becomes a session card, so the sort key is constant, the stable sort preserves order,
and nothing is demoted. Arm P therefore measures a flag flip on a HOMOGENEOUS corpus, while the
product's question — [[task-13.4-include-sessions-policy]]'s question — is what happens on a MIXED
one, where 66 session cards compete with 558 docs and 366 memories and are pushed below all of them
by design.

So arm P can tell you whether the filter is reached; it cannot tell you what flipping the default
would do in production, which is the decision 13.4 is supposed to make on these numbers.

**Fix:** Say that 13.4's evidence must come from a mixed corpus (this repo's own store), not from
arm P, and keep arm P scoped to the claim it can support.
