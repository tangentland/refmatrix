### b-3 closed, and the deviation is correct {#b-3-closed}

The deviation: for a column the winning source predates, SET writes `col = NULL` rather than
keeping the target's value. That is the right choice, for three reasons:

- **NULL is what the slot would really hold.** `ENTITY_COLUMN_UPGRADES` columns are added with no
  DEFAULT. So NULL is exactly what that slot reads after `upgrade_catalog`, and what a BY NAME
  insert of the row gets.
- **Every reader treats NULL as "unknown".**
  - `canonical_name` NULL is re-filled by `_backfill_canonical_name_if_needed` on every write
    connect.
  - `vectors_updated_at` NULL puts the row back in `pending_embeddings`. That is correct: the
    winner's content is newer than A's vector.
  - `vectors_partition` NULL is the documented "embedded before this column existed" state.
- **Keeping the target's value would be worse.** It would splice A's metadata onto B's row: a
  vector stamp and partition that belong to content the merge just overwrote.

`closed` is checked there. An instance cannot hand out a cursor after its last close. On 1.5.2, see
[[#s-r2-1]].

## Findings {#findings}

### SKETCHY s-r2-1: closing a stale reader's instance while its cursor executes segfaults duckdb 1.5.2, the dev and test interpreter {#s-r2-1}

**File:** `src/refmatrix/backend.py` (`_ROInstance.shut`, reached from `_close_stale_holders`)

**What:** `shut(interrupt=True)` interrupts each cursor and then immediately calls
`self.base.close()`. Meanwhile, other threads may still be inside `execute`/`fetch` on cursors of
that instance.

**Evidence:**
- `stress2.py` on 1.5.2 hit **SIGSEGV in 3 of 3 runs** (rc 139, faulthandler logs
  `/Volumes/littlebig/bsd112-scratch/r2/s152_{1,2,3}.log`). The crashing thread was a reader at
  `h.execute(...)`, and the replacer was in `shut` at `base.close()`.
- r1's code under the same stress on 1.5.2 raised `INTERNAL Error: Attempted to dereference
  shared_ptr` instead. So close-under-use is unsafe on 1.5.2 in both designs, but r2 turns it into
  a process crash.
- 1.5.3 is clean in 3×30 s.

**Reach today:** latent. pyproject pins `duckdb>=1.5.3` and the deploy venv is 1.5.3. A stale RO
instance on a slot needs the snapshot absent while a merge or reclaim replaces the slot. But
`.venv-eval` is 1.5.2, below the pin, so every dev suite run uses a duckdb that crashes on this
path.

**Fix:**
1. Bring `.venv-eval` to duckdb 1.5.3, the pinned floor. Ask the user first, per #no-workarounds.
2. Harden `shut` so it does not rely on the driver tolerating a close under a running statement:
   - count in-flight `execute`/`fetch*` calls in `_ROHandle`;
   - after `interrupt()`, wait (bounded, about 1 s) for that count to reach 0;
   - then close.
3. Add a 1.5.2/1.5.3 stress test: N readers plus a replacer, asserting the child exits 0.

**Pattern match:** YES. This is r1 s-2's version split (1.5.2 and 1.5.3 behave differently on one
call) in a new place.

### SKETCHY d-1: the deploy gate — the bug-118 fix makes enforce-rmx-grep block bare corpus greps the moment a master checkout's hooks are regenerated, because the `learn.off` stand-down (0611d2f) is not on master {#d-1}

**Files:**
- `.claude/settings.json` (generated)
- `.claude/hooks/enforce-rmx-grep.sh` (master: no stand-down; `wave0-spec-reviews`: has it)

**Answer to the brief:**

1. **Deploying master plus this branch does NOT by itself block anything.** Hooks run from
   `$CLAUDE_PROJECT_DIR`, the dev tree's working copy. Its `.claude/settings.json` (on
   `wave0-spec-reviews`) still carries the `… || true` form (lines 149 and 153), which cannot
   block.
2. **Blocking starts when the new rendering lands in a checked-out tree.** That happens through
   either of two routes:
   - the merge reaches the dev tree's working copy;
   - someone runs `rmx install-hooks` with the deployed code (and `--check` will flag the drift,
     inviting exactly that).
3. **Which script is checked out then decides the outcome.**
   - **Master's script:** a bare `grep -rn X src` exits **2**, and PreToolUse blocks it,
     preempting the global grep-rewrite-guard.
   - **The `wave0-spec-reviews` script:** it stands down. `~/.refmatrix/learn.off` is present
     (2026-10-15 00:29), so it exits 0.

No other project under `~/claude_tools` or `~/github` carries the script.

**Fix:** cherry-pick 0611d2f onto master in the same merge as this branch, before anyone
regenerates hooks. Alternatively, record in the deploy checklist that hooks must not be regenerated
on a master checkout until 0611d2f lands.

### MEH m-r2-2: `shut` interrupts handles that already closed, flooding rmxd.log with false warnings {#m-r2-2}

**File:** `src/refmatrix/backend.py` (`_ROInstance.shut`, `_drop_handle`)

**What:** a closed handle stays in `inst.handles` (a WeakSet) for as long as its Python object
lives, for example a closed Store still holding `_conn`. `shut` then logs
`interrupt of a reader … failed: Connection already closed`. The stress run logged 305 such lines
against 54 real closes.

**Fix:** in `_drop_handle`, `inst.handles.discard(handle)`. Alternatively, skip handles whose
`_fin.alive` is False.

### MEH m-r2-3: `_detach_backend_log` has no production caller {#m-r2-3}

**What:** only tests call it. Every in-process `Daemon.serve_forever` (the test daemons, and any
