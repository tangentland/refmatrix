**What:** "Every route that runs a doc walk through `ingest_gmd_paths` has exactly one
dispatcher". The listed sync ops are `_op_sync_files`, `_op_sync_since` and the watcher flush.
The CLI dispatches only for `rmx ingest-gmd` and `rmx ingest`.
**Evidence:** every caller of `_sync_paths` and `ingest_path`, enumerated at `4b4b96e` (each
reaches `ingest_gmd_paths(…, as_memory=False)` at `sync.py:308` or `ingest.py:1354`):
- **daemon OPS not listed:**

  - `"flush_queue_async": _op_flush_queue_async` (its `_runner`, `:3516-3519`). This is the Stop

- **CLI in-process routes not listed:**
  - `cli._sync_in_process` (`cli.py:8763`), all three branches: `sync_since` (`:8788`),
    `flush_queue` (`:8804`), `sync_files` (`:8808`);

    `sync_files`);

    Dispatching in the `ingest` command rather than in `_ingest` misses them.

On each of these, R-220b still takes the memdir files out of the doc set, so they are neither
ingested nor counted. That is the silent loss U2 named, on more routes. The dirty queue gets

twice.
**Fix:**

  `rmx watch`, and `cli._ingest` (the CLI's in-process site) to the list.

- Turn the "a route that collects and does not dispatch is a defect" sentence into a check, in the

### SKETCHY: the V1 guard exemption has no AC, and the natural implementation exposes it to every socket caller {#w2}

**File:** `task-26.5…:546-549`, `:599`
**What:** "The same-store start issued by that job's own dispatch is exempt from A's
single-active-ingest guard for that one start; it names the parent job, and the guard holds for
every other caller." The lead's check asks for an AC or mutation proving this. There is none.
**Why it's sketchy:** the same-store start is "a detached `ingest_gmd_start` on A, called
in-process" (`:598-599`). OPS handlers take only `(d, args)`, and `args` comes from socket JSON.
So "names the parent job" naturally becomes an `args["parent_job"]` key, which any client can
send to bypass the guard. That lets a second writer start beside the running job, which the guard
exists to prevent ("the two would fight over the write lock", `cli.py` `ingest-gmd` docstring).
"For that one start" (consumed once) is not tested either.
**Fix:**
- State that the exemption is not reachable from OPS args. It is an internal function the
  dispatcher calls, or a token held only on the parent job record and consumed on first use.
- Add AC-220 (m):
  - while a job is active on A, a socket `ingest_gmd_start` carrying that job's id (and any
    `parent_job` value) is refused with `ingest already active`;
  - a second exempt start from the same parent is refused.
- Mutations: "exemption read from args" and "exemption not consumed" each kill (m).
**Pattern match:** NO.

### MEH: "tells the two apart by where the call failed" needs a `daemon.call` change it does not name {#w4}

**File:** `task-26.5…:582-589`
**What:** `daemon.call` raises the same `socket.timeout` for a connect timeout and for a reply
timeout. `sent` is local, and nothing outside sees it (`daemon.py:657-680`). The helper cannot
tell `rerouted_failed` from `rerouted_unconfirmed` without a change to `daemon.call`, such as a
typed `ReplyTimeout` raised when `sent` is true (the bug-116 distinction), or its own socket
code.
**Fix:** name the mechanism in R-220c and in Files.

### MEH: the bounds may be tight for an embed-model cold load (a flaky failure, not a hang) {#w5}

**File:** `task-26.5…:645-651`
**What:** (a)'s recall leg and the same-store/B jobs run the memory-vector drain. In task 23.0's
sandbox there is no hub, so the first drain loads the embedding model in-process (several
seconds), inside a 30 s job deadline and behind 10 s call bounds. This fails loudly, never hangs,
but can flake.
**Fix:** a warm-up of the sandbox's model worker before the timed cases, or a job deadline that
names the cold-load allowance.
