## Findings {#findings}

### BULLSHIT: d9bf's in-daemon swap depends on bug-112, which has no fix and no task; the data-loss mode reproduces {#b-1}

**File:** `workflow/plan-review-2026-10-14.md` d9bf; `workflow/bug_registry.md:165`
**What:** d9bf reshapes 18.3 into an in-daemon rewrite under `_store_lock`: close the writer,
`os.replace`, then reopen the SAME path in the daemon process. It "DEPENDS on bug-112".
**Why it's bullshit:** bug-112's Fix column says "None yet", and no task spec owns a fix. The
only plan references to bug-112 are 19.3/19.4 working around it and the old 18.3 text. The old
18.3 avoided bug-112 by design: "A new process has no DuckDB instance cache, so bug-112 cannot
serve the old file" (task-18.3 `:76`). d9bf throws that property away. 18.1's timings come from
fresh child processes, which have no instance cache, so they say nothing about the in-daemon
reopen.
**Evidence:** I reproduced it on duckdb 1.5.3. With a second in-process `connect` to the path
still open, `close` the first, `os.replace` a new file over the path, and `connect` again: the
reopen returns the OLD database (`[1]`, not `[2,3]`). A write through it, followed by a
CHECKPOINT, never reaches the file on disk (`[2, 3]`; the row 99 is lost silently). A cursor
from the closed connection does not trigger it, but a second `connect` does.
**Fix:** Pick one of two:
- Keep 18.3's rewrite AND its reopen out of process (an offline restart, or a child that
  verifies the new file before the daemon re-execs).
- File a bug-112 fix task now, with an AC that reproduces this exact swap. 18.3 then asserts
  after the reopen that the connection serves the NEW file: a sentinel row written into the
  rewrite before the swap, read back after the reopen. Without it the swap refuses and rolls
  back.

Until one of these exists, d9bf cannot stand.
**Pattern match:** YES — plan-19 r6 #s-3 (in-daemon render exposed to bug-112).

### BULLSHIT: "a store over 5 s keeps the offline route" points at a route d9bf deletes (rule 9a) {#b-2}

**File:** `workflow/plan-review-2026-10-14.md` d9bf
**What:** d9bf says "A store whose measured max rewrite exceeds 5 s keeps the offline route". In
the same sentence block, it says the reshape "removes the watchdog pause, launchd stop/kickstart
and `daemon.lock` machinery the offline design needed".
**Why it's bullshit:** This is an unanchored deferral. Once 18.3 is rewritten, no task spec will
build the offline route, so any store that grows past 5 s has nowhere to go. Rewrite time follows
live data (refmatrix 177 MiB live -> 1.94 s), so this is a matter of growth, not a hypothetical.
**Fix:** Either:
- route a store over 5 s to the existing Table C refusal (`refused:rewrite_too_slow`, then the
  helix plan); or
- keep the offline path as a named task with ACs.

### SKETCHY: in-daemon feasibility is an idle-copy number, and the 2x margin is spent under modest load {#s-1}

**File:** d9bf; task-18.1 R3 `#r3` (recorded-not-built)
**What:** "every store's max rewrite <= 5 s; worst 1.98 s against 18.2's 10 s hold ceiling".
**Why it's sketchy:** The 1.98 s came from a dedicated child, on a warm, freshly copied file,
with nothing else running. On the same copy with 6 concurrent read loops, I measured 3.60 /
3.72 / 3.92 s. That is 2x the idle figure, which is the whole margin R3 reserved for "the live
writer is also serving".

The hold also covers more than the rewrite: the gate, the close, `os.replace`, the reopen and
the snapshot refresh. Measured on the copy, those added about 0.3 s: gate counts 0.005 s,
content hash 0.10 s, CHECKPOINT ~0 s, cp 0.04-0.18 s, open 0.005 s.

The rewrite's peak RSS was 884 MiB, and in the daemon that would add to the serving process.
R4's ±25 % check compares a copy with a copy, so it cannot see any of this
(`impression_bsd_cost_measured_idle`).
**Fix:** The rewritten 18.3 spec must:
- measure the FULL hold (rewrite + gate + swap + reopen + snapshot) in a tmp daemon under a
  scripted read/write load;
- state the 5 s gate on that loaded max;
- abort the copy past a budget (`con.interrupt()`, then roll back) instead of trusting a number
  from the night before.

### SKETCHY: the growth band's baseline makes it blind to the four stores 18.1 found due {#s-2}

**File:** d9bg; task-18.2 R5 `#r5-band`
**What:** Under `growth` mode, a store is A2 when `file_bytes >= 2x baseline`. d9bg says the
baseline is "each store's 18.1 `file_bytes`". 18.2 R5 says it is "the first successful run's
`file_bytes`". The two disagree.
**Why it's sketchy:** Both baselines are the BLOATED size. refmatrix (r 0.776, A2 today) would
flag only at 1,578 MiB (r ≈ 0.89), and global only at 484 MiB (r ≈ 0.93). The nightly band is
d9bc's reason gate, so it cannot trigger the reclaim that 18.1 just said is due. The band mode
follows the pre-registered Table B row, but the baseline makes that row useless until after a
first reclaim.
**Fix:** Get a user decision row for one change: baseline = 18.1's `rewrite_bytes` (the live
size), reset to the post-reclaim size after each 18.3 run. Then `file_bytes >= 2 x live` is
exactly r ≥ 0.50, Table A's A2 edge. Then make d9bg and 18.2 R5 say the same thing.

### SKETCHY: the gate checks names and counts, and three of its four legs are untested {#s-3}

**File:** `eval/catalog_maint/measure_catalogs.py:187-203`; `tests/test_catalog_measure.py:129`
**What:** The gate compares four things:
- per-table row counts;
- sequence `last_value`;
- the sorted index NAMES;
- constraint counts per type.

d9be reports "every gate passed".
**Why it's sketchy:** Mutation M2 deleted the sequence, index and constraint legs, and all 10
tests still passed (`bsd181-m2-gate-tables-only.log`). Only AC-4's dropped row exercises the
gate. The gate also cannot see changes to:
- a column DEFAULT (the `nextval` that ids depend on);
- CHECK text;
- an index definition;
- a new view, macro or type;
- any value change that keeps the counts.

d9bf makes this gate the last check before `os.replace` over the live writer. Every one of these
was equal on the refmatrix copy, and a full content hash cost 0.10 s, so the stronger gate is
cheap.
**Fix:**
- Gate on per-table `count(*)` plus a hash over every column.
- Gate on `duckdb_columns` (type, default, nullable), `duckdb_constraints.constraint_text`,
  `duckdb_indexes.sql`, and the non-internal views, functions and types.
- Add an AC-4 variant per leg: drop a sequence/index, alter a default, change one value.

### SKETCHY: the amended AC-1 no longer pins `f` (cheap-fix shape) {#s-4}

**File:** `tests/test_catalog_measure.py:89`; d9bh
**What:** The spec's `f >= 0.80` cannot hold on the real schema (forced; f 0.63). The amendment
replaced it with `0 < f <= r`.
**Why it's sketchy:** Mutation M1 passed `used_blocks` as `free_blocks` (f ≈ 0.37), and all 10
tests passed (`bsd181-m1-f-used.log`). AC-2 tests `derive` alone, not the wiring. `f` is the
input to Table B, and so to d9bg. The fleet values are right (I checked them independently: 0.145
vs 0.147), so the decision stands, but no test would catch a regression.
**Fix:** In AC-1, read `free_blocks / total_blocks` from the test's own tmp catalog (the TEST may
open its own fixture). Assert that the row's `free_blocks` / `total_blocks` / `f` equal it, and
keep `f <= r` as a separate assertion.

### SKETCHY: AC-1 is flaky, and `rewrite_bytes` is noisier than 18.3's 1 % tolerance {#s-5}

**File:** `tests/test_catalog_measure.py:87`; `measure_catalogs.py:251`; task-18.1 R4
**What:** One of 8 AC-1 runs failed with `r = 0.7998 >= 0.8` (`bsd181-fakehome.log`; the other
7 passed). The rewrite size is not deterministic. Six rewrites of the same refmatrix copy gave
184.0-186.4 MB, a spread of about 1.3 %. The script keeps only the LAST run's `rewrite_bytes`.
**Why it's sketchy:**
- A flaky test in the suite is red noise.
- R4 / 18.3 AC-7 require the production rehearsal within 1 % of `rewrite_bytes`, which is inside
  the measured noise.
**Fix:**
- Give AC-1 margin (`r >= 0.75`, or 95 % deleted).
- Record all three `rewrite_bytes` and report the median.
- Set R4's bytes tolerance from the measured spread (≥ 2 %).

### MEH: d9bg's numbers and mechanism are off {#m-1}

contradicts R3's "`f <= r` is expected" and d9bg's mechanism. The "index and partly-used blocks"

### MEH: a noisy rerun drops the first batch from `rewrite_s_max` {#m-2}

`measure_catalogs.py:249` takes the max of the final batch only, so `in_daemon_feasible` ignores
the spike that made the store noisy.
**Fix:** Take the max over every run.

### MEH: scratch handling and uncaught failures {#m-3}

- `run()` calls `shutil.rmtree(scratch)` on the whole directory the user passed, deleting
  anything that was already in it.
- An exception outside `(StepError, OSError, SubprocessError, ValueError)` aborts the run with no
  report and no R6 row, and leaves about 800 MB of copies behind (for example a `KeyError`, or
  the `TypeError` from AC-5's own spy).

**Fix:** Delete only the per-store work directories, in a `finally`. Turn any `Exception` per
root into an error row.

### MEH: version and naming in the record {#m-4}

- The tests' children run duckdb 1.5.2 (`.venv-eval`), while the fleet ran 1.5.3. The rows do
  not record the duckdb version.
- The report names the global store "tholley" (`parent.name`).

**Fix:** Record `duckdb.__version__` per row, and name stores from the root path (global =
`~/.refmatrix`).
