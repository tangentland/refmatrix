## Findings {#findings}

### SKETCHY s1-r2: a second hub started in the live hub's startup window still removes the live hub.pid {#s1-r2-startup-window}

**File:** `src/refmatrix/hub.py:937-943` (`run` preflight) and the `_claim_pid_file` call after it.
**What:** The preflight only refuses when `:7777` already has a LISTENer. A hub binds the port
last. Its order is: claim pid, models, global daemon, watchdog, `serve_sock`, then uvicorn. So
for the seconds a hub spends starting up, `is_running()` is False and the port is free.
`rmx ui` and the detached `rmx hub start` both read that state as "no hub" and call
`spawn_hub`. The second hub passes the preflight, overwrites hub.pid, and rebinds hub.sock. One
of the two uvicorns then loses the bind. If the loser is the second hub, its `shutdown()`
releases the file, which names the second hub, so the live hub is left with no pid file.
**Evidence:** In a scratch probe, hub.pid named 4191 (a first hub mid-startup), `_pid_on_port`
returned None, and the second `Hub.run` had uvicorn losing the bind and calling `shutdown()`.
`assert hub.hub_pid() == 4191` fails because the file is gone
(`bsd-bug129-r2-window-probe.log`). r1 s1 named exactly this window ("`rmx ui` → `spawn_hub` in
the gap where `is_running()` is False"). The port preflight cannot see it. The new comment in
`run()` and the commit body ("a losing second hub returns without touching the live hub") claim
it is covered. They are true only for a hub that loses at the preflight.
**Fix:** Pick one.
- Refuse to claim while `hub_pid()` names a live process (`os.kill(pid, 0)`, not ping, because
  ping is also dark during startup). Log it and return.
- Better: take an exclusive `fcntl.flock` on `hub.lock` as the first act of `run()` and hold it
  for the life of the process. That gives the singleton every startup path is missing.

Add the probe above as a test. It is about 10 lines.
**Pattern match:** YES. It is r1 s1, narrowed to this window and not closed.

### MEH m1-r2: guard residue: an ImportFrom alias, and owners exempted by name in any module {#m1-r2-guard-residue}

**File:** `tests/test_bug129_hub_pidfile.py::test_only_the_helpers_reach_the_pid_file`.
**Evidence:** I added probes to scratch `cli.py`. The control, `from refmatrix.hub import
hub_pid_path; hub_pid_path().unlink()`, is caught. Two realistic shapes pass:
- `from refmatrix.hub import hub_pid_path as _hp; _hp().unlink()`. The `ast.alias` is not
  inspected, and `_hp` is not a flagged Name.
- A function named `hub_pid` in `cli.py` that unlinks `h.hub_pid_path()`. Owners are exempted by
  function name in every file, not only in `hub.py`.

Contrived shapes also pass: `hub_log_path().with_suffix(".pid")`, getattr by string, and
`hub_home().glob("hub.*")`. A guard is not expected to catch these.
**Fix:** Flag `ast.alias` entries whose `name` is `hub_pid_path`/`HUB_PID`. Require
`f.name == "hub.py"` before applying the owner exemption. About 2 lines.

### MEH m2-r2: headless fallback now refused while the port is held, and a corrupt pid file at stop_hub is still silent {#m2-r2-small-residue}

**File:** `src/refmatrix/hub.py:937` and `_release_pid_file`.
**What:**
- (a) The preflight used to sit after `import uvicorn` in `_serve_http`. It now runs at the top
  of `run()` whenever `serve_http=True`. On an install without `[ui]`, a port held by any
  process used to fall through to the headless supervisor. Now the hub refuses to start at all.
  Gate the preflight on uvicorn being importable, or accept the change and say so in the
  comment.
- (b) `stop_hub` reads `pid = hub_pid()`, which is None for a corrupt file. So
  `_release_pid_file(None)` returns before the new log line, and a garbage hub.pid is still left
  in place with no record (r1 m1). `Hub.shutdown` does log this case.
