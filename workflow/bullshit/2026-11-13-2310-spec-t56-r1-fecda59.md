### BULLSHIT B1: 22.6 R10 logs `evidence_remove` for ingest rows, which 22.2's replay guard and AST pin forbid {#b1}

**File:** `workflow/plans/plan-22-audited-removal-and-repair-tasks/task-22.6-removal-entry-points.md:512-514`
(R10 "Replayable") and `:792-800` (AC-10).
**What:** "each deleted row logs 22.2 R3's `evidence_remove` row op by name, through
`edge_records.row_event` with `c_kind` (d9bl: one format, one resolver; no new op), so a rebuild
from `facts.log` does not resurrect it." The rows R10 deletes are, by construction, the
non-learned ones (`rel:` and other ingest details).
**Why it's bullshit:** 22.2 defines `evidence_remove` with a learned guard. See
`task-22.2-repair-then-remove.md:72-82`: "By default the learned guard above holds: a row whose
`detail` is not `learned from grep…` is not matched. `ingest_ok=True` lifts it, and exactly two
callers pass it: R2's concept-side rule … and R9's `remove_dangling_evidence` … replay … applies
the learned guard unless the event carries `ingest_ok: true`." 22.2 AC-3c (`:880-881`) pins it:
"`remove_evidence(..., ingest_ok=True)` is called only from R2's concept-side rule and
`remove_dangling_evidence`; mutation 'a third caller passes `ingest_ok=True`' FAILS it."
R10 names neither `ingest_ok` nor `keep`. The builder has two literal readings, and both fail:
- Log without `ingest_ok`. Replay skips the event for row (a), so 22.6 AC-10's "a rebuild … holds
  … neither (a) nor (d)" FAILS on correct code.
- Pass `ingest_ok=True` (a third caller). 22.2 AC-3c FAILS.

A goal that builds 22.2 and then 22.6 unattended reaches a red test it cannot satisfy without
editing an approved spec.

**Also (same requirement):** R10 keys the drop on the catalog's current `c_kind`. R5, which drops
rows with a dead entity, needed d9bz/d9cc's "the orphan's OWN appends" keying (`:249-262`). A LEGACY
`evidence` append with no `c_kind` is resolved at rebuild by `resolve_c_kind` over the kinds logged
for `c`, and a name logged under two kinds is exactly bug-216's MISBOUND doc/concept case. A drop
keyed on the catalog kind then misses the rebuilt row, and the row is resurrected. AC-10 seeds only
fresh appends, so it cannot see this.
**Evidence:** `edge_records.EDGE_OPS = {"link","unlink","evidence"}` (`edge_records.py:27`).
`Store.unlink` deletes only `entity_links` and leaves evidence (`store.py:4862-4888`), which is how
stale evidence arises.
**Fix:** decide one of these, and record it in 22.2 and 22.6 together:
- (a, recommended) R10 gets its own row op, mirroring R5's `evidence_orphan_drop`. Call it
  `evidence_stale_drop{linkage, c_kind, c, e_kind, e, file, line, detail, manifest}`, added to
  `ROW_OPS` and keyed on the row's own appends (R5's rule). The learned exclusion is stated in the
  op, and 22.2's guard stays two-caller.
- (b) 22.2 R2/AC-3c is amended to name vacuum step 3b as the third `ingest_ok` caller, with
  `keep=0`.

Either way, AC-10 gains a legacy-append variant (an `evidence` append with no `c_kind` for a name
logged as both `concept` and `doc`), and the rebuild must not resurrect it.
**Pattern match:** YES. It is the R5 keying defect that r10/r11 fixed (d9bz, d9cc), reintroduced
in a sibling step (`imp-order-key-every-stage`; `feedback_check_the_sibling_condition`).

### SKETCHY S1: bug-218 does not model the GMD root-mirror, so AC-2 and AC-5 are wrong and R0b's drop count is inflated {#s1}

**File:** `workflow/plans/task-bug218-reinforcement-edge-direction.md:163-167` (AC-2), `:176-177`
(AC-5), `:98-107` (R0b), `:121-124` (R3).
**What:** AC-2: "the GMD ingest … each produce exactly one `entity_links` row … `concept_id = m` and
`entity_id = c`". AC-5: "Mutation: drop the kind filter: FAILS (c reads 1.1)". R0b counts "rows
whose source … is not `kind='memory'` (R3's drop)".
**Why it's sketchy:** every memory file carries `# Title {#root}` (MEMORY-RULES). The ingester
mints `<doc>#root` as a `kind='concept'` node (`ingest_gmd.py:1510-1544`; only the synthetic
`__root__` maps to the doc entity). A `rel:` line under it links `src_eid = m#root` (`:1766`), then
mirrors the same edge onto the doc-level entity (`:1784-1797`, detail `rel: … (root-mirror)`). One
GMD statement therefore writes TWO rows: `(m#root → c)` with source kind `concept` and `(m → c)`
with source kind `memory`. As a result:
- AC-2 fails on correct code for a canonical memory file. The builder has to drop `{#root}` from the
  fixture, which tests a shape users never write (`feedback_measure_the_path_users_run`, which the
  spec itself cites).
- AC-5's doc with `{#root}` reads 2.1 under the mutation, not 1.1. The mutation still fails, but the
  stated value is wrong.
- R0b's "R3 drop" count includes one `m#root` twin for every root-level statement. That is not a
  drop, because the mirror row carries the signal, so the census overstates what R3 discards.
- R3 silently does a second job: without it, every root-level statement counts twice. The spec
  gives R3 only the "memories reinforce" rationale, so a later "let docs reinforce" change would
  double-count with no test noticing.

**Fix:**
- R0b splits out `(root-mirror)` twins: a source of kind `concept` whose name is `<memory>#root`
  and that has a mirror row.
- AC-2 counts the canonical row(s) explicitly: one `(m → c)`, plus at most the `m#root` twin for
  GMD.
- AC-5's value is restated.
- R3 states the de-duplication role and gains a mutation: "count `kind='concept'` anchor sources"
  makes AC-3's GMD-seeded variant read double.

**Pattern match:** YES (`imp-per-file-count-misses-orphan-rows`: a census that does not know a
second writer shape).

### SKETCHY S2: after R1-R2, GMD reinforcement still reaches no reader unless its target is a path-less concept {#s2}

**File:** bug-218 `:108-120` (R1, R2), `:173-175` (AC-4); code `cli.py:13204-13219`,
`daemon.py:5418-5436`, `store.py:3305-3333`.
**What:** the spec unifies ORIENTATION but not TARGET BINDING. `memory_link` (CLI local and
`_op_memory_link`) always targets `add_concept(c)`, a `kind='concept'` entity in the memory
partition. GMD binds a bare `[[c]]` doc, then memory, then concept (bug-216 R6, the spec's own
`depends-on`). The readers ask only for concept ids:
- `rmx memory score` resolves with `resolve_concept_ids` (`WHERE … kind='concept'`, `store.py:3329`);
- the `RMX_BOOST_REINFORCE` block passes term concept ids (`store.py:5614`).

**Why it's sketchy:** the common GMD case, a memory that reinforces another memory or a doc,
lands its signal on a memory or doc id after the fix, and no reader ever asks for that id. "Both
writers and the reader agree" (title) holds only for concept targets. AC-2's "for the same m and
c" is satisfiable only if c is a concept with no same-named doc or memory, and the spec never says
so. bug-216 R7's `denotes` (concept → same-named doc/memory) is the obvious bridge, and the spec
never mentions it. This is an open decision the spec does not recognise.
**Fix (put to the lead, options):**
- (a, recommended) `rmx memory score <name>` and `_op_memory_score` resolve the name the R6 way
  (doc, memory, concept) and also sum over concepts that `denotes` it. AC-4 gains a memory-target
  row.
- (b) Scope bug-218 to concept targets explicitly and log a bug row for memory/doc targets.

Either way, AC-2 pins c's kind.
**Pattern match:** NO (new).

### SKETCHY S3: `memory_link` rows carry no evidence, so after R1 they share the GMD key space unprotected {#s3}

  census cannot tell a `memory_link` row from a stale GMD edge either.
- R0b can classify these rows only as "the rest … or of unknown origin".

**Fix (lead decision):** R1 makes `memory_link` also write `add_evidence(linkage, m, c, detail="memory
link …")`, logged. That protects the row under bug-185 R10, gives R0b a positive writer class, and
gives the plan-22 stale-edge census a discriminator. Add an AC: memory_link + GMD write the same
edge, the GMD line is removed and re-ingested, and the edge survives. Mutation: no evidence row.
**Pattern match:** YES (`feedback_decay_never_loses_knowledge`: a cleanup keyed on evidence loses a
producer that writes none).
