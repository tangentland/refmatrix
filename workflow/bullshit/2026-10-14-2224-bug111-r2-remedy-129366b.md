## Findings {#findings}

### SKETCHY: the every-partition clear goes through `with_partition`, which upserts a partition row per foreign partition on every purge {#s-1}

**File:** `src/refmatrix/store.py:6330-6334` (calling `with_partition` at `:2005-2013`)
**What:** For each id it purges, `_clear_purged_bits` reads the partition NAMES and enters
`with_partition(pname)` once per partition. For every foreign partition that runs `INSERT OR IGNORE INTO partitions` + `commit()` +
`SELECT id ... WHERE name=?` + `row[0]`. The names were just read from that same table, so the insert can never
insert anything.
**Measured** on a refmatrix copy (2 partitions; `bug111-bsd-r2-cost*.log`, `-prof.log`, `-percall.log`; the
machine was shared with two other suites, so read the ranges, not single figures):
- `purge_entity` loop over 200 docs (`_skip_lance`): base 3.97-4.37 s, head 5.01-5.48 s, +25-28%.
- `purge_path` on cli.py (764 entities, the watch re-sync shape that runs under `_store_lock`): base 20.8-24.6 s,
  head 27.7-28.0 s.
- cProfile over 20 warm calls: the `with_partition` scope costs 3.75 ms per call for ONE foreign partition.
  Everything else in the delta is fragment work that is actually needed. The cost grows linearly with the number of partitions.
- The fragment cache doubled, 5.2 MB to 10.4 MB, because every partition's fragments are now resident.

Semantics, as you asked: the transaction semantics did NOT change. The DuckDB wrapper's `commit()` is a no-op (`backend.py:228`), and
`purge_entity` / `_bulk_purge_ids` already commit on their own. Nested `with_partition` under the
daemon's ingest binding restores correctly, and `_clear_purged_bits` never yields. Two things DID
change. First, (a) the ingest/re-sync hot path now issues one `INSERT OR IGNORE` per entity per foreign partition. That
is the DuckDB ON-CONFLICT hammer behind the viascope SIGABRT (`project_daemon_sigabrt_diagnosed`, still
latent upstream). Second, (b) `with_partition` resolves by name without the damaged-zonemap fallback that
`_ensure_partition` carries (`:2039-2076`, the cliquet `[]` incident). If the zonemap is damaged, every purge
raises `TypeError: 'NoneType' object is not subscriptable`. Before the fix, `purge_entity` never looked up a partition at all.
**Failure scenario:** the watcher re-syncs store.py (407 entities) on a store with N partitions. That
issues 407×(N-1) no-op partition upserts under the writer lock, and on a damaged zonemap the whole re-sync raises instead of
purging.
**Fix:** read `SELECT id, name FROM partitions` once, then swap `(self._partition_id,
self._partition_name)` directly in try/finally, the way `flush_fragments` does (`:4205-4215`). That takes no insert,
no commit, no `_vs` swap and no by-name lookup. The fix is a few lines.
**Pattern match:** YES. It is the bug-085 shape (per-entity work under the lock on file re-sync).
