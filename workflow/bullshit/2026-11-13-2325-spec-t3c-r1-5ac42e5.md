## Findings {#findings}

### BULLSHIT: the push reading cannot fail, because outcome (6) is larger in A by construction {#b1}

**File:** `workflow/plans/plan-28-handhold-outcome-experiment.md:145-147`, `:127-129`;
`task-28.3-outcome-scorer.md` R7.

**What:** The push reading is "if A is not better than B on any of outcomes (2)-(4) and (6) while
costing (5), the recommendation is to shrink ambient injection". Outcome (6) is "R12 explicit uses
plus `cited_in_answer` per 100 human prompts", and it counts uses of DELIVERED items only.

**Why it's bullshit:** The two arms do not deliver the same things.
- In cell B the per-prompt hooks deliver nothing (28.1 R3). In A, scan_prompt and prompt_recall
  deliver about 12 items per prompt.
- A `cited_in_answer` hit or an R12 explicit use can only score an item that was delivered. The
  denominator is human prompts, not delivered items. So A's numerator includes uses of
  push-delivered items, and B's cannot.
- scan_prompt delivers the symbols named in the user's prompt. The agent's reply then names them
  because the user asked: this is the prompt-echo confound that sank `bash_name` (pilot: 8 of 14
  refmatrix lag 0-3 pairs). It inflates A only.
- P-5's fallback to explicit-only does not remove the bias. In B, an `rmx context X` for an X
  that was never delivered is not a "use" at all.

So A beats B on (6) whatever the handholds do, "not better on any" never holds, and the
recommendation to shrink ambient injection is unreachable. The brief asks whether every outcome
can fail. This one cannot. 10.2's nested band has the same structural tilt (`full` delivers more
than `dedupe`), but it points against keep, so it is conservative and is not filed.

**Evidence:** `plan-28:146` "on any of outcomes (2)-(4) and (6)". `task-28.1:77-78`: B "runs no
retrieval and no pack". Pilot `measurement-task-21.5-r12-pilot-2026-11-13:88` on prompt-echo.

**Fix:** Take (6) out of the push reading, or replace it there with a measure that does not
depend on delivery. Two options:
- explicit lookups per 100 human prompts, whether or not the target was delivered;
- (6) restricted to boundary- and pull-delivered items, which both arms receive.

Report push-channel "used" descriptively only. Exclude prompt-named items from `cited_in_answer`,
or count them apart. Freeze this in 28.4 R2.

**Pattern match:** YES. It is the proximity / prompt-echo mechanism that the R12 pilot refuted.

### SKETCHY: the paired leg leaks later knowledge, and the cells leak unequally {#s1}

**File:** `task-28.2-paired-reentry-runner.md:80-87` (R2 Clone, Memory snapshot);
`plan-28:105-106`. The plan claims "Fresh agents see only the memories and handoffs that existed
at the task's start, so no later knowledge leaks in". That claim is false on two paths.

1. **Git refs.** "A new clone … checked out at the start sha, with its git remote removed" still
   carries every ref of the source repo. That includes master past the start sha, so the
   reference continuation (the next session's commits) is in `git log --all` and in the object
   store. The spec names this exact hazard ("it is reading the answer", `:36-37`) and guards only
   the memory dir.
2. **The global store.** The generated recall hooks run `rmx memory recall … --scope both`
   (`hooks.py:326,361,389` on master; `:333,388,418` in the 25.1 tree), which merges the hub's
   global memory store. That store holds rows written after the start, and no snapshot filters
   it. The leak reaches A and B through hooks, but not C, which has no hooks. That biases the
   primary B-vs-C comparison toward the handholds.

**Fix:**
- R2 builds the clone with only the start sha reachable, e.g. a `--single-branch` clone reset to
  the start sha, with the other refs deleted and the reflog expired. An AC checks that no commit
  after the start is reachable.
- The paired cells run with the global leg off, or with a global snapshot filtered by date.
- R0 adds a probe for both.
- AC-1 gains a git-refs case and a global-row case.

**Pattern match:** NO.

### SKETCHY: the paired leg's cell B cannot be pinned as specced {#s2}

**Files:** `task-28.1:68-69` (R1: the paired-leg record is "scoped to 28.2's clone roots"),
`task-28.2:80-81,88-89,138-141`.

- **Scope.** 10.2's `scope` is a list of project slugs: the root's basename
  (`launchctl._slug_for_root`). Each paired run gets a new clone root,
  `/Volumes/littlebig/<project>-handhold-<run-id>`, whose slug is not known when the record is
  committed into deployed code. Neither 10.2 nor 28.1 defines a prefix or glob scope.
- **Order.** The records stay "inert … until 28.5 commits them" (`task-28.1:65-66`). But 28.2
  AC-6, which must pass before 28.4's freeze, needs a real `B` run in a clone. With the record
  inert, `draw` returns `A+dedupe` and AC-6 cannot pass.
- **`/clear`.** R0 (a) and (b) probe `--session-id` and `/clear`'s SessionStart source. They do
  not probe whether the session id survives `/clear`. If `/clear` mints a new id, which Claude
  Code does for a new conversation, the post-clear session is drawn randomly and the pin is lost
  for the `clear` trigger.

**Fix:**
- Define the paired record's scope: either a frozen prefix rule in 10.2's record shape, or the
  run ids drawn and frozen before the record is committed.
- Activate the paired record, scoped to clone roots only, before 28.2 AC-6.
- Add R0 (g), whether the session id survives `/clear`, and a pin mechanism if it does not.

**Pattern match:** NO.

### SKETCHY: `cited_in_answer` is not 19.6's clause, and its tokeniser cannot match two of its three forms {#s4}

**File:** `task-28.3-outcome-scorer.md:87-97` (R7).

- R7 says the definition is "19.6's read-back clause, verbatim". 19.6 (`task-19.6:365`) scopes
  it to "A delivered **memory** item". 28.3 elides the noun ("an item is read back") and applies
  it to every delivered item: code symbols, docs, grep-floor items. That is a scope change under
  a "verbatim" label.
- The chosen tokeniser, `_NOTE_TOKEN_RE = [A-Za-z0-9_.\-]+` (`telemetry.py:1473`), splits on `/`
  and `#`. A file path (`src/refmatrix/cli.py`) or a `doc-id#anchor`, two of 19.6's three
  forms, can therefore never be one token, so those forms never match.
- AC-4 tests only the bare-name form, so nothing catches this.

**Fix:**
- Quote 19.6 exactly and state the scope widening as a ruling, or restrict the outcome to memory
  items.
- Match paths and `doc-id#anchor` as whole substrings bounded by non-path characters, as
  `note_used_keys` already does for wikilinks (`_WIKILINK_RE`).
- AC-4 gains a path case and an anchor case, each with a mutation.
