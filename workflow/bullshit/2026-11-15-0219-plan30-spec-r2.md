## plan-30 D12: my call {#d12}

**Are the two claims of `#r3-why-not-marks` true in the code?**

1. **True as the write path stands.** The handlers call `d._request_snapshot()` after leaving
   `with d._store_lock:`:
   - `_op_flush_queue`, `daemon.py:3479-3488`;
   - `_op_sync_files`, `:3585-3597`;
   - `_op_ingest_path`, which releases the lock in a `finally` and then requests,
     `:3655-3656`.

   `_snapshot_catalog` takes `_store_lock` itself for the checkpoint and the copy (`:2826-2849`).
   So a tick already woken by an earlier request can publish a write's rows between that
   handler's unlock and its mark. The window is real.

   One qualification: it comes from where the mark is set, not from marks as such.
   `_request_snapshot` is documented "safe to call under `_store_lock`", and setting a partition
   mark inside the critical section would close it. "Unsound at base" is accurate. "Unsound"
   without that qualifier would not be.
2. **True, structurally.** `build_adjacency`'s operational filter is a global query
   (`pagerank.py:277`, "NOT partition-scoped", `:265`). Its typed rows are selected by the
   partition of their entities (`JOIN entities ce … AND ce.partition_id = ?`, `:331`, `:340`),
   not by the binding they were written under. A write under one binding can change another
   partition's graph, and a rename anywhere can change the operational set. A per-binding mark
   would miss both.

**Is the digest sound?** Yes, by construction.
- It hashes exactly what `read_adjacency_inputs` returns: the mentions fragment's values, the
  typed rows with their weights, the resolved linkage ids, the parameters, and the operational
  ids that are endpoints.
- `assemble_adjacency` is a pure function of that object (30.2 `#r1-two-steps`).
- AC-18 walks the object's fields, so a field left out of the digest fails by name.
- The cases the lead raised:
  - **Weights** are in the typed rows.
  - **Entity deletes** cascade from `entity_links` (`ON DELETE CASCADE`, `store.py:580-582`), and
    a purged fragment bit shows in the fragment's values.
  - **Partition moves** change which rows the join selects.
  - **Noise and protected flags** are not build inputs; the walk reads names and kinds from the
    read store at ranking time.
  - **Duplicate typed rows** cannot occur (`PRIMARY KEY (entity_id, linkage_id, concept_id)`,
    `store.py:579`), so an order-free set digest loses nothing.
  - **Restricting the operational ids to endpoints** is exact: the filter acts only on
    endpoints.
- A write that leaves the digest equal leaves the assembled graph equal.

**Does it cost too much?**
- Each live key pays a read and a digest at every publish. With 2 keys, that is at most two
  passes.
- R0 item 3 measures the read and digest against the full build, with a band (25%) that turns
  the check off.
- R0 item 4 prices one read and digest per key per publish, plus assembles, against the 2%
  service-time band, and prints a worst case.
- The read is probably most of the 506 ms build: an 834 k-value fragment and about a million
  typed rows. So the band may well turn the check off. That outcome is priced, and it is bounded
  by the cap of 2.

**Call: accept D12 over per-partition marks.** It meets L116's purpose: a key rebuilt only when
its graph's inputs changed. It is exact where marks would need write-path discipline across every
binding. Two residues remain, [[#m1]] and [[#m3]]. {#d12-call}

**Caller expecting per-walk demand?** None left. AC-9 now runs with the project key made live by
the op first, and asserts a walk on another partition leaves the live set unchanged. The replay
counts `context` rows only to show what a live key would have served. 30.2's callers read
`cached_adjacency` in-process, as before. {#d12-demand}

**`writer="never"`.** `_read_with_fallback` reaches the writer only through
`_writer_lock(d, writer_wait_s)`, in two places (`daemon.py`, base):
- the partition-missing check after a read store opens;
- the final fallback.

R4's keyword turns both into a raise, which is `names-unavailable`. AC-4's second leg (lock free,
no read store) fails mutation 7. One path outside the helper still touches the writer's object:
[[#m2]]. {#d12-writer}

## New findings {#findings}

### MEH M1: the digest is taken before the operational filter, so session ingests cost assembles AC-18 says they don't {#m1}

**Where:**
- 30.4 `#r3-inputs` (the fragment values and typed rows are digested raw; operational ids are
  restricted to endpoints);
- AC-18, third bullet ("a session card ingested into a sessions partition … `built` did not
  grow");
- `build_adjacency`'s own comment (`pagerank.py:265-268`): "a code partition's `mentions`
  fragment can carry cross-partition edges to session-card concepts".

**What:** a session ingest that adds such a bit changes the project fragment's values, so the
digest changes. The assembled graph does not, because the edge touches an operational id and is
dropped. That is an assemble for nothing on a frequent write.
- AC-18's bullet holds only if the fixture's session ingest writes no project-fragment bit. If it
  does, the test is red at GREEN for a correct implementation.
- The replay's per-partition attribution of assembles undercounts it.

**Fix:** digest the edge set after the operational filter: fragment pairs and typed rows with
neither endpoint operational. This is equivalent for the graph. It still changes when an endpoint
enters or leaves the operational set, since its edges appear or vanish, and the separate
operational-id field then goes. Or add an AC-18 case where a session ingest writes a
project-fragment bit, and state that it assembles.

### MEH M2: AC-17's census scope is unstated, and `open_snapshot_store` can reach the writer's object {#m2}

**Where:** 30.4 AC-17: the census covers "anywhere in `adjacency_service` and in what the service
calls to build", with an empty allow list. Base `daemon.py:2683-2685`: `_open_read_store` builds
`Store(…, partition=partition or self._st()._partition_name, read_only=True)`.

**What:**
- **Read broadly,** "what the service calls" includes `open_snapshot_store` → `_open_read_store`,
  which must construct a `Store` to open the snapshot. The census then cannot pass.
- **Read narrowly** (adjacency_service and the read and assemble steps), `_open_read_store`'s
  `self._st()` is unscanned. With `partition=None` it reads the writer's current binding, which
  is the bug-098 transient-binding read.
- The same holds for the op's `_read_with_fallback` call if `partition` is ever omitted.

**Fix:**
- State the scope: `adjacency_service.py` plus `read_adjacency_inputs` and `assemble_adjacency`.
- Make `partition` required in `open_snapshot_store`, raising on `None`, and in the op's
  arguments, so `self._st()` is unreachable from the service and the op.
- Add a mutation: the service opens with `partition=None`.

### MEH M3: which service time the 2% band reads is not stated {#m3}

**Where:** 30.4 R0 item 4 prints two figures: an estimated split (an assemble "when the publish
followed a write signal for that key's partition", which the spec calls an estimate) and a worst
case (an assemble for every key at every publish). Item 5's band reads "service time".

**What:** the estimate's partition attribution is admitted unreliable, and [[#m1]] lowers it
further. The band could pass on the estimate and fail on the worst case.

**Fix:** the band binds on the worst case, or on both with the worst case deciding. Or name the
estimate as binding and say why it is safe.

### MEH M4: AC-4's no-read-store leg needs an entry first {#m4}

**Where:** 30.4 AC-4, second leg: "the mirror off, and no snapshot or reader-slot file … the op
answers `unavailable: names-unavailable`".

**What:** with no snapshot the service has no entry, so the op answers `building` before it
reaches the names read. The leg as written produces the wrong reason.

**Fix:** state the order: let the entry build, then remove the mirror and the snapshot file, then
call.
