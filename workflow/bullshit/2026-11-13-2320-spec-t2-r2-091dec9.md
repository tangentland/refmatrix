## Findings {#findings}

### SKETCHY: an in-daemon cross-store dispatch still waits on B, and nobody owns dispatch on the CLI's daemon route {#t1}

**File:** `task-26.5…:533-536`, `:547-551`, `:215-222`
**What:** cross-store goes "through the same path `_sync_memory_dir(memdir, root=B)` takes
today, including its existing no-daemon leg". An in-daemon walk "never waits on B (no
`_bridge_wait_for_active_job` from inside A's op)".
**Why it's sketchy:** the path `_sync_memory_dir` takes today IS a wait. It runs
`_ingest_gmd_sync` → `daemon_mod.call(root, "ingest_gmd", …, timeout=24 * 3600.0)`
(`cli.py:10688-10695` at `4b4b96e`), with `daemon.call`'s default `retries=2`. That synchronous
call holds A's op thread for B's whole ingest and its embed drain. The lock is released, but the
thread is not: on the sync/watcher route, A's next flush stalls behind B. So the lead's criterion
(no in-daemon wait on B) is met only for `_bridge_wait_for_active_job`, not for the dispatch
itself. Three more gaps sit under it:
- **Two dispatch owners.** Files gives "dispatch after the doc ingest" both to `cli.py` (`:216`)
  and to the daemon body (`:219`). On the CLI's daemon-up route the CLI calls A's `ingest_gmd`
  op, which already dispatches. If the CLI dispatches again, B refuses the second call as
  `ingest already active`, and the CLI counts a spurious `rerouted_failed`.
- **The library helper has no home.** "The op-call helper lives in a library module" names no
  module. The no-daemon leg it must include (`_store_rw`, `_ingest_gmd_in_process`) lives in
  `cli.py`.
- **No AC covers the in-daemon cross-store branches.** That covers B up, B absent ("never opens
  B's store in-process") and B busy. (g)/(g2) are CLI runs, so the mutations "in-daemon fallback
  opens B in-process" and "in-daemon synchronous wait" both survive.
**Fix:**
- In-daemon cross-store starts a DETACHED job on B: the `ingest_gmd_start` op (`daemon.py:3881`),
  with `retries=0` and a short connect timeout. B's job id goes on A's op record. B down or busy
  is `rerouted_failed`.
- Name the dispatcher per route: the daemon body for every daemon route, the CLI only for its
  in-process route. The CLI prints the counts from the op result.
- Name the library module.
- Add AC-220 (k), a sync-op walk reaching B's memdir:
  - B up: the op returns before B's job finishes, and the rows appear in B;
  - B down: `rerouted_failed`, and B's catalog files are not opened (unchanged mtime);
  - mutations "synchronous call" and "open B in-process" each kill (k).
**Pattern match:** YES. It is the same lock/thread-hold class as r1 s3 (bug-085).

### SKETCHY: AC-220 (i), the only lock-safety test, contradicts the no-store rule and passes vacuously {#t2}

**File:** `task-26.5…:612-615` vs `:552-553`, `:628`
**What:** (i) "`_sync_paths` over a project root that holds a marker memdir outside any dot-dir
… The files reroute as in (a) … an audit hook on the lock asserts it is not held during the
dispatch."
**Why it's sketchy:** by R-220c, "a marker dir with no slug form is file-only". It is counted as
`rerouted_no_store` and nothing is dispatched. So "reroute as in (a)" cannot hold, and the audit
asserts over a dispatch that never happens. The named mutation "dispatching under the writer lock
kills (i)'s audit assertion" survives. (i) is the only test of the lead's lock-safety criterion.
**Fix:**
- Make (i)'s memdir the TARGET of a `HOME/.claude/projects/<slug>/memory` symlink, so the sync
  walk finds the slug through the symlink map.
- Run it twice: slug → the walking store (same-store branch), and slug → B (cross-store branch).
- Assert the audit observed at least one dispatch.
**Pattern match:** YES. A gate that cannot fail
([[feedback_clean_corpus_hides_a_dead_gate]] family).

### MEH: (h)'s named mutation survives by design, and the marker branch's unresolved form is unspecified {#n1}

**File:** `task-26.5…:503-512`, `:625`
**What:** "resolving before `memdir_of` kills (h)". The symlink map (`:509`) maps a resolved
path back to its slug, so a resolve-first implementation still lands in the slug's store and (h)
passes. Two mutations would actually kill (h):
- "hand the resolved form to the store resolver";
- "drop the symlink map" (this kills (h)'s sync leg).

Separately, the marker branch (`:507`) is tried before the map. For a marker-on viascope reached
by a sync walk it must still get the UNRESOLVED form through the map, or the store resolver sees
the resolved path and returns `no_store`. The spec never says so.
**Fix:** rename the mutation as above, and add one line: every branch maps the memdir through the
symlink map to get its unresolved form.

### MEH: (g2)'s fault injection may not fault {#n2}

**File:** `task-26.5…:604-607`
**What:** "B's store root is made unwritable". On the daemon-up leg, B's daemon already holds
its catalog files open, and `vectors/` is a subdirectory whose mode is unchanged. The bridge may
succeed, and then (g2) fails at GREEN for the wrong reason. It also runs only "whichever leg"
`_sync_memory_dir` takes.
**Fix:** use a deterministic fault on each leg, run both:
- daemon up: B holds an active ingest job (`ingest already active`);
- daemon down: B's slot `active` marker made unreadable, or a held writer lock.

### MEH: one ADR sentence over-scopes the hard error onto R-264a {#n3}

**File:** `docs/adr/0005-memory-dir-layout.md:160-162`
**What:** "This governs every explicit memdir argument: the organise verb's (26.5 AC-1) and
R-264a's file/subdir resolution". R-264a accepts a marker dir outside `projects/` (its marker
branch). It refuses only when no memdir is found, and it resolves no store. A literal reader
would add a "not under projects" refusal to R-264a.
**Fix:** "the hard error is the organise verb's; R-264a refuses only when no memdir is found
(its own `Error:` line)".

### MEH: prestage drops rerouted files uncounted (bug-216 R6b) {#n4}

**File:** `task-26.5…:520-524` vs bug-216 `#r6b` (`4b4b96e`)
**What:** `ingest-gmd --prestage <dir>` without `--as-memory` walks through `collect_gmd_files`.
R-220b takes memdir files out of that set, and nothing counts them on the prestage result. bug-216
rev 6 R6b requires prestage to name its exclusions.
**Fix:** the prestage result and CLI line carry the `rerouted` count and names, like `ignored`.

### MEH: the CLI's no-daemon leg opens B in-process {#n5}

**File:** `task-26.5…:534`, `:550-551`
**What:** "including its existing no-daemon leg" and "The CLI may use … the existing no-daemon
leg". With B's daemon absent, the CLI opens B's `Store()` in-process (`_store_rw`). The lead's
r2 check reads "no in-process open of B's store". This is today's bridge fallback, guarded by
`require_daemon`'s busy refusal, so the hazard is not new. Still, the spec allows exactly what the
check names, and does not say it is an exception.
**Fix:** the lead confirms which it is:
- a deliberate CLI-only exception, written as such; or
- the CLI also counts B-absent as `rerouted_failed`.

### MEH: 27.5 AC-5 does not pin which root the restore runs in {#n6}

**File:** `task-27.5…:57-63`
**What:** the restore runs `rmx ingest-gmd --as-memory --force-rebridge <file>`, which writes
the CALLER's store (ruling 2). The AC checks "the file's memdir resolves to the row's store". It
never says to run the command in the root of the store that holds the row. Inside cliquedb's
session window, the natural cwd is cliquedb.
**Fix:** "run in the root of the store R-202a recorded for the row; `rmx version -v` and the
resolved store printed in the log".
