## Findings {#findings}

### SKETCHY: the lock-exit drain fires at every cooperative yield, on a queue every lock holder shares {#x1}

**File:** `task-26.5…:546-559`, `:616-617`
**What:**
- "The OUTERMOST exit of the `d._store_lock` context drains the queue … In the daemon every
  `ingest_gmd_paths` call runs under that lock, so at release the queue holds only that holder's
  groups."
- The queue is "ONE per-process pending-dispatch queue", filled "as soon as they are collected,
  before the doc ingest" (`:553`).
**Why it's sketchy:** the daemon has no "outermost exit".
- **The lock has no depth.** `d._store_lock` is a `_FairLock` (`daemon.py:258`, `:796`). It is
  non-reentrant, with no depth or owner. It is taken through `with` (71 sites) and through bare
  `acquire()`/`release()` (`_run_ingest_gmd_body`, `daemon.py:3759-3764`).
- **`ingest_gmd_paths` releases it mid-walk.** It runs with `yield_lock=_yield`, and the yield is
  `d._store_lock.release(); time.sleep(…); d._store_lock.acquire()` (`_partition_keeping_yield`,
  `daemon.py:3560-3579`). `RMX_INGEST_YIELD_EVERY` defaults to `1`, so that happens between files.
  `_ingest_path_inner` yields the same way (`_CommitWindow.boundary`).
- **On release, the lock passes straight to the next queued op.** The FIFO handoff
  (`_pass_or_release_locked`) gives it to the next waiter, which may be another op running its own
  `ingest_gmd_paths` and enqueuing its own groups.

So "at release the queue holds only that holder's groups" is false. Built as written (the drain
hooked to release), the design has four defects:
1. **Mid-walk dispatch.** The first yield after the early enqueue drains the groups while the
   walking store's ingest is still running. That breaks R-220c's own rule (`:546`: "only AFTER
   the walking store's ingest has returned").
2. **Two writers, the race the guard exists to stop.** The same-store memory job, started under
   the parent's single-use exemption, then runs CONCURRENTLY with its parent's doc ingest.
   Preventing that is the single-active guard's whole purpose ("the two would fight over the
   write lock and interleave their two-pass parse/resolve state"). The exemption turns it on.
3. **Groups land on the wrong op.** Op Y, running in X's yield window, drains X's groups, and the
   result attaches to Y's reply and job. X's job then reads `done` without its reroute result,
   which brings back r3 V1 under interleaving.
4. **Spurious failures.** X's same-store group, drained under Y's exemption or none, meets
   X's active job and becomes a spurious `rerouted_failed`.

No AC interleaves two ops, so none of this is caught. The (i) audit only checks that the lock is
not held at dispatch, and that is true here: the drainer has released it.
**Fix:**
- Drain at the op and job boundary, never at a lock release. Wrap, in `try/finally`:
  - the daemon's request handler that runs every `OPS` entry (this covers all socket routes by
    construction);
  - `_run_detached_job`;
  - the `ingest_gmd_start` runner;
  - the in-daemon watcher flush.
- Key the queue to the invocation (a `contextvar` or job id set by the wrapper), not the process.
- `enqueue` with no invocation context raises loudly, which catches a new unwrapped route at
  runtime.
- A yield never drains.
- Add an AC: two ops interleave through a yield (a gate on X's second file). X's groups are
  dispatched once, after X's ingest returns, onto X's record; Y's drain carries only Y's groups.
  Mutation: "drain on lock release" kills it.
**Pattern match:** YES. It is the r3 V1 / bug-098 shape: state bound to a lock holder that moves
under in-flight writes ([[project_bug098_writer_partition_race]]).

### SKETCHY: no AC drains on an exception path, and one of the two named CLI mechanisms skips exceptions {#x2}

**File:** `task-26.5…:218`, `:560-566`
**What:** "the top-level wrapper (`cli_entry` / the click result callback) drains
`memory_reroute` on exit".
**Why it's sketchy:**
- **The result callback is the wrong hook.** A click result callback runs only when the command
  returns normally. It is skipped on `ClickException`, `ctx.exit(n)` and `sys.exit(n)`. Those are
  the paths a failing walk takes, or the `MemoryOwnershipError` exit in `sync` (`cli.py`
  `_sync_in_process` caller). The groups were enqueued before the raise, on purpose (`:553`), so
  they would sit undrained and uncounted when the process exits.
- **`cli_entry` is right, but tests bypass it.** It has a `try` around `main()`
  (`cli.py:14970-15000`), so its `finally` would drain on exceptions. But the repo's CLI tests run
  through `CliRunner` / `main`, not `cli_entry`. A drain in `cli_entry` alone is invisible to
  (n)'s CLI rows unless they spawn the console script.
- **The daemon side has no case either.** An op that raises after its enqueue has no AC.

Lead check 2 asks for exactly this case, and no AC exercises it.
**Fix:**
- Name ONE CLI mechanism that runs on every exit: `cli_entry`'s `finally`, with (n)'s CLI rows
  run through the console script. Or a root-group `ctx.call_on_close`, which click runs on context
  teardown, exceptions included.
- Add an AC:
  - (CLI) a command that raises after its walk enqueued a group still drains, or names the
    undrained group loudly, and exits non-zero;
  - (daemon) an op that raises after the enqueue drains in the wrapper's `finally`, with the error
    and the reroute result on the record.
- Mutation: "drain only on success".
**Pattern match:** YES. The CLAUDE.md `#no-silent-failures` / [[feedback_errors_fail_loudly_on_the_console]]
family.

### MEH: (n)'s completeness scan has no must-fail proof, and misses daemon threads that are not OPS {#x3}

**File:** `task-26.5…:762-772`
**What:** "scans `daemon.OPS` and the CLI command tree for handlers whose call graph reaches
`ingest_gmd_paths` … and fails on any name missing from the parametrization".
- **Seeds:** the scan seeds from OPS and the CLI tree only. The daemon's own watcher
  (`Daemon._start_watcher` → `sync_files`, `daemon.py:3172-3185`) is neither an OPS entry nor in
  (n)'s parametrization. `#reroute-routes` lists it; (n) does not run it.
- **Edges:** the start ops reach their bodies through `self._bg_pool.submit(lambda: …)`
  (`daemon.py:3950`). An AST or `tldr` walk that does not follow lambda/`submit` arguments misses
  that edge.
- **No proof:** nothing shows the scan FAILS ([[feedback_clean_corpus_hides_a_dead_gate]]).
**Fix:**
- Seed from `OPS`, the CLI tree, and every `Thread(target=…)` / `_bg_pool.submit(…)` site.
- Follow lambda bodies.
- Add a must-fail fixture: a planted OPS entry that reaches `ingest_gmd_paths` and is missing from
  the parametrization makes the scan fail.
- Add the daemon watcher row.

### MEH: the CLI drain's same-store leg has no store handle, and the command's store may still be open {#x4}

**File:** `task-26.5…:566-571`, `:618-619`
**What:** the CLI drain passes `_ingest_gmd_in_process(…, as_memory=True)` as the same-store
leg, and that function takes an open `Store`. At wrapper exit the drain has none. Some commands
still hold one: `sync` opens `s = _store()` and never closes it in a `finally`
(`cli.py:8746-8752`), so A's DuckDB writer is still open when the drain runs. A second `Store` on
the same root in one process means two fragment caches over one catalog (the bug-105 class).
**Fix:** say whether the command closes its store before the drain and the drain reopens it with
`_store_rw()` and closes it, or the drain reuses the command's open store through the invocation
context (X1's key).
