## Findings {#findings}

### SKETCHY S1: the new GMD pass on the live route holds the daemon's store lock for its whole duration — about 17 min on a repo-sized tree {#s1}

**File:** `src/refmatrix/ingest.py` `_ingest_markdown_gmd` (no `yield_lock` / `yield_every`), called
from `_ingest_path_inner`, which DOES receive `yield_lock` (`daemon._op_ingest_path` passes
`_partition_keeping_yield`).

**What:** the daemon runs `ingest_path` cooperatively. Its tldr/python/pseudo/sql passes call
`_yield_flush` every `yield_every` units, but the markdown GMD pass takes no yield hook. So
`ingest_gmd_paths` runs inside one commit window with `_store_lock` held from start to finish.

Before bug-241 the live refmatrix store (which has a `.tldr` cache) never ran this pass, so this is
new behaviour for the store the deploy is about to reingest.

**Measurement** (`time_gmd_pass.py`, `time_gmd_pass.log`): `_ingest_markdown_gmd` on a copy of
this checkout (784 markdown files, R4 ignore file) on a throwaway store, load ≈ 5.3, gave
**733 GMD docs in 1027.7 s, all under one transaction**.

On the live daemon, every write queued behind it waits that long: hook writes, STM focus notes,
grep learning, the watcher, the bridge. That is the lock-holding wedge class of the 2026-10-07
daemon wedges (bug-085).

**Fix (small):** thread the hook through, as the `ingest_gmd` op already does:
- `_ingest_markdown_gmd(s, root, *, ignore_root, yield_lock=None, yield_every=10)` passes them to
  `ingest_gmd_paths(..., yield_lock=yield_lock, yield_every=yield_every)`;
- `_ingest_path_inner` passes its `yield_lock` / `yield_every`;
- `_ingest_tree` is called on the same route, so it passes them too.

Pin it: a cooperative `ingest_path` with a counting `yield_lock` on a tree with a cache and more
than 10 markdown files sees yields during the markdown phase. Until then, run the live forced
reingest only with the lock-hold announced, accepting minutes of busy hooks.

**Pattern match:** YES. `feedback_main_path_must_exercise_core_mechanisms`: the cooperative path
exists, and the new pass bypasses it.

### SKETCHY S2: a failed GMD pass is printed to the daemon's stderr log and nowhere else; the caller sees success {#s2}

**File:** `ingest.py` `_ingest_markdown_gmd`, the `except Exception` branch.

**What:** the branch prints `rmx ingest: GMD pass failed …`, registers the files as plain docs, and
returns their count. Two gaps:
- **No counter.** Nothing goes on the store (compare `vector_delete_failures`), so `_op_ingest_path`
  returns only `{"entities": n, "path": …}`.
- **No surface.** On the production (daemon) route the `print(..., file=sys.stderr)` lands in
  `daemon.stderr.log`. `rmx ingest` / `rmx reingest` print `ingested N entities` and exit 0.

That is the shape ch-bsd 26.1 #s-3 already ruled not loud ("the daemon's stderr log reaches no
one"; `feedback_errors_fail_loudly_on_the_console`). The lead asked for "counted and surfaced";
this is counted nowhere and surfaced only in a log.

The branch also has **no test and no mutation**. Deleting the whole `except` body survives the
bug-241 file, because no case makes `ingest_gmd_paths` raise.

Severity is limited because the next `rmx ingest` retries the GMD pass (the helper does not consult
the mtime gate).

**Fix:**
- Count the failure: a `gmd_pass_failures` counter on the store, or a field in `ingest_path`'s
  return.
- Return it in `_op_ingest_path`'s result.
- Have the CLI print `Error:` and exit non-zero when it is non-zero, as `vector_delete_failed`
  does via `_say_vector_delete_failures`.
- RED: a markdown file that makes `ingest_gmd_paths` raise, through the daemon route. The CLI must
  exit non-zero with a line naming the GMD pass.

### MEH M1: `rmx ingest <FILE>` checks the file only after `_store(write=True)` {#m1}

**File:** `cli.py` `ingest`: `_ingest(_store(write=True), …)`, with the refusal coming from
`ingest_path` inside.

**What:**
- **Daemon busy:** `require_daemon` raises first, so the user reads "busy — writes go through the
  daemon", not "use `rmx sync -f`".
- **Daemon absent:** `_store_rw()` opens the catalog read-write in-process (taking the writer lock)
  only to refuse.

The verb already checks before `require_daemon`, for exactly this reason (its own comment). The CLI
should too.

**Fix:** one call of the same helper before `_store(write=True)` (not a copy):
`try: refuse_file_target(resolved) except IngestFileTargetError as e: raise click.ClickException(str(e))`.
Add a RED with the daemon busy (or a `require_daemon` that raises `VerbBusyError`).

### MEH M2: "markdown is GMD-routed whatever `--source`" is stated only in a code comment and the summary {#m2}

**File:** `cli.py` `--source` help text, `docs/INTEGRATION.md:64`, `docs/SYSTEM.md:79`.

**What:** the behaviour is right (the else-branch comment; summary `#fix-callers`). But the help
text still reads "graphify forces the knowledge-graph JSON to be the only ingest", which is now
false for markdown, and the docs say nothing.

**Fix:** one clause in the help text and in INTEGRATION's ingest section: "`--source` picks where
CODE structure comes from; markdown always goes to the GMD pass".
