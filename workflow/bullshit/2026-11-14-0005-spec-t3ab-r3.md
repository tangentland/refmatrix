## Findings {#findings}

### SKETCHY (carried, r2 S3): AC-26's out-of-scope `/dev/null` assertion still fails on correct code {#s3}

**What:** unchanged at `22e4623`:
- R12 `:170` reads "**Out of scope** (stdout to `/dev/null`, or not rmx): … `focus hook` on `tool`
  / `say` / `input`".
- AC-26 (`:290-299`) reads "The out-of-scope commands are asserted to send rmx stdout to
  `/dev/null`."

**The generated commands do not match.** On the 25.1 branch at `23caf45`, `hooks.py:156`, `:165`,
`:170` and `:177` redirect only stderr (`rmx focus hook --event tool|tool-pre|input|say 2>/dev/null
|| true`). `cli.focus_hook` (`cli.py:2103`) writes stdout only on `session-start`.

**Also missing:** `tool-pre` and 10.3's `compact-marker` are in neither list.

**Fix:** as in r2.
- AC-26 runs each silent command (focus hook `tool`, `tool-pre`, `input`, `say`,
  `compact-marker`) and asserts empty stdout. Alternatively, R12 routes them through `emit`.
- The `/dev/null` assertion stays only for the sync flush and the primer.

### SKETCHY (carried, r2 S4): curator status runs in a second command, and its share is unattributable {#s4}

**What:** unchanged at `22e4623` `:159`: "`cli.curator_status` (one command, two writers, 4,500 B
/ 500 B shares)".

**A second command also runs it.** SessionStart `startup|resume` runs `sess_cmd`, with the same
argv `rmx curator status || true` (`hooks.py:208-215` at `23caf45`). There curator status is the
command's only writer, so its share is 9,500 B.

**Why:** `hook_budget.emit(text, *, command, channel)` cannot tell the two commands apart.

**Fix:** as in r2.
- Name the SessionStart entry in R12 and in `HOOK_COMMAND_CHANNELS`.
- Either use the fixed `curator_status` share everywhere, or add a `--hook-command` argv.
- Add an AC-26 row for the SessionStart curator command.

### SKETCHY (new): nobody owns the key that `pack` passes to `Held.covers` {#s5}

**Files:** 25.1b `#k3` (`:94`) and Files (`:397`); 10.2 h8 (`:68`), R3 (`:120-126`) and Files
(`:345-346`).

**What:**
- **25.1b's `pack` calls `held.covers(key, full_run_tier)` for "a row whose key …"**, but 25.1b
  never says how `pack` derives `key` from a row.
- **10.2 h8 makes the key ONE function.** "`(scope, entity_id)`, else `(scope, kind, name)`: ONE
  function, `telemetry.item_key`, for the state, both renderers and 10.5's replay." 10.2's Files
  row builds `telemetry.item_key` (`:345`).
- **But 10.2 can no longer wire it into the pack.** Its Files row now says `recall_pack.py`:
  "none" (`:346`).
- **25.1b builds first and has no `item_key`.** So it must invent a key, for example the name.

**Why:** if 25.1b's key and `HeldSet`'s `item_key` differ, `covers` never matches and the recall
dedupe silently does nothing.
- **10.2 AC-1 catches it at RED.** But the only repair edits `recall_pack.py`, which 10.2 says it
  does not touch, and it re-opens the single-owner ruling.
- **Same-name collisions break too.** A name key would also merge the "two code symbols with one
  name in two files" that h8 exists to split.

**Fix:** 25.1b owns the key:
- `pack` calls `telemetry.item_key(row)`, and 25.1b BUILDS `telemetry.item_key` per h8, moving it
  out of 10.2's Files row.
- Add an AC-25 leg with two same-name rows in different files, where `covers` is True for one key
  only and only that row moves.
- 10.2 h8 cites 25.1b as the builder.
