2. **AC-0.15 (RED):** in a throwaway git repo with no ignore rules, after one `scan-prompt`

3. **Mutation M0-10:** drop the `.gitignore` write. It must fail AC-0.15.
4. Correct the D1 row in the POP: the capture holds payload text, including up to eight prompt

### S1 SKETCHY: the R0.5 cost band is measured on a path that understates the cost {#s1}

**Spec:** [[task-31.5-scan-prompt-block-measure#r0-5]] measures on "a throwaway store built from
`docs/` and `src/refmatrix/`" with 40 synthetic prompts, using added wall p95.

**Evidence:**
- **The token stop is not a tail event.** In regime A, before the byte cap hid the marker,
  `# [truncated by --max-tokens]` was in 411 of 775 scan outputs (53%; my count over the
  transcripts, counts only). So the extra builds set the p95.
- **Probe on a read-only copy of the live `catalog.read.duckdb`** (1.3 GB; in-process; warm
  after one call; the dev tree's `build_context` with `max_tokens=600, max_entities=10`):
  - per call: p50 34 ms, p95 92 ms;
  - identifiers 25-33 ms; plain hub words `daemon` 92, `memory` 74, `partition` 71,
    `session` 69 ms;
  - four extra builds come to about 140 ms at the median and about 370 ms when they are hub
    words.

  Tier-3 bundles (plain words and PPR expansions) are the ones past the stop, because tier 1
  comes first. So the expensive bundles are exactly the ones the capture adds. The first call
  in a fresh process cost 116 ms, and every hook call is a fresh process.
- A `docs/` + `src/` store has far fewer edges per hub word than the live store, which also
  holds memory, workflow, sessions and canon. So it will understate the cost.
- The live hook already runs p50 3.6 s and p95 5.3-6.7 s in regimes B and C (`durationMs` in
  the transcripts), and p95 17.2 s in regime A.
- With 40 prompts, the p95 is the second-largest sample.

**Fix:**
1. Measure on a copy of the live catalog, through the generated hook's exact command line, in
   fresh processes, with at least 200 alternated runs, quiet and loaded.
2. Report what the leg produced (bundles built per call, ms per bundle) beside the wall time
   ([[feedback_measure_the_outcome_not_the_wall]]).
3. Add `capture_ms` and `capture_built` to the record.
4. **AC-0.17 (live, after release A):** the p95 of `capture_ms` over the first 100 captured
   prompts falls inside the band chosen before release. If not, the cheaper path ships as
   A.1.

### S5 SKETCHY: `followed` is sound only as a label-gated candidate class, and five gaps let it, or `ignored`, misplace credit {#s5}

`u` reads only CAUSED + INFORMED labels
([[task-31.5-scan-prompt-block-measure#r1-1-table]]). So `followed` adds candidates, not
credit. That part is sound. These gaps are not:

1. **Self-found chains are credited.** A grep whose output lists a path, followed by a `Read`
   of that path, is `followed`. "Touched earlier" does not cover a path that appeared in the
   output of the agent's own call. **Fold:** add a class `self_found` (counted, in no rate)
   for a fetch whose path appeared in an earlier main-loop call's output in the same turn.
2. **A search scoped by the injection is scored against the agent.** For example, a grep for
   a pattern inside a delivered file. The target is "the pattern or name, and any path
   argument", so a delivered path argument makes the call `ignored`. Yet the pilot's only
   signal leg was `bash_path`: main-loop C+I 9/26
   ([[measurement-task-21.5-r12-pilot-2026-11-13#breakdowns]]). **Fold:** when the match is
   only through the path argument, the call is `followed`. It is `ignored` only when the
   searched name or pattern itself was delivered.
3. **No lag bound.** The pilot found 0 CAUSED of 13 at lag 7+ and 0 of 40 with prior touch,
   and "credited to the item's first delivery" sends credit to old prompts. **Fold:** report
   `u` by lag band (0, 1-3, 4-6, 7+). The bands read lag 0-6.
4. **The label cap has no sampling rule for `followed`.** It says "all of them up to 150 per
   block kind", and nothing about the rest. `ignored` has a seeded draw. **Fold:** the same
   seeded uniform draw, with `u` computed from weighted labels.
5. **Attribution across kinds is undefined.** When a path is in two delivered blocks of
   different kinds, the spec does not say which kind gets the credit. **Fold:** credit every
   kind that carried it, and report the overlap count.

Also: 25 blind pairs at 80% agreement has a Wilson lower bound of 61%. Set the 80% gate on the
lower bound, which needs about 60 pairs.

### S6 SKETCHY: the band table has a hole, `shrink` is out of reach at the window's sizes, and the window closes on a different count than `insufficient` reads {#s6}

Wilson 95% (my computation):

- **A hole in the table.** Take `u` upper < 5% on a kind dropped on 40 or more prompts whose
  `a` interval straddles 5%. For example, 0 avoidable in 40 to 72 drops gives an `a` upper
  bound of 8.8% to 5.1%. That case is not `cut` (which needs `a` upper < 5% or fewer than 40
  drops) and not `cut-was-the-cap` (which needs `a` lower ≥ 5%). The `ambiguous` row reads
  "the interval" without saying which one. **Fold:** add the missing row (→ `ambiguous`) and
  name the interval in each row.
- **`shrink` is out of reach at small n.** No count gives an interval inside 5% to 15% at
  n = 80 or n = 120. At n = 160 only k = 14 or 15 does. At n = 80, every `u` from 1.2% to
  22.5% is `ambiguous`. So at the 400-prompt close, most kinds with modest use will reach
  `shrink` only through D5's default. **Fold:** print this reachability table in the spec, so
  the outcome is not read as a measured `shrink`.
- **Closure and band count different things.** Closure condition 3 counts prompts on which a
  kind was **produced**, but `insufficient` reads **delivered**. The composite was delivered on
  3 of 22 prompts in regime C, which projects to about 55 at 400 prompts. So the window can
  close with the composite `insufficient`. **Fold:** condition 3 counts delivered prompts.
