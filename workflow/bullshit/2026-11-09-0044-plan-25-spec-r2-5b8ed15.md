## Findings {#findings}

### SKETCHY S1: moving the replica-first leg into the verb silently changes MCP recall, and the leg being moved is bound to the CWD {#s1}

**File:** [[task-25.1-recall-hook-byte-budget#r5]], d5; `cli.py:11347-11420`, `verbs.py:898-958`.

**What:** R5 puts the replica-first leg into `verbs._memory_recall_rows`. That verb is also what MCP
`rmx_memory_recall` runs (`mcp.py:142`). After R5, an agent's MCP query recall becomes:
- served from the replica snapshot rather than the live daemon slot, so it lags the writer;
- dependent on the MCP process's own environment for `RMX_RECALL_REPLICA_FIRST` and for the rerank
  default (`_reranker.rerank_enabled()` runs in-process, not on the daemon);
- dependent on the hub's shared workers.

R5 does not mention MCP, and no AC or decision row covers it. The parity tests will not notice:
`test_mcp_memory_recall_routing.py` mocks `daemon.call`, and in the sandbox there is no
`models.sock`, so the replica leg returns None and the old route passes unchanged.

**Buildability:** `_replica_memory_recall` takes no root. It reads `_reader_store()` and
`_resolve_partition()`, which are CLI globals for the CWD's store. If it is moved as-is, an MCP call
with `project=cliquedb` from a refmatrix session reads REFMATRIX's replica. This is the same
"CWD resolver inside a root-taking verb" shape as plan-26 r1 #b2. The verb-side primitive already
exists: `search.cached_replica(root)` is what `memory_partition` uses.

**Interactive path:** R5 also says the CLI calls the verb "for every hook mode". The interactive
query path (`rmx memory recall "q"`, table and `--json`, `hook_mode` False at `cli.py:12323`) still
computes its own rows, including the CLI-only `kind=doc` leg. The rev-round claim "closes plan-3's
open 'dense path is a second which-rows'" is therefore true only for hooks.

**Fix:**
- Add a decision row: MCP query recall goes replica-first, yes or no, and with whose rerank default.
- Signature: `recall.replica_memory_recall(root, *, partition, …)` over `cached_replica(root)`.
- Add an MCP AC: worker present, `root=`/`project=` naming a second sandbox store, and the rows come
  from THAT store.
- Either route the interactive query mode through the verb (and decide the doc-kind leg), or narrow
  the claim to hook modes and leave plan-3's row open.

**Pattern match:** YES. This is the seventh "two ways to compute which rows" sighting, and the
second CWD-resolver-in-a-root-verb sighting today (imp plan-26/27 r1).

### SKETCHY S2: the event budget is split by producer, but the cap and the overflow are per hook command; two producers are uncapped and one is not counted {#s2}

**File:** [[task-25.1-recall-hook-byte-budget#r0]], `#r1`, AC-12; `hooks.py:247-250`, and the 3.7
clone's `hooks.py:252`.

**What:** No runtime coordination is needed: each process caps itself to a static share. But:
- **Outcome (A) overflows one hook.** scan-prompt and `curator status` are ONE hook command
  (`rmx scan-prompt … ; rmx curator status …`). Outcome (A) gives "every producer `0.9 × cap`", so
  that single hook's stdout can reach `1.8 × cap` and be previewed.
- **Two shares are not bounds.** `curator_status` and `focus_input` get "the measured max on the
  fixture + 20%". That is a fixture reading, not a cap. 3.7's `curator status` prints up to
  `--limit 10` repo-relative paths of any length, plus overflow text, on every prompt, and nothing
  fits it to its share.
- **A producer is missing.** The user's global settings install a non-rmx UserPromptSubmit hook
  (`~/.claude/hooks/caveman-mode-tracker.js`). Under a per-event cap its bytes count, and
  `EVENT_SPLIT` has no entry for it.

**Fix:**
- Budget per GENERATED HOOK COMMAND, with `scan_cmd` = scan-prompt + curator.
- Give `curator status` a byte cap through `fit_blocks` (or a `--max-bytes`).
- Have R0 record any non-rmx hook bytes on the event as a reserved share.
- Make AC-12 assert per hook command under (A), and the event sum under (B)/(C), with a curator
  queue of long paths in the fixture.

### SKETCHY S3: 25.4 R1/R2 still carry rules that disagree with both greps, and the spec records one BSD/GNU divergence where there are at least three {#s3}

**File:** [[task-25.4-grep-bre-translation#r1]], `#r2`, AC-2, AC-5, e4. Evidence is in [[#probes]].

**What:**
- **(a) `-w` is wrong.** `-w` → `\b(?:p)\b` fails on patterns with non-word edges. For `-w '@foo'`,
  both greps return ` @foo ` while the Python form returns `a@foo b`. The counts happen to be equal
  and the lines differ. AC-5 tests only `a\|b`, which has word edges, so it passes. grep's rule is
  `(?<!\w)(?:p)(?!\w)`, and the same applies to the stdin leg.
- **(b) A compile failure has no defined outcome.** `^*a` (literal `*` after a leading `^`) is not
  in R1's literal-`*` positions, and `a**b` is not covered either. Both translate to patterns that
  raise `re.error`, and nothing in R1 maps that to `UntranslatableBRE`. The likely result is a
  traceback where both greps answer.
- **(c) Stacked quantifiers change meaning silently.**
  - `.*\+x` becomes possessive `.*+x` in Python 3.11+ and matches 0. BSD exits 2; GNU matches 4.
  - `a*\?b` becomes lazy `a*?b` (6). BSD answers 0; GNU answers 6.
  These are two more BSD/GNU divergences, plus `a**b` and `.*\+x` (BSD exits 2). e4 says BSD is
  the authority, but R1 would answer like neither grep.
- **(d) POSIX classes are mapped to ASCII.** R1 maps POSIX classes "to explicit ranges". Under the
  workstation's default `LANG=en_US.UTF-8`, both greps match `café` with `caf[[:alpha:]]`, and an
  ASCII range does not. R1's `\w` is kept as Python's Unicode `\w`, so the translation is
  internally inconsistent too. The test locale is not pinned.

**Fix:**
- `-w` becomes `(?<!\w)(?:p)(?!\w)` on every leg.
- Any `re.compile` failure of the translation is `UntranslatableBRE`, which goes to the real grep.
- A quantifier immediately after a quantifier is `UntranslatableBRE`.
- POSIX classes follow the locale grep runs under: Unicode classes under a UTF-8 `LC_CTYPE`, ASCII
  under C. Or delegate any line set with non-ASCII bytes.
- Pin `LC_ALL` in the differential test and add a second-locale column.
- Add AC-2 rows `-w @foo`, `^*a`, `a**b`, `.*\+x`, `a*\?b` and `caf[[:alpha:]]`, plus their
  mutations.

**Pattern match:** YES. This is r1 #s9's class: a translation rule written from the regex
dialect's docs rather than from the oracle's answers.

suppressed note counts toward `_HELIX_NEIGHBOR_NOTES` and `_HELIX_NEIGHBOR_SCAN`, and give AC-10's
fixture more than five stale neighbours.
