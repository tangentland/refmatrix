## New findings (changed sections only) {#findings}

### SKETCHY NS1: a provably-behind old stamp turns into `code_unknown` and stays there {#ns1}

**Where:**
- 29.2 `#r7-compare`: "any other tag (`p1`, another Python), or untagged → `code_unknown`";
- `#r8-rule`: digests differ → `left`, untouched;
- AC-24: "one pass file given a real edit after the stamp → `left`, untouched, still
  `code_unknown`";
- `#d27`: the closing re-derive covers "exactly the affected passes" of deploy B.

**What changes.**
- **Today:** a `p1` stamp is compared with `derive_code_hash(pass)` (`store.py:7676-7704`). A
  pass file edited after the stamp makes the stamp read `behind_code`. That feeds `stale`, the
  reason line and the alert.
- **After deploy A:** the same stamp reads `code_unknown`, which is not hot.
- **After the rehash:** the stamp is counted `left` and kept unknown. Nothing re-derives it.
  Deploy B's closing step takes its pass list from the NEUTRAL / REAL table of the release, not
  from the rehash's `left` list.

**Why it's sketchy.** The design already holds the witness that would decide such a stamp. The
`raw` digest is "computed exactly as the `p1` scheme computes it", and that is the comparison
`derive_status` makes today. So a stamp whose stored `p1` hash differs from the current files'
`raw` is not unknown. It is provably behind, and R7 hides it.

Which passes could end this way: `embed` for certain, because deploy B does not re-derive it;
and every pass on a store whose last derive predates a pass-file release (0.83.1, for one,
touches the ingest path). After a Python upgrade, the same thing happens to every stamp under
the previous tag whose `raw` no longer matches.

**Fix:**
- In `#r7-compare`: a stamp under `p1`, or under this scheme with another Python, is compared
  through `raw`. Unequal → `behind_code`, labelled with its tag. Equal → `code_unknown` until
  rehashed, as now.
- AC-21 and AC-24 change the real-edit and comment rows to `behind_code`.
- Deploy B's closing step also re-derives every pass the rehash reported `left`, from the
  rehash's own output, or the release record names each one with its reason.

### SKETCHY NS2: the `raw` witness goes stale after the first neutral edit, so M9's cost claim does not hold {#ns2}

**Where:** 29.2 `#r7` "Standing cost": "With `#r8` that costs one `rmx derive rehash` per store,
verified by `raw`, and no re-derive, provided the upgrade is deployed with no change to any pass
file in the same deploy". Also `#r8-rule`: current tag with `normal` equal → no action.

**What happens:**
1. A stamp records `raw` when it is written or rehashed.
2. Neutral edits are the point of R7: annotations, comments, and the `# noqa` justifications of
   29.3 slice c, shipping in deploy B and in every later release. Each one leaves `normal` equal
   and changes `raw`.
3. R8 never refreshes `raw` on a current-tag stamp whose `normal` matches.
4. At the next Python upgrade, every such stamp is `left` (its `raw` differs), so it reads
   `code_unknown`, and per [[#ns1]] nothing re-derives it.

The proviso about the same deploy is not enough. Any neutral edit since the stamp was written
breaks the witness, and over months that is nearly every pass.

**Fix:** R8 refreshes `raw` on a current-tag stamp whose `normal` is equal and whose `raw`
differs. It writes the hash only, keeps `version` and `derived_at`, and records a history row of
`kind: rehash`. The deploy checklist runs `rmx derive rehash` after every deploy that touches a
pass file. AC-24 gets a row: a comment added after a current-tag stamp, then rehash, then the
stamp is re-verified by `raw`, then a simulated other-Python tag still converts. Then restate
M9's cost.

### SKETCHY NS3: deploy B re-compiles memory subjects on every store, with pruning on by default {#ns3}

**Where:** 29.2 `#d27` ("The memory compile is not a step of `rmx reingest`; its two scopes are
re-compiled by their own existing command"), `#r7-release` step 3, and 29.3 `#c-pass-rows`. Six
of the 22 rows touch `consolidate.py`, so both compile scopes read `behind_code` after deploy B.

**Why it's sketchy:**
- The command is `rmx memory compile --apply`, and pruning is on unless `--no-prune` is passed
  (`cli.py`, `memory compile` options).
- The compile clusters the memory a store holds **now**. Its result on a live store is not "the
  same output again". It is a new plan over everything written since the last compile, and with
  pruning it removes subjects that plan no longer has.
- The digest's compile leg proves equality only on the fixture corpus.
- So the closing step, presented as clearing a stamp, is a content-changing and possibly
  subject-removing write to every store's memory. The go request is not required to show it.
- It also contradicts R7's own rule for compile scopes: `code_unknown` must not send a reader to
  a re-compile, because a re-compile "is a write that changes subjects".

**Fix:** choose one, stated in `#d27` and in deploy B's go request:
- (a) keep `consolidate.py`'s 6 rows out of deploy B, declared to a later owner. The compile
  scopes are verdict-excluded and print only their own line, so leaving them behind affects no
  partition verdict. This needs an explicit exception to L109's window rule.
- (b) the closing step runs `memory compile` without `--apply` per store first, puts each
  store's plan diff (added, renamed, pruned subjects) in the go request, and applies only with
  the user's go per store, `--no-prune` unless the user says otherwise.

### MEH M1: G5's "no test's outcome changed" has no data source in 29.4's runner {#m1}

29.5 G5 and `#r4-probe` fail "on any other change of outcome … and on the node id still being
xfailed after the commit". 29.4's `--compare` compares failure sets: failed and errored phases
in `failures.jsonl`. An xfailed, skipped or passed outcome is not recorded per test, and junit is
specified only for T0.7's runs. The one check NB1's remedy rests on (the probe actually passing
at the rename commit) is therefore not computable from what the runner writes.
**Fix:** 29.4 `#r2` writes per-node outcomes for every run (an `outcomes.jsonl`, or one junit
file per shard, always), and `--compare` gains an outcomes mode that 29.5's gate script calls with
the named exception.

### MEH M2: `git blame -w` does not follow a rewrap {#m2}

29.6 `#r1` says blame `-w` follows "whitespace-only rewraps". It does not follow a paragraph
reflow that moves the `cli.py:NNNN` token to a different line. Blame then names the reflow
commit, which has the same failure as the last-change sha. The named-symbol check catches only
sentences that name a symbol.
**Fix:** take the earliest commit that added the exact token (`git log -S'cli.py:NNNN' --
<spec>`, the oldest hit), and use blame as the fallback. Add an AC-3 fixture with a reflow.

### MEH M3: 29.5 and 29.2 disagree about what the rehash does to unmapped-pass stamps {#m3}

29.5 `#r9-restamp` step 4 offers "phase 2's release waits for R7's release and the affected
stamps are rehashed there". 29.2 `#r8-rule` counts "a pass name this rmx has no module set for" as
`unknown` and leaves it untouched. The branch only applies on a non-zero count (zero is
expected), but as written its remedy cannot work.
**Fix:** 29.5 step 4's first option becomes "re-derive those passes", or R8 converts an unmapped
stamp against the union's `raw`. Say which in both specs.

### MEH M4: D27's closing step names one bug it depends on, not two {#m4}

29.2 `#d27` names bug-096 (exit 0 on failed steps). It does not name bug-241: on `master`'s
registry, `rmx reingest --force` left GMD docs as plain `doc` rows, and the measured cause is that
reingest skips the GMD pass whenever a `.tldr` cache answers. With bug-241 open, the forced
re-derive can leave the `gmd` pass un-derived on the project partition while every step reports
ok.
**Fix:** name bug-241 beside bug-096 as a precondition of deploy B's closing step (fixed in
0.83.1 or earlier), and have the step check that each affected pass's stamp time moved.

### MEH M5: the rehash is an MCP write tool, which the spec reserves for the lead {#m5}

29.2 `#r8` and AC-27 add `rmx_derive_rehash` to the MCP surface for parity. The spec's rule is
"No agent rehashes … a live store", and every session offered the tool can call it with writes on.
**Fix:** the MCP adapter defaults `dry_run` to true and needs an explicit `apply`. Or record in
the spec that parity exposes it and that the lead's rule is procedural.
