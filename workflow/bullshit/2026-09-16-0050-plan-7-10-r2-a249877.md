### #b-7 — the replay that actually exercises it {#b-7-replay}

Your own check was right to doubt: `counted == 0` on the live log (every row predates byte
accounting), so "0 windows instead of 10,740" was `0` for a reason that has nothing to do with
anchoring — the r1 code returns 0 there too. Replaying the real hook timeline with measured sizes:

```
replayed hook rows: 23,662
OLD (r1)      windows=10,802   p50=0       p95=4,370   max=12,000
NEW (anchored) windows= 1,273  p50=4,370   p95=4,370   max=11,260
bytes in anchored windows from non-UserPromptSubmit commands: 153,240 of 5,024,140 (3.0%)
```

`rmx focus hook --event tool` and `--event tool-pre` each write **0 bytes** to stdout (measured,
with stdin supplied — they block without it). That is why the old p50 was literally zero: the median
"per-prompt budget" was a tool call that injects nothing. The fix is real and the residual
contamination is `curator status`, which shares the hook line with `scan-prompt` and arguably
belongs. **Closed.**

Minor: `PROMPT_ANCHORS` is a single command, so a prompt whose `scan-prompt` hook is disabled,
fails, or is renamed silently drops the whole window rather than being counted wrong. Worth one
sentence in the docstring.

Those are `ch-bsd`'s own `rel: contradicts -> [[the-rule-it-violates]]` edges — a deliberate

### BULLSHIT #b-6-r2: `--max-tokens` is inert on `--format json` — depth is still dead for `scan`, one flag over {#b-6-r2}

**File:** `eval/production/longmemeval/run.py:185-198` (`_scan_argv`, `SCAN_TOKENS_PER_DEPTH`)
**You said the translation was a guess. Measured, it is inert on the path the harness uses.**

`rmx scan-prompt`, deployed binary, live store:
```
json --max-tokens 1       -> 11,931 bytes      json --max-tokens 100,000 -> 11,931 bytes
json --max-tokens 200     -> 11,930 / 10 ids   json --max-tokens 20,000  -> 11,930 / 10 ids
big prompt, json  200     -> 23,152 bytes      big prompt, json  20,000  -> 23,152 bytes
big prompt, TEXT  200     ->  2,754 bytes      big prompt, TEXT  20,000  ->  6,059 bytes
```
A budget of **1 token** produces 11,931 bytes of JSON. `max_tokens` binds only in text mode: in
`scan.py` the pool is cut at `matches = _dedup_twin_concepts(matches)[:max_concepts]` (line 917,
default 5) *before* any budgeting, and the `if used + cost > max_tokens: break` accumulator at line
1019 is on the text render; the `fmt == "json"` branch at 964-975 emits every match unconditionally.

`_scan_argv` builds `["scan-prompt", query, "--format", "json", …, "--max-tokens", k*40]` — it
passes the token budget in the one output format where the budget is not applied. So `_meta["depth"]`
and the printed `depth=50` header are still claims the argv cannot keep, `scan`'s `recall_ceiling`
(0.642) is still the ceiling of an uncontrolled pool, and REPORT.md's re-run at `--depth 200` will
still move `context` and leave `scan` byte-identical.

The new gate does not see it: `test_every_method_carries_the_depth_it_is_labelled_with` asserts that
the argv STRING differs and that "the depth-bearing number scales with k". It never invokes
`scan-prompt`. That is an existence check on a flag the surface ignores — the same shape the test's
own docstring cites.

**Fix:** either find the knob that genuinely widens the JSON pool (`--max-concepts` did not move it
on my probe either — 5/20/50 all returned 10 ids on the same query, so this needs measuring on a
prompt whose bundle is actually budget-bound before a constant is chosen), or state plainly in
`_meta` and REPORT.md that `scan` is depth-uncontrolled and drop `depth` from its label. A
translation constant chosen to keep an old number comparable, on a flag that changes nothing, is
worse than the dropped argument: it looks measured.
**Pattern match:** YES — `{#imp-quoted-line-sibling}` / `{#imp-verbatim-fix}`.

load (0 of 7 deployed hook runs reranked).
