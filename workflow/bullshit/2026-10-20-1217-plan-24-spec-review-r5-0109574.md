## Findings {#findings}

### SKETCHY s1: `idempotency_keys` is outside the catalog's rebuild and snapshot machinery {#s1}

- **(a) Wrong DDL file.** The DuckDB backend creates its tables from
  `duckdb_catalog.CATALOG_DDL` (backend.py:609, `init_duckdb_catalog`), but 24.2's files table
  names only `store.py`.
- **(b) A rebuild drops the keys but keeps the effects.** `rebuild_index_from_log` (store.py:7911;
  daemon op at daemon.py:6404; CLI at cli.py:10120) wipes the catalog and replays `facts.log`.
  The writes' effects come back; the keys do not, because `dump_catalog_to_log` (store.py:7539)
  emits no key event. After any rebuild or repair, "key absent ⇒ safe to re-run" is false, and a
  re-submit doubles the effect. `replica_merge` also has no rule for the new table. Slot rotation
  is no risk: it was dropped (daemon.py:3002), so the writer stays pinned.
- **(c) The pre-check can read stale data.** R8's "host checks the table BEFORE running" goes
  through the read path, and the mirror and snapshot lag the writer. The check has to happen in
  the op's own transaction: an `INSERT … ON CONFLICT DO NOTHING RETURNING` that skips the effect
  on a conflict.
- **(d) Partial writes look complete.** A verb that makes two write ops records the key in the
  first op's transaction. A crash between the two answers `replayed` while the second op never
  ran.

**Fix:**
- Add the DDL to `duckdb_catalog.py`.
- Write an `idempotency` facts.log event inside the write's transaction, which `rebuild` replays
  and `dump` keeps for 7 days; or have a rebuild stamp an epoch, so keys older than it answer
  `NotConfirmed`.
- Do the check and insert inside the op.
- Settle the key in the verb's LAST write op, or record one key per op.
- Add ACs for a rebuild followed by a re-submit, and for a two-op verb killed between its ops.

### SKETCHY s2: the probe-log hashing leaks answer text (r4 m1, second occurrence) {#s2}

The replacement stops at the first escaped quote, so the answer text after the hash survives:

- `eval/mod_probe/batch2/logs/cA/probe.log:68`: `answer_sha256=30c83c8e9f45029a1. **\`rp_set\`** returned …`
- `cB/probe.log:56`: `…73ff9890305c5ca2BG-TEST" ver=1`
- `cB/probe.log:73`: `…6853a5192831a61cThe background agent finished. Its report, verbatim: …`

The README says this text was replaced. It holds no personal data, but it is model output.
This is the second time the finding has been raised, so it is escalated from MEH.

**Fix:** hash the whole field, escaped quotes included. Add a check that no line holds text
after a `*_sha256=<16 hex>` token.
