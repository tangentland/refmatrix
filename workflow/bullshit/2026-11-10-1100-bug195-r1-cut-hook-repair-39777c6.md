## Findings {#findings}

### MEH m-1: `_store_sidecar` changes the sidecar's mode 0644 -> 0600 on every save {#m-1}

**File:** src/refmatrix/memory_index.py:337 (`tempfile.mkstemp` + `os.replace`)
**What:** `mkstemp` creates the file 0600, and the rename keeps that mode. Every `save_hooks`, which runs on every save-state, now leaves `.memory_hooks.json` owner-only where `write_text` left 0644. Measured on all four copies: e0086d5 gives 0o644, ccb9398 gives 0o600. The bytes are identical, but the behaviour changed without being reported or tested.
**Fix:** before `os.replace`, `os.fchmod(fd, <existing sidecar mode, else 0o666 & ~umask>)`, plus a test that the mode is preserved across `save_hooks`.

### MEH m-2: the two safety properties the live run relies on are unpinned {#m-2}

**File:** src/refmatrix/memory_index.py:1062-1110 (`main` unknown-flag refusal) and :333-352 (temp + rename)
**What:** no test fails if `main` goes back to dropping unknown `--` args (the docstring names the hazard: a mistyped `--repair-cut-hook` used to rewrite MEMORY.md), and none fails if `_store_sidecar` becomes a direct `write_text`, so R3's atomic write has no test.
**Fix:** a subprocess test, `--repair-cut-hook <copy>` gives rc 2 with MEMORY.md and sidecar bytes unchanged, plus one for a stray positional; for atomicity, monkeypatch `os.replace` to raise and assert the old sidecar is intact and no temp file remains.
