## Findings {#findings}

### MEH m-r4-1: `SlotRepairError`'s repr drops the root cause from daemon.log {#m-r4-1}

**File:** `src/refmatrix/daemon.py:711-718` (`SlotRepairError`). Its consumers are the startup
repair log at :3055 and the merge op's `d._log` at :5783.

**What:** the message is `f"{stage}: {msg}"` and the cause is attached only through `from`. A
`repr()` does not show `__cause__`:
`SlotRepairError('clone: clone A -> B failed')`, which I checked by running it.
- **Startup repair:** it logs `rotation slot repair failed: {exc!r}`. Before r4 that line named
  the real error, for example `OSError(28, 'No space left on device')`. Now it names only the
  stage.
- **Merge op:** the `d._log` line has the same gap. The returned `error` string still carries
  `rexc.__cause__!r`.

This is a loudness regression on a store-repair path. The failure is still logged, but the
reason for it is gone from the daemon log.

**Fix:** pass the cause into the message, for example
`super().__init__(f"{stage}: {msg}: {cause!r}")` with `cause` given by the two raise sites. As an
alternative, log `{exc!r} caused by {exc.__cause__!r}` at both log sites. No test asserts the
cause in the startup log, so add one: inject a clone failure at startup and assert the errno
appears in daemon.log.

**Pattern match:** YES. This is the same family as r3's m-r3-3, where log text did not say what
actually happened.
