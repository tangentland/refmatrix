## Findings {#findings}

### SKETCHY: verify exit 128, and exit 1 with stderr, are read as "does not resolve" and skipped; a corrupt candidate is skipped silently {#s-1}

**File:** `src/refmatrix/handoff.py:151` (`if rc in (1, 128): continue`)
**What:** under `--quiet`, a name that does not exist gives `rev-parse --verify --quiet
<name>^{commit}` exit 1 with an empty stderr. I probed git 2.50.1:

| case | exit | stderr |
|---|---|---|
| missing name | 1 | empty |
| ref to a missing sha | 1 | empty |
| corrupt loose object | **128** | `error: inflate: data stream error … unable to unpack` |
| unreadable object (mode 000) | 1 | `unable to open loose object …: Permission denied` |
| broken ref file | 1 | `warning: ignoring broken ref` |
| ref to a tree | 1 | `expected commit type …` |

Under `--quiet`, exit 128 never means "not found". It means git failed.
**Why it's sketchy:** L96 ruled S1 "fixed, not ruled silent (no silent failures on a memory
path)". The walk still reads a git failure as "not found". I ran a probe against `053499d`:
origin/HEAD unset, and `origin/main` pointing at a corrupt commit object. The result was
`ahead_base='origin/master' n_ahead=2 trunk_error=''`. The correct trunk was skipped, the count
was taken against the next name, and nothing was said, which is bug-225's shape. When
origin/HEAD itself names the corrupt ref, the note says "does not resolve", which is the wrong
cause, and git's corruption message is dropped. No test needs 128 to mean "not found":
narrowing the line to `if rc == 1:` leaves all 26 tests passing
(`workflow/review-output/bsd225-r2-mut128.log`). So the 128 case was never derived from a
failing case, and neither reading is pinned.
**Evidence:** `workflow/review-output/bsd225-r2-probe.log`. The lines are
`unset, origin/main corrupt: ahead_base='origin/master' n_ahead=2 trunk_error=''` and
`origin/HEAD=main corrupt: … trunk_error='origin/HEAD names origin/main, which does not
resolve; measured against origin/master'`.
**Fix:** about 3 lines. Treat a candidate as "does not resolve" only when `rc == 1 and not err`.
Anything else stops the walk with `_ss_git_failure`, as the other exits already do. Add one
test using the existing `git_shim` with a mode that exits 128 and writes stderr for
`rev-parse`, and assert that `trunk_error` names it. This needs only a confirm-lite.
**Pattern match:** YES. [[bsd-impressions#imp-fail-closed-covers-every-call]] (bug-212) and
[[bsd-impressions#imp-loud-read-silent-skip]] (r1 S1). On its own this would be MEH: it needs a
corrupt repo, and the measured base is named. The pattern is now on its third occurrence, so it
is escalated to SKETCHY.

### MEH: no trunk at all is not stated (#open-no-trunk) {#m-1}

**File:** `src/refmatrix/handoff.py:157-163`, `_ss_trunk_lines`
**What:** this is green's `#open-no-trunk`. When origin/HEAD is unset and no list name
resolves, the result is no ahead line and no trunk line. Probe: a local-only repo on branch
`trunk` gives `ahead_base='' trunk_error=''`. That silence is not a failure, and for a repo
with no remote "no trunk" is the truth. The reader still cannot tell "no trunk exists" from
"the measurement is missing". The save-state doc has no git line that marks the absence, and
recall-state shows no anomaly. git 2.50's `fetch` creates origin/HEAD when it is missing (I
probed this: `remote add` + `fetch` → `origin/develop`), so a repo with a remote nearly always
resolves. The remaining case is mainly local-only repos, where silence is defensible.
**Fix (cheap, optional):** in the doc, add one info line, `- trunk: none (origin/HEAD unset;
no origin/main, origin/master, main or master)`, kept out of recall's anomalies. Or write a
ruling that silence is correct, and close `#open-no-trunk` with it.
**Pattern match:** NO.
