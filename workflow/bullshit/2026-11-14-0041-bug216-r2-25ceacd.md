### (d) The M2 survivor {#m2-survivor}

**The equivalence holds for the returned bitmap.** `load_bitmap("denotes", c)` yields only the
concept → doc direction. `_equivalents` adds both directions to the frontier at the level the
concept enters (`new_eq` is computed from `next_frontier` itself). So every id the raw link could
add is already in `seen` one level earlier, or at the seed level, before the raw link is read.
Noise is subtracted on both paths. The only behavioural difference would be a node entering
through the raw link rather than through `new_eq`, which gives full expansion instead of
typed-only expansion. That cannot happen for the same reason. L86's RED requirement ("neighbors
lists a concept's raw `denotes` target") is met through the equivalents either way.

## Findings {#findings}

### BULLSHIT B1-r2: for a target outside the store's project, `ingest_ignore_root` falls back to the target or to a FOREIGN store's root {#b1r2}

**File:** `src/refmatrix/ingest.py` `ingest_ignore_root`: `return find_project_root(t) or t`.
The behaviour is documented in INTEGRATION `#ignore-rules`: "… else the nearest `.refmatrix/` above
`<dir>`, else `<dir>`". That sits under a heading that says "never the ingest target".

**What:** L81 rules that the segment and spec rules "judge a path against the PROJECT ROOT the
store belongs to, never the ingest target". The remedy does this only when the target lies inside
the store's project. Outside it, two things go wrong.

1. **The r1 repro still lands memories as kind=doc** when no `.refmatrix/` sits above the memdir.
   The fallback is the target, the hidden ancestors go unchecked again, and r1's
   `probe_memdir.py` gives the same result as at df092ac:
   `ingest_path(home/.claude/projects/x/memory) -> 2; rows=[('doc','feedback_a'), ('doc','feedback_b')]`
   (scratchpad `probe_memdir_tip.log`).
   - On this workstation the real memdir is excluded only because `~/.refmatrix` (the global
     store) happens to sit above it. `find_project_root(~/.claude/projects/<slug>/memory)` returns
     `/Users/tholley` (`probe_memdir_home.log`).
   - A machine, CI box or account without a global store has no such protection.
   - The RED placed every memdir under the project (`<proj>/.claude/projects/x/memory`), which is
     not where Claude Code puts memdirs. That is why this stayed green.
2. **New regression: another store's ignore spec judges this store's ingest.**
   - Any out-of-project tree with a `.refmatrix/` higher up is judged against that store, which on
     this machine is the global store at `~`, with lines `Library`, `refmatrix`, `claude_tools`.
     A real case: the atldb second root `/Users/tholley/DataGripProjects/evolution` resolves to
     `/Users/tholley`.
   - Probe `probe_foreign_spec.py`: a store at `home/github/proj` ingesting
     `home/claude_tools/gmd` under a `home/.refmatrix` whose spec lists `claude_tools`:
     - judged against `home`;
     - **`ingest_path` → 0** at 25ceacd, **→ 1** at df092ac.
   - The drop is silent: `ingest_path` reports a count and names no exclusion.

**Why it's bullshit:** the fix reaches the shapes the RED pinned and quietly changes the rule for
every other caller (rule 10, scope by test shape). One shape is the exact repro the finding cited,
and it still fails. The other is a new silent exclusion that the multi-watch-root recipe
(`rmx ingest <tree-B>`, reference_multi_watch_root_one_store) will hit.

**Fix:**
- `ingest_ignore_root` returns the store's own project root (`Path(s.root).parent`) whenever the
  store has one. For a target outside it, `ignore_reason` then has no `rel` and no `base`-relative
  parts, so it judges the absolute path: hidden ancestors and `INGEST_IGNORE_DIRS` exclude, as at
  758bca1. No foreign spec is read.
- Fall back to the target only for a store with no root.
- Fix the INTEGRATION wording to match.
- RED, both failing at 25ceacd:
  - an out-of-project memdir with no store above stores no doc rows;
  - an out-of-project tree under a dir that a parent store's spec lists is ingested.

**Pattern match:** YES — r1's `imp-default-reaches-every-caller` and
`imp-probe-real-dirs-not-fixture`. The fixture's memdir was not where real memdirs live.

### BULLSHIT B2: the merge_slots fresh-id move still overwrites A's memory body, and leaves bitmaps and vectors on the old id {#b2}

**File:** `src/refmatrix/replica_merge.py` `_merge_into`: step 7b, step 12, and the remap report.

**What** (the lead's question (a); the bug predates bug-216, but the move ships on this branch as a
fix):

1. **memory_content (memory data loss).** Step 7b runs `UPDATE memory_content … FROM
   b.memory_content bc WHERE m.entity_id = bc.entity_id AND bc.updated_at > m.updated_at`. It does
   not exclude moved ids. When both colliding entities are memories (two slots that diverged and
   each wrote a new memory, the likeliest collision), A's body is overwritten by B's. Step 7c then
   copies B's body to the fresh id as well. Probe `probe_merge_mem.py` (`probe_merge_sameparts.log`):

   ```
   A [(2, 'mem-a', 'BODY OF A')]     B [(2, 'mem-b', 'BODY OF B')]
   merged: [(2, 'mem-a', 'BODY OF B'), (3, 'mem-b', 'BODY OF B')]
   ```

   Before the move (df092ac's `replica_merge.py`), `mem-a` was lost whole. After it, `mem-a`
   survives carrying B's text: a memory whose name and body disagree, with A's body still gone.
2. **Bitmaps.** Step 12 copies B's fragment rows only for `(partition, linkage)` pairs A lacks. A
   new linkage type in B is likely (`denotes` itself is registered on first use). Its fragment rows
   keep B's ids, and a bit for a moved entity now points at A's entity under the old id.
   `Store.repair_fragments(id_map=…)` exists for exactly this (merge_partition passes its
   collisions) and is not called with `remap_b`.
3. **Vectors.** Both slots write one shared `vectors/` Lance dir keyed by entity id. The moved
   entity has no vector at its fresh id, and the vector at the old id is whichever slot wrote last.
   The merge result folds the moves into `remap.b_loser_count`, so an operator cannot tell which
   ids need re-embedding.
4. **Residual shape, pre-existing and loud.** B's id is a name-loser (remapped to A's twin) while A
   holds a DIFFERENT entity at that id. The entity UPDATE (it excludes only `remap_fresh_b`)
   overwrites A's entity with B's loser row and raises `ConstraintException: Duplicate key …
   name: shared`. The merge fails and the target is unlinked. This fails identically at df092ac
   (`probe_merge_pre.log`), and contradicts the new comment "A loser … is never a candidate".
5. **No test** drives the `MergeRefused` headroom path.

**Why it's bullshit:** the move fixes 6 of the tables that hold B's id and leaves the one that
matters most on a memory path. A's memory body is still lost, now under A's own name. A merged
target in which a memory says another memory's text is a silent corruption
(#no-silent-failures; feedback_decay_never_loses_knowledge).

**Fix:**
- Exclude every `remap_b` loser id (moved ids included) from step 7b and from the entity UPDATE.
  This also removes shape 4's crash.
- Call `repair_fragments(id_map=remap_b)` on the merged target, or rebuild the merged
  fragments from `entity_links`.
- Report `fresh_moved: [[old, new], …]` in the result, and make the CLI print a re-embed line.
- RED, all failing at 25ceacd:
  - two colliding memories keep their own bodies;
  - shape 4 merges;
  - one more than `REMAP_HEADROOM` collisions raises `MergeRefused` and leaves no target.
- If the lead logs this as its own bug, the move must not ship labelled "fixed" without the first
  test.

**Pattern match:** YES — r1's `imp-new-table-copy-census`, now at column level: every step that
reads B's ids needs the remap, not only the steps the fixture exercised.
