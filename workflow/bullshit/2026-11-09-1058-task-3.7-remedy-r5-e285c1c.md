### BULLSHIT: bug-184 is recorded as fixed, but the pre-merge suite fails 4 AC-11 setups, and the fix retries a cold start for a fixed count {#b-1}

**File:** `tests/test_task21_1_used_events.py` (`_prompt_recall_delivering`, `attempts=3`),
`workflow/bug_registry.md` (bug-184 row, status `fixed (9b664c6 …)`)

**What:** 9b664c6 routes every AC-11/R12 setup through a helper that allows 3 attempts of the
generated recall hook. The row names the root cause as "the hook's 5 s budget expires under
suite load".

**Why it's bullshit:**
1. **The gate it was meant to clear still fails.** I ran the full suite at e285c1c with the real
   HOME (`bsd-r6-full-suite.log`): **6 failed, 3733 passed, 19 skipped** in 37 min. Two of the
   failures are bug-155 and bug-156, matched by E-line. The other four are the AC-11 tests ac11a,
   ac11b (code symbol), ac11d and ac11f. Each fails with the helper's own SETUP error, `the prompt
   recall never delivered ('feedback_alpha_rule',) in 3 attempts`, and every attempt is
   `('skipped_budget', None, 5004…5022, None)`. At 55a5e8d, before the helper, the suite had 2
   bug-184 failures. It now has 4.
2. **The cause in the row is not what happens.** I measured it on an idle machine with a probe
   test that uses the AC-11a setup and 8 sequential hook calls (`bsd-r6-probe-recall-latency.log`):
   - On the branch, call 0 was `skipped_budget` (5003 ms) and calls 1-7 were `ok` at 78-126 ms.
   - On dev master `da67220` (a `git archive`), calls 0 and 1 were `skipped_budget` and calls 2-7
     were `ok` at 233-4537 ms.
   - The sandbox `rmxd.log` shows why (probe re-run with log capture): each `SandboxDaemon` has no
     hub, so on first use it spawns a **private embed worker (warm in 7.4 s / 7.9 s)** and a
     **private rerank worker (4.7 s / 5.5 s)**.

   The first recall in every fresh sandbox therefore misses the 5 s budget **deterministically,
   with no load at all**. Load only stretches the cold window. Once it passes 3 × 5 s, three
   attempts cannot cover it.
3. A fixed retry count tuned to one machine's warm-up time is the workaround shape (rule 10). The
   error was a readiness signal, and the helper polls it a fixed number of times instead of
   waiting for the thing it signals.

**Can the helper mask a real regression?** No. Mutation H1 made `memory recall --stdin-json` print
`[]` every time. ac11a then failed with the helper's SETUP error after 3 attempts
(`bsd-r6-mut-H1.log`). The retry warns with each failed attempt's `query.log` outcome, so an
intermittent regression would show up as warnings rather than a pass. The helper is honest. It is
simply not a fix.

**Is this a task-3.7 src regression?** No. Master shows the same cold first call (2 misses, against
1 on the branch). The defect is in the test setup, and it predates 3.7.

**Fix (small):**
- Make the setup wait for readiness, not for a count. Poll until both sandbox daemons report their
  embed and rerank workers warm: the `embedder warm` / `reranker warm` lines in the sandbox
  `rmxd.log`, or the daemon status worker kinds. Alternatively, retry the delivering call until a
  deadline (for example 120 s) and record the attempts.
- Set the bug-184 row back to open, or to "fixed at <sha>" once the **full suite** is green apart
  from bug-155 and bug-156. Replace "under suite load" with the measured mechanism (cold private
  workers per fresh sandbox daemon, about 12 s idle).

**Pattern match:** YES. The "fixed" status was claimed from a narrower run than the gate (the
`tests/test_task21_1_*.py` loops and the r1-r5 set, not the full suite). This is the same shape as
"verify a fix is reachable before recording it as fixed".

### SKETCHY: the r5 cold-hub rule re-arms at base forever for a hub that accepts and never answers, so the backoff no longer caps on the daemon or the request path {#s-1}

**File:** `src/refmatrix/recall.py` (`reprobe_shared_client`:
`cold = stage == "header" and isinstance(exc, TimeoutError)`; `if cold: wait = min(base, cap)`),
`src/refmatrix/daemon.py` (`_maybe_adopt_shared` docstring: "Backs off (doubling to
`RMX_SHARED_REPROBE_MAX_S`)")

**What:** A wedged or SIGSTOPped hub, or a ModelServer whose worker hangs, still accepts on
`models.sock`. Every probe therefore connects and then times out at the header stage, so every miss
is classified as `cold`, and the backoff never grows.

**Evidence:**
- **Request path** (`bsd-r6-probe-mutehub-backoff.log` against `-e4faf32.log`): mute `_StubHub`,
  base 1, cap 8, 25 s of calls. HEAD made **22 probes and 22.0 s of request-path stall**, with
  backoff fixed at `1.0`. e4faf32 made **5 probes and 5.0 s**, with backoff 2, 4, 8, 8, 8.
- **Daemon tick** (`bsd-r6-probe-daemon-mutehub.log`, the real `Daemon._maybe_adopt_shared`,
  `PROBE_TIMEOUT_S=0.5`, base 100, cap 400): HEAD's re-arm waits were `[100, 100, 100, 100, 100,
  100]`. e4faf32's were `[100, 200, 400, 400, 400, 400]`.
- **At the defaults:** the daemon's background tick waits the full 45 s `PROBE_TIMEOUT_S` per role
  (embed and rerank) every 300 s, for as long as the hub stays wedged. Before r5 this settled at
  one probe per 1800 s. That tick also runs the flush and the grep-learn drain.
- The log line misreports it. After a 45 s wait the daemon logs "cold, loading its model". A cold
  worker answers within the 45 s cold bound (6-33 s), so a 45 s timeout means the hub is not cold.
- Mutation G7 (drop the `stage == "header"` conjunct) survives. That conjunct is unobservable,
  because the connect stage never raises `TimeoutError`.

**Why SKETCHY, not BULLSHIT:** the stall per probe is still bounded, and a wedged hub that keeps
accepting is the rarer outage. But r5 regresses a documented guarantee in order to fix a MEH, and
no test pins the mute-hub case. `test_backoff_doubles_and_is_capped` only covers
`shared_available → False`.

**Fix:** re-arm at base only once per run of misses. A second consecutive cold miss should double,
because a worker that is still cold after a full base window is not loading. Alternatively, treat
a miss as cold only when `bound < modelsrv.PROBE_TIMEOUT_S` (the request path). The daemon's 45 s
probe already is the cold bound. Pin it with a mute-hub test on both the daemon and the request
path that asserts the waits are base, 2×base, … up to cap. Correct the docstring or the log line to
match.
