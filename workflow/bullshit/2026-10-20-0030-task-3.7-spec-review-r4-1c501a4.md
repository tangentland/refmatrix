## Findings {#findings}

### SKETCHY: "entries are never dropped" is false across a daemon exit {#s-1}

**File:** spec #fam-refine-drain; daemon.py:1462-1475 (`os._exit` on writer-lost / fast-exit)
**What:** On a lock timeout, the watcher keeps entries in daemon memory for the next flush.
**Why:** A fast-exit (`os._exit(2)` on a DuckDB fatal, the frequent launchd-respawn path) or a
stop between flushes loses them silently.
**Fix:** On a lock timeout, append the entries to `curator.queue.pending` (O_APPEND, no lock).
Every locked append, status or drain first merges that file into the queue and deletes it.
A test kills the daemon while entries are pending and checks they survive.

### SKETCHY: a counter reset or the crash ordering can validate a stale token {#s-2}

**File:** spec #fam-refine-drain
**What:** The spec does not say what happens when the counter is missing or corrupt, or whether
the lock file may be deleted.
**Why:**
- A recreated lock file restarts at 0, so an old `{generation: 0}` token can match again.
- If drain bumps the generation AFTER its in-place rewrite, a crash between the two leaves the
  generation at `g` over rewritten content. A token holder can then delete unprocessed entries.
**Fix:**
- The lock file is created with `O_CREAT` and never deleted.
- A missing counter is seeded with a random epoch, and token = `{epoch, generation, size}`.
- An unparseable counter is a `VerbError`; it is never reset.
- Drain writes and fsyncs generation+1 BEFORE the rewrite.

### MEH: the unlink sites are not forbidden {#m-1}

**File:** cli.py:9136/9160/9171; gmd_curator.py:41-46
**What:** Today's sites unlink `curator.queue`.
**Why:** An unlink followed by the watcher recreating the file keeps the generation at `g`, and a
token holder would delete the new file's prefix.
**Fix:** The spec says no src path unlinks the queue, and a test checks it. Note the rollout: a
daemon running old code appends without the lock until it is restarted.
