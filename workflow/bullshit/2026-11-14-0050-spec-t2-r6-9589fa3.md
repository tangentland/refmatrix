**(q) under CliRunner (lead check):** both legs are real. `CliRunner.invoke` calls `main.main(…)`,
which runs the command inside `with ctx:`. `Context.__exit__` calls `close()` at depth 0 whether
the body returned or raised `ClickException`, `Exit` (`ctx.exit(2)`) or `SystemExit`, and close
runs the `call_on_close` callbacks. Two consequences:
- **The exit code is settable.** On a normal return click raises `Exit(0)` inside the `with`, so
  the drain can tell "already non-zero" from `sys.exc_info()` during `__exit__`, and can raise a
  non-zero `Exit` only on the 0 case. On `ClickException` it must NOT raise, or the original
  error's `show()` is lost; the spec says "unless the command is already exiting non-zero", which
  covers it.
- **Callback order is LIFO.** `call_on_close` callbacks run in reverse order (an `ExitStack`), so
  a close callback a Store registers AFTER the drain runs BEFORE it. See Y3.

## Findings {#findings}

### SKETCHY: the named OPS boundary, `Daemon._handle`, is not the thread where the op runs {#y1}

**File:** `task-26.5…:566-572`
**What:** "Each boundary opens the invocation and drains it in `try/finally`, in the thread where
the work runs. `contextvars` do not cross into `bg_pool` or new threads … the request handler that
runs every `OPS` entry (`Daemon._handle` → `OPS.get(op)`, `daemon.py:3332`), for synchronous ops".
**Why it's sketchy:** `_handle` runs on the connection thread. For every op except `ping` it hands
the handler to a pool: `fut = target_pool.submit(run, self, args)`, then `fut.result()`
(`daemon.py:3349-3377`). `bg_pool` runs every ingest and sync op. `ThreadPoolExecutor.submit` does
not copy the caller's `contextvars` context, so an invocation opened in `_handle` is invisible in
the worker where `ingest_gmd_paths` runs.

Built where the spec points, `enqueue` raises on EVERY daemon sync/ingest op that reaches a
memdir: `sync_files`, `sync_since`, `flush_queue`, `ingest_path` and `ingest_gmd`. The spec's own
sentence ("in the thread where the work runs") contradicts its own named site. (n) would catch it
at GREEN, but the spec should say where it goes.
**Fix:** open the invocation INSIDE the submitted callable. Wrap `run` before
`target_pool.submit` (`daemon.py:3376`), opening and draining in the worker. Or submit
`contextvars.copy_context().run(run, …)` with the invocation opened in `_handle` and drained after
`fut.result()`. Name one of them. Either way the drain result goes on the reply.
**Pattern match:** YES. Same class as r1 S3 / r5 X1: the boundary is named by its code site, not
by the thread that holds the work.

### SKETCHY: (p) can pass without interleaving, so the global-queue mutation survives {#y2}

**File:** `task-26.5…:814-820`, `:862-863`
**What:** "Two ops X and Y each walk their own rerouted files through A's daemon, with
`RMX_INGEST_YIELD_EVERY=1` and a gate on X's second file, so Y runs inside X's yield window." The
mutation list says "a global process-wide queue … kills (n)'s must-fail fixture and (p)".
**Why it's sketchy:** three things the spec leaves open each decide whether Y really runs inside
X:
- **The gate must sit in the yield window.** "A gate on X's second file" naturally patches
  per-file processing, which runs UNDER `d._store_lock`. Then Y just waits for the lock and runs
  after X, with nothing interleaved. To interleave, the gate must sit in X's yield window, between
  the `release()` and the `acquire()` in `_partition_keeping_yield` (`daemon.py:3575-3579`), for
  example by patching its sleep or `between` callback for X's thread.
- **Y cannot be an ingest job.** If X and Y are both `ingest_gmd` / `ingest_path` ops, Y is
  refused by `_register_ingest_job` ("ingest already active", `daemon.py:3661-3673`), so Y never
  walks. Y must be a non-job op such as `sync_files`.
- **The interleave is never asserted.** Nothing checks that it happened.

Without real interleaving, (p) still kills "drain on lock release" through its timestamp leg
(X's own first yield dispatches mid-walk). It does NOT kill "a global process-wide queue that
still requires an open invocation", and (n)'s must-fail fixture only catches an unguarded queue,
so that mutation survives both.
**Fix:**
- Place the gate in X's yield window (a registered test-side patch of the yield's sleep or
  `between` for X's thread, with the Bounds deadline).
- Make Y a `sync_files` op over its own (i)-shaped fixture.
- Assert that Y's reply arrived while X's gate was still closed.
- Then "global queue" fails, because Y's drain takes X's groups.
**Pattern match:** YES ([[feedback_clean_corpus_hides_a_dead_gate]]: a test that never builds the
state its mutation needs).

### MEH: the CLI Store-reuse rule does not fit 26.2's close-in-finally, and the open counter measures the wrong thing {#y3}

**File:** `task-26.5…:592-599`, `:864-865`
**What:** "The drain's same-store leg uses THAT Store … The invocation context closes the
registered Store after the drain (the drain's callback runs first)". The test guard "counts
Store opens per root".
**Why:**
- **The Store is already closed.** On the `ingest-gmd` no-daemon route, `_ingest_gmd_sync` already
  CLOSES its Store in `finally` (`cli.py:10729`, the 26.2 fix that releases DuckDB's lock in
  long-lived processes). At drain time the registered Store is closed. A sequential reopen is
  legitimate.
- **The guard pushes the wrong fix.** A guard that counts opens (rather than concurrent opens)
  flags that reopen, which pushes the build to undo 26.2's release.
- **Callback order is backwards.** Click runs `call_on_close` callbacks LIFO, so "the drain's
  callback runs first" holds only if the Store's close is done INSIDE the drain callback, not
  registered as its own callback after it.
**Fix:**
- The invariant is "never two Stores OPEN on one root at once": reuse the Store if it is open,
  reopen once if it is closed, and close it in the drain callback.
- The guard counts concurrent opens.

### MEH: the ingest_path fallback can swallow the "no invocation" raise, and `enqueue` may only raise when there are groups {#y4}

**File:** `task-26.5…:558-566`, `:611-617`
**What:** "`enqueue` with no open invocation RAISES loudly … an unwrapped new route fails at
runtime." Two holes in that:
- **The fallback swallows it.** On the `ingest_path` route, `ingest_gmd_paths` sits inside
  `_ingest_path_inner`'s `except Exception:` fallback (`ingest.py:1356`), which catches that raise
  and degrades every GMD file in the batch to plain doc registration. The raise is not loud there.
- **It may only fire when there are groups.** If `enqueue` is called only when there are groups,
  an unwrapped route fails only once a memdir appears.
**Fix:**
- The fallback re-raises the no-invocation error class.
- `ingest_gmd_paths(as_memory=False)` asserts an open invocation unconditionally, OR the spec
  states that the check is group-triggered and (n)'s scan is the static guard.

### MEH: nested invocations are undefined {#y5}

**File:** `task-26.5…:568-588`
**What:** standalone `rmx watch` opens an invocation per flush INSIDE the root group's invocation.
The `ingest_path_start` "runner" IS `_run_detached_job`, and both are listed as boundaries. The
spec never says whether `invocation()` nests (the inner drains its own groups) or joins the outer
one.
**Fix:** one sentence: nested `invocation()` scopes are independent, and each drains its own
groups at its own exit.
