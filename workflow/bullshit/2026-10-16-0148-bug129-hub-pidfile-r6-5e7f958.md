## Caller sweep of the new fail-fast {#caller-sweep}

The new check is `rc != 0 and not ping(root)`, and it runs as soon as the launcher exits. These
are the `spawn_daemon_subprocess` callers and the ways `rmx daemon start` exits:

- **Callers:** `ensure_global_daemon` (hub.py:145), `Watchdog._restart` (hub.py:389), the bus
  accept (bus.py:538), the UI (ui/server.py:267), and about 12 real-daemon test fixtures. Every
  caller catches the RuntimeError or lets it surface; none of them retries inline.
- **Already running:** the outer `ping` returns before the launcher runs. If the daemon comes up
  between that ping and the launcher's own, `spawn_daemon`'s ping returns its pid with rc 0.
  Benign.
- **Racing a concurrent start:** the loser blocks on `daemon.lock` while the winner waits for
  readiness, then sees `ping` and exits 0. Benign. If the winner's own window expires, the loser
  forks a second daemon. That race is pre-existing and was the same at base.
- **launchd-supervised:** `lc.kickstart` returns and the launcher exits 0 straight away, so the
  outer poll covers the boot. A kickstart that raises falls back to the fork. Benign.
- **Slow boot: regressed.** See s1-r6.

## Findings {#findings}

### SKETCHY s1-r6: fail-fast also fires when the launcher's own 15 s window expired and the daemon is still booting {#s1-r6-slow-boot-false-failure}

**File:** `src/refmatrix/daemon.py:6795`. This is the `proc.returncode != 0 and not ping(root)`
check in `spawn_daemon_subprocess`.
**What:** The launcher's `spawn_daemon` waits `RMX_DAEMON_SPAWN_WAIT`, which defaults to 15 s,
and then raises "daemon did not start within …", so it exits 1. The grandchild it forked keeps
booting. Until this commit, the caller then polled the full 30 s `wait_for_ready` window, which
gave up to 45 s in total. The comment directly below the new check still says this is why that
poll exists: "under load the inner `daemon start` can exit before its child has bound the socket,
so a short poll would spuriously fail". Now any daemon whose boot takes 15–45 s is reported as a
failure, even though it comes up a moment later.
**Evidence:** `bsd-bug129-r6-probe-slowboot.log` uses a real store and a real launcher, with the
launcher's window shortened to 0.01 s to stand in for a boot longer than the window:
- **Head:** `RuntimeError: … exited 1 … daemon did not start within 0.0s` after 0.29 s. The same
  daemon answered ping 0.11 s later.
- **93d5a0b:** `ok pid=…` after 0.39 s.

With the default window, both versions start a fresh store in about 0.5 s.

**Effects (by reading the callers):**
- The UI reports `ok:false` for a daemon that is about to come up. A second click then starts a
  second launcher, which finds `daemon.lock` free and the socket not yet bound, and forks a
  second daemon onto the same store.
- `Bus._write_memory` raises, so the accept is lost.
- `ensure_global_daemon` returns False during exactly the cold window when the hub starts.
- The watchdog logs "spawn failed". Its no-process gate limits how often it repeats.
- Real-daemon test fixtures become flaky under suite load once a boot takes more than 15 s.

**Fix:** Make the launcher's window equal to the caller's. Pass
`RMX_DAEMON_SPAWN_WAIT=str(wait_for_ready)` in `env`. A non-zero exit then means the launcher
really failed, or the daemon missed the whole window, and failing fast is correct in both cases.
Also:
- update the comment that the new check now contradicts;
- add a test that a launcher which times out while its child is still booting does not make
  `spawn_daemon_subprocess` raise. For example, put a tiny `RMX_DAEMON_SPAWN_WAIT` in the
  environment and assert that the caller's window wins.

**Pattern match:** YES. The prescription in r5 (mine) was narrower than the defect it named.
This is the shape of the "prescriptions narrower than the defect" impression from the 0916
post-deploy audit.
