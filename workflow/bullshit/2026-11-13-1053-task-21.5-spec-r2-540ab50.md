## BULLSHIT {#bullshit}

### b-1: the Bash cwd fallback in R3 / D11 re-opens the clone leg that D12 rules out {#b-1}

**Spec:** [[task-21.5-tool-used-signal#d12]], [[task-21.5-tool-used-signal#d11]], [[task-21.5-tool-used-signal#r3]], [[task-21.5-tool-used-signal#why-data]].

**What:** D12 says a clone's copy of a file is a different path, so there is no clone or repo-relative leg. But R3's `bash_path` resolves a relative ref against the envelope `cwd`, or else against `logical_root`'s parent (`cwd_fallback`). Nothing in R1 or R3 parses an in-command `cd X &&`, `pushd X` or `git -C X`. So `cd /Volumes/littlebig/<clone> && sed -n 1,40p src/refmatrix/telemetry.py` is credited to the PROJECT's `telemetry.py`.

**Evidence (legacy window):**
- 3,114 of 3,925 Bash + git ring events (79%) name a `/Volumes/littlebig` path in their command.
- All 35 `bash_path` credits resolve through `cwd_fallback`.
- 23 of those 35 come from commands that name a littlebig path. Across all legs, 38 of 64 credits do, and 32 of those 38 `cd` into a clone.
- 5 of the 18 headline units are clone `bash_path` credits.
- So the `#why-data` claim that "the Bash legs are the whole signal" rests largely on the clone activity D12 excluded for Read. A clone Read is not matched; a Bash read of the same clone file is.

**Post-task:** the envelope `cwd` is the session's working directory, not the directory a compound `cd X && …` ran in, and subagent cwds reset on every call. The defect does not go away once the legacy lines age out.

**Fix:** the Bash leg takes its base directory from a leading `cd <dir>`, `pushd <dir>` or `git -C <dir>` in the command. A base outside the project counts `refs_outside_project` and does not match. AC-7 gains a negative case: `cd <other-dir> && sed -n 1,40p src/x.py` with `cwd` = the project dir is not credited, and is counted. Re-run `#why-data` under the fix.

**Pattern match:** YES — [[bsd-task-21.5-spec-r1-15e8f64#imp-prototype-the-join]] (a join premise that is false on the data it joins).

## SKETCHY {#sketchy}

### s-1: `kind=git` ring lines get no R1 fields and match on a diffstat {#s-1}

**Spec:** [[task-21.5-tool-used-signal#r1]], [[task-21.5-tool-used-signal#r10]].
The window has 474 git lines, and 11 of the 64 credits come from them. The git branch of `focus_hook` writes `s.record("git", terse, refs=diff_refs, detail=...)` (`cli.py:2161-2180`). Its `refs` are a diffstat of `d.get("cwd") or project`, not the command's paths, so a commit made in a clone records the project repo's diffstat. R1 adds fields only to `tool` events, and R10 reads `git` as Bash only on legacy lines. Post-task git lines would therefore carry no `t_start`, `tool`, `command` or `origin`.
**Fix:** route the git branch through `stm.tool_event_fields`, and match git lines on `command` only, never on the diffstat refs.

### s-2: legacy global events are resolved against the project snapshot {#s-2}

**Spec:** [[task-21.5-tool-used-signal#r10]].
R10 resolves a pre-task event's `entity_id` from "the read snapshot", but a `scope=global` event's id belongs to the GLOBAL catalog. Today none of the 6 global deliveries for this root is found (`path_unresolved`), so the global memory-Read leg produces nothing on the legacy window. If an integer id collided, the event would get a confident wrong path, counted silently as `path_from_catalog`.
**Fix:** resolve `scope=global` events against the global store's snapshot through the normal read path, or make them `path_unresolved` by rule. Add to AC-9 a global legacy event whose id collides with a project entity.

### s-3: R12 does not say whether prior-touch credits are in the precision sample {#s-3}

**Spec:** [[task-21.5-tool-used-signal#r12]], [[task-21.5-tool-used-signal#d8]].
