## Findings {#findings}

### SKETCHY: verifying origin/HEAD's name still goes through the swallowing `_ss_sh`, so a failure there falls back to the list with no message {#s-1}

**File:** `src/refmatrix/handoff.py:131-140` (the candidates loop), `handoff.py:71-77` (`_ss_sh`)
**What:** `_ss_origin_head` separates exit 0, exit 1 and other failures, and puts the error in
`trunk_error`. But the name it returns is then checked with
`g("rev-parse", "--verify", "--quiet", base)`, and so is every other candidate. `g` is `_ss_sh`,
which returns `""` on any exception (timeout, OSError) and ignores the exit code and stderr.
**Why it's sketchy:** The lead's statement of L82 is that "dangling origin/HEAD falls back;
other git failures are not swallowed". A verify that times out or cannot run is one of those
other failures. It looks the same as "does not resolve": the list decides, `trunk_error` stays
`""`, and the handoff says "N ahead of `origin/master`". That is bug-225's symptom (a correct-
looking line measured against the wrong trunk), with no message. The dangling case (pinned
silent by AC-6b, `tests/test_bug225_handoff_trunk.py:243-251`) behaves the same way. The
ruling allows it to fall back, but the reader is never told that the repo's declared trunk was
skipped. For atlftpd, whose trunk is reached through a local `set-head origin develop`, a
renamed and pruned `develop` would silently bring back the original "24 ahead of
origin/master". A probe in a throwaway copy also shows that `rev-parse --verify` does not check
that the object exists: a ref holding a missing sha verifies, and the ahead `git log` failure
is then swallowed as "0 ahead — in sync". That part is pre-existing for every candidate, but
origin/HEAD's ref now reaches it as well.
**Evidence:** `handoff.py:139` `if g("rev-parse", "--verify", "--quiet", base):`. `_ss_sh`
docstring: "'' on any failure (never raises)". Probe log
`workflow/review-output/bsd225-r1-probe-verify.log` (run against a throwaway copy):
`verify: 0 '1111…'`, `broken: {'ahead_base': 'origin/develop', 'trunk_error': ''}`.
**Fix:** (a) When `origin_head` is non-empty and its verify comes back empty, set a note:
"origin/HEAD names `<x>`, which does not resolve; measured against `<y>`". This can reuse the
`trunk_error` line or be a sibling `trunk_note` that both composers print. (b) Run origin/HEAD's
verify through a call that tells exit 1 apart from an exception or another exit, the same way
`_ss_origin_head` does, and verify `<x>^{commit}`. About 15 lines plus two tests (dangling
gives the note; an unresolvable object id gives an error). If the lead rules the dangling case
silent on purpose, write that into L82 and keep (b).
**Pattern match:** YES. [[bsd-impressions#imp-fail-closed-covers-every-call]] (bug-212 r2/r3:
only the git call that answers was made loud, and its sibling calls in the same guard still
fail open). Second time, so MEH is escalated to SKETCHY.

## Answers to the lead's questions {#answers}

1. **Reach:** see [[#wiring]]. Every production caller gets the origin/HEAD trunk. trunk_error
   reaches the doc and the recall anomaly, but not save-state's console ([[#m-1]]).
2. **Timeout:** `_ss_origin_head` uses `timeout=20`, the same as `_ss_sh`. `TimeoutExpired` is a
   `SubprocessError`, so it becomes `trunk_error`. A hung git costs at most 20 s per call, the
   same bound every other handoff git call already has. The premise that bug-212's L82 adds
   `timeout=10` on every git call is wrong: L82 puts `timeout=10` only on
   `sync.changed_since`'s `git diff`. No collision. `git merge-tree --write-tree` of this branch
   with bug-212's tip `a1bde19` is clean (`63d583f`), and so is the merge with master `f7c0d39`
   (`84d322b`). bug-212 touches `handoff.py` only in `_promote_digest`.
3. **Silent failures:** exit 1 is silent by design. OSError, SubprocessError and other exits on
   the symbolic-ref read are surfaced. The rev-parse verify and the ahead `log` are still
   swallowed ([[#s-1]]).
4. **Template:** no generated artifact, golden or CLI tree depends on the template text. The
   tests read it from the package (`test_install_commands_user_level.py`). No check compares the
   installed copy with the template, so the drift is silent ([[#m-2]]).
5. **Tests:** `be9acae` touches only the test file. `bug225-red.log` shows 4 failed / 2 passed,
   and the first E line is `assert 'origin/master' == 'origin/develop'`, which is a real assertion
   failure, not an import error. The mutation logs show kills: mut1 4F, mut2 1F, trunk_error
   mut1/2/3 5F/1F/1F. My own mutation A (drop `--quiet`) in a throwaway rsync copy (imports
   confirmed from the copy's `src`, restored in its own command, `__pycache__` cleared;
   `workflow/review-output/bsd225-r1-mutA.log`): 4 failed, killed by `test_origin_head_unset_or_readable_has_no_trunk_error` with "is not a
   symbolic ref". Mutation B (gate → `if True`) survived ([[#m-3]]).
6. **Full suite:** 7F / 4305P / 1S. By E line: brief-daemon (DuckDB lock conflict) and the two
   AC-6 tests are identical to 0.82.0. GMD-lint is bug-155, not the 0.82.0 content ([[#m-4]]).
   sandbox_redirect ×2 carry the conftest `UsageError` "would exercise refmatrix from
   /Users/…/src". catalog_measure gives `KeyError: 'rewrite_bytes_all'` after "measured 0/1
   stores; failed=1". My rerun with an absolute `PYTHONPATH`: catalog_measure + sandbox_redirect
   + bug-225 + install_commands = **65 passed**
   (`workflow/review-output/bsd225-r1-rerun.log`). That confirms the 3 were caused by the
   relative `PYTHONPATH`.
