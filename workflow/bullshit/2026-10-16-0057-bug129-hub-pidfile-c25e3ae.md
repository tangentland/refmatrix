## Findings {#findings}

### BULLSHIT b1: the stated mechanism did not happen; the measured actor is the test suite, and it is still unaddressed {#b1-wrong-mechanism}

**File:** `src/refmatrix/hub.py` (`_release_pid_file` docstring), `tests/test_bug129_hub_pidfile.py`
(module docstring + `_stop_with_successor`), commit body.
**What:** The commit says `rmx hub stop` was still polling when launchd's successor (4191) wrote
its pid, and then unlinked the successor's file. The regression test models exactly that
interleaving.
**Why it's bullshit:** The telemetry rules it out.
- `<dev>/.refmatrix/cli.log`: `{"ts": "2026-10-15T01:58:38", "argv": ["hub", "stop"], ...
  "latency_ms": 401, "pid": 4141}`. `ts` is the END time. The global log row for the old hub
  (84577) shows `ts 01:58:42`, `latency_ms 2716338`, and it started at 01:13:25, so ts is written
  at exit. `stop_hub` therefore exited at 01:58:38, four seconds before 4191 existed (`ps`:
  4191 started 01:58:42, ppid 1). It returned in 0.4 s because `serve_sock` closes and unlinks
  `hub.sock` as soon as `_stop` is set (hub.py:852-864). `is_running()` went False at once, and
  the unlink hit the OLD hub's own file. The new code would make the same correct unlink.
- `Hub.shutdown` of 84577 also cannot be the cause. Its unlink runs before `run()` returns, and
  `run()` returned before the exit-0 telemetry row at :42. KeepAlive is `SuccessfulExit:false`,
  so launchd starts the next instance only after this exit (via the follow-up kickstart).
- No second `hub starting` line appears in hub.log after 4191, so no second hub ran the
  preflight-failure path (see s1).

What actually deletes the live file, reproduced: `tests/test_hub.py::test_stop_hub_clean_when_nothing_running`
(and `test_stop_hub_reaps_port_orphan`) call the real `stop_hub()` with `is_running` patched False.
They do not use `short_home`, and nothing in `conftest.py` sets `RMX_HOME`, so `hub_pid_path()` is the LIVE
`~/.refmatrix/hub.pid`. At `release-0.79.0` the unconditional unlink deletes it:
`RMX_HOME=<tmp with hub.pid=4191>` → run that one test → the dir is empty afterwards. The suite
does run against the live home: on 2026-10-15, 12 pytest sessions wrote rows into the live
`~/.refmatrix/cli.log`, and test daemons `/tmp/rmxp4-*` show up in the live hub's watchdog log.
One of them, `pytest-2607`, ran after 4191 started. Its last test_grep_stdin_dialect row is at
03:21:17. test_hub.py runs eight files later alphabetically, and `~/.refmatrix`'s directory mtime
(the time an entry was last created or removed) is **03:21:28**. That fits, but it does not prove
it on its own, because a DuckDB WAL create/delete also moves the dir mtime.
**Why the fix only covers it by luck:** At c25e3ae those two tests also patch `hub_pid` to None, so
`_release_pid_file(None)` is a no-op. Remove that one patch and the new code reads the live 4191,
sees `is_running()` False, finds the owner check true, and deletes the live file again. The owner
check is right for real stops. It does not protect against a test that calls the real stopper
against the real home.
**Fix:** (1) Put both `test_hub.py` stop_hub tests on `short_home`. Better, add a conftest autouse
fixture that points `RMX_HOME` at a short mkdtemp, so no test resolves `~/.refmatrix` (task 23.0
territory). Name it in the registry. (2) Rewrite the `_release_pid_file` docstring, the test
docstring and the commit narrative to say what was measured (the 401 ms stop, the suite reaching
the live home, the dir mtime). Keep the successor-race test as a defence-in-depth case, labelled
hypothetical. (3) bug-129's registry row should record the suite as the cause. Effort: about
15 lines.
**Pattern match:** YES. This is "name the mechanism only after measuring it", and it is the
suite-reaches-live-sockets family (the 2026-10-07 wedges).

### SKETCHY s1: a second hub still overwrites and then removes the live hub's pid file (preflight-failure path) {#s1-second-hub-claim}

**File:** `src/refmatrix/hub.py:932` (`run` → `_claim_pid_file`) and `:982-987` (`_serve_http`
preflight → `self.shutdown()`).
**What:** `run()` claims hub.pid before anything checks that another hub owns the port. The
order is: a second `Hub.run()` replaces the live hub's pid with its own; `_start_models` and
`serve_sock` run (serve_sock unlinks and rebinds the live `hub.sock`); preflight finds the port
held; `shutdown()` calls `_release_pid_file(own pid)`. The file names the second hub, so the
owner check passes and the file is unlinked. The live hub is left with no pid file, the same
symptom. This is reachable through launchd `hub start --no-detach` while an unsupervised hub
holds :7777, and through `rmx ui` → `spawn_hub` in the gap where `is_running()` is False.
`cli hub start` (detached) checks the port first; these two paths do not. This was not the live
incident (no second "hub starting" line), but the commit's rule ("a stopper removes it only
while it names the pid it stopped") is defeated by a claimer that never had a right to the file.
**Fix:** Claim only after the port preflight passes and the control socket binds. Or refuse to
claim while `hub_pid()` names a live process that answers ping. Add a test: a live owner pid in
the file, a second `Hub.run` that fails preflight, then assert the file still names the owner.

### SKETCHY s2: the AST guard catches only the literal `hub_pid_path().<method>()` shape in hub.py {#s2-ast-guard-evadable}

**File:** `tests/test_bug129_hub_pidfile.py::test_only_the_helpers_write_or_remove_the_pid_file`.
**Evidence:** I appended each probe as a new function to a scratch copy of hub.py and ran the file.
- `p = hub_pid_path(); p.unlink(missing_ok=True)`: 5 passed (evaded)
- `os.unlink(hub_pid_path())`: 5 passed (evaded)
- `(hub_home() / HUB_PID).unlink()`: 5 passed (evaded)
- control `hub_pid_path().unlink()`: guard FAILED (caught)

Mutation C, where `run()` writes `(hub_home() / HUB_PID).write_text(...)` instead of claiming,
survives all 5 tests. The guard also scans only `hub.py` and only code inside functions. A
stopper in `cli.py`/`launchctl.py`, or code at module level, is not checked.
**Fix:** Have the guard resolve uses of `hub_pid_path`/`HUB_PID` instead of the receiver text.
Flag any function outside the two helpers that references `hub_pid_path` or `HUB_PID` other than
through `hub_pid()`. Scan every module under `src/refmatrix/`. The other mutations I ran were all
caught by the tests: owner check dropped, `stop_hub` releasing `hub_pid()`, shutdown alias
unlink, `os.unlink` in shutdown.

### MEH m1: a declined release says nothing {#m1-silent-decline}

**File:** `src/refmatrix/hub.py` `_release_pid_file`, `stop_hub`.
**What:** `_release_pid_file` returns a bool that no caller reads. `hub_pid()` maps an unreadable
or corrupt pid file to None, so a garbage file is left in place forever with no log line, and a
`stop_hub` that declines because the file names another pid prints nothing. This is not a
memory path, so it rates MEH. A one-line `_log` on decline ("hub.pid names X, not the stopped Y;
left") would have made this bug visible at the moment it occurred. Not a silent failure:
`PermissionError` now propagates instead of being swallowed as `OSError` was, which is louder
than before.

## What holds {#what-holds}

- The owner check is correct and needed. `stop_hub` reads `pid` after sending `stop`, and
  `Hub.shutdown` releases `os.getpid()`. The 5 new tests plus the existing hub tests pass (26/26).
- Mutations killed: owner check dropped (2 fail), `stop_hub` releasing `hub_pid()` (1 fail), the
  shutdown unlink rewritten through an alias or `os.unlink` (1 fail each, by the behaviour test,
  not the guard).
- `_claim_pid_file` uses tmp + `os.replace` in the same dir. A leftover `hub.pid.<pid>.tmp` is
  possible only on a crash between the two calls, which is negligible.
- launchctl.py `_stop_hub_before_bootout` never touches the pid file. The cli `hub start` /
  `hub stop` / `ui` paths go through `spawn_hub` / `stop_hub` / `Hub.run`; the exposure is in s1.
