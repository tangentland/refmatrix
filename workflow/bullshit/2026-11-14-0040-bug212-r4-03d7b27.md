## Findings {#findings}

### BULLSHIT: `rmx compact` and `rmx migrate-to-duckdb --overwrite` still write a git-tracked catalog in-process; the census only looks for `Store(` {#b-1}

**File:**
- src/refmatrix/cli.py:8000-8100 (`compact`: `open_duckdb(src)`, then `src.rename(backup)`, `new_path.rename(src)`, `legacy.unlink()`);
- src/refmatrix/cli.py:4045-4085 (`migrate_to_duckdb` → `migrate.migrate_catalog`, which unlinks and rewrites `catalog.duckdb` through `open_duckdb`);
- tests/test_bug212_r4_red.py:252-300 (`_read_write_store_constructions` matches only calls to `Store`);
- docs/INTEGRATION.md#sync-tracked-catalog (heading "No command opens a tracked catalog read-write in-process"; "Every such open goes through one of two checked openers").

**What:** r4 routes every read-write `Store(` through `cli._store_rw()` or `verbs.local_write`, and both call `store.refuse_tracked_catalog_open`. That part is right and verified ([[#verified]]). The census and the doc then claim every in-process catalog write is covered.

**Why it's bullshit:** two CLI commands open the writer catalog with `open_duckdb` (the backend's raw DuckDB opener) and replace the file without constructing a `Store`, so the census cannot see them.
- `rmx compact` also STOPS a running daemon first. That defeats the daemon route the docs offer as the remedy.

**Evidence:** `logs/probe-r4.log`, `tracked_repo`, no daemon, on clean 03d7b27:

| command | slots layout | legacy layout |
|---|---|---|
| `rmx compact --no-keep-backup` | exit 0, no refusal; ` M .refmatrix/catalog.A.duckdb` and ` D .refmatrix/catalog.duckdb` (the tracked legacy catalog is deleted) | exit 0; ` M .refmatrix/catalog.duckdb` |

- `migrate-to-duckdb --overwrite` was not run: it needs a SQLite `catalog.db`. By reading the code, `migrate_catalog` unlinks the destination `catalog.duckdb` and rebuilds it through `open_duckdb(duckdb_path)` with no check.
- The non-`Store` census, outside the daemon: `open_duckdb` writers exist in `compact` (×2) and `migrate_catalog`. `replica_merge.merge_slots` is called only from `daemon.py:5869`. `Store.rebuild_index_from_log` is reached through `_store()` (checked) or the daemon op.

**The miss traces to my r2 prescription:** b-1 fix #3 asked for "an AST scan for read-write `Store(` constructions". That is narrower than the defect, which is any in-process open of a writer catalog. The census does exactly what was prescribed. The doc's "No command …" sentence is what is false.

**Fix** (small: about 15 lines of src plus 2 RED tests and a census extension):
1. `compact`: call `store.refuse_tracked_catalog_open(root, src)`, turning `TrackedCatalogRefused` into a `ClickException`, BEFORE it pings or stops the daemon.
2. `migrate_to_duckdb`: call the same check on `dst` before `migrate_catalog`.
3. RED on `tracked_repo`: `rmx compact` gives one refusal line, unchanged bytes, and a running daemon is not stopped.
4. Extend the census to `open_duckdb(` / `duckdb.connect(` calls whose first argument is not the literal `":memory:"` and which pass no `read_only=True`. Allowlist: `backend.open_duckdb` / `_open_write` / `DuckDBBackend.connect` (the opener internals behind `Store`), `replica_merge.merge_slots` (daemon-only), and `migrate.migrate_catalog` once its caller checks. A census-sees guard must name `cli:compact` until it is fixed, so a quiet scanner cannot pass.

**Pattern match:** YES. This is the fourth "census claim without a census" (26.2 r2, bug-212 r1 s-1, bug-212 r2 b-1, now this). I wrote that pattern down at r2 and then prescribed a census keyed on one constructor. Lesson: census the RESOURCE (the catalog file), not the constructor of one class that opens it.

### SKETCHY: in the same `rmx save-state` run, a refused memory bridge is stdout-only with exit 0, the sibling of the promote that L82 made loud {#s-1}

**File:** src/refmatrix/cli.py (`save_state`: the `memory bridge FAILED:` print; the promote raise at the end)

**What:** L82 turned a failed promote into `promote FAILED` plus one `Error:` line on stderr and exit 1, and that holds ([[#verified]]). The bridge step of the same command (`ingest-gmd --as-memory` of the memory dir, through `_store_rw()`) is refused on the same tracked catalog. It prints `memory bridge FAILED: ClickException: refusing to open … — run rmx ingest-gmd --as-memory <dir> by hand` on STDOUT, and the command's exit status does not change.

**Evidence:**
- `logs/probe-ss-nopromote.log`: `rmx save-state --no-promote` on `tracked_repo` gives **exit 0**. stdout carries `memory bridge FAILED … refusing to open …catalog.A.duckdb read-write in-process …`, and stderr only the MEMORY.md line.
- With promote on (`logs/probe-r4.log`), the run exits 1, but only because of the promote.
- The handoff names its own bridge step as the path by which the new `savestate_*` memory reaches the store. That path failed, and the exit code says nothing.

**Why it matters:** the CLAUDE.md rule "no silent failures on memory paths" and feedback_errors_fail_loudly_on_the_console ("CLI exit+stderr") cover this. It is printed, so it is not silent, but it sits on stdout with exit 0, which is the shape L82 just ruled out for the promote. feedback_check_the_sibling_condition: one condition of the same gate was fixed and its sibling was left.

**Fix:** collect a bridge failure the way `promote_error` is collected, and raise once at the end. The line should name the handoff target and each failed step. Pin it with a `--no-promote` test on `tracked_repo`: exit non-zero, refusal on stderr, handoff written.

Cosmetic, same function: the promote line embeds the exception class, `promote failed: VerbError: refusing to open …`, because `handoff._promote_digest` formats `f"{type(e).__name__}: {e}"`.
