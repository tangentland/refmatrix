## New findings {#findings}

### M1 (31.1 `#r6-removed-inbound`): the converted pending row's fields are not all named {#m1}

**What:** the spec writes the row "with the row's file, line and link as written". It does not
name `target_name`, `weight` or `detail`.

**Why it matters:** `pending_refs_for(names)` matches `target_name` against the canonical names
a batch registers, and `resolve_pending_refs` only retries those rows. If an implementation
stores the link as written as `target_name`, the put-back never re-binds. Once 31.6 lets a link
written `[[CLAUDE#a]]` bind `claude#a`, the written form and the canonical name differ.

**What worked in the probe:**

- `target_name` = the removed anchor's entity name.
- `ref` = the evidence `detail` after `-> `, with ` (root-mirror)` stripped.
- `weight` = the edge's weight, read before the purge.
- `detail` = the evidence row's, so the root-mirror marker survives.
- One pending row per evidence row: 2 per line.

**Fold:** name those fields in `#r6-removed-inbound`, and add a mutation: store the written form
as `target_name`, so the put-back step stays unbound. {#m1-body}

### M2 (31.1 `#r6-removed-rows`): a removed `doc` row's citers get no pending rows {#m2}

**What:** the changed-`id:` variant removes the old `doc` row. `#r6-removed-inbound` converts
the inbound `rel:` edges of a removed **anchor** only. The old doc row's inbound edges, from
citers of the old id, are dropped by `purge_entity` without pending rows.

**Why it matters:** those lines go unresolved silently until each citer is edited, and putting
the old id back does not re-bind them. That is bug-264's symptom in small, which is the reason
L148 kept the conversion.

**Fold:** apply the same conversion to a removed `doc` row, and add to AC-11's second variant a
citer of the old id that gets a pending row. {#m2-body}

### M3 (31.6 `#r10-marker`): name the writer of the `reingest-force` row {#m3}

**What:** the obvious writer, `stamp_derive("reingest-force")`, would do two things the spec
does not want:

- It upserts a `derive_stamps` row for a pass that `derive_pass_modules` does not map.
- It hashes the **union** of modules (an unmapped pass reads as maximally stale), and it fills
  `counts` from `derive_counts()`, the partition's shape, not "re-processed / skipped".

**Fold:** state that the marker is one `derive_history` insert with
`code_hash = derive_code_hash("gmd")` and the stated `counts`, and no `derive_stamps` row. Or
map `reingest-force` in `_DERIVE_PASS_MODULES` and say how `rmx derive` status shows it.
Mutation 19a's partner: the marker carries the union hash, so AC-12's "applies after
`reingest --force`" leg refuses. {#m3-body}

### M4 (31.2 AC-14 GMD leg): the RED E line at base is not quite what happens {#m4}

**What:** at base, `rmx sync -i a` with no `-f` / `--since` / `--flush-queue` runs
`purge_path` and stops (`cli.py:9014`, then the report branch); nothing re-derives `a` in that
command.

**So** the E line at base is `adoc#sec` **absent** (a new id only after a later sync) and
`b`'s edges 0, not "the anchor has a new id". On the daemon route at base `-i` reaches the
replica (bug-203), which is the other half of the E line.

**Fold:** correct the E line so that the RED author does not record a mismatch as a pass.
{#m4-body}

## Impressions {#impressions}

- A purge that is moved has to take its pending-row bookkeeping with it, and the pending row's
  key must be the name the resolver will look up later, not the text the author wrote. {#imp-pending-key-is-the-lookup-name}
- A marker that "only X writes" must name its writer's API. The convenient one may add a stamp,
  a hash or counts that turn the marker into something else. {#imp-marker-names-its-writer}
