## Findings {#findings}

### BULLSHIT b1-r3: a daemon the hub bare-forks inherits hub.lock, so no hub can start while it lives {#b1-r3-forked-daemon-holds-lock}

**File:** `src/refmatrix/hub.py:940` and `:1041` (`_take_hub_lock`, held for the process
lifetime). The forking sites are `src/refmatrix/ui/server.py:263` (`POST /api/daemon`, any action
other than stop) and `src/refmatrix/bus.py:536` (`_write_memory`, reached from the hub op at
`hub.py:555` and from `ui/server.py:502` `accept_refinement`). Both call `daemon.spawn_daemon`, a
double `os.fork` with no exec, inside the hub process.

**What:** `O_CLOEXEC` only takes effect at exec, so a bare fork copies every hub fd. The
daemonized grandchild closes only its own `daemon.lock` (`daemon.py:6699`). It keeps the hub.lock
fd for its whole life, and `flock` is held by the open file description. `Hub.shutdown` then
closes the hub's copy (`_drop_hub_lock` uses `close()`, not `LOCK_UN`), and so does a crash, but
the lock stays held. Every later `Hub.run` (launchd KeepAlive respawn, a deploy kickstart,
`rmx hub start`, `rmx ui`) logs "another hub holds hub.lock — not starting" and returns 0. That
log line is false, because the holder is a project daemon. Under launchd, `KeepAlive
{SuccessfulExit: false}` does not respawn a 0 exit, so the fleet has no hub, watchdog, shared
models or bus until that daemon dies, which can be days. Before this commit the same fork leaked
only harmless fds.

**Evidence:** In `bsd-bug129-r3-ui-daemon-fork.log`, a hub-process child took the lock, called the
real `daemon.spawn_daemon(<tmp store>)`, ran the shutdown drop and exited. Then:

- `lsof -p 76476` showed the daemon holding fd `5w .../hub.lock`.
- "a respawned hub can take hub.lock: False".
- A real `Hub.run` returned at once with `['another hub holds hub.lock — not starting']`.
- After `stop_daemon`, the lock could be taken again (True).

The same probe's pipe read never reached EOF because the daemon also inherited the pipe write
end, which is a second symptom of the same leak.

**Why the fix missed it:** the hub's own comments (`hub.py:142`, `:387`) already require
"Subprocess, not os.fork" because the hub is multi-threaded. These two call sites predate that
rule and were never moved. The new lock turns that latent fork-safety violation into a
fleet-wide startup outage.

**Fix (small):**
1. Route `ui/server.py:263` and `bus.py:536` through `daemon_mod.spawn_daemon_subprocess`, which
   the hub already uses twice.
2. Make `_drop_hub_lock` call `fcntl.flock(f, LOCK_UN)` before `close()`. This makes a clean stop
   immune to any stray inherited copy. A crash still depends on (1).
3. Add a guard test that the hub process never reaches `spawn_daemon` and no bare `os.fork`
   module call runs from `hub.py`, `ui/server.py` or `bus.py`. Or turn my probe into a test:
   fork, take the lock, `spawn_daemon`, drop, exit, then assert the lock can be taken.

Optionally, have the stand-down log name the holder (`lsof -t hub.lock`) so a misattributed
"another hub" is visible.

**Pattern match:** YES. It is the daemon's own lesson: `spawn_daemon`'s comment says "the child
closes the lockfile fd before serving so the parent's flock is the only thing keeping siblings
out". It is also [[feedback_clean_corpus_hides_a_dead_gate]]'s shape: the suite never forks a
daemon from inside a hub.

### SKETCHY s1-r3: `rmx hub stop` reports stopped seconds before the old hub drops hub.lock; an immediate successor stands down {#s1-r3-stop-start-window}

**File:** `src/refmatrix/hub.py` `stop_hub` (exit criteria: no ping and no port LISTENer) vs
`Hub.shutdown` (drops the lock only after `_stop_models` + `watchdog.stop` + release).

**What:** Uvicorn exits and the control socket goes dark first. `ModelServer.stop` then takes
about 4-5 s. The live `hub.log` shows 4-5 s between "hub stopping" and "models stopped" in 10 of
10 stops since 2026-10-07. In that time `stop_hub` has already returned True, while the old
process still holds the lock. A successor that does not share the old hub's launchd label then
stands down with exit 0:

- `rmx hub stop && rmx hub start`
- `rmx hub stop && rmx ui`
- a launchd kickstart after stopping an unsupervised hub

Before the lock, the port was free, so the successor started, and r1's owner check kept the old
hub's late release off the new file. This is loud: `spawn_hub` reports "hub failed to start" and
hub.log names the lock. But it is a new failure on a documented restart path, and under launchd
a 0 exit is not retried.

**Evidence:** `bsd-bug129-r3-stop-start-window.log`. With a 0 s model stop, `stop_hub` returned
in 0.17 s, the first hub was gone, and the successor could take the lock. With a 3 s model stop
(standing in for the measured 4-5 s), `stop_hub` returned True in 0.16 s with the first hub still
alive, and the successor could take the lock: False. The first hub exited at 3.02 s.

**Fix:**
- Add one more `stop_hub` exit criterion: wait, within `timeout`, until a non-blocking `flock`
  probe on hub.lock succeeds (take and release at once). Then "stopped" means the lock is free.
- Raise the default `timeout` above the measured model-stop time.
- Alternatively, have `Hub.run` wait a bounded few seconds on a blocking lock before standing
  down. That costs a delay only when a hub really is live.

### MEH m1-r3: the lock drop on both paths is unpinned {#m1-r3-drop-unpinned}

**File:** `hub.py` `shutdown()` `_drop_hub_lock(...)` and the preflight-fail `_drop_hub_lock`.
**Evidence:** Mutations M4 (shutdown keeps the lock) and M5 (preflight refusal keeps the lock)
each pass 22/22 (`bsd-bug129-r3-mutations.log`). Today the process exits right after either
path, so the effect is small. But the commit claims both drops, and b1's fix (2) moves real

## Verdict {#verdict}

3 findings (1 BULLSHIT, 1 SKETCHY, 1 MEH). **Not mergeable as written.** Every r2 item is closed
and each is held by a test that kills its mutation. The lock does decide the singleton for
hub-vs-hub startups. But a reachable production path, the web UI's daemon start or accepting a
refinement for a stopped project daemon, hands the lock to a long-lived daemon. After that, no
hub can come back until the daemon dies, and launchd will not retry. Move those two call sites to
`spawn_daemon_subprocess` and add `LOCK_UN` before close (b1). Then make `stop_hub` wait for the
lock (s1-r3).
