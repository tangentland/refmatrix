## Answers to the five checks {#answers}

### 1. The `Store.add_memory(updated_at=)` guard {#q1}

- **Core: sound.** At HEAD `store.py::Store.add_memory` stamps `now = time.time()` into
  `memory_content.created_at/updated_at` (DuckDB `DOUBLE`, `duckdb_catalog.py:95-96`), so an
  authoring time carried as a JSON float compares exactly; equal timestamps are the dual case
  (same entry dialed and queued) and `>=` correctly skips the second. `_op_memory_add`
  (`daemon.py:4998`) builds its call from named `args` keys, so the pass-through is one line.
- **Clock.** Wall clock is the right choice and the spec's claim ("the same clock
  `Store.add_memory` uses, one host") holds: the queue file survives a reboot and a daemon
  restart, and `time.monotonic()` does not compare across a reboot. Residual: a backward wall-clock
  step between two turns skips the newer one until the next promote ([[#m2]]).
- **The bridge.** `ingest_gmd.py:956` calls `store.add_memory(...)` with no time, so it keeps
  today's behaviour and a memory FILE edit is never skipped. The rule must stay that way: a bridge
  that passed the file's mtime would make a file edit skippable behind a later digest. The fold's
  "every existing caller ... behaviour is today's exactly" covers it. Other `None` callers at
  HEAD: `store.py:2716` (`upsert_subject`), `handoff.py:343`, `mcp.py:116`, `cli.py:11652`,
  `daemon.py:5471` (brief save), and the two replay sites.
- **Plan-26 26.2.** No conflict. 26.2 n1 switches the bare `con.commit()` (`store.py:2506`) to
  `_maybe_commit` or adds a dedicated method. 23.1 R11.3's precondition already says 23.1 makes
  the switch itself if 26.2 takes the alternative. The guard's early return commits nothing.
  26.2's legacy-row refresh is logged as a `memory_content` event (see [[#s1]] for the field it
  should carry).
- **facts.log replay: NOT sound** ([[#s1]]). A skipped write emits no event, so replay never
  sees it; that part holds. But the stored time does not survive replay. The live
  `memory_content` event (`store.py:2511`) has no `updated_at` field, and both replay paths call
  `add_memory` with no time: `_apply_one_event` (`store.py:7879-7888`) and
  `rebuild_index_from_log`'s last-write-wins pass (`store.py:8040-8044` and `:8183-8195`). Every
  replayed row gets the replay's wall time.

## Findings {#findings}

### SKETCHY s1: the authoring time does not survive facts.log replay {#s1}

**File:** `workflow/plans/plan-23-bounded-write-harness-tasks/task-23.1-queue-and-drain.md`, R11.3
"A queued apply never overwrites a newer digest" item 1; code `store.py:2511`, `:7879-7888`,
`:8040-8044`, `:8183-8195`.
**What:** The guard compares a new write's `updated_at` with the stored `updated_at`. The fold
specifies how that time is stored on a live write. It does not specify the event or the replay.
**Why it matters:** `rebuild --from-log` restamps every memory row with the replay's wall time.
The `hook_writes` segments and their offsets are outside facts.log. After a rebuild, every queued
entry authored before the rebuild therefore compares older than its row and is counted as
`superseded`. A digest that was queued but not yet drained when the store needed repair is lost
for good. The skip is counted, not silent, but the newest content is gone. Replay also stops
being faithful in the way `dump_catalog_to_log`'s docstring promises: compaction emits
`ts = mc.updated_at` (`store.py:7634`), and the replay throws that value away.
**Fix:** R11.3 item 1 gains three things:
(a) `add_memory`'s `memory_content` event carries `updated_at`, the stored value, and
`dump_catalog_to_log` emits it;
(b) `_apply_one_event` and the rebuild's last-write-wins pass call
`add_memory(..., updated_at=ev.get("updated_at"))`, and the pass orders by that value when it is
present (legacy events without it keep today's `ts` ordering);
(c) AC-21 gains a step: guarded write → `rebuild --from-log` into a fresh store → the stored
`updated_at` equals the authoring `ts`; then a queued entry authored before it is skipped and one
authored after it applies. Mutation: drop the field from the event, and the step FAILS.
26.2's legacy-row event carries the same field.
**Pattern match:** YES. This is the replay half of the plan-26 26.2 n1 finding: there, an
unlogged UPDATE was lost on rebuild.

### SKETCHY s2: `last_wins_by_name` orders by arrival, so the guard never sees the newer entry {#s2}

**File:** task-23.1 R11.1 (`merge_fn=last_wins_by_name`, "the newest line for a key is the whole
truth"), R11.2 (`ts` taken when the entry is built), R11.4 (dial before append).
**What:** The fold's own rationale says to order by authoring time "whichever path lands first".
But the in-window merge still keeps the LAST LINE, and a line's position is its append time.
**Why it matters:** Each producer stamps `ts` before its dial and appends only after the dial
fails. The save-state promote gets `deadline = monotonic() + 30.0`, so its append can come up to
about 29 s after its `ts`. The Stop hook's append comes within about 4 s of its own. A save-state
entry stamped at T=100 can therefore append after a Stop-hook entry stamped at T=110 for the same
`focus_summary_<slug>`. Both land in one window and the merge keeps the T=100 line. The T=110
line is dropped before `add_memory` runs, so the guard compares the older entry against the row
and applies it. This is the overwrite s-n1 was meant to close, recreated inside the queue. AC-21
step 5a covers successive windows (`batch=1`) only.
**Fix:** replace the position-based merge with an explicit authoring-time merge:
`newest_by_ts(acc, ev) -> ev if ev["ts"] >= acc["ts"] else acc` (a tie goes to the later line).
Keep R3.1's "explicit, not a default" wording. Optionally union the `subject` labels so the
dropped line's filing still lands, since a bit is order-free. AC-21 5a gains a fourth sub-case:
two producers append into one window with `ts` order opposite to append order, and the row holds
the higher-`ts` content. Mutation: position last-wins FAILS.
**Pattern match:** YES. Same class as [[bsd-impressions#imp-queue-beside-sync-writer]]: a
cross-path order that is fixed at one stage but not at every stage that orders.

### MEH m2: state the wall-clock residual {#m2}

R11.2 should name why the authoring time is a wall clock and not a monotonic one (the queue
outlives the process and the boot). It should also name the residual: a backward NTP step between
two turns makes the newer promote compare older, so it is skipped and counted `superseded` until
the next turn re-promotes. One sentence; no mechanism.

### MEH m3: m2's rationale wording {#m3}

- [[task-23.1-queue-and-drain#facts]] round 12 says a `None` refresh could point readers "possibly
  at a slot file that does not exist yet". `_refresh_read_only_link` prefers
  `catalog.read.duckdb` whenever it exists, so that risk applies only to a store that has never
  been snapshotted. The decision stands; the reason is overstated.
- "`None` keeps today's link behaviour" is true for the two `None` sites. The fourth site,
  `_bootstrap_rotation_if_needed`'s reopen on slot `A` (`daemon.py:3077`), GAINS a refresh it

  slot rebind's install records one") should state its fixture. On a legacy-only store the
  bootstrap installs `A`, `db_path == active_path`, the rebind is skipped, and the recorded caller
