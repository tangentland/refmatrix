### BULLSHIT #b-1-r5: plan-10's negative result was measured on `--format json`, which omits the composite — the one block that repeats 100% {#b-1-r5}

**File:** `eval/injection_overlap.py:134-140` (the `scan()` argv), `workflow/measurements/injection-overlap.md`,
`workflow/plans/plan-10-injection-dedup-tasks/task-10.1-plan-10-injection-dedup.md:21`

**What:** the harness that produced plan-10's `median carried 0.000 → STOP` runs

```
rmx scan-prompt <prompt> --format json --no-composite --max-tokens 2000
```

The production hook (`.claude/settings.json:117`) runs

```
rmx scan-prompt --composite-every 3 --max-tokens 2000 --timeout 5
```

**Why it's bullshit:** `--format json` emits a bare LIST of per-concept bundles. The STM
**topic-composite** — default ON, budgeted SEPARATELY from `--max-tokens` (`--composite-max-tokens`
floor 1200), and described by `scan-prompt --help` in exactly plan-10's own words as *"a running
aggregate of every prompt+result"* — **is not in the JSON at all**. Measured on the live store with
the deployed binary:

```
--no-composite       --format json : 11,949 B   composite present: False
--composite-every 1  --format json : 11,949 B   composite present: False   <- byte-identical
--no-composite       text (prod)   :  2,575 B
--composite-every 1  text (prod)   :  6,265 B   <- composite = 3,690 B = 59% of the payload
```

So `--no-composite` in the harness is a no-op *because the surface it measured could never see the
composite in the first place*. The harness measured the bundle half and reported a verdict on the
whole.

And the composite is the repeat. Eight consecutive real `query.log` prompts, production text render,
splitting bundles from composite and comparing each block to its predecessor:

```
 bundle_B  comp_B  bundle_sim  comp_sim
     1646    3694         0.0       1.0
     1828    3694       0.147       1.0
     1516    3694       0.110       1.0
     1303    3694       0.146       1.0
     4853    3694       0.135       1.0
     2537    3694       0.086       1.0
     2537    3694       1.000       1.0
median bundle similarity : 0.135          <- consistent with the harness's 0.000 on entry identity
median COMPOSITE similarity : 1.000       <- 3,694 B re-sent byte-identical, 7 of 7 pairs
```

**The premise plan-10 declared false is true for the larger half of the payload.** Plan-10 `#context`
says *"the same neighbourhood … is plausibly re-injected turn after turn, and the window is charged
every time"*. That is a literal description of the composite.

**Second leg, and it points the same way.** The harness's `overlap()` returns `None` when either side
is empty, justified in its docstring as *"a 0.0 that would drag the median down and make the case
look worse than it is"*. 112 of 400 replays (28%) were empty, so ~140 of 327 candidate pairs were
dropped. In production those are precisely the turns where the carried fraction is ~1.0, because
nothing BUT the composite is injected:

```
prompt='go'        json/--no-composite =     3 B ("[]")   production text = 3,623 B
prompt='ok do it'  json/--no-composite =     3 B ("[]")   production text = 3,623 B
```

The exclusion rule removed the strongest pro-dedup evidence in the sample, on the stated grounds of
not making the case look worse than it is.

**The task spec is where the defect entered** — `task-10.1:21` itself names
`rmx scan-prompt --format json` as "the PRODUCTION path" in the same sentence as
*"No bespoke re-implementation of the selection logic ([[feedback_measure_the_path_users_run]])"*.
It is also [[feedback_main_path_must_exercise_core_mechanisms]]: the measurement turned a core
mechanism off with a flag and read the remainder.

**Fix:** re-run 10.1 on the production render (text, `--composite-every 3`, `--timeout 5`), splitting
the report into `bundle_carried` and `composite_carried` and weighting by BYTES, since the two halves
differ ~2:1 in size and ~7:1 in repeat rate. Keep the empty-side rule only for the BUNDLE leg; a
composite-only turn is a 1.0 observation, not a missing one. If the composite does repeat in a live
session with an advancing focus, the plan's own `#degrade` design applies to it and the STOP is
withdrawn — and if it does not, say so with the number. **The one thing that cannot stand is the
current STOP**, which never looked.

**Honest limit on my own number:** my eight runs are separate processes with no advancing session, so
the STM focus did not move between them and 1.000 is an upper bound. That is *also the harness's
condition* — it replays the same way — so had it rendered production output it would have reported
~1.0 on 59% of the bytes. What a live session's advancing focus does to that figure is the
measurement plan-10 still owes, and production's `--composite-every 3` throttle is itself evidence
that someone already judged this block expensive and repetitive.

**Pattern match:** YES — `{#imp-metric-population-unchecked}` and
[[feedback_main_path_must_exercise_core_mechanisms]], and the 2nd sighting in this lineage of a
flag turning off the mechanism under measurement (r1 #b-6, `--depth` inert for `scan`).
