## (a) m-4: is EVENT_SPLIT with only an import-time reader acceptable? {#a}

**Verdict: acceptable as built. R1 needs no amendment, and m-4 is closed.**
- R1 lists `EVENT_SPLIT`, `NON_RMX_RESERVE_BYTES` and `MIN_USEFUL_RECALL_BYTES` as contents of the
  module (task spec `#r1`).
- R0 gives them a formula only under outcomes (B) and (C). It also says exactly one outcome per
  event sets `hook_budget`, and R0 measured outcome (A) on both events (`d748196`).
- So under the spec as written, the absence of a runtime consumer is correct behaviour, not
  scope that was dropped. Deleting the constants would break R1. Inventing a runtime use would
  contradict R0's measured outcome.

What changed is that the constants now carry a contract that fails at import. I proved each new
check fires by executing `hook_budget.py`'s source with one edit at a time in a fresh module
(`m4-import-checks.log`):
- `prompt_recall` set to 1,500 B: `ValueError: … under MIN_USEFUL_RECALL_BYTES 2000 B`;
- a new channel with no event: `ValueError: channel(s) ['newchan'] sit on no EVENT_SPLIT event`;
- a hand-written `EVENT_SPLIT` share of 99,999 B: `ValueError: … exceeds the channel's own cap
  1500 B`;
- the unedited table imports.

The share-over-cap check can only fire on a hand-edited literal, because the shares are built
from `CHANNEL_BUDGET_BYTES`. The placement check and the floor check bind any future table edit.
No test exercises the failing side; see [[#m-a]].
