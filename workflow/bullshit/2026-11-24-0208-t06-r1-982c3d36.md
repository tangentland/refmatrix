## Findings {#findings}

### BULLSHIT: the `-rr` rows are mostly unreranked, and nothing in the artifact says so {#b-1}

**Files:** `README.md` and `docs/PERFORMANCE.md` (the `recall-rr` and `recall-fuse-rr` rows),
`eval/production/longmemeval/REPORT.md` (`#restricted`, `#union`, `#per-type`, `#next` item 2),
`results/summary-120-0.84.0.json`, `eval/production/longmemeval/run.py:299-321` (`rank_all`
keeps ids only).

**What:** The docs publish `recall-rr` and `recall-fuse-rr` as cross-encoder rerank surfaces.
REPORT `#next` item 2 reads the 34-of-120 difference as proof: "`recall-rr`'s rankings differ
from `recall`'s on 34 of 120 questions, so the reranker answered in this run."

**Why it's bullshit:** That 34 is the evidence that the reranker did NOT run on the other 86
questions.

- **recall-rr:** on 86 of 120 questions, `rank-recall-rr.json` is byte-identical to
  `rank-recall.json`, which is the unreranked dense top 50. A cross-encoder over a 100-doc pool
  does not reproduce the dense order of 50 documents 86 times.
- **recall-fuse-rr:** on 72 of 120 questions, `rank-recall-fuse-rr.json` is byte-identical to
  `rank-recall-fuse.json`.
- **Deploy code:** this matches the fallback in `recall.replica_memory_recall` (deploy
  `cab0a7dc`, `src/refmatrix/recall.py:1049-1080`). It appends `"rerank skipped: …; hits
  unreranked"` to `warnings` and returns `hits[:k]` in dense order.
- **Harness:** `run.py` keeps only ids. It drops the payload's `warnings` and each hit's
  `reranked: True` flag, so the artifact cannot tell a reranked row from a skipped one.
  `n_failed = 0` on every surface. This is the same blindness ch-bsd r1 #s-13 fixed for dead
  surfaces.

**Evidence:**

- Ranking identity, from the data volume's rank files:
  - `recall-rr == recall`: 86 of 120.
  - `recall-fuse-rr == recall-fuse`: 72 of 120.
- Per-call latency, from the eval store's `cli.log`, read-only, the 01:2xZ window, 120 calls
  each:

  | call | median |
  |---|---:|
  | `--no-rerank` | 0.76 s |
  | `--rerank`, ranking changed (34 calls) | **4.25 s** |
  | `--rerank`, ranking identical to dense (86 calls) | **1.72 s** |
  | `--fuse --rerank`, changed (48 calls) | 4.97 s |
  | `--fuse --rerank`, identical (72 calls) | 1.82 s |

  The skipped calls cost about 1 s over `--no-rerank`. That fits the 1 s `RERANK_PROBE_S` info
  probe giving up while 4 harness workers share one hub rerank worker. **That cause is not
  measured**, because the warning text was discarded.
- **Item 6, the ceiling.** `recall-rr`'s 0.625 ceiling is 2 questions above `recall`'s 0.608
  (`d851d5ba`, `e4e14d04`). Both are among the 34 reranked questions, where the rerank
  over-fetches `k × DEFAULT_POOL_MULT = 100` and pulls gold from dense ranks 51-100.
  `recall-fuse-rr` gains 2 and loses 2, so it nets 0.608. The mechanism REPORT calls "not
  measured" can be read off the code and the rank files. The ceiling of an `-rr` row is set by
  which questions happened to be reranked.

**Consequence:**

- Every `-rr` figure measures a mixture: 28% reranked for `recall-rr` and 40% for
  `recall-fuse-rr`.
- The README and PERFORMANCE rows labelled `recall-rr` are not rerank results.
- The per-type `-rr` columns and REPORT's bug-032 reasoning in `#next` item 2 ("the exposed rows
  are `scan` and the two `-rr` rows") rest on the same mixture.
- R6.6 ("a failure is a result") was not met for the rerank leg. AC-6.1's "all four dense/fused
  methods" holds only by label.

**Fix:**

- **Harness.** `rank_all` records, per question, whether the payload's hits carry `reranked` and
  any `warnings`. `_meta` gains `n_reranked` and `rerank_warnings`, the same carry pattern as
  `n_failed`. `test_longmemeval_artifact_carries_its_provenance` asserts `n_reranked == 120` on
  every `-rr` surface.
- **Re-run.** Re-run the two `-rr` methods so that the rerank lands on all 120, for example
  `--workers 1`, or whatever the recorded warnings show is binding.
- **Fallback.** If a full rerank cannot be had, label the rows with the reranked fraction, drop
  every rerank claim drawn from them, and log a registry row (rerank silently skipped under
  harness concurrency).

**Pattern match:** YES. It matches ch-bsd r1 #s-13 (a degraded surface is indistinguishable in
the artifact) and the impression `imp-ruled-out-leg-returns-via-fallback`. The bug-025 family is
a rerank skip said in `warnings` that a caller never reads.

### BULLSHIT: the ‡ footnote states a false mechanism, in README, PERFORMANCE, REPORT and the artifact {#b-2}

**Files:**

- `README.md`, the ‡ note.
- `docs/PERFORMANCE.md`, the ‡ note.
- `REPORT.md`, the `#restricted` ‡ note and the second bullet of `#fusion`.
- `results/summary-120-0.84.0.json`, `_provenance.notes`.
- the implementation summary, `#results-lead`.

**What:** "The difference from `recall-rr` comes from the hybrid's wider dense pool
(k = max(k, rrf_k)), not from fusion."

**Why it's bullshit:** There is no wider pool under rerank. `replica_memory_recall` sets
`retrieve_k = min(max(50, 50 × 2), 100) = 100` before `hybrid_memory_recall`. `hybrid_recall`'s
`max(k, rrf_k)` is then `max(100, 60) = 100`, the same pool the non-fuse path draws. On this
corpus the symbolic leg is empty (bug-300), so the fused list equals the dense list. The two rows
should be identical, and they are whenever the rerank did the same thing in both:

- Both calls reranked: 14 questions. `recall-rr == recall-fuse-rr` on 14 of 14.
- Neither call reranked: 52 questions. Identical on 52 of 52.
- Exactly one call reranked: 54 questions. These are all of the difference (20 reranked only in
  `-rr`, 34 only in `fuse-rr`).

So the whole `recall-rr` / `recall-fuse-rr` gap, including union R@5 0.266 vs 0.298 and
restricted 0.527 vs 0.513, comes from which questions the rerank skipped ([[#b-1]]). It has
nothing to do with pool width. A mechanism was named without being measured, and it was published
in README, the user-facing doc. The memory `feedback_causal_story_before_evidence` already
records this pattern.

**Fix:** Replace ‡ in all five places with the measured cause: the rows differ only where the
rerank ran in one call and was skipped in the other (54 of 120). Better, remove the cause by
fixing [[#b-1]], after which the two rows should be identical until bug-300 lands. The
`_provenance.notes` edit is allowed, because only that key is added to run.py's output.

**Pattern match:** YES (`feedback_causal_story_before_evidence`).
