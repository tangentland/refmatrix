## Findings {#findings}

### BULLSHIT: a booting daemon is "absent" to the write control point — the in-process writer still opens the live slot in the window plan 4 made longer {#b-1-r2}

**File:** `src/refmatrix/discovery.py:162` (`daemon_status`: `busy = daemon_mod.socket_path(root).exists()`), `src/refmatrix/verbs.py:194` (`require_daemon`), `src/refmatrix/cli.py:372` (`_store`: `VerbAbsentError → _store_rw()`), `src/refmatrix/cli.py:8449` (`_ingest_gmd_sync`: same), `src/refmatrix/daemon.py:1195–1358` (`serve_forever`: pid file written, then `Store()`, index repair, snapshot, mem mirror, THEN `srv.bind`)
**What:** The remedy defines "absent" as `daemon_status` does: not answering AND (no live pid OR no socket file). `serve_forever` unlinks any stale socket in `_reap_predecessor`, writes `rmxd.pid`, opens the Store, runs the queued boot repair, snapshots, warms the mirror, and only then binds the socket. For that whole span the daemon holds the DuckDB writer lock and `daemon_status` returns `busy: False`.
**Why it's bullshit:** r1's fix spec (which the summary cites) said: "only `absent` (no pid, no socket) → in-process". The shipped classifier says absent when the pid is alive and the socket is not there yet — and `VerbBusyError`'s own docstring lists "starting" as busy. Probe (a) on a tmp root with a live pid and no socket: `require_daemon` → `VerbAbsentError: daemon not running` → `_store(write=True)` returns `_store_rw()` and `_ingest_gmd_sync` opens the slot in-process. The window on this store is ~3 s per boot (rmxd.log: `daemon starting` 23:18:45 → `mem mirror ready` 23:18:48, same shape at 21:19, 21:44, 21:46, 21:49, 22:02, 22:34), longer on the big fleet stores and on any boot that runs the plan-4 queued repair. Plan 4 now relaunches the fleet and respawns on every detector, so this window opens on every daemon many times a day, exactly when the Stop/PreCompact/SessionStart hooks fire. It is not hypothetical: `daemon.stderr.log` lines 70–76 and 150–156 are two boots (18:50:13/18:50:26 crash pair, 21:46/21:49) that died on `Could not set lock on file catalog.B.duckdb: Conflicting lock is held in /opt/local/…/python3.14` — a CLI Python process had the writer open while the daemon booted. Whichever side wins the race, the other one dies: CLI first → the daemon fast-exits and launchd crash-loops; daemon first → the "absent" CLI fallback raises an IOException that the bridge reports as its own failure with no busy wording and nothing to retry. Fifth busy≠absent sighting; the guard was built for the fixed state (silent socket) not the incident (boot).
**Evidence:** scratch `probe_busy.py` (a): `boot-window classified: ABSENT -> daemon not running for /tmp/rmxboot-…/.refmatrix`; `serve_forever` order at `daemon.py:1197` (pid) vs `:1358` (bind); `_reap_predecessor` unlinks the socket at `:1170`; stderr lines above; `rmx daemon status` renders the same state as `stale pid N` (`cli.py:11179`).
**Fix:** In `daemon_status`, a live pid is busy whether or not the socket exists (`busy = True` after `os.kill(pid, 0)` succeeds); a stale pid file whose process is gone stays absent. Refusing a write on a pid-reuse false positive is the safe direction and `rmx daemon start` already reaps stale pids. Add the probe as a test: pid file with `os.getpid()`, no socket, assert `_sync_memory_dir` returns a busy error and `_store(write=True)` raises. Re-run `test_plan2_remedy`/`test_plan4_remedy` for callers that expect "stale pid" to mean absent.
**Pattern match:** YES — `bsd-pattern-busy-is-not-absent` (5th), `imp-same-input-guard` (guard built for the fixed state), `imp-fix-at-quoted-line`.
