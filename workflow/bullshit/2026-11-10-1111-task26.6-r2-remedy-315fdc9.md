## Findings {#findings}

### MEH: a compiled subject with an unknown `compiled_scope` makes `derive_status` raise, hiding the whole partition verdict {#m-1-r2}

**File:** `src/refmatrix/store.py` `_memory_compile_status` (the `raise ValueError(... unknown
compiled_scope ...)` branch), called from `Store.derive_status`
**What:** The fail-closed branch raises out of `derive_status`. That loses the ingest passes'
`stale` / `behind_code` verdict as well as the compile line, on every surface that calls it:
- ping health (`daemon.py:4031`, which becomes `derive_error` for EVERY partition);
- `daemon status`, which prints "unknown";
- the `derive_status` op;
- `rmx derive status` (`cli.py:7441`, its fallback path).
Reachable when a later release writes a new scope and the deploy is rolled back, or when a row
is hand-edited.
**Evidence:** Probe `test_probe_r2_unknown_scope_blinds_the_partition_verdict`: `derive_status()`
raises "compiled subject with unknown compiled_scope 'future_scope'"
(`bsd-26.6-r2-probe.log`).
**Fix:** Keep it loud but local. Record the unknown scope under
`memory_compile.scopes[<name>] = {unknown: True, needs_compile: True, compiled_subjects: n}` and
have `render_memory_compile_warning` print "scope <name>: unknown to this rmx". Never raise out
of `derive_status`. Add one test.

### MEH: brief's compile scope rides `rmx_memory`'s overloaded `scope` parameter, and the CLI cannot ask for it {#m-2-r2}

**File:** `src/refmatrix/verbs.py:1735-1736` (`_memory_payload` brief), `:1758` (`scope` is
shared with recall, where it means project | global | both); `src/refmatrix/cli.py` `memory_brief`
(no `--scope`; it passes `DEFAULT_SCOPE`)
**What:**
- An MCP caller can run a pattern-scope brief; the CLI cannot. That is a CLI/MCP capability gap
  on a verb-paired command.
- The same `scope` argument means different things per action. A recall-minded `scope="project"`
  on brief fails loudly (`_check_scope`), but the schema documents neither meaning.
- With the default, impression contradictions and impression-only orphan concepts now appear in
  no CLI brief. This is the intended one-corpus result, but no surface can reach the pattern
  corpus from the CLI.
**Fix:** Add `memory brief --scope memory|pattern` (it forwards the same key). Give `rmx_memory` a
`descriptions={"scope": ...}` that names both meanings, or a dedicated `compile_scope` key.

### MEH: the R3 residual names a helper that skips unless it is handed bridge files {#m-3-r2}

**File:** `workflow/plans/plan-26-memory-organisation-tasks/task-26.6-compile-subject-hygiene.md`
`#r3-req`; `src/refmatrix/ingest_gmd.py` `regenerate_memory_index` (returns
`status: skipped, reason: no ingested file under the store's memory root` unless some entry of
`files` resolves under the memroot)
**What:** The residual says R3 regenerates "through
`ingest_gmd.regenerate_memory_index_reported`". A compile has no ingested files, so a literal
build (`files=[]`) is a silent no-op. Only the marker-ON AC would catch it.
**Fix:** State in `#r3-req` that the compile passes `files=[memdir]` (an equal path passes the
`relative_to` check), or split the helper into a gate-free `regenerate_for_memroot`. Name the
mutation "compile calls the helper with no files".
