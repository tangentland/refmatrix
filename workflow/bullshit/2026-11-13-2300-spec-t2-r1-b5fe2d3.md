### SKETCHY: the "unresolved path" rule cannot be honoured where R-220a runs, and the one symlinked fleet memdir keeps bug-220 {#s1}

**File:** `workflow/plans/plan-26-memory-organisation-tasks/task-26.5-memory-organise-verb.md:492`
**What:** R-220a: "else the `~/.claude/projects/<slug>/memory` shape, tested on the unresolved
path". R-220e:518 then takes the store from "AC-1's resolver on the memdir `memdir_of` returned".
**Why it's sketchy:** the walk never sees an unresolved path. `ingest-gmd` resolves every target
before anything else (`cli.py:10411` on the bug-216 branch: `resolved = [Path(t).resolve() for t
in targets]`), and `_sync_memory_dir` resolves again (`cli.py:10839`). The Files list
(`:215-218`) does not change that. `_root_from_projects_slug` does `cwd.relative_to(Path.home() /
".claude" / "projects")` (`cli.py:122-126`), so a resolved symlink target returns None.
**Evidence:** viascope's memdir is a symlink:
`~/.claude/projects/-Users-tholley-github-atollogy-bdep-viascope/memory ->
/Users/tholley/at/bdep/viascope/.claude/projects/-Users-tholley-github-atollogy-bdep-viascope/memory`
(read 2026-11-13). `rmx ingest-gmd <that memdir>` without the flag would play out like this:
- today (flat): the resolved path fails the HOME-anchored shape test, `memdir_of` returns None,
  and the file lands as a `kind=doc` twin. That is bug-220 itself, unfixed for viascope.
- after plan-27 organises viascope: the marker sits at the resolved path, outside the projects
  shape, so the walk takes the `rerouted_no_store` branch. Nothing lands, although the store is
  resolvable from the path the user typed.

No AC-220 case has a symlinked memdir, and 26.5's own Test Strategy (`:233`) lists one for AC-1
only.
**Fix:** state that the CLI hands `memdir_of` the UNRESOLVED target (ADR-0005
`#store-resolution` rule), and add AC-220 (h): a symlinked memdir whose target sits outside
`projects/` (viascope's shape), checked marker-off and marker-on. The memories land in the slug's
store. Mutation: "resolve before `memdir_of`" turns (h) RED.
**Pattern match:** YES. The same "never `.resolve()`" defect class as plan-26 r2 m2 / r3 m10
(AC-1), now on the reroute's path.

### SKETCHY: ADR-0005 now contradicts itself on store resolution, and its amendment log says nothing changed {#s2}

**File:** `docs/adr/0005-memory-dir-layout.md:159-160`, `:238-242`, `:384`;
`task-26.5…:518`, `:525`
**What:**
- `#store-resolution:159`: "A path that is not under `~/.claude/projects/<slug>/` is a hard
  error that names the fix. It never silently becomes 'no store'."
- The new `#marker` bullet (`:238-240`) and R-220e (`:525`) say instead: "a marker dir outside the
  `~/.claude/projects/<slug>/memory` shape is file-only, as ADR-0005 says". That is the lead's
  ruling, and it is right.
- `#amendments:384` says "No folder, identity, resolution or gating rule changes".
**Why it's sketchy:**
- **Two rules, one ADR.** An unattended build has two ADR rules for the same input, and R-220e
  cites the ADR for the opposite of what `:159` says. "AC-1's resolver" (`:518`) is the
  exit-2-raising one (task-26.5 `:45-48`). Used as written, AC-220 (c) exits 2 instead of
  counting `rerouted_no_store`.
- **The `:238` claim is wider than the spec.** "ingested as `kind=memory` by ANY walk … into the
  store its memdir resolves to" goes past what 26.5 specifies. R-220b/e cover `as_memory=False`
  only. An explicit `ingest-gmd --as-memory <B's memdir>` run from A still lands in A, so the
  same file reaches different stores depending on the flag.
- **The "writes no file" justification is false for organised dirs.** `:242` and `:531` say "The
  reroute writes no file". The cross-store branch goes through `_sync_memory_dir` →
  `_ingest_gmd_sync(as_memory=True)`. On the daemon path that regenerates `MEMORY.md` for a
  marker-on memdir (`daemon.py:3805`, `regenerate_memory_index_reported`, marker-gated). The
  behaviour is fine, because that write is marker-gated. The reason given for "ungated" is wrong.
**Fix:**
- Scope `:159` to the organise verb's explicit memdir argument, and add the walk-reached
  carve-out (file-only, counted).
- R-220e names a non-raising resolver variant.
- `:238` either says "every walk without `--as-memory`" or 26.5 gives the flagged walk the same
  store rule.
- Restate the every-dir reason as "store-side; any file write it causes is marker-gated".
- Correct `:384`.
**Pattern match:** YES. It is the "two copies of one rule" shape (ADR `#open` vs
`#marker-encoding`, which spec-t2 itself fixed in this range).

### SKETCHY: where the reroute executes is unspecified; the daemon path calls another daemon under the writer lock, and same-store rerouted memories get no vectors {#s3}

**File:** `task-26.5…:496-530`, `:507`, `:533`; `#files:215-218`
**What:**
- R-220b puts the reroute "in `collect_gmd_files` / `ingest_gmd_paths`".
- R-220e sends a foreign memdir through `_sync_memory_dir(memdir, root=)`, and the same store
  "through the in-process memory path of the same call".
- R-220c: "A daemon walk records the count on its op record."
**Why it's sketchy:** on the bug-216 branch, the daemon's ingest-gmd body runs
`ingest_gmd_paths` holding `d._store_lock` (`daemon.py:3759`, `_run_ingest_gmd_body:3696`).
Read literally, the spec has five gaps:
1. **Cross-store call under the lock.** A's daemon would call `cli._sync_memory_dir` while
   holding A's writer lock. That puts the library calling into the CLI, and a socket call to B's
   daemon with `daemon.call`'s retries, under A's lock.
2. **The wait can run on the same lock.** B's single-active-ingest refusal triggers
   `_bridge_wait_for_active_job`. That is the bug-085 lock-held wedge class, and the spec does not
   address it (the self-call case is handled, the A→B case is not).
3. **No vectors or index on the same-store branch.** The op's memory-vector drain and index regen
   are gated on the CALLER's flag (`daemon.py:3790`, `:3805`: `if args.get("as_memory")`). The
   in-process twin has the same gate (`cli.py` `_ingest_gmd_in_process`, `if as_memory:`). So
   rerouted rows get no vectors (bug-065: durable but invisible to recall) and no index line.
4. **The ACs cannot see it.** AC-220 checks `kind` and row counts only, never recall, although
   26.5 itself `reinforces -> feedback_verify_memory_by_recall_not_get`. It does not say whether
   the daemon is up, so "reroute only on the in-process path" survives every listed mutation.
5. **No failure branch.** `_sync_memory_dir` "never raises" and returns an `error`. What the walk
   does with B unreachable is unspecified (CLAUDE.md `#no-silent-failures`). `daemon.py` is not
   in Files.
**Fix:**
- Name the split site. Recommended: split in the CLI before dispatch for the `ingest-gmd` route,
  so the memdir set goes to its store's bridge and A's daemon gets only the doc set. In-daemon
  walks (`sync.py:308`, `ingest.py:1354`) that reach a FOREIGN memdir count and name it, and
  bridge only after the lock is released.
- The same-store branch runs the memory drain + index exactly as `--as-memory` does.
- AC-220 runs (a) and (g) with the daemon up AND down, and adds "`rmx memory recall <phrase
  unique to a rerouted memory>` returns it".
- Add an error case: B's daemon is busy or unreachable, and the walk exits non-zero naming it.
- Add `daemon.py` to Files.
**Pattern match:** YES. Prior impressions record lock-held cross-op waits (bug-085) and "kind
proved, recall not proved" (r1 #s5 family on plan-26).

### SKETCHY: the bug-202 restore branch is a full organise apply, out of order, possibly on another project's dir {#s4}

**File:** `task-26.5…:456-466` (R-202b, lead ruling T2-O2)
**What:** "The file is re-bridged … into the store that holds the row, with `rmx memory organise
<memdir> --apply --force-rebridge <id>` … It runs with the deployed `rmx` after this task is
released".
**Why it's sketchy:**
- **It organises the whole dir.** `organise --apply` is the whole migration: backup, every move,
  the marker, index regeneration (AC-3/AC-4). It has no way to re-bridge one file alone. "After
  this task is released" puts it BEFORE 26.8. If the file is in refmatrix's memdir, the restore
  organises the live dir ahead of 26.8's AC-0 snapshot and refresh measurement, and past 26.8
  AC-4's `--apply` go-ahead.
- **It may land in another project's dir.** If the file is in another project's memdir, it
  organises that dir ahead of plan-27 (and 27.5's session-boundary gate, if it is cliquedb). The
  only `guardrail-*` memory files on disk today are in cliquedb's memdir (scoped `find`,
  2026-11-13). My scoped frontmatter search found neither bug-202 id, which agrees with M4.
- **It can write the wrong store.** "Into the store that holds the row" contradicts AC-1: organise
  writes the store the MEMDIR resolves to, never the row's. If the row is in refmatrix's store and
  the file is in another memdir, the restore writes the other store, and the anchor check reads
  whichever store it picks.

The branch is conditional, and R-202c (not found) is the likely path. An unattended goal still
needs a correct "found" branch.
**Fix:**
- R-202b rides the dir's own scheduled apply: 26.8 AC-4 for refmatrix, or that dir's plan-27 task
  otherwise. Its `--force-rebridge <id>` is added to that apply.
- When the memdir's store differs from the row's store, log a bug row (a cross-store row) instead
  of restoring.
- AC-202 reads the anchor set from the store `organise` resolved.
**Pattern match:** NO.
