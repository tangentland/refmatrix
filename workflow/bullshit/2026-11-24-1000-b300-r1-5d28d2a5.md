## Findings {#findings}

### BULLSHIT b-1: the L199 length rule applies only when some block row matched the query {#b-1}

**File:** `src/refmatrix/store.py:5326-5366`
**What:** the code sets `_block_len` (a memory's length = own postings + all its blocks')
only `if _block_rows:`, that is, only when at least one block anywhere in the partition carries
a query concept. Otherwise the credited path keeps `dl = doc_len.get(eid, avgdl)`, the memory's
OWN postings only.
**Why it's bullshit:** L199 (`task-bug300-memory-body-bm25#r1-scope`) defines the document as
"one document per memory, its length the memory's own postings plus all its blocks' postings". The
code comment at `:5357-5362` and GREEN's summary (`#shipped`: "dl = own length + every block's
length") both state that rule without a condition. As built, the length of one memory depends on
whether an unrelated term hits a different memory's body, so the same two memories can swap
places when an unrelated word is added to the query.
**Evidence:** probe p6, a throwaway store with three memories:
- `longone`: tag `quokka`, body ~800 words of filler
- `shortone`: tags `quokka wombat platypus echidna`, body "Tiny."
- `third`: body "The kettle is blue."

`quokka` is on no block, so both quokka memories match through their own postings only.
`content_rank(["quokka"], kinds=["memory"])` returns `longone 2.354, shortone 2.264`.
`content_rank(["quokka","kettle"], kinds=["memory"])` returns `third 0.364, shortone 0.260,
longone 0.040`.

`longone` and `shortone` swap places because of `kettle`, a word neither of them contains. In
the one-term query, the 800-word memory is scored as a 3-posting document. No test covers a
memory that matches only through its own (title or tag) postings. `test_a_memorys_bm25_length_is_its_own_plus_its_blocks`
uses body words, so a block row always exists.
**Fix:** on the credited path, take `_block_len = self._memory_block_doclen(mlid)` whenever
`credit_blocks` is true and `rows or _block_rows` is non-empty. Build `_merged` from `rows` in
that case too, so every tf on the path is a raw tf. Add the p6 shape as a case of the length
test, with the one-term and two-term queries giving the same relative order. The change is about
5 `src` lines plus one parametrize case. The length cache is already cached and already built on
most fused queries.
**Pattern match:** YES. "the default reaches every caller" / "one control point is a census": a
rule applied on one branch of a gate and not on its sibling branch.

### SKETCHY s-1: a forgotten memory's blocks are credited to the next memory of the same name {#s-1}

**File:** `src/refmatrix/store.py:4955-4966` (`_MEMORY_BLOCK_JOIN`) together with
`store.py:2751` (`forget_memory`, bug-302).
**What:** `forget_memory` purges the memory entity and leaves its blocks (bug-302, open). The
name-prefix join then adopts those blocks for ANY later `memory` entity with that name.
**Evidence:** probe p5, all through the real CLI and daemon:
1. ingest GMD memory `s7783_1`, whose body is "Driving to the office through heavy traffic …";
2. `rmx memory forget s7783_1 --yes`, after which `content_rank(["traffic"])` returns `[]`, which
   is correct;
3. `rmx memory add s7783_1 -c "A note about cats and the vet."` creates memory id 140;
4. snapshot, then on a read-only Store `content_rank(["traffic"], kinds=["memory"])` returns
   `s7783_1 3.38` and `["office"]` returns `s7783_1 7.93`. `["cats"]` returns `[]`.

`s7783_1#root` and `s7783_1#office` still carry the old file's path. The new memory is ranked by
a dead memory's body, and its own content is not. Base never read blocks, so this behaviour is
new in bug-300. The store comment at `:4960` ("A block whose prefix names no memory (an orphan …)
joins nothing and so credits nothing") is true only until the name is reused. AC/L199 are met
to the letter, but the "orphans credit nothing" guarantee does not hold across a forget followed
by a re-add.
**Fix:** land bug-302's purge (forget removes every block whose `split_part(name,'#',1)` is the
memory's name) in the same release as bug-300, with one planted forget → re-add case in
`test_context_nl_ref.py`. Otherwise, gate the release note on it. The registry row already names
this fix.
**Pattern match:** NO (new).

### MEH m-1: the length cache can serve a stale dl for up to one flush interval after an ingest or forget {#m-1}

**File:** `src/refmatrix/store.py:4992-5016`, invalidated only by `flush_fragments` (`:4172`).
**What:** the lead asked whether a stale dl can never be served after an ingest or forget. The
answer is that it can, for a bounded window. `ingest_gmd_paths` and `forget_memory` leave dirty
fragments (p5: `dirty_after_ingest=True`, `dirty_after_forget=True`, and the cache is still
present after the forget). The cache drops at the next `flush_fragments`, which the daemon runs
from the periodic tick (`RMX_DAEMON_FLUSH_S`, 30 s) or a transaction exit. In-process, between
the ingest and the flush, `s7782_1` (its body regrown by ~800 words) scored 1.516 with the stale
length and 0.242 after the flush, and it moved from 2nd to 3rd. A new memory id missing from the
cache falls back to `avgdl` (`:5363-5366`), which under-counts a memory whose real length is own
plus blocks.
**Why only MEH:** this is the same contract `_doclen_cache`, `_bm25_stats_cache` and the other
caches already have ("small staleness between ingests is harmless"), and it is bounded at 30 s.
The new cache does not widen the window. The credited path does make the error larger, because
a memory's length is now much greater than `avgdl`.
**Fix (optional):** drop the content_rank caches at the end of the daemon's ingest-gmd and
memory-forget ops, rather than waiting for the tick.
**Pattern match:** NO.

### MEH m-2: `--kinds memory,doc` still misses doc bodies, which have the same shape as bug-300 {#m-2}

**File:** `src/refmatrix/store.py:4962-4966` (`m.kind = 'memory'`).
**What:** the verb's own help says "add 'doc' for ingested .md memory files". A doc's body sits
on its blocks just as a memory's does, and the join credits memories only.
`content_rank(["lighthouse"], kinds=["memory","doc"])` returns `[]` for a doc whose only
`lighthouse` is in `travel-guide#lighthouse`. When no memory matches, the warning fires. When a
memory matches, the doc bodies are missing from the leg and nothing says so. R1 scoped this out,
and M10 pins that docs are not credited, so this is not a defect of the change. It is a gap with
no task behind it.
**Fix:** a bug-registry row, or a one-line follow-up in the bug-300 spec `#follow-up`.
