## Findings {#findings}

### SKETCHY: the verb's own deadline still raises a plain `VerbBusyError`, so most live "budget spent" skips print "daemon busy" {#s1}

**What R18 says.** R18's table: "`verbs.VerbDeadlineError` … raised by `_left`'s deadline
(`cli.py:12622-12628`) and by `recall.replica_memory_recall`'s deadline (`recall.py:1094-1095`)".
The Files row reads "recall.py's replica deadline".

**What the code does:**
- **`recall.py:1094-1095` raises nothing.** It is `except _verbs.VerbBusyError: raise # the
  deadline itself`. The exception it re-raises comes from the `left` callable that
  `verbs.memory_recall` passes in (`left=_left`, `verbs.py:1455`, passed on at `:1244`).
- **The deadline's real raise site is `verbs.memory_recall`'s own `_left`** (`verbs.py:1386-1394`):
  `raise VerbBusyError(f"recall not confirmed within {timeout:g}s — daemon busy; …")`.
- **The verb also re-wraps** any `VerbBusyError` under its deadline as a fresh plain
  `VerbBusyError(...) from e` (`verbs.py:1522-1526`).
- **The recorder then sees only the top error.** `_raw_transport_cause` returns the first NON-verb
  exception in the chain, else the OUTERMOST error (`cli.py:12917-12930`). An inner
  `VerbDeadlineError` under that re-wrap is therefore recorded as the plain wrapper.

**Why:**
- **The CLI's `_left` rarely fires live.** The hook hands the verb `timeout=_left(budget)`, the
  whole remaining budget. So a budget spent in the dense or recent legs is spent INSIDE the verb.
  As specified, the builder edits `cli._left` and `recall.py`, where there is nothing to change,
  and the live budget-spent case keeps printing `daemon busy`.
- **That is the mislabel S1 existed to remove**, now hidden behind a leg, (c), that passes only
  because `--timeout 0` trips the CLI's `_left` first.

**Fix:**
- `verbs.memory_recall`'s `_left` (`:1391`) raises `VerbDeadlineError`.
- The `:1524` re-wrap keeps the subclass: it raises `VerbDeadlineError` when the caught error is
  one, or the deadline branch raises it directly.
- Either the cause function looks for a `VerbDeadlineError` anywhere in the `__cause__` chain, or
  `_raw_transport_cause` returns the most specific `VerbError` when there is no transport cause.
- Correct the Files row: `verbs.py` (`memory_recall._left`, the re-wrap), not `recall.py`.
- Add an AC-28 leg in which the deadline expires INSIDE the verb. For example, a unit leg calls
  `verbs.memory_recall(timeout=ε)` with a real slow leg, or the CLI path runs with `--timeout`
  just above the partition probe's cost. Expect `budget spent`.
- Mutation: "the verb's `_left` raises plain `VerbBusyError`".

### MEH: leg (d)'s expected `daemon busy` depends on two pings fitting the budget {#m1}

- **Where the time goes.** With no reader store, `_memory_intent`'s partition probe pings the
  stopped daemon first: `verbs.memory_partition`, no snapshot → status → `VerbBusyError`
  "no read snapshot yet … busy" (`verbs.py:517-528`), warned. That costs up to
  `min(5.0, budget)`. Then `require_daemon` pings again inside the verb.
- **The race.** If the two pings together reach the budget, `_left` raises first and the recorded
  type is `VerbDeadlineError` (`budget spent`), not `daemon busy`.
- **Leg (b)'s assertion doesn't cover it.** It asserts ONE ping below the budget, and in (b) the
  replica answers the partition probe.
- **Fix:** (d) asserts that the two pings' timeouts sum below the generated command's budget, as
  (b) does for one ping. Alternatively, it accepts the cause its recorded type names.
