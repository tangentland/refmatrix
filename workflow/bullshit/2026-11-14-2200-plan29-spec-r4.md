## New findings (changed sections only) {#findings}

### MEH M1: `--expect` names no phase, and the xfail outcomes are not mapped to pytest's reports {#m1}

**Where:** 29.4 `#r2-list` ("one record per test node and phase"; outcomes `passed`, `failed`,
`error`, `skipped`, `xfailed`, `xpassed`; `--expect '<node id>:<from>-><to>'`), `#ac-3`;
29.5 `#r4-probe`.

**What:**
- **No phase in `--expect`.** The compare is "phase by phase", but `--expect` names only a
  node. For AC-4's probe the change is on the `call` phase only; `setup` and `teardown` stay
  `passed`. The spec does not say which phase `<from>` and `<to>` refer to.
- **Pytest's reports carry no `xfailed` or `xpassed` outcome.** Pytest
  (`_pytest/skipping.py::pytest_runtest_makereport`) reports:
  - an xfail as `outcome == "skipped"` with `wasxfail`;
  - a non-strict xpass as `"passed"` with `wasxfail`;
  - a **strict** xpass as `"failed"`, with longrepr `[XPASS(strict)] …` and no `wasxfail`.

  The hook has to derive the two extra outcomes, and the spec does not say how. AC-3's fixture
  lists "a strict xfail, an xpass" without saying whether that xpass is strict, so a hook that
  reports a strict xpass as `xpassed` could pass AC-3 while losing the failure. That failure is
  what keeps the probe honest after the marker goes.

**Fix:**
- `--expect` takes `<node id>::<phase>:<from>-><to>`, or the spec states "the `call` phase".
- `#r2-list` gives the mapping: skipped + `wasxfail` → `xfailed`; passed + `wasxfail` →
  `xpassed`; a strict xpass stays `failed`.
- AC-3 adds a strict-xpass fixture row that must read `failed`.

### MEH M2: `git log -S` matches substrings {#m2}

**Where:** 29.6 `#r1`; 29.5 `#r8` item 2 and `#ac-8`.

**What:** pickaxe counts occurrences of a substring. When the tool resolves `cli.py:981`, a
commit that added `cli.py:9818` is also a hit. A spec that cites both tokens would then be
resolved at the wrong commit, with nothing to show it. 271 sites over two modules make such
pairs likely.

**Fix:**
- Search with `-G 'cli\.py:981(?![0-9])'` (or `-S`, then keep only commits whose added lines
  hold the token followed by a non-digit).
- Add an AC-8 / AC-3 fixture citing `mod.py:10` and `mod.py:100`.

### MEH M3: nothing checks that a "neutral" edit really is neutral, and `refreshed` now endorses it {#m3}

**Where:** 29.2 `#r7` (the normal form drops annotations outside dataclass, `NamedTuple` and
`TypedDict` bodies; drops docstrings, `TYPE_CHECKING` blocks and `typing` imports);
`#r8-rule` (`refreshed` on `normal` equal).

**What:** a refresh is "proven by `normal`". That proof holds only while no pass module reads, at
run time, what the normal form drops:
- `typing.get_type_hints`, `__annotations__`, `__doc__`;
- `functools.singledispatch` registration by annotation;
- an `attrs` or `pydantic` class;
- `@dataclass` imported under another name (`from dataclasses import dataclass as dc`), which
  the kept-class rule would not recognise.

At `master` none of the seven pass modules does any of these (checked: they import only
`typing` names, and the dataclasses use the plain decorator). There is no guard for later. If
one appears, a behaviour change reads as neutral, and the next rehash `--apply` writes it down as
proven.

**Fix:** the normaliser checks each pass file for those readers and decorators. If it finds one,
it treats the file as not normalisable and hashes its raw bytes under the marker AC-22 already
uses, so every edit reads as real. The `derive-digest` "unknown column stops it" rule is the
precedent. Add an AC-20 row (an aliased `@dataclass`; a `get_type_hints` call) and a mutation.

### MEH M4: rehash rows are never pruned {#m4}

**Where:** 29.2 `#r8-rule` ("A rehash row never prunes a derive row and does not count toward
the per-pass history cap"), `#r7-cost` (rehash `--apply` after every deploy that touches a pass
file).

**What:**
- Each refresh writes one `derive_history` row per stamp per partition per store.
- `_write_derive_history` (`store.py`, `master`) prunes only by its per-pass cap.
- Rehash rows are excluded from that cap and are never pruned.

With a refresh after every pass-file deploy, the rows grow without bound. They are small, but
`derive log` prints them, and every history reader must skip them.

**Fix:** give rehash rows their own per-pass cap, pruned only among rehash rows (for example the
last N per pass). Or state the growth as accepted, with its rate.
