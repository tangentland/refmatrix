## Findings {#findings}

### MEH: `pid_is_rmx` calls an un-signalable live process absent — the one branch that does not take the "refuse the write" direction its docstring promises {#m-1-r3}

**File:** `src/refmatrix/discovery.py:168-170`
**What:** `os.kill(pid, 0)` raising `PermissionError` (the process exists but belongs to another uid) returns `False` → `daemon_status.busy = False` → `_store(write=True)` falls to `_store_rw()`. The same docstring says "A `ps` failure counts as rmx: refusing a write is the safe direction", and `daemon.is_alive` (daemon.py:380) treats `PermissionError` as alive.
**Why it's MEH not more:** unreachable on the shipped topology — `launchctl.py` installs per-user LaunchAgents, so every daemon a CLI can reach runs as the CLI's uid (probe: `pid_is_rmx(1)` → False for launchd, correctly). A root-owned daemon on the same store would also hold DuckDB files the CLI user cannot open. Consistency gap, not a live hole.
**Fix:** treat `PermissionError` as "exists" and fall through to `ps` (which can read a foreign uid's command line) — two lines; add the case to `test_pid_is_rmx_reads_the_process_command_line` via a monkeypatched `os.kill`.
**Pattern match:** NO (first sighting).
