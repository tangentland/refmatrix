## Findings {#findings}

### BULLSHIT B1: 29.5 phase 0b cannot move the three handoff helpers as specified {#b1}

**File:** `task-29.5-split-giant-modules.md` `#r2b`, `#ac-13`, `#r2` item 4.
**What:** Phase 0b moves `_sync_memory_dir`, `_subject_link` and `_subject_upsert` "down" into the
engine. It says "every test unchanged" and "G5 around the commit". AC-13 then requires that
`handoff.py` imports nothing from `refmatrix.cli`.
**Why it's bullshit:** At `f3709d2` these functions are CLI code. Their bodies call names that live
in the CLI and that tests patch on `refmatrix.cli`:
- `_subject_upsert` (`cli.py:1851`) and `_subject_link` (`:1867`) call `_root()`, `_store()` and
  `_memory_daemon_call(...)`, and fall back to an in-process `_store().upsert_subject` /
  `.link_part_of`.
- `_sync_memory_dir` (`:11058`) calls `_resolve_partition` (patched at 6 sites),
  `_memory_partition_default` (patched at 2), `_bridge_stats` and `_ingest_gmd_sync`.
- `_root` is patched at 160 sites. `_memory_daemon_call` is patched in
  `tests/test_mcp_session_pointer.py:251`. 29.5's own R2 item 4 names it as a patched name that
  "does not move".

Moved into `handoff` with no `refmatrix.cli` import, these functions can no longer see those
patches. Every save-state test that patches `cli._root` or `cli._memory_daemon_call` would then run
against the real function. That is the silent-miss case `#fact-patch` exists to prevent. The other
outcome is that the tests must be edited, which 0b forbids. The in-process fallback also needs a
writer the engine does not have yet: 29.2's daemon-absent accessor arrives two tasks later.
"`cli` keeps a name bound to the same object" protects readers of the names. It does nothing for
the patches the moved code has to observe.
**Evidence:** an AST pass over `cli.py` at `f3709d2` for the names each function uses:
`_subject_upsert: ['_memory_daemon_call', '_root', '_store']`, `_subject_link:` the same,
`_sync_memory_dir: ['_bridge_stats', '_bridge_wait_for_active_job', '_ingest_gmd_sync',
'_memory_partition_default', '_resolve_partition', …]`.
29.2's `#needs-295` at `11e9f9f` sees the same cut from the other side: "After the move they
cannot reach the CLI's `_store`; whatever they use instead is typed by the same Protocol or by the
daemon-absent accessor". Neither spec says what that replacement is. 29.5 needs it in phase 0b,
and the accessor does not exist until 29.2 or 29.3(d).
**Fix:** Write 0b as an injection, not a move. The CLI adapter resolves `_root`, the writer and
the daemon call, and hands them to the engine function, so patches on `refmatrix.cli` still apply.
Add AC-3-style probes: for each patched name these three functions use, a save-state run with the
name patched on `refmatrix.cli` calls the patched object. Alternatively, defer the three functions
until 29.2's accessor exists, and give the layering census an allow-list entry with an owner until
then. Either way, state the test impact before RED.
**Pattern match:** YES. This is `imp-unpack-the-carried-result` / sibling-path: the fix covers one
side (readers) and not the other (patchers).

### SKETCHY S1: the dev-tree merge is a lossy store event, and the spec does not pin it down {#s1}

**File:** `task-29.5-split-giant-modules.md` `#r9` items 4-5, `#r4-gates` G6.
**What:** R9 item 4 says: "The lead counts the learned rows on `cli.py` and `store.py` before the
merge and backs up first". It names no backup command or location, no pre/post counts held as an
AC, and no decision about what happens to the rows.
**Why it's sketchy:**
- bug-107 is open. `purge_path` deletes protected grep-learned rows, and `vacuum` then drops their
  evidence. Deleting `cli.py` from a watched tree therefore deletes its learned rows, and
  `git mv` does not carry them to `cli/__init__.py`.
- In `store.py`, rows keyed to lines that moved fail verification (bug-073/074).
- Counting the rows and taking a backup does not keep them. This is knowledge loss on the live
  store, and the spec leaves it to the lead without a decision
  ([[feedback_decay_never_loses_knowledge]]).
- **Ordering.** G6 runs `--merge-gate` after `git merge --no-commit` in the owning checkout. The
  watcher sees the deletion at that moment, before any announced event step. A red G6 followed by
  `merge --abort` brings `cli.py` back and re-ingests it, so the store churns twice.
- The queue review's `plan-review-fable D4` asks for a standing deploy go on the premise of
  releases "none changing hooks or the store on disk". 29.5's merge changes the store on disk.
  29.2 and 29.3 change it too: plan-29 D4 is a write to every store's stamps.
**Fix:**
1. Name the backup: the command, the path, and what is captured.
2. Order the steps: count and back up, then `merge --no-commit`.
3. Count again after the merge, and keep both counts in an AC beside AC-9.
4. Either re-point learned rows through the symbol map, or put the loss to the user as a
   plan-29 D-label.
5. Say what a red G6 does to the store.
6. Tell the lead that `plan-review-fable D4`'s premise does not cover 29.5's release, or 29.2/29.3's.

### SKETCHY S5: the package changes module identity in every `-m refmatrix.cli` process {#s5}

**File:** `task-29.5-split-giant-modules.md` `#fact-argv`, `#r0` item 5, AC-4.
**What:** The spec treats the re-exec as a `sys.path[0]` shadowing question.
**Why it's sketchy:** At `f3709d2`, `python -m refmatrix.cli` runs `cli.py` as `__main__`
(`cli.py` ends with `if __name__ == "__main__": cli_entry()`), and so does every re-exec of it.
Four production spawn sites use that form: `daemon.py:7059`, `scheduler.py:131`, and
`ui/server.py:191` and `:578`. In those processes:
- the commands run in `__main__`;
- `handoff.py:669/699` and `telemetry.py:1011` lazily import `refmatrix.cli`, which is a **second
  copy** with its own module state (`_partition_override`, caches).

After the split, `cli/__main__.py` imports `refmatrix.cli`, so there is one copy. That is a
behaviour change on production spawn paths. The suite cannot see it: tests drive the CLI
in-process as `refmatrix.cli`, so G5 compares two runs that never exercise it. This contradicts the
spec's "no behaviour change" and its non-goal.
**Fix:**
- R0 item 5 inventories module identity in `-m` processes: which state is per-copy today, and who
  reads it across the two copies.
- AC-4 adds a child-process probe: under `-m refmatrix.cli`, a lazily imported `refmatrix.cli` is
  the module running the command.
- The ADR records the unification as an accepted behaviour change, or 29.5 keeps the two-copy
  semantics and says how.
