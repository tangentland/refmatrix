## Answers to the lead's points {#answers}

1. **B2b deviation: correct.** `repair_fragments(id_map=…)` maps every fragment row through
   `remap_fragment`, and A's rows hold A's ids. A bit at a moved id X belongs to A's entity X, so
   mapping A's rows would move A's bit onto B's fresh id. Scoping the kernel to B-only rows is the
   right transform for those rows. The B-only selection is complete for what it selects: it is
   keyed on `(partition_id, linkage)`, which is the fragment row key, so partitions are covered.
   It is **not complete for B's bits in rows A also holds**; those are dropped. See [[#s1]].
2. **Vectors.**
   - **What re-embeds automatically.** Only memories. An `--as-memory` ingest, which includes the
     save-state bridge and the SessionStart catch-up, ends in `drain_memory_vectors`
     (`daemon.py:3781-3797`), and that drains `kind=memory` rows the merge marked unembedded. Docs
     and code have no automatic embed: their window is open until someone runs `rmx embed`.
   - **Is the window reported?** Loudly: in the reply, the daemon log and a yellow CLI line.
   - **Can a dense read return the wrong entity?** Yes. Between the merge and the embed, the Lance
     row at the old id X is whichever slot embedded last, so a dense hit on B's text can return A's
     entity X, and the moved entity cannot be hit at all.
   - **Ruling: MEH, not BULLSHIT.** Replica merge is a rare, operator-run recovery op, the window is
     named with its ids, and memories close it on the next bridge run. The better shape would turn
     the wrong answer into a miss. See [[#m1]].
3. **B1-r2 callers.** One caller (above). `sync._ingest_tldr(s, project_root)` and the other
   non-ingest callers pass their own project root, as before. `ec38f84` (INTEGRATION) is
   **correct** about which root is used. It omits one detail: the store's OWN spec still matches an
   outside file's name (`*.glob` / bare names on `p.name`, `ignore_reason`'s `rel is None` branch).
   This is folded into [[#m3]].
4. **M1-r2 / M2-r2:** closed (table above).

## Findings {#findings}

### SKETCHY S1: a merge drops B's bits from every fragment row A also holds, so moved entities are missing from the bitmaps {#s1}

**File:** `src/refmatrix/replica_merge.py` step 12. The docstring at `:19` and the comment at
`:595` both claim "daemon recomputes fragments on the next flush anyway".

**What:** step 12 inserts all of A's rows, then only B's rows for `(partition, linkage)` pairs that
A lacks. B's bits in every row A also has are discarded. Before the move, a B entity that shared
id X with A's entity happened to be "covered" by A's bit at X. After the move it sits at a fresh
id, and no row carries that id.

Probe `probe_merge_bits.py`: both slots add a doc that mentions `zebrafinch`, so A and B both
carry `(proj, mentions)`.

```
fresh_moved: [[7, 14], [8, 15], [10, 16], [12, 17]]   fragment_bits_remapped: 0
entity_links mentions: ['adoc#root', 'bdoc#root', 'd0#root']
bitmap mentions      : ['adoc#root', 'd0#root']          <- bdoc missing
```

At 758bca1 the same probe gives `['bdoc#root','d0#root']` with `adoc` gone entirely, which was the
old overwrite. The remedy keeps both entities in `entities` and `entity_links`, but a moved entity
is absent from the bitmap of every linkage A also uses. That covers most linkages, `mentions`
included. Bitmap-backed reads (`QueryEngine`, `neighbors`, `load_bitmap`) miss it. Name-losers'
post-divergence links are missing the same way; that part predates bug-216.

The "daemon recomputes" claim does not hold. `_op_replica_merge` only flushes fragments before
the merge. The writer then reopens on the merged slot and loads the table as written. My probe read
it through `Store.load_bitmap` on the merged catalog, which is the same path.

**Why sketchy, not bullshit:** fragments are derived. `repair_fragments` (the union of
`entity_links` and the fragment bits) restores them, and replica merge is a rare operator op.
Still, B2 was ruled "completed here because a partial collision fix is still data loss" (L94), and
this is the part of B2's bitmap item that the B-only test cannot see.

**Fix (small, same kernel):**
- For each B row whose `(partition, linkage)` A also has, OR `remap_fragment(B row, remap_b)` into
  A's row.
- Alternatively, run `repair_fragments(dry_run=False)` with no `id_map` on the merged target. It
  unions `entity_links`, which already holds B's remapped links.
- Correct the docstring at `:19` and the comment at `:595`.
- RED: the probe's shape. The moved doc must be in the shared `mentions` bitmap; it fails at
  bff34c1.

**Pattern match:** YES — `imp-collision-column-census` (r2). Row-level census done, bit-level
census of rows shared by both slots not done.

### MEH M1: between a merge and an embed, a dense read can return A's entity for B's text {#m1}

**File:** `replica_merge.py` (`vectors_updated_at = NULL` on both ids), `daemon.py` `re_embed`.

**What:** see answer 2. The window is reported, and memories close it on the next bridge run; docs
and code wait for a manual `rmx embed`.

**Fix (cheaper and safer):** after a successful non-dry-run merge, the op deletes the Lance rows
of every moved old id and every fresh id (the per-partition `vectors` delete that `purge_entity`
uses). A dense read then misses both entities until the embed instead of returning the wrong one.
Alternatively, submit an `embed` job for those ids from the op.
