### BULLSHIT #b-1: `drain_memory_vectors` says the remainder is COUNTED; the producer can only return 0 or 1 {#b-1}

**File:** `src/refmatrix/ingest_gmd.py:1387-1442` (`drain_memory_vectors`), `:1444-1467` (`render_memory_embed_line`), producer `src/refmatrix/daemon.py:5471`

**What:** bug-065's drain is bounded at 8 × 256. Its docstring states the contract:

> A store that is thousands of vectors behind (a first run, a model switch) is NOT silently re-embedded inside a bridge call: the cap is hit, **the remainder is COUNTED**, and `rmx embed --kinds memory` is named.

and the renderer spends it:

```python
return (f"memory embed capped after {emb.get('batches')} batches: "
        f"{emb.get('embedded')} embedded, {emb.get('remaining')} "
        f"still without vectors — finish with `rmx embed --kinds memory`")
```

**Why it's bullshit:** `remaining` comes from `_op_embed`, which computes it as

```python
remaining = len(d._st().pending_embeddings(kinds=kinds, limit=1))
```

`limit=1` is a SQL `LIMIT 1`, so `remaining ∈ {0, 1}` by construction. It is a boolean wearing a count's clothes. At the cap the operator is told **"2048 embedded, 1 still without vectors"** when the true remainder may be thousands — and "1 left" is exactly the reading that makes someone skip the named command, leaving the rows durable and unreachable, which **is bug-065's harm**.

**Evidence:** proven on a throwaway store (no daemon, `/tmp` root), not inferred:

```
total pending: 5 | len(limit=1): 1
```

The loop logic is fine — it breaks on `remaining == 0`, so the drain itself drains. Only the number the human acts on is wrong.

**Why no test caught it:** `tests/test_save_state_embeds_memories.py:229` feeds a fake
`lambda args: {"embedded": 1, "remaining": 9999}` and asserts `out["remaining"] == 9999` — a value the real producer cannot emit. The fake is the blindfold; this is [[impression_bsd_faked_wire_field]] with the value inverted (the fake supplies a field shape the producer does not have, instead of omitting one it does).

**Fix:** either have `_op_embed` return a real count (`pending_embeddings(kinds=kinds)` length, or a `COUNT(*)`), or stop claiming a count: say "rows remain" without a number. Then re-point the test at the real `_op_embed` over a store with >2048 pending memory rows, or at minimum make the fake's `remaining` a value `_op_embed` can produce.

**Pattern match:** YES — "a counter that cannot move / a number sampled outside its interval", third family sighting.

### BULLSHIT #b-2: the drop-in order fix was applied to `-l`/`-L` and to nothing else {#b-2}

**File:** `src/refmatrix/cli.py:6478-6530` (the `-l`/`-L` block), `:6586-6598` (the plain + `-c` render)

**What:** `35b20c5` ("-F reaches rg, and -l/-L get grep's order and exit status") names the root cause itself:

> ORDER — **the tool emits fan-out/completion order**, so `-l alpha a.txt b.txt` came back `b.txt, a.txt` and `grep -l X *.py | head -1` picked an arbitrary file.

It then sorts by argument rank **inside the `if gf["files_only"] or gf["files_without_match"]:` block only**. Every other render path still emits `res.stdout.splitlines()` in rg's completion order, and the `-c` path builds `counts` from the same parse so it inherits both the order and a second defect.

**Why it's bullshit:** `rmx grep` IS the drop-in for every bare grep on this machine (the `grep-rewrite-guard` PreToolUse rewrite, no escape since `RMXGREP_MODE=plain` was removed). Three contract breaks, measured on the **deployed 0.76.0 build** against `/usr/bin/grep` on the same files:

```
$ rmx grep -n "alpha" b.txt a.txt        $ /usr/bin/grep -n "alpha" b.txt a.txt
a.txt:1:alpha.beta                       b.txt:1:alpha.beta
a.txt:2:alphaXbeta                       a.txt:1:alpha.beta
b.txt:1:alpha.beta                       a.txt:2:alphaXbeta

$ rmx grep -c "alpha" a.txt b.txt c.txt  $ /usr/bin/grep -c "alpha" a.txt b.txt c.txt
b.txt:1                                  a.txt:2
a.txt:2                                  b.txt:1
                                         c.txt:0
```

So `grep -n X f1 f2 | head -1` and `grep -c X *.py` both answer differently through the rewrite than through grep — the same class of consequence the commit message cites for `-l` (`| head -1` picks an arbitrary file), on the paths it did not touch. The zero-count omission is structural: `counts` is derived from `triples`, and a file with no match never appears in the tool's `file:line:text` output at all.

**Evidence:** the live probes above (`/tmp/bsdprobe`, `RMX_LEARN=0`, deployed `rmx`), plus the code: `rendered = [_shaped(f, n, t) for f, n, t in triples]` and `counts[f] = counts.get(f, 0) + 1` with no `rank` sort anywhere outside the `-l`/`-L` block.

**Fix:** lift the existing `rank`/`_rank` sort out of the `-l`/`-L` block and apply it to `triples` before rendering (one move, the comparator already exists); and for `shape["count"]`, seed `counts` with `0` for every named file path so the zero rows appear, in argument order. The docstring of `_resolve_output_shape` should gain the zero-count rule it currently omits.

**Pattern match:** YES — 5th sighting of [[impression_bsd_quoted_line_sibling]] (fix at the quoted line, sibling keeps the bug), and the diagnosis in the commit body is *general* while the patch is *local*. See [[#pattern-note]].

### SKETCHY #s-2: three of four new `daemon.call` sites pass `retries=0`; the omitted one is the only write {#s-2}

**File:** `src/refmatrix/cli.py:10036` (`_stamp_derive_pass`), siblings at `:6779`, `:3472`, `:10060`

**What:** the range adds four `daemon_mod.call` sites. Three are reads and all three pass `retries=0`:

```
derive_history  timeout=5.0, retries=0
derive_status   timeout=5.0, retries=0
derive_status   timeout=10.0, retries=0
derive_stamp    timeout=30.0            <- the write
```

**Why it's sketchy:** `daemon.call`'s default is `retries=2`, and it retries on `TimeoutError` — re-sending the request. `derive_stamp` is **not idempotent**: `Store.stamp_derive` upserts the stamp *and* appends a `derive_history` row (`_write_derive_history`) in the same transaction. A client-side 30 s timeout on a write the daemon actually completed therefore writes 2-3 history rows for one derive. `derive_stamp` is not in `CLI_OPS`, so it lands on `bg_pool` behind any in-flight ingest and must take `_store_lock` — a 30 s timeout there is likely, not hypothetical. The corrupted rows are exactly what `rmx derive diff` ("what the last derive changed") reads, and they render as *"no change from the previous derive"*. The worst case is also a 90 s stall after `rmx embed`/`rmx sessions ingest` has already printed `done`, which is what [[feedback_daemon_call_retries_multiply_timeouts]] exists to stop.

**Evidence:** `daemon.call(root, op, args=None, timeout=60.0, retries=2, …)`; `stamp_derive` → `_write_derive_history` inside the stamp's transaction; `CLI_OPS` lists `derive_status` and `derive_history` and not `derive_stamp`.

**Fix:** `retries=0` on the stamp call (the stamp is a record — losing it is already handled loudly by `_stamp_derive_pass`'s own `except`, which is the whole point of that function), or make `_write_derive_history` dedupe on `(partition, pass, version, code_hash)` within a short window.
