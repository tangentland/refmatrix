## Findings {#findings}

### SKETCHY S1: `build.py`'s guard and AC-13 check the slug resolver, but under 23.0's sandbox the bridge writes to `REFMATRIX_ROOT` {#s1}

**File:** G22 R4 "The order inside `build.py`" and AC-13. Code: `cli._root()` (`cli.py:90-113`) and `discovery.discover_roots()` (`discovery.py:108-133`). Spec: `task-23.0-test-sandbox.md:46`, `:62`.

**What:** at HEAD the bridge (`ingest-gmd --as-memory`, through `_store()` → `_root()`) picks its store in this order:
1. `REFMATRIX_ROOT` wins;
2. else a `~/.claude/projects/<slug>` CWD (`_root_from_projects_slug(cwd)`);
3. else the cwd walk.

The slug is read from the CWD, not from the memdir argument. Task 23.0 R2 sets `REFMATRIX_ROOT` per test with an autouse fixture.

So in AC-13 the bridge writes `REFMATRIX_ROOT`'s store, whatever the copy's slug. The mutation "assert AFTER the bridge runs: FAILS (Z's `facts.log` changes)" cannot fail, because Z is never the write target. The guard then checks a resolver the write path does not use. The same holds for any `build.py` run that sets `REFMATRIX_ROOT`, or that runs the bridge with its cwd inside W.

The guard is still meaningful once the write path matches it. `discover_roots` unions the real launchd-supervised roots (`_roots_from_launchd()`), so a copy that keeps the live slug does resolve to the LIVE store, and the guard catches that.

**Fix:**
- R4 names the bridge invocation: run with `cwd` = that build's memdir copy and `REFMATRIX_ROOT` UNSET, so `cli._root()` resolves through the same `_root_from_projects_slug` the guard asserts. An alternative is ADR-0005's memdir-argument resolution, once 26.5 ships it, named as such.
- W and N must be discoverable for that resolution, for example registered in the sandbox registry by `rmx init`. State this.
- AC-13 unsets `REFMATRIX_ROOT` for the bridge subprocess (as an explicit override of 23.0's autouse value, stated).
- AC-13's positive leg also asserts that W GAINED the copy's memory rows, which proves the write went where the guard resolved.
- The mutation then fails as specified.

**Pattern match:** YES (`feedback_clean_corpus_hides_a_dead_gate`): the gate is proven against a path the write never takes.

### MEH M1: AC-6's on-disk leg edits a COPY of the module tree, but the rebuild runs the imported predicate {#m1}

**File:** G22 AC-6 "On-disk adjacency (r4 M1, r5 M2)".

**What:** editing `is_operational`'s prefix list in the `_DERIVE_SRC_DIR` copy moves `derive_code_hash`, so the stale file is not served. That part is sound. But the rebuild calls the IMPORTED `memory_layout.is_operational`, which is unchanged, so "the rebuilt adjacency excludes the new name" does not hold. The mutation's "the new member is a node" detection relies on that clause.

**Fix:** either:
- also apply the same prefix to the live predicate (monkeypatch `memory_layout`'s prefix tuple, a dependency of `cached_adjacency`, registered in `workflow/test_mock_registry.md`); or
- assert only that the file is rebuilt and rewritten under a new key (the mutation: the old file's mtime and contents are unchanged).
