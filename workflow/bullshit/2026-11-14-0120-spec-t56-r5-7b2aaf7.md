## Findings {#findings}

### SKETCHY S1: the live-store guard in `build.py` has no AC, and its order is not pinned {#s1}

**File:** G22 R4 recipe (`:174-180`, "On a mis-slugged copy it exits non-zero BEFORE any write"), Files `eval/dq1/build.py`, and the AC list (no AC tests it). L67 S1 required "(AC)".

**What:** this guard is the only thing between the W/N build and a bridge write to the live project store (ADR-0005 resolves by slug). No test shows that `build.py` FAILS on a mis-slugged copy (`feedback_clean_corpus_hides_a_dead_gate`).

"Prints the resolved store root of every bridge run" reads as a report of what the bridge did. To exit BEFORE any write, `build.py` must resolve the slug itself, through the bridge's own resolver (`_root_from_projects_slug`, ADR-0005 `#store-resolution`), before it calls the bridge. The spec does not say so.

**Fix:**
- R4 states the order: resolve with the bridge's resolver, assert the result equals W's or N's `.refmatrix/` root, and only then run the bridge.
- Add an AC in `tests/test_dq1_measure.py` or a `test_dq1_build.py`. A sandbox memdir copy under a slug that decodes to a DIFFERENT existing store root makes `build.py` exit non-zero, and that root's catalog and `facts.log` are byte-identical afterwards.
- Mutation: "assert after the bridge run" (the other root's store gains rows).

### MEH M1: the USEFUL `rel:` channel can report false defects {#m1}

**File:** G22 R4 USEFUL `rel:` bullet; code `cli.py:5250-5259` (`--limit` default 50), `graphread.neighbors_payload` (`entities` = the first `limit` of `list(bm)`, in ascending id order).

**What:** two cases make a working edge look like a miss:
- **Truncation.** `rmx neighbors <S>` lists only the first 50 neighbours by entity id. A source node with more than 50 outbound links (for example an index doc's `#root` with many `rel:` lines) can push a later-ingested `workflow/` target past the cut.
- **No concept to resolve.** `QueryEngine.neighbors` resolves `S` through `resolve_concept_ids` (kind `concept` only). A `rel:` line whose enclosing block is the synthetic root has no anchored concept, so `S` resolves to nothing.

Either case is a "`rel:` miss", which R4 sends straight to the user as a defect, with no re-tune. So the gate can report a defect that is only an artefact of how it measures.

**Fix:**
- The query is `rmx neighbors <S> --linkage <verb> --limit <cardinality>`, or membership is tested on the full walk.
- The draw samples only edges whose `S` is an anchored `{#…}` concept, and records the verb.

### MEH M2: `OPERATIONAL_RULES_VERSION` is bumped by hand {#m2}

**File:** G22 R1 ("a constant … that changes whenever `is_operational`'s rules change"), AC-6.

**What:** a hand-bumped constant drifts. Edit the prefixes without bumping it, and every on-disk adjacency keeps serving the old rules. AC-6 tests only that a DIFFERENT version is rebuilt; it never tests that a rules change produces a different version. Meanwhile AC-4 already gets the same freshness from the module's code hash (`_DERIVE_PASS_MODULES` → `behind_code`).

**Fix (`feedback_converge_repeated_shapes`):** pick one of these.
- Key the adjacency caches on the same code identity the derive staleness uses (the `pagerank` pass's module hash, which includes `memory_layout.py`).
- Keep the constant, plus a test that pins `(OPERATIONAL_RULES_VERSION, hash of is_operational's source)`, so a rules edit without a bump fails the suite.
