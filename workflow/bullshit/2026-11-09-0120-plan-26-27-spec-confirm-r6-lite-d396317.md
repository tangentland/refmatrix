## Findings {#findings}

### MEH: AC-1b's "ONE store write" has no write primitive at HEAD, and the legacy refresh must be logged {#n1}

**File:** `task-26.2` AC-1b.
**What:** The id row and the legacy rows are to be refreshed "in ONE store write per file".
**Why:**
- `Store.add_memory` ends with an unconditional `con.commit()` (`store.py:2506`), not
  `_maybe_commit`. So it would end an outer `store.transaction()` early (see the
  `_maybe_commit` docstring).
- The bridge opens no `transaction()` at all.
- An UPDATE on the legacy rows' `memory_content.metadata` emits no facts.log event. Replay
  (`_apply_one_event` `memory_content`, `store.py:7879`) would then restore the old path on
  `rebuild --from-log`.

**Fix (implementation note):**
- Wrap the id-row `add_memory` and the legacy UPDATE in `store.transaction()`, and switch
  `add_memory`'s commit to `_maybe_commit`. A dedicated store method that does both also works.
- Log each legacy row's refresh as a `memory_content` event carrying the updated metadata.
- Add a test assertion: after the AC-1b fixture, a log replay into a fresh store gives
  `legacy-x` the new path.

**Pattern match:** YES. These are unlogged write paths, as in the facts.log audit
(`project_factslog_audit_verdict`).

### MEH: where `moved_legacy` sits in the arithmetic is stated two ways, and it is counted only beside a `moved` id row {#n2}

**File:** `task-26.2` AC-3; `task-26.5` AC-8; `task-26.2` `#impl-notes-r5`.
**What and why:**
- 26.5 AC-8 says `refresh_pending` "includes the `moved_legacy` term".
- 26.2 AC-3's pre-registered formula still has three terms. Its stats bullet calls
  `moved_legacy` a separate row count.
- AC-1b refreshes every row on the old path of any moved file. But it COUNTS extra rows only
  "for each file whose id row would be refreshed as `moved`". Under m3 precedence, a moved file
  whose id row is in symlink form is `stale_before`, so its legacy rows would be refreshed but
  counted nowhere.
- refmatrix has 0 such rows (probe), so 26.8 is unaffected. Plan-27 includes a symlinked memdir
  (viascope), where this could occur.

**Fix (implementation note):**
- `moved_legacy` counts the extra rows refreshed alongside ANY id row whose file moved,
  whatever term the id row lands in.
- 26.2's `refresh_pending` = the three file terms + `moved_legacy`. Print each term on its own
  line.
