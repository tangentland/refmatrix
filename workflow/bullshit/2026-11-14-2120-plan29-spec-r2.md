## A correction to r1 first {#r1-correction}

r1 `#s2` said 29.5's change to `_DERIVE_CODE_MODULES` was "a fleet-wide `behind_code` flip",
because `derive_pass_modules` returns the union for unmapped passes and for the no-argument caller
(`store.py:7601`). The mechanism is real. The inference was not checked, and it is wrong for every
stamp the current code writes:

- **Every stamp site writes a mapped pass name.** `ingest.py:433` writes `ingest`/`semantic`;
  `ingest_gmd.py:1981` writes `gmd`; `daemon.py:6699` writes `pagerank`; `cli.py:11660` writes
  `embed`; `cli.py:14439/14455/14480` write `sessions`; `consolidate.py:873` writes the two
  compile scopes. All of these are keys of `_DERIVE_PASS_MODULES`.
- **No stamp is compared against the union.** `derive_status` compares each stamp with
  `derive_code_hash(r["pass_name"])` (`store.py:7675-7676`). The no-argument hash at `:7601` is
  only copied into the output field `code_hash`, which only `cli.py:7562` prints.
- **The suite already pins this:** `tests/test_derive_pass_identity.py::test_editing_store_py_does_not_make_any_pass_stale`.

So moving `Store` methods into `store_*.py` files, and extending `_DERIVE_CODE_MODULES`, flips
nothing, unless a fleet store holds a legacy stamp under a pass name no longer mapped. Only R0
item 8 can count those. L106 and L107 built 29.5's user-gated fleet re-stamp on r1's claim. See
[[#ns1]]. {#r1-correction-body}

## New findings {#findings}

### BULLSHIT NB1: 29.5's one-copy probe is RED at base, so the task's own gates cannot pass {#nb1}

**File:** `task-29.5-split-giant-modules.md` `#ac-4`, `#r4-baseline`, G5, `#test-strategy`.

**What:** AC-4's new one-copy probe "is **RED at base** (two copies) and green from the rename
commit on". Phase 0 commits the tests before any move.

**Why it's bullshit:** the task's own gates forbid the state it mandates.
1. `#r4-baseline`: "A phase does not start on a suite that is not clean." Phase 0 leaves one
   failing test in the suite, so phase 1 cannot start.
2. At the rename commit, G5 runs `--compare` against the parent. 29.4 `#r2` makes that exit 0
   only on equal (node id, phase, E line) sets. The parent has the probe's failure and the
   commit does not, so G5 is red on the one commit meant to turn it green.
3. The move-commit rule allows test edits only in source-reader-inventory files, so the probe
   cannot be added in the rename commit instead.
4. The test strategy also says AC-4's process tests "pass before the split", which contradicts
   AC-4's own "RED at base".

This is r1's `imp-gate-vs-own-mandate` again: the gate gets bent by whoever meets it first.

**Fix:** pick one path and state it in AC-4, `#r4-baseline`, G5 and the test strategy.
- Record the probe's RED in phase 0 on a throwaway branch, logged. Commit the probe in the rename
  commit as a named exception to the "tests do not change in a move commit" rule, and let G5
  accept exactly that node id appearing as a pass.
- Or commit it `xfail(strict=True)` in phase 0, and remove the marker in the rename commit as the
  one allowed test edit. Strict means an unexpected pass fails the run.

### BULLSHIT NB2: the re-stamps have no safe mechanism, and the one named would falsify history {#nb2}

**Files:** `task-29.5-split-giant-modules.md` `#r9-restamp` step 3 ("re-stamp through the existing
derive-stamp path (R0 item 8 names the command)"), `#ac-17`; `task-29.2-mypy-gate.md` `#r7` ("this
release carries its own announced, user-gated re-stamp under the new tag … the lead runs both").

**What exists:**
- No CLI command stamps without deriving. The `derive` group has `log`, `diff`, `unstamp`,
  `status` (`cli.py:7496-7665`).
- The only path is the daemon op `derive_stamp` (`daemon.py:4715`). It passes `pass_name`,
  `partition` and `duration_s` to `Store.stamp_derive` (`store.py:7358`).
- `stamp_derive` with no `version`, `at` or `code_hash` writes the running version and `now`, and
  appends a `derive_history` row "in the same transaction … a stamp claiming a derive the history
  did not record would make the pair disagree".

**Why it's bullshit:** a re-stamp through that path, on every fleet store:
1. overwrites `version` and `derived_at`, which erases `stale` ("which version built this");
2. writes a history row for a derive that never ran;
3. marks every pass fresh **whether or not its old stamp was behind**. A fleet store whose `p1`
   stamp was really `behind_code` at R7's release (ingest code changed, store not re-derived)
   reads clean afterwards.

This is a knowledge-losing write to every live store, gated by the user, with the mechanism left
for the lead to improvise.

**Fix:** specify a rehash op in 29.2 R7, as its own requirement, with RED tests and mutations. A
daemon op, `derive_rehash` or similar, that for each stamp:
- computes the **old** scheme's hash of the current files;
- writes the new-scheme hash **only if** the stored hash equals that old hash, keeping `version`
  and `derived_at`;
- leaves a stamp that does not match untouched (it really is behind or unknown);
- records a history row marked `rehash`, not a derive.

The re-stamp steps then name that op, its CLI, and its per-store output (counts rehashed / left).
For 29.5, see [[#ns1]]: it needs no re-stamp unless R0 item 8 finds a stamp under an unmapped
pass name.

### SKETCHY NS2: R7's normal form erases dataclass fields {#ns2}

**File:** `task-29.2-mypy-gate.md` `#r7` ("an annotated assignment with a value becomes a plain
assignment; one with no value is removed"), AC-20 ("a variable annotated → equal").

**Why it's sketchy:** in a `@dataclass` body the annotation **is** the field. The pass modules
hold six dataclasses: `ingest_gmd.py:196` `GmdNode`, `:210` `GmdDoc`, `:587`, `:965`, `:1144`;
`session_ingest.py:32` `SessionData`. Under R7:
- adding or removing a required field (`imports: list[str]`) leaves the hash equal;
- `x = 5` → `x: int = 5` turns a class attribute into an `__init__` parameter, a behaviour change,
  and also leaves it equal.

A real change to what a pass builds would read as no change.

**Fix:**
- Keep annotated assignments, as statements, inside class bodies decorated `@dataclass`
  (`dataclasses.dataclass`) or deriving from `NamedTuple`/`TypedDict`.
- Add AC-20 rows: a dataclass field added must differ; a class-level `x = v` annotated must
  differ; a function-local annotation stays equal.
- Add a mutation: drop the dataclass exception.
