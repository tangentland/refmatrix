## Findings {#findings}

### SKETCHY: the waits in (k), (g2) and the job-id assertions are unbounded; one named mutation deadlocks {#u1}

**File:** `task-26.5…:606-608`, `:660-666`, `:685-686`
**What:**
- AC-220: "the test waits for the dispatched job ids through `ingest_gmd_status` before
  asserting". No deadline is stated.
- (k) B up: "B's job is held at its start by a test-only gate … A's op returns … while B's job
  is still gated. Once the gate opens, the rows appear in B". The mutation "waiting on B's
  ingest (a synchronous `ingest_gmd` call, status polling, or `_bridge_wait_for_active_job`)
  kills (k)'s B-up leg".
**Why it's sketchy:** the lead's check (3) requires bounded waits. Under that mutation, A's op
waits for B's job, B's job waits for the gate, and the gate opens only after A's op returns. That
is a deadlock.
- The synchronous call it reintroduces carries `timeout=24 * 3600.0` (`cli.py:10695` at
  `4b4b96e`).
- The test's own call to A defaults to 60 s (`daemon.call`, `daemon.py:635`).
- A daemon stop drains `bg_pool` (`daemon.py` start-op comment: "a clean `rmx daemon stop` still
  waits for in-flight ingest"), so teardown can hang too.

So the mutation hangs instead of failing ([[feedback_mutation_must_fail_not_hang]]). (g2)'s and
(k)'s "B busy" legs hold a job the same way.

Where the gate lives is also unstated. A monkeypatched gate needs B to serve in the test process
(a threaded `serve_forever`). A subprocess B could only be gated by a `src/` env-flag hook, which
CLAUDE.md `#no-mocks` forbids.
**Fix:** state, in AC-220:
- every call from the test to A has a timeout ≤ 10 s, and (k)'s B-up assertion is "A's op returned
  within that bound while B's job is still gated";
- every job-id wait has a deadline (e.g. 30 s) and fails with the job's last status;
- the gate auto-releases at its own deadline and in `finally`, and teardown kills daemons that do
  not stop within a bound;
- B (and the gate) run in the test process with a threaded `serve_forever`, and the gate is a
  registered test-side monkeypatch of B's job body, never a `src/` flag.
**Pattern match:** YES ([[feedback_mutation_must_fail_not_hang]]).

### SKETCHY: the `ingest_path` route collects rerouted files but has no dispatcher, so they vanish uncounted {#u2}

**File:** `task-26.5…:222-225`, `:538-540`; `src/refmatrix/ingest.py:1350-1368` at `4b4b96e`
**What:**
- The dispatchers are listed as "the `ingest_gmd` op body, the detached `ingest_gmd_start` job,
  and the sync/watcher op".
- Files: "Modify `sync.py` / `ingest.py` only to pass the `rerouted` result up".
- `ingest.py:1354` calls `ingest_gmd_paths(s, gmd_paths, lenient=True, project_root=root)` inside
  `_ingest_path_inner`. That is the body of `rmx ingest`, `_op_ingest_path` (`daemon.py:3605`) and
  `_op_ingest_path_start`, and it returns an `int`.
**Why it's sketchy:** on that route, R-220b takes the memdir files out of the doc set, and no named
dispatcher receives the `rerouted` groups. A memdir the project walk reaches (exactly the (i)
fixture's shape) is never bridged and never counted. That is a silent loss on a memory path
(CLAUDE.md `#no-silent-failures`).

The same block also has a pre-existing fallback. When `ingest_gmd_paths` raises, it runs
`except Exception:` → `s.upsert_entity(kind="doc", …)` for EVERY GMD path, with a bare
`except: pass` per file (`:1356-1368`). That mints exactly the `kind=doc` twin R-220b says "no
caller flag can mint", and a raise also loses the collected `rerouted` groups.
**Fix:**
- Name the `ingest_path` routes as dispatchers: `_op_ingest_path`, the `ingest_path_start` job
  runner, and the CLI's in-process `rmx ingest`. Plumb `rerouted` out of `_ingest_path_inner`.
- Say that "the sync op" means `_op_sync_files`, `_op_sync_since` and the watcher flush.
- The fallback skips memdir files (via `memdir_of`) and counts its own per-file failures.
- Add an (i) leg through `ingest_path` with the mutation "the ingest_path route drops `rerouted`".
**Pattern match:** YES ("a route the spec did not enumerate", bug-216 R2's walker enumeration).

### MEH: on the detached route, the reroute result lands after the job reads `done` {#v1}

**File:** `task-26.5…:219-224`, `:534-536`
**What:** the dispatch runs "after `d._store_lock` is released and the job record is closed"
(needed so the same-store start passes the single-active guard). On `--detach` / `--progress`,
`ingest_gmd_status` reports `done` before the dispatch counts and job ids are written. The
`--progress` client exits without them, while R-220d says the CLI prints them.
**Fix:** a `dispatch: pending|done` field on the record, with `--progress` / `ingest-status`
reporting the counts only once dispatch is done. Or write the dispatch result before the flip,
with the guard exempting that job's own dispatch.

### MEH: "connect timeout ≤ 2 s" is a whole-call timeout, and a slow reply reads as a failure {#v2}

**File:** `task-26.5…:552-555`
**What:** `daemon.call` has one `timeout` for connect AND reply (`s.settimeout(timeout)`,
`_recv_line(s, timeout)`), and it never retries after the send (`daemon.py:657-675`). B's start
op runs `collect_gmd_files` and `_register_ingest_job` before replying (`daemon.py:3881-3913`).
If that reply takes over 2 s on a loaded B, A reports `rerouted_failed` while B's job is in fact
running. The report would then be wrong.
**Fix:** count a timeout after the send as `rerouted_unconfirmed` (named, "job may be running on
B"). Or split a ≤ 2 s connect bound from a longer reply bound.

### MEH: the cross-store start does not name B's memory partition {#v3}

**File:** `task-26.5…:552-559`
**What:** `_op_ingest_gmd_start` lands `as_memory` rows in `args["partition"]`, else in the
daemon's bound (code) partition. The CLI's own comment says "without this, ingested memories are
orphaned". R-220c's start args list `as_memory=True` only. (g)'s recall-in-B leg would catch it.
**Fix:** "with `partition` = B's memory partition from the resolved root's own default (AC-1)".
