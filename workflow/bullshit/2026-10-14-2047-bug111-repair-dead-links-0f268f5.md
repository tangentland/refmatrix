## Findings {#findings}

### BULLSHIT: the orphan `entity_links` rows are deferred to a plan with no task for them {#b-1}

**File:** `src/refmatrix/store.py:4384-4388`, summary `#fix` + `#live`
**What:** "The row itself is left alone (its removal is an audited removal, not a fragment repair)";
"removing it is an audited removal (plan 22)"; "The 5,298 + 8 orphan `entity_links` rows stay until
an audited removal."
**Why it's bullshit:** Rule 9a. Plan 22 is `drafting`. None of its four task specs
(`workflow/plans/plan-22-audited-removal-and-repair-tasks/task-22.{1..4}`) names an `entity_links` row
with a dead endpoint. Its classes are path, alias and learned-row classes (`orphan-root`,
`orphan-alias`, `empty-learned`, `stale-line`, ...). No acceptance criterion closes this gap. The rows
are not inert either. `scan.py:175` counts them into a concept's `deg`. On the cliquedb copy,
`feedback` carries 21 dead rows out of 297 and `testing` 13 of 129. Also, only the 8 dead-concept rows
are visible in a counter. The 5,298 dead-entity rows sit inside `links_skipped`, mixed with unknown-linkage
skips.
**Failure scenario:** plan 22 ships as specified and all 5,306 rows survive it. The summary's "stay
until an audited removal" then has no end.
**Fix:** add a `dangling-link` class (entity OR concept absent from both tables) to task 22.1/22.2
with an AC and the cliquedb counts. Alternatively, remove the rows now behind the manifest the repair already writes. Either
way, give dead-entity rows their own counter (`links_dead_entity`) instead of `links_skipped`.
**Pattern match:** YES. Unanchored deferral, same shape as bsd-0661 #stale-deferrals.

### SKETCHY: `purge_entity`, the path the fix routes to, leaves dead-concept bits in other partitions {#s-1}

**File:** `src/refmatrix/store.py:6060-6071` (also `_bulk_purge_ids` `:6355-6375`)
**What:** The summary says orphans "come from deletes that bypass `purge_entity`."
**Why it's sketchy:** the concept-side clear loads only the BOUND partition's fragments (`_load_fragment`).
`DELETE FROM entity_links WHERE concept_id=?` is global. probe1 (`bug111-bsd-probe1.log`): doc D is in
partition `mem`, entity E is in the default partition, and E part-of D. After `purge_entity(D)` under
`mem`, the default partition still holds the bit, and the repair dry run reports `dropped_dead_concept=1,
links_dead_concept=0`.
**Failure scenario:** an as-memory replace (or forget) purges a doc that some entity in another partition links to. The next
cliquedb dry run reads `dropped_dead_concept=1`, which is bug-111's exact symptom. That contradicts the
summary's `#live` promise of `dropped_dead_concept=0`, and it sends the operator hunting a
"writer" again. Cross-partition links are rare (1 on the refmatrix copy), but they exist.
**Fix:** clear the concept prefix in every partition's fragments in both purge paths, the way
`repair_fragments` reads every row. Add a cross-partition purge test.
**Pattern match:** YES. bug-105 class (partition-scoped cache vs global table).
