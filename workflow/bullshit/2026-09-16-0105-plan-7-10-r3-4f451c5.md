### 2. Two `_read_with_fallback` calls per `brief` op — acceptable, with one caveat {#attack-2}

Yes, worth paying. `_open_read_store` resolves mirror → snapshot file → writer slot, and the mirror
is zero file I/O (~1 ms), so the second call costs about a millisecond in steady state. Measured on
a real daemon with real briefs, `memory brief --json` returns promptly with the full names map.

The caveat is the branch you did not ask about: `_read_with_fallback` falls through to
`with d._store_lock, d._st().with_partition(part)` when `_open_read_store` returns `None`, which is
the pre-first-snapshot bootstrap window. In that window the op now takes the writer lock **twice**,
and that is exactly the multi-second window plan-4 and plan-5 spent five rounds on
(`{#imp-boot-window-is-busy}`). The one-line removal of the question: compute the names inside the
SAME closure as `compile_briefs` —
```python
result, names = _read_with_fallback(d, part, lambda s: (
    brief_mod.compile_briefs(s, **kw), _names_for(s, <ids from that result>)))
```
— one read store, one lock acquisition, and the two halves cannot see different snapshots (today
they can: the replica may swap between the calls, so an evidence id can resolve against a newer
catalog than the brief was derived from).

**Why no test caught it, precisely:**

- `test_the_gmd_flag_does_not_crash_through_a_real_daemon` asserts `returncode == 0` and no
  `AttributeError`.

Between the three, nothing checks the bytes a user receives. The fake omits the exact field the r2
fix added; that is what made the defect invisible at the moment it became reachable.
