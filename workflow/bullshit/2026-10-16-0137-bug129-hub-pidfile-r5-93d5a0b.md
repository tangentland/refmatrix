### SKETCHY s1-r5: the never-fork AST guard is evaded by an alias or getattr (third guard-evasion in this arc) {#s1-r5-guard-evaded}

**File:** `tests/test_bug129_hub_pidfile.py` `test_the_hub_process_never_forks_a_daemon`.
**Evidence:** `bsd-bug129-r5-mutations.log`. M1 (bus reverted to `spawn_daemon`) and M2 (ui
reverted) both fail the test, as claimed. Two mutations survive with 16/16 passing, although
both are a real fork of a daemon from inside the hub:
- M3: `_sd = daemon_mod.spawn_daemon; _sd(root)` in `ui/server.py`;
- M5: `getattr(daemon_mod, 'spawn_' + 'daemon')(root)`.

The guard matches only `Call` nodes whose callee is named `spawn_daemon`. r1 s2 (the alias,
`os.unlink` and `hub_home()` evasions) and r2 (the `ImportFrom` alias) were the same weakness on
the earlier guards.
**Fix:** test the behaviour instead of the spelling:
- monkeypatch `os.fork` to raise;
- drive `POST /api/daemon` through a `TestClient` and `Bus._write_memory` (project scope) against
  a short-tmp store;
- assert that a daemon came up.

A cheaper fallback is to flag any `Attribute`/`Name` reference to `spawn_daemon` plus any
`ImportFrom` of it in hub-side files. That catches M3 but not M5.
**Pattern match:** YES. Third occurrence in bug-129 (r1 s2 SKETCHY, r2 MEH, now this), so it is
escalated from MEH.

### MEH m1-r5: a failed UI or refine start now costs a fixed 30 s on the event loop, its cause is discarded, and `rmx refine accept` times out first {#m1-r5-failure-path}

**File:** `src/refmatrix/ui/server.py` `daemon_ctl` (`async def`), `:503` `refine_accept`
(`async def`), and `src/refmatrix/daemon.py` `spawn_daemon_subprocess`.
**Evidence:** `bsd-bug129-r5-probe-head.log`.
- `POST /api/daemon` for a root with no store returned after **30.3 s** with
  `RuntimeError: subprocess daemon did not start … within 30s`.
- A concurrent `GET /api/health` on the same server took **29.4 s**, so the whole web UI froze.
- `rmx daemon start` exited non-zero at once with "no refmatrix at … Run `rmx init` first". That
  message goes to `DEVNULL`, and the function then polls a full 30 s for a child that was never
  forked.
- Through the CLI, `refine_accept` → `hub.rpc(timeout=30.0)` expires before the hub answers. The
  result is an uncaught socket timeout that ends the batch, which is exactly what the
  `cli.py:2270` comment says must not happen.

Base already blocked the loop for up to 15 s on a failed fork-start, so this is mostly
pre-existing. The new path doubles that time and drops the cause.
**Fix:**
- make both handlers plain `def`, which FastAPI runs in its threadpool;
- in `spawn_daemon_subprocess`, fail fast when the launcher's rc is non-zero and ping is down;
- capture the launcher's stderr into the RuntimeError so the caller sees the real cause.
