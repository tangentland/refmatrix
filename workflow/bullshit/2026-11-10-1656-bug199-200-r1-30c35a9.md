## Findings {#findings}

### SKETCHY: a drop overwrites a hand-written hook on the affected line {#s-1}

**File:** `src/refmatrix/memory_index.py:1056-1064` (`_repaired_index`)
**What:** Every line whose key changed gets `side.get(rel) or side.get(mid) or derived`, whatever
the line says now.
**Why it's sketchy:** Probe B1 (flat dir) went like this:
1. The sidecar held the derived cut, and `write` rendered it.
2. The user then edited the line to `MY OWN HAND-WRITTEN HOOK`.
3. The repair ran `--apply`.

At `fb0f35e` the hand edit survives the apply and the next `write`, because a non-prefix index
hook wins in `_index_hook_wins`. On the branch the apply replaces it with the derived prose. The
loss is printed only as `rewrite MEMORY.md line …`, and the hand edit is kept only in the backup.
This regresses master, which keeps the edit. It also contradicts the function's own docstring,
which rejects a whole re-render because it would lose hand edits, yet does the same thing on the
affected line. The tests cover a hand edit on an *unaffected* line only. A restore over a hand
edit (B2) also overwrites it. That is explicit operator intent, but it is printed the same way.
**Evidence:** `scratchpad/probeB.py`: base `B1 after write: MY OWN HAND-WRITTEN HOOK`; branch
`B1 repair … line now: Fix one condition in a gate and then check every sibling condition too.`
**Fix:**
- Rewrite an affected line only when its current hook is what the old value renders to:
  `_with_hook(link_part, old_cur) or link_part == body`, with `old_cur` taken from `data` the same
  way the new hook is taken from `new`.
- Otherwise keep the line and print `kept hand edit on MEMORY.md line <rel>`. On a drop, the
  hand edit wins the next `write` anyway.
- For a restore over a non-render line, print that the hand edit was replaced.
- Add one test per case, each with a mutation.
**Pattern match:** YES — `imp-widening-fold-breaks-identity-clauses` (an "affected" predicate
wider than the change it guards).

### SKETCHY: an index-write failure leaves exactly the bug-199 state, by hand, untested {#s-2}

**File:** `src/refmatrix/memory_index.py:1170-1181`
**What:** The sidecar is written first. If the `MEMORY.md` write then fails, the run prints
`refused: … was repaired but writing … failed; … copy <backup> back before the next write`
and exits 1.
**Why it's sketchy:**
- After this failure the sidecar is repaired and the index is stale. That is the exact state
  bug-199 names. Probe C on the branch (index write fails with ENOSPC, then the next `write`)
  showed the restore reverted to the cut.
- The next `write` is not something the operator controls. The save-state bridge and the
  SessionStart index update run it automatically, so a manual "copy the backup back" races an
  automated writer.
- The docstring promises "no partial write (R4)". This path is a partial write.
- The word `refused`, used everywhere else to mean "nothing written", here follows a write.
- No test makes the index write fail, so the branch is unproven.
**Evidence:** `scratchpad/probeB.py` part C: `C rc 1`, then `C after next write sidecar: A
hand-written hook whose full text is lost because the renderer cut…`.
**Fix:**
- On an index-write failure, write `raw` back to the sidecar atomically, so both files hold
  their pre-apply bytes.
- Print `nothing changed; backups in <dir>`, and name a second failure if the rollback also
  fails.
- Add a test with an in-process failure injected only for `INDEX_NAME`, and register it in the
  mock registry: both files byte-equal to the backup, exit 1.
- Estimated effort: about 8 lines of code and one test.
**Pattern match:** YES — `imp-ledger-outside-txn` (a two-file commit with no rollback for the
second write).

### MEH: a restore keyed by an old path misses the moved file's line {#m-1}

**File:** `src/refmatrix/memory_index.py:1057-1059`
**What:** The affected-line test matches `rel in changed` or `mid in changed`. `changed` holds the
sidecar keys as written. A path key whose file has moved (`project_curated.md`, now at
`sub/project_curated.md`) aliases to the same id in `_with_id_aliases`, which is what `Entry`
reads. But the id is not added to `changed`, so the line `](sub/project_curated.md)` is not
rewritten.
**Why it's meh:** Probe D (flat dir, moved file, `--restore project_curated.md=…`) reported
`applied: … restored 1, rewrote 0 MEMORY.md line(s)`, and the next `write` reverted it to the
cut. That is bug-199's shape, through the move door, reported as a success. It is the same on
base. The trigger is a path-keyed sidecar plus a move with no `write` in between, which is the
26.4/26.5 migration window. There is no live exposure today: the live keys are equal to their
rels.
**Fix:** Add the alias for each changed path key:
`changed |= {_id_of_link(memdir, k) for k in changed if _is_path_key(k)}`. Add one test.
**Pattern match:** YES — 26.1 r4 m-1, the move window.
