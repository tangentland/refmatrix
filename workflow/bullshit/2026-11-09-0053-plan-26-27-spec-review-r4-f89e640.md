## Findings {#findings}

### SKETCHY: viascope is already laid out in type folders, so 26.1's ungated `collect` contradicts "un-organised = HEAD's render" exactly where it matters {#s1}

**File:** `task-26.1` AC-3 vs AC-9; `plan-26` `#layout-marker` ("Only two changes reach every dir",
"the latent viascope wipe").

**What:** AC-3 makes `memory_index.collect` use `iter_memory_files` with no marker condition. AC-9
says a marker-off `write` "IS HEAD's write: HEAD's render". The plan says un-organised dirs keep
"the latent viascope wipe".

**Why:**
- HEAD's `collect` is `glob("*.md") + glob("impressions/*.md")` (`memory_index.py:232`).
- Probe: viascope's memdir (no marker) already holds **142** nested memories: `feedback/` 65,
  `project/` 68, `reference/` 9. It is the ONLY fleet dir with nested non-impressions `.md`.
- So in viascope, marker-off, HEAD's write sees ~4 entries (the r1 157 → 1 wipe), while AC-3's
  `collect` sees ~146. The two specs build different files in the one dir the trade is about,
  and AC-9's flat fixture (one prose line, one entry) cannot tell which was built.
- The same applies after a rollback ([[#m1]]): kept files under `feedback/` are indexed or not
  depending on which reading wins.

**Fix:** decide one, in text. Recommended: keep AC-3 ungated (it only ADDS entries; on every
flat dir it is byte-identical to HEAD) and:
- name it as a third every-dir change in `#layout-marker` (with AC-2's walk, see below);
- scope AC-9's "HEAD bytes" to dirs with top-level + `impressions/` files only, and add a
  marker-off NESTED fixture in viascope's shape: entries under `feedback/` survive a write
  (RED at HEAD), prose still dropped (HEAD trade);
- restate the viascope trade as "prose loss on a save-state", not "the wipe".

AC-2's bridge walk is the other ungated change; probe: 0 dotfile/dot-dir/README `.md` across
the fleet, so it changes no store today. Name it anyway.

**Pattern match:** YES, `imp-exactly-head-run-head`: run the "exactly HEAD" claim on the real
dirs, not only a fixture.

### SKETCHY: 26.2's dry-run needs three flags that do not exist, says it needs none, and does not say which gate it evaluates {#s2}

**File:** `task-26.2` AC-3, `#files`; `task-26.8` AC-0.

**What:** "The CLI needs no extra flag for this. `--store-snapshot <copy>` points the dry-run …
`--path-map <live>=<copy>` is the alternative." 26.8 AC-0 runs
`rmx ingest-gmd --as-memory --dry-run --store-snapshot <copy> <LIVE memdir>`.

**Why:**
- Probe: `rmx ingest-gmd` at HEAD (`cli.py:10230`) has `--verbose --as-memory --memory-mtype
  --prestage --detach --progress`. No `--dry-run`, no `--store-snapshot`, no `--path-map`;
  none appears anywhere in `src/`. The relocated-twin case REQUIRES `--path-map`, so both are
  needed, not alternatives. `#files` names `cli.py` only for `_bridge_stats`.
- **Which gate?** AC-3b makes the path-aware gate marker-gated. Every dir measured at AC-0 is
  un-organised (refmatrix included). A dry-run that faithfully runs the dir's gate reports 0
  everywhere. The spec must say the dry-run evaluates the path-aware rule regardless of the
  marker ("what organising would refresh").
- **Daemonless.** HEAD's command always goes through `daemon_mod`, and the live memdir path
  resolves to the live root. The dev build must not contact the live daemon or hub (CLAUDE.md
  hard rule). The spec does not require `--store-snapshot` to be in-process and socket-free.

**Fix:** list the three flags in AC-3 and `#files` (`cli.py` ingest-gmd options, an
in-process read-only open of the copied catalog); delete "needs no extra flag"; state the
dry-run computes the marker-on rule; add an assertion that the `--store-snapshot` path opens no
socket (e.g. `RMX_HOME` pointed at an empty sandbox and the run still succeeds).

**Pattern match:** YES, `imp-copy-measures-the-copy` (the fix to it, one layer down).

### SKETCHY: 26.8 AC-2 compares a pre-move count with the bridge that re-ingests every moved file {#s3}

**File:** `task-26.8` AC-2; `task-26.5` AC-4/AC-5.

**What:** "After AC-4's apply writes the marker, the first bridge … must show re-ingested rows
equal to AC-0's measured `refresh_pending`, within ±5, plus the save-states forced by 26.5 AC-5."

**Why:**
- The first marker-on bridge is the apply's own (26.5 AC-4 step 4 / AC-5). It runs after the
  moves, and 26.2 AC-1 refreshes every moved file. 26.8 AC-3 expects 40 + 250 = 290 moves.
- AC-0 was measured on the unmoved dir, where "files moved since last ingest" is about 0.
- So correct code reports ≈ AC-0 + 290 and fails ±5. The "plus forced save-states" term also
  double-counts: all 40 refmatrix save-states move, so they are already in the move count.
- The >50 STOP is evaluated "before AC-4" but written inside the post-AC-4 comparison.
- I missed this in r2 and r3; it predates this fold.

**Fix:** expected = AC-0 `refresh_pending` + the preview's move count + forced save-states NOT
moved, each term reported by the bridge (26.2/26.5 stats split `moved` vs `stale-before`),
±5. Put the >50 STOP on AC-0's number, before AC-4.

**Pattern match:** YES, `imp-sort-key-granularity`: run the AC's own check through each step.
