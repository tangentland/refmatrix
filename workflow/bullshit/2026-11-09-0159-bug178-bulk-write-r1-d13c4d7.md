### BULLSHIT: two flagged silent failures deferred to "a follow-up" with no registry row {#b1}

**File:** `workflow/implementation_summaries/bug-178-bulk-write-helper.md` `#flagged`;
`src/refmatrix/store.py` `_clear_gmd_content_hashes` (the `continue`s before the new
`bulk_write`); `src/refmatrix/pagerank.py` `store_scores` (`except Exception: pass` after the
new `bulk_write`)
**What:** The summary says the pagerank swallow "is left for a follow-up" and the uncounted
skips are "left as is". Neither has a row in `bug_registry.md`, `deferral_registry.md` or
`docs/architecture/todo.md` (grep: the only hit is bug-178's own row).
**Why it's bullshit:** Rule 9a — "a follow-up" names no plan or task. `_clear_gmd_content_hashes`
selects `kind IN ('doc','memory')`: a memory row whose meta contains `gmd_content_hash` but does
not parse keeps the stamp, so `clear_tracked_stamps` leaves that memory file at `pass1-skip` on
every reingest, and `gmd_hashes_cleared` does not count it. That is a memory path, covered by
`CLAUDE.md#no-silent-failures`. The pagerank swallow is not on a memory path. On DuckDB
`commit()` is a no-op, so the `except` can only fire on SQLite. Both are HEAD behaviour on lines
this diff did not change, so neither has to be FIXED in this merge. Both still have to be
ANCHORED.
**Fix:** Either count the skips now (`gmd_hashes_skipped` in the result, about 3 lines), or file
a `bug_registry.md` row with symptom, file and root cause. File a second row for the pagerank
swallow. Then point the summary's `#flagged` at both rows.
**Pattern match:** YES — the registry-row deferral lineage (`impression_bsd_registry_row_deferral`).

### SKETCHY: the dup-key `updated_at` touch has no test — m4 survives {#s1}

**File:** `src/refmatrix/store.py` `bulk_upsert_entity` (`if touch_rows: bulk_write(... SET updated_at ...)`)
**What:** The second statement is the one piece of `_collapse_entity_payload` that the goldens
cannot see. The summary says so ("checked by hand"). Disabling it leaves 31/31 green. probe1
shows the regression: a flip-flop batch (B then the stored A) leaves `updated_at=100` where the
sequence leaves `200`, and a meta flip does the same.
**Fix:** Add a test that pins the clock, compares DuckDB against the SQLite row-wise reference,
and covers at least flip-flop, meta flip, agree-equal-stored (no bump) and agree-new (bump).
probe1's scenarios can be lifted verbatim.
**Pattern match:** YES — a golden that excludes the column the fix is hardest on.

### SKETCHY: "ALWAYS unregisters (finally)" is untested — m2 survives {#s2}

**File:** `src/refmatrix/backend.py` `bulk_write` `finally: duck.unregister(name)`
**What:** R1 requires the unregister. Removing it leaves every test green. The cost is real: each
call's Arrow table would stay pinned on the daemon's long-lived writer connection, under a new
unique name every time. That covers pagerank's whole score table on every reingest and
`compile_pairs`' blobs.
**Fix:** Add a test that, after each site op and after a statement that raises, asserts no
`_rmx_*` relation is left registered on the connection. Use `duckdb_views()` or the connection's
registered objects. The probe pattern is in `bug178-bsd-r1-probe1.log`.

### SKETCHY: the R3 fence is untested and its accessor has no caller — m5 survives {#s3}

**File:** `src/refmatrix/backend.py` `DuckDBConnection.executemany`,
`DUCK_EXECUTEMANY_MAX_ROWS`, `duck_executemany_calls()`
**What:** No test raises `DuckDBExecutemanyError` or reads the counter. Setting the threshold to
10^12 leaves 31/31 green. `duck_executemany_calls()` has zero callers in `src/` or `tests/`, while
its docstring and the summary present it as how a stray call is "counted". Today the static AC-5
scan carries the whole guard. The runtime half of R3 ("raises above a small count or logs a
counted warning") is unproven.
**Fix:** Add a test where 33 rows raise and name `bulk_write`, and where <=32 rows run, bump
`duck_executemany_calls()` by one and emit the warning (`caplog`). Otherwise delete the accessor
and say that the count appears only in the log line.

### MEH: pinned Arrow `int64` silently truncates floats and rejects bools {#m1}

**File:** `src/refmatrix/backend.py` `bulk_write` (`pa.array(vals, type=pinned)`)
**What:** Probe: `1.5` into a pinned `int64` column stores `1` without an error, and `True`
raises `ArrowTypeError`. HEAD's DuckDB `executemany` cast both. No current site passes either: I
traced every pinned int column, and all of them get `int()`, `len()`, entity or linkage ids, or
the constant `protected=0`. The helper contract does not state this.
**Fix:** Document it in the `bulk_write` docstring, or reject non-int values for int-pinned
columns.
