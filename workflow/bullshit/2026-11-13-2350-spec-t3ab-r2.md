## Findings {#findings}

### SKETCHY: two specs build `pack(held=…)`, with incompatible `held` types {#s1}

**Files:** 25.1b `#k3` (`:94`) and Files (`:344`); 10.2 R3 (`:120-140`) and Files (`:339`).

**What:**
- **25.1b (r2) now builds the held path.** `#k3` reads: "`recall_pack.pack(..., held:
  "Collection | None" = None)` performs steps 1-4; `held=None` is the empty set, and 10.2 supplies
  the held KEYS". Its Files row reads "`pack(held=…)` with tier-pinned removal", and AC-25 passes
  `held` = {r, q}, which is key membership.
- **10.2 still claims the same build.** Its Files row reads "`pack(held=…)` tier-pinned (h13)",
  and R3 declares the same `"Collection | None"` signature. But R3 decides each row by
  `held.covers(item_key, full_run_tier)`: a `HeldSet` with h15's tier-aware rule.

**Why:**
- **A key collection cannot express tier-aware held in one pack call.** The full-run tier exists
  only inside `pack`. A pointer-shown item that the full run puts at tier 1 must NOT be held
  (h15; 10.2 AC-2, the pointer-then-body leg).
- **So the caller is forced to pick a workaround:**
  - run `pack` twice, which breaks `#k3`'s "One pack call";
  - or change 25.1b's signature, which 10.2 R3 says it doesn't touch.
- **The ownership is doubled.** An unattended build hits both problems at 10.2's RED.

**Fix:**
- Make 25.1b the one owner.
- Type `held` as a protocol with `covers(key, full_run_tier) -> bool`, where a plain key set
  adapts to "covered at every tier".
- Add an AC-25 leg in which `covers` is false at the full-run tier (the row stays at its tier),
  with the mutation "membership used instead of `covers`".
- Change 10.2's Files row to "passes a `HeldSet`".

### SKETCHY: 10.2's S9 n-floor and plan-28's end rule conflict {#s2}

**Files:** 10.2 R7 (`:207-209`); plan-28 task 28.4 (`spec-wave-t3c`, `:60-61`); plan-28 `:97`.

**What:**
- **10.2:** "If either of `A+dedupe` / `A+full` has fewer than 40 sessions in a store at the
  period's end, the period is extended ONCE by 14 days. If the floor still fails … INCONCLUSIVE".
- **28.4, which owns the period:** "the end rule (the later of 14 days and 40 sessions per cell per
  store; at 42 days without the minimums, the session leg reads report-only)". plan-28 `:97`
  calls that "10.2 R7's minimum".

**Why:**
- Under 28.4 the period cannot end below 40 before day 42, so 10.2's "+14 days once" can never
  fire as written.
- The two specs give different inconclusive horizons: day 28 by 10.2's reading, day 42 by
  plan-28's.
- The period has two owners (L53: the period values are plan-28's).

**Fix:** 10.2's n-floor row defers to 28.4's end rule ("report-only at 42 days" ⇒ INCONCLUSIVE,
no default change). Alternatively, the lead rules one horizon, and 28.4 adopts it.
