## Findings {#findings}

### BULLSHIT: the carried block re-carries truncated entry lines on every render; real cliquedb grows 8 lines per render and then freezes {#b-1}

**File:** `src/refmatrix/memory_index.py:197-203` (`Entry.line`), `:387-393` (`_prose_lines`)
**What:** `Entry.line` cuts every line at 200 chars. When the title is long, the cut lands before
`](rel)`. The line still starts with `- [` but has no link, so `_prose_lines` reads it as prose.
The next organised render carries it, and then renders the same truncated entry again.
**Why it's bullshit:** AC-5 says re-rendering "re-carries it once. It never duplicates". The
summary claims AC-5 is met. It is false on 2 of the 4 real fleet dirs I tested.
**Evidence:** `bsd-26.1-carried-growth-cliquedb.log`, run on a copy of cliquedb's memdir with a
layout-1 marker added:
- the carried block goes 8 → 16 → 24 … → 64 lines over renders 1-8, with only 8 unique lines;
- at render 11 the index is 40,458 chars, well over the ~24.4 KiB load limit;
- from render 12 on, every write refuses with "96 prose lines, 19355 chars leaves less than 25%";
- so once save-state has run about 12 times, the index is frozen for good.

cliquet grows by 1 line per render. HEAD's live cliquedb index already holds 8 link-less entries,
a pre-existing defect: those 8 memories cannot be reached from the index. The fixtures missed this
because every title in them is short.
**Fix (small):**
(a) `Entry.line` never cuts the link: shorten the title, then the hook. I probed this on the same
copy: 122 lines on each of 4 renders, `--check` in sync.
(b) `_prose_lines` (organised path) skips any line that equals an entry line the render
generates. Without (b), the 8 legacy HEAD lines are carried once as junk.
(a) changes marker-off bytes for long-title dirs (cliquedb), so record it as a stated change or
gate it.
Add a test with a title over 200 chars that renders twice. Log the HEAD link-cut in
`bug_registry`.
**Pattern match:** YES. Fixtures miss the real-data shape (feedback_green_tests_are_not_a_working_command).

### SKETCHY: the lose-any-prose refusal is unreachable, a dead guard {#s-1}

**File:** `src/refmatrix/memory_index.py:549-555`
**What:** `lost = [p for p in prose if p not in after_set]` checks text that starts with
`_carried_block(prose)`. Every prose line came out of `splitlines()`, so it has no line break in
it, and it re-splits to itself. The condition cannot be true.
**Evidence:**
- 0 of 48 organised renders made it true (4 real dirs × budgets 24000/40000/8000/3000 × 3
  re-renders; `bsd-26.1-probes.log`);
- the implementer's mutant survives with 82 passing;
- the summary says it is "a check on the written text". It is not: it checks `text` before the
  write, and the guard never sees what lands on disk.

It also guards the wrong failure. Prose is lost through [[#b-1]] (growth, then a frozen index) and
through [[#m-1]] (an over-budget tail). The guard can see neither.
**Fix:** Remove the branch. Amend AC-6's "or when ANY prose line would be lost" to say the render
carries all prose by construction. The AC-5 verbatim test already pins that, and it kills the
drop-the-block mutant. Do not keep it as a tautology.

### SKETCHY: the "ONE ordering" of save-states is intransitive, so which is newest depends on input order {#s-2}

**File:** `src/refmatrix/memory_layout.py:184-204` (`_cmp_newer`)
**What:** On the same day, two datetimes are compared directly. A date-only value, or a mix of
tz-aware and naive, falls back to mtime. The relation is not transitive.
Probe (`bsd-26.1-probes.log`): A has `12:00`, mtime 1000. C has `10:00`, mtime 3000. B is
date-only, mtime 2000. So A beats C, C beats B, and B beats A. Across the 6 input orders,
`sort_savestates(...)[0]` returned each of A, B and C, so `newest` follows scandir order.
**Why:** 26.3 AC-3 routes `rmx recall-state` through `iter_savestates`. A cycle there resumes the
wrong session. The spec's rule (r3 m2 plus the datetime rule) is what produces the cycle. 26.3's
two-file cases cannot show it.
**Fix:** Amend the spec before 26.3 builds on this. Make the key a total order: within one day, use
the datetimes only when EVERY same-day candidate has one with the same tz-awareness, otherwise
mtime for the whole group. Or key on `(day, mtime, name)`. Add the 3-file test.

### SKETCHY: the memory walk drops three file shapes without counting them, and the daemon path's count reaches no caller {#s-3}

**File:** `src/refmatrix/memory_layout.py:118-136`; `src/refmatrix/ingest_gmd.py:1415-1420`
**What:** The docstring says `skipped` receives "every `.md` path the walk excluded". In practice:
- a symlinked sub-folder is skipped without being counted;
- a dangling `x.md` symlink is skipped without being counted;
- a `.gmd` file is skipped without being counted, and HEAD's bridge did ingest it.

Probe (`skip.py`): the bridge took only `feedback_a.md`, and stderr counted only `.hidden/y.md`.
On the daemon ops, the "skipped N" line goes to the daemon's stderr log. It is not part of the
report or stats that the hook or CLI receives.
**Why:** CLAUDE.md #no-silent-failures (CRITICAL): a skipped file is counted and printed. Live
exposure today is 0: across 19 fleet memdirs there are 0 symlinks and 0 `.gmd` files.
**Fix:** Append these paths to `skipped`. Return the skip count and names in the op result (stats)
so the caller prints them.

### MEH: an organised write writes a render it knows is over budget {#m-1}

**File:** `src/refmatrix/memory_index.py:541-571`
**What:** The 25% rule tests the prose alone. On cliquedb, marker-on render 1 is 24,378 chars
(marker-off is 23,716) and reports "STILL OVER … the tail WILL be cut on load", then writes it
anyway. The carried prose is what pushed the tail out.
**Fix:** In an organised dir, refuse when the render is over `max_chars` and the prose is the
margin. Name the prose count, as the 25% refusal does.

### MEH: dead curated hooks have no way to retire {#m-2}

**File:** `src/refmatrix/memory_index.py:350-372`, `:326-347`
**What:** In an organised dir, a hook whose memory is gone stays in the sidecar forever and is
re-announced on every write. MEMORY-RULES #forget does not name the sidecar, so forgetting a memory
leaves its hook behind. If a later memory reuses the same id, it inherits the dead hook.
**Fix:** Add a sidecar step to the forget flow, or have `organise --check` list the dead keys.
This is not a deferral. AC-4 chose "kept and reported".
