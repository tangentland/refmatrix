### S1 SKETCHY: no test pins the pairing invariants the docstring claims {#s1}

**File:** `src/refmatrix/telemetry.py:1397-1457` (`pair_cli_recalls_with_query_log`).
**What:** The docstring promises three things. Pairing is one-to-one, so "two hook calls in the
same second stay two calls". The match is the earliest eligible query row, "a maximum matching
for equal-width windows". The key is cwd + channel + invocation. The R8.2 node never exercises
any of them. Its paired calls are minutes apart, all in one cwd, and no two calls share a key
within 1 s. Each of the following mutations passes all 34 tests:
- M8.6: `del times[hit]` removed, so one query row absorbs every eligible end row;
- M8.13: the latest eligible query row is matched instead of the earliest;
- M8.14 / M8.15 / M8.16: cwd, invocation or channel dropped from the key on both sides;
- M8.5: the window made symmetric (±1 s).

**Why it matters live:** the copied live query.log has 6 same-key recall rows within 1 s of the
previous one. Those are the concurrent hook calls the one-to-one rule exists for. With M8.6 a
query row absorbs two end rows, and one call vanishes from both legs. That is an undercount:
bug-196's double count with the sign flipped. M8.13 loses a pair for q10, q11 / e11, e12. M8.15
pairs an agent `recall` end row with a hook `recall` query row. The docstring states the
invariant, and no test fails when it is removed.
**Evidence:** `bsdt08-r1-m8.{5,6,13,14,15,16}.log`, each `34 passed`. Direct probes of the
function show the intended behaviour at HEAD. P1: two same-second calls give `paired=2`. P3:
q10, q11 / e11, e11 gives `paired=2`.
**Fold (RED → ch-test-engineer, then GREEN if needed):** add one R8.2 node (or extend the
existing one) holding:
(a) two same-key calls in the same second, both in both logs; each is counted once (kills M8.6);
(b) q10, q11 with end rows e11, e12; both pair (kills M8.13);
(c) a same-second pair of calls that differ only in cwd, then only in invocation, then only in
channel, where one of the pair has no query row; that call's end row is counted (kills
M8.14-M8.16);
(d) once the lead rules on the direction (Q1), a cli-only call at t followed by a query-only
call at t+1 of the same key (kills M8.5 if the ruling is "after only").
**Pattern match:** YES. `imp-placebo-symmetric` / "a property stated in a docstring needs a

### M1 MEH: the window comment names the wrong interval, and a missed pair is invisible {#m1}

**File:** `src/refmatrix/telemetry.py:1390-1394`; summary `#ts-window`.
**What:** The comment derives "the end row lands 0 or 1 s after the query row" from the
ordering alone. The ordering only proves the sign. Between the two stamps,

names. The report prints `paired_with_query_log`, but not how many non-MCP query recall rows
absorbed no end row.
**Evidence:** the bound holds on real data. Over the copied live logs, 613 query→end gaps:

reached p95 3.6 s and max 10.8 s.

the live logs, 2026-11-15). Optionally print `query_rows_unpaired=<n>` per invocation on the

## Answers {#answers}

### Q1 The window direction {#q1}

**Ordering verified on every route that writes both rows.** `cli.memory_recall`
(`cli.py:12735`) runs `with log_query(...)`. Its `__exit__` stamps the query.log `ts` at
`telemetry.py:600`. Next, `rec.emit()` runs (`cli.py:12746`), then `main()` returns, then
`cli_entry`'s `finally` (`cli.py:15212`, in `cli_entry` `:15163`) calls `log_cli_invocation`, which stamps the end
row at `telemetry.py:381`. The hooks run the same CLI (`hooks.py:396`, `:453`, `:482`:
`rmx memory recall --session-start|--stdin-json|--recent`), so they take the same order. The
MCP / verb route (`verbs.py:1232`, `source=memory-recall-mcp`) writes a query.log row and no
cli.log row. The only cli.log writers are `cli.py:15228` (end) and `cli.py:11826` (start
intent), so no daemon or MCP path can produce an end row before its query row. On every route,
end ≥ query.

**Can a real gap exceed 1 s?** Yes in principle. The comment omits that `rec.emit()` (STM read,
name spans, recall-events write) runs between the stamps, and second truncation turns a real
gap in [1, 2) s into a `ts` difference of 1 or 2 (M1). **Measured:** 613 real paired calls
from the copied live logs, 2026-10-19..11-15: 610 at 0 s and 3 at 1 s. Widening to 30 s pairs
nothing more. That held under load (recall p95 3.6 s, max 10.8 s). A throwaway-store live run
was not done. A dev-venv `rmx` from the clone would hit the hub version handshake, and the
real-log measurement covers the same routes over a month of real load. The 1 s "after only"
window holds on the evidence. The lead may still rule symmetric, but no observed row needs it.

### Q2 One-to-one matching and pair choice {#q2}

Two concurrent same-key calls can cross-pair: A's end row with B's query row. That does not
change the counts, because every attribute the cli.log leg prints (channel, invocation) is in
the key, and cwd is not printed. Probes P1 (two same-second calls → `paired=2`) and P3 (q10,
q11 / e11, e11 → `paired=2`) confirm it. The greedy choice (end rows ascending, earliest
eligible query row) is a maximum matching for equal-width windows. The only count-changing case
needs two anomalies of one key inside the window: a query-only call (killed after `log_query`
exited) and an end-only call (a usage error that never reached `log_query`). They pair, and one
call is lost. On the live logs the 4 end-only rows (exit 2) have no same-key query row within
30 s. The live store has 6 same-key query rows within 1 s of the previous one, which is why
one-to-one must be pinned (S1).

### Q3 Nothing silent {#q3}

- `internal_excluded` (`:2086`) is a real count of cli.log **recall** rows skipped as internal.
  Before this diff they were skipped uncounted.
- `ts_unparseable` and `query_ts_unparseable` are real counts. A bad-ts end row is kept among
  the unpaired, so it is counted on its channel, never dropped (P5).
- All three are printed on the `cli.log: memory_recall …` line. Dropped rows are counted, not
  listed one by one. The report has no per-row print anywhere, and the CLAUDE.md rule asks for
  counted and printed, which a count on a printed line satisfies.
- None of the three has a test, and M8.7-M8.9 survive. That is S2.
- Outside the diff, and pre-existing: `_in_window` (`:1943`) compares strings, so a row with
  no `ts` is dropped uncounted by any `--since` before it reaches the new counter. That holds on
  both legs and predates T0.8. It is not filed here.
- The cli.log leg counts click usage errors (`exit_code=2`, 4 live rows) as calls. That is the
  old semantics, unchanged.
