## Findings {#findings}

### SKETCHY: an empty memory dir under the clone's own slug, which Claude Code creates on its own, silently disables the origin fallback {#s-1}

**File:** R1.4 `:196-199` ("resolves the memory dir as today, from the checkout's own slug. If
that dir does not exist, …"); AC-1.6 `:247-248` ("In a fixture whose own slug has a memory dir, no
fallback line is printed").

**Evidence:** `~/.claude/projects/` already holds empty `memory/` dirs under slugs where a Claude
Code session ran with that cwd and wrote no memory. Examples:
- `-private-tmp-claude-501--Users-tholley-claude-tools-refmatrix-47bc8f5e-…-scratchpad-modprobe-cwd/memory/`, empty;
- `…-modprobe-batch2-c5/` through `…-cB/`, all empty.

The harness creates the dir. Any session the goal starts with its cwd inside
`/Volumes/littlebig/refmatrix-t0-<n>` (an implementer driven in the clone, a `claude -p` probe)
leaves an empty `~/.claude/projects/-Volumes-littlebig-refmatrix-t0-<n>/memory/` behind.

From then on:
- R1.4 sees that the own-slug dir "exists" and takes no fallback;
- no stderr line is printed;
- the scope gains an empty dir;
- the ~1,046 memory-id refs dangle again.

The failure is loud as a lint failure but silent about its cause. AC-1.6's second case actively
blesses that path. R7.5 and AC-1.5 then fail depending on whether a session ever ran in the clone,
and R7.6 files the result as "bug-155's fix did not hold". This is the case the lead asked about:
the resolver *can* pick the wrong dir, and it does so without saying so.

**Fix:**
- An own-slug dir counts only if it holds at least one `*.md` file (MEMORY.md or a memory file).
  An empty dir falls through to the origin, and the stderr line says `own memory dir <path> is
  empty; using origin <path>`.
- Add an AC-1.6 case for an empty own-slug dir (fallback taken, line printed), and a mutation that
  treats "exists" as enough, which turns that case red.

**Pattern match:** YES (`imp-probe-real-dirs-not-fixture`: the fixture models "dir exists or
not", and the real world has a third state).

### SKETCHY: T0.3 does not say what happens when a fix fails inside its 45 trials, and no trial has a timeout {#s-2}

**File:** `#t0-3-band-fixed` `:352-355` ("Any failure in the 45 means the fix did not hold");
`#t0-3-bound` `:359-360` ("at most 30 base trials … and 45 post-fix trials").

1. **No branch for a failed fix.** If a fix fails at trial 12 of 45, nothing says whether the
   implementer:
   - tries another fix with a fresh 45, which breaks the stated bound and can repeat without end
     in an unattended goal;
   - or drops the row to `diagnosed-loud`, and whether the failed fix's code is then kept or
     reverted.

   Read literally, the bound allows one fix attempt and then no defined outcome.
2. **No per-trial wall cap.** The count bound does not bound time. A trial can hang: bug-088's
   second sighting is a test hung on a busy live daemon, and T0.3 multiplies that exposure by 3 to
   8 concurrent suites (`#t0-3-sockets`). One hung trial stalls the goal. `#t0-3-bound` records
   wall time but caps none.

**Fix:**
- Allow at most two fix attempts per bug, each with a fresh run of 45 (≤ 90 post-fix trials).
  After the second failure, keep only R3.4's diagnostic, revert the rest of the fix, and set the
  row to `open / diagnosed-loud` with both runs' counts.
- Run every trial under a wall cap derived from the R0 durations run (for example 3 × its sum for
  those files). A trial that hits the cap counts as a failure, recorded as `hang` with
  `lsof`/`ps` of the stuck process.

### MEH: `--durations=25` does not yield "the 25 slowest files" {#m-1}

**File:** `#t0-3-r0` `:343-346`.

`--durations=25` prints the 25 slowest test *phases* (setup, call and teardown entries). Summing
those by file yields as many files as those 25 entries happen to touch, often fewer than 25, and
it ranks files by their worst phases rather than their totals. Use `--durations=0` (every phase),
then sum by file and take the top 25.

### MEH: the memdir resolver either hands a child the real HOME or needs a home argument the spec does not name {#m-2}

**File:** R1.4 `:204-207`.

The resolver has to check existence under the **real** HOME. The `--print-memdir` mode, run as a
child, would need the real `HOME`, and the same bullet forbids that ("It never hands the child the
real `HOME`", per 23.0 ch-bsd r1 m3). Only the helper route is buildable as written. It must take
the home as an explicit argument and be called in-process, which is read-only, as the test already
reads `RMX_SANDBOX_REAL_HOME` at `test_gmd_lint_requires_version.py:126`.

Also state how the origin path is canonicalized before the slug is computed: strip a trailing `/`,
reject `file://` as non-local, and resolve a relative origin from `$ROOT`. Each of those cases
currently becomes the loud "neither exists" line. That is safe but avoidable.

### MEH: the header says "User gates: none", but a hook-drift stop can only be cleared by a user-gated install window {#m-3}

**File:** `:26-27` versus R7.4 `:726-733` and R7.6 `:771-777`.

When master's hook render differs from the deployed one, R7.4 stops on the O5 path. It re-runs
"only once the cause is fixed", and that fix is a deploy plus an `install-hooks` window (G31, which
is user-gated). State in the header that W1-e can wait on a G31 window. T0 adds no window, but it
can be held by one.
