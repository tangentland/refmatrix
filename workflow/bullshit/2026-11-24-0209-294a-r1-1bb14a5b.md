## Findings {#findings}

### BULLSHIT: a failed merge gate passes when it is run again, and a different merge then inherits the failure {#b-1}

**File:** `scripts/ptest.py:699-705` (`mode_merge_gate`), `:733-739` (`previous_gate`),
`:479-486` (`make_run_dir`).

**What:** The gate compares by E line against "the newest earlier `merge-gate-*` run with a
summary". It does not check whether that run passed or which merge it gated.
`make_run_dir` moves an existing run dir aside to `merge-gate-<sha>.<timestamp>`, which still
matches the glob. So the second run of a failed gate reads the first run's failures as `seen`
and passes. Any later gate inherits them too.

**Why it's bullshit:** #r7 says "a new node id or a new E line fails the gate"; only "a row that
is still open" is carried. The merge's own new failure is not an open row. P1 shows it:
- run 1: exit 1, `NEW FAILED tests/test_topic.py::test_fails_plainly`;
- run 2, same merge: exit 0, `merge gate passed: 1 shard(s), 1 failure record(s) all open in the previous gate`;
- a different merge carrying the same test: exit 0.

The failure is named (`seen (open in the previous gate) FAILED …`), so it is visible, not silent.
But the verdict and the exit code pass it, and the exit code is what a lead's merge step reads.

**Evidence:** `workflow/review-output/bsd-294a-p1-gate.log`. MX1 (the gate never reads the
previous run) survives all 69 RED tests: every AC-9 test runs exactly one gate on a fresh tree.
L194's carry-over is unpinned.

**Fix:**
- The baseline is the newest gate that PASSED for a merge that is now in `HEAD`'s history: its
  merge head is an ancestor of `HEAD`, and its summary's last line is `merge gate passed`.
- A moved-aside dir of the same merge head is never a baseline.
- Tests:
  - a failing gate run twice fails twice;
  - a second merge carrying a failure first seen in a failed gate fails;
  - a failure carried from a passed, merged gate is `seen` and named.

The effort delta is small: a filter in `previous_gate` and 3 tests.

**Pattern match:** YES. `imp-carry-rule-eats-own-output`: the carry-over reads the gate's own failed output as its baseline.

### SKETCHY: `tier_of` puts `test_suite_tiers.py`, AC-1's own file, in `devtree` because of a string in an assertion {#s-1}

**File:** `tests/tiering.py:266-280` (`_reads_real_home`), triggered by
`tests/test_suite_tiers.py:149` (`assert "real_home(" in src or "RMX_SANDBOX_REAL_HOME" in src`).

**What:** Any `ast.Constant` equal to `"RMX_SANDBOX_REAL_HOME"` counts as a real-home read. RED's
L192 follow-up (`50fd0ce2`) added that literal to an assertion, so the tier test file is now
`devtree`: 7 devtree files, where L192 names 6.

**Why:** `test_suite_tiers.py` reads nothing from the real home. As `devtree`, it is `NOT RUN`
by `ptest.sh --tier all` in every clone and lane worktree. The comment beside line 138 says
the tier tests "must run in every clone and lane (tier (c) runs in neither)", yet the file is
itself in tier (c).

No test pins the devtree set, so the drift was silent. `test_tier_of_gives_every_test_file_…`
checks only that each file has one tier. The docstring's "a docstring that MENTIONS either is not
a read" is half true: a docstring is skipped, but any other string literal counts.

**Fix:**
- Count the key only as the subscript or first argument of an environment lookup
  (`os.environ[...]`, `.get(`, `getenv(`, `setenv(`).
- Add a test that pins the exact devtree set: the 6 names of L192 plus `DEVTREE_FILES`.
- A must-fail case: a bare string literal of the key is not `devtree`.

**Pattern match:** YES. `imp-gate-false-positive-population`: a heuristic with no exact-set pin, and here a
false positive went unseen.

### SKETCHY: a quarter of the `unit` tier spawns processes or connects to daemon sockets at runtime {#s-2}

**File:** `tests/tiering.py:143` (`_NOT_A_HELPER = {"conftest"}`), `:229-244` (`_helpers` follows
only `tests.`-prefixed imports). The signal rule reads only the test file and its `tests/`
helpers, never the `refmatrix` code or the conftest fixtures it calls.

**What:** P9 ran `-m tier_unit` (2239 passed, 434 s, `bsd-294a-unitprobe.log`) under a
`sys.addaudithook` plugin. **56 of the 213 unit files** recorded at least one `subprocess.Popen`
or AF_UNIX connect (`/private/tmp/claude-501/bsd294a/unit-spawns.json`). Spot checks, each file run
alone with an argument probe:
- `test_kwic.py`, RED's own exemplar for "unit: no signal" in `test_tier_of_on_real_files`,
  spawns `rg` through the grep backstop.
- `test_bus.py` connects 11 times to a sandbox `rmxd.sock` and once to `hub.sock`.
- `test_launchctl_label.py` spawns through the `deployed_rmx` fixture (`conftest.py:247` ->
  `launchctl.binary_identity` -> `subprocess.run`, `launchctl.py:124`).
- `test_daemon_restart_cli.py`, `test_phase8_mcp_sched.py`, `test_global_memory.py` and
  `test_bug241_r3_l114.py` connect to unix sockets.

One session-level `lsof -iTCP:7777` is charged to whichever test triggers it, so the count may be
high by a file or two.

`_helpers` also skips bare helper imports (`import task25_1_support`, `from devbin import …`).
No unit file relies on that today, so that part is latent.

**Why SKETCHY, not MEH:** the tier follows #r1's letter. But its purpose ("a process or socket
signal" -> `daemon`) misses 26% of `unit`, and RED's own unit example is one of the misses.
- `-m tier_unit` is not the process-free selection its name promises.
- `default_shards` gives unit and daemon each half the core budget on the assumption that unit
  shards keep no child busy, against L192 (3)'s "at or under the core count".

Both tiers still run, so no test is lost: not BULLSHIT.

**Fix (lead's call, it may amend #r1):**
- Either a measured census: a conftest audit hook under the runner names the unit files that
  spawned or connected, and they move to `daemon`, through a `tiering.py` list with reasons or a
  must-fail census test;
- or follow the fixtures a file requests and the `refmatrix` entry points known to spawn.
- In both cases, follow bare `tests/` helper imports.

### MEH: the hang-guard process snapshot is never taken for a single-threaded hang {#m-1}

**File:** `scripts/ptest.py:350-362` (`watch_timeouts`).

**What:** P3: a test that hangs in its main thread fails on the timeout, but no `*.ps.txt` is
written, and the summary does not say no snapshot was taken. The common hang is a parent
blocked in `waitpid` on a stuck child: one thread, so no banner and no snapshot. That is the
case the snapshot exists for ([[feedback_mutation_must_fail_not_hang]]).

**Why MEH:** L194 accepted the second-thread limit. I record the measured consequence and the
cheap route:
- when a `failures.jsonl` record's E line holds `Timeout (>` while the shard is still running,
  snapshot the process group;
- or say `no process snapshot (single-threaded timeout)` on the shard line.

### MEH: the pytest-timeout refusal passes when the plugin is importable but not loaded {#m-2}

**File:** `scripts/ptest.py:122-133` (`require_hang_guard`), `:305-318` (`shard_env`, `start`).

**What:** P8: with `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` inherited, `import pytest_timeout` succeeds
but pytest does not load the plugin. The `timeout = 600` key is then an unknown-option warning,

or have the check look for `--timeout` in `pytest --help` under the shard's environment.

### MEH: the `/tmp` random-segment rule normalises the tail of any first-level `/tmp` name {#m-4}

**File:** `scripts/ptest.py:79-80`.

**What:** `normalise_e_line("E FileNotFoundError: /tmp/fixture_alpha")` equals the same line with
`/tmp/fixture_bravo`: both become `/tmp/fixtu<RAND>`. #r2 says the rule replaces "/tmp random
segments … and nothing else". A different failure can then compare equal, and the merge gate
would read it as `seen`.

**Fix:**
- Anchor the rule on mkdtemp's shape: a `tmp` prefix or a known tag, then exactly 8
  `[a-z0-9_]` characters that make up the whole component.
- Add a keep case to `test_normalise_e_line_keeps_what_tells_errors_apart`.
