### BULLSHIT #b-1: `memory_index` caps LINES; the loader cuts BYTES — the index is still truncated, right now, on the deployed build {#b-1}

**File:** `src/refmatrix/memory_index.py:38-41`, `:174-212`; `src/refmatrix/handoff.py:242-256`

**What:** bug-042 exists because "the last 34 entries [were] silently unreachable
from the surface whose entire job is to reach them". The fix enforces
`MAX_LINES = 200` and `MAX_LINE_CHARS = 200`, and reports `234 -> 193 lines`.

**Why it's bullshit:** the constraint that truncates `MEMORY.md` is a BYTE
budget, not a line count, so the cap was placed on the wrong dimension and the
failure it names is still happening. The index on disk is the generator's own
output — the deployed build agrees:

```
$ ~/refmatrix/.venv/bin/python -m refmatrix.memory_index <memdir> --check
MEMORY.md: in sync                       (exit 0)
$ wc -l -c MEMORY.md
     197   31607
```

and the load banner in THIS session, reading that in-sync file, says:

> WARNING: MEMORY.md is 30.3KB (limit: 24.4KB) — index entries are too long.
> Only part of it was loaded: 38 of 197 lines were cut off, starting at line 160

Independent computation of the byte prefix agrees: the first line past 24.4 KB
is **line 157**, leaving **41 lines** unreachable. 193 lines was never the
target; ~152 is, at the current mean of 159 B/line.

The evidence was in the author's hand. bug-042's own registry row quotes the
pre-fix banner as *"MEMORY.md is 227 lines and 31.5KB. Only part of it was
loaded: 33 of 227 lines were cut off"* — 33 cut from 227 is a cut at line 194,
which a 200-line cap does not explain, and the KB figure is quoted in the same
sentence. The mechanism was named without being measured
([[feedback_causal_story_before_evidence]]).

The two caps are also inconsistent with each other and with the budget:
200 lines × 200 chars is a 40,000-character ceiling against a ~25,000-byte
budget, and `MAX_LINE_CHARS` counts CHARACTERS while the budget counts BYTES —
18 lines in the live index exceed 200 bytes (max 208) because `—`, `→` and the
truncation `…` are 3 bytes each.

**Evidence:** `--check` in sync on both builds; 197 lines / 31,607 B; byte
prefix ends at line 157; 18 lines over 200 B; this session's own banner.

**Fix:** cap the rendered BYTES (fold until `len(text.encode()) <= budget`,
default ~24 KB with an env override), make `MAX_LINE_CHARS` a byte measure, and
assert the rendered size in a test. `render()` already returns the string — the
check is one `len(...encode())`.

**Pattern match:** YES — [[feedback_causal_story_before_evidence]],
and #b-4 of the plans 7-10 r4 round (an honest fallback firing at 100%).

### BULLSHIT #b-2: the index writer prints to stdout, and stdout is the MCP JSON-RPC channel {#b-2}

**File:** `src/refmatrix/memory_index.py:215-252` (`write(..., out=None)` → `sys.stdout`);
called from `src/refmatrix/handoff.py:249-256` with no `out=`

**What:** `write()` prints `MEMORY.md: N -> M lines (cap 200; K memories on disk)`
so the rewrite is not silent. `_ss_update_index` calls it on every save-state.
`rmx mcp` speaks newline-delimited JSON-RPC over **stdout**
(`mcp.py:246 sys.stdout.write(line + "\n")`), and `rmx_save_state` is an MCP
tool that runs in that process.

**Why it's bullshit:** every `rmx_save_state` MCP call now injects a non-JSON
line into the protocol stream. Reproduced against the real `serve_stdio` loop
with a throwaway root and memdir:

```
line 1: OK json          {"jsonrpc":"2.0","id":1,"result":{...initialize...}}
line 2: *** NOT JSON *** 'MEMORY.md: 1 -> 2 lines (cap 200; 2 memories on disk)'
line 3: OK json          {"jsonrpc":"2.0","id":2,"result":{...save_state...}}
```

MCP is the model's primary path to save-state in this project
([[feedback_mcp_first_agent_stm]]), so this is the common case, not an edge.
Worse, `mcp._emit` holds `_OUT_LOCK` precisely *"so writes from both never
interleave"*; a bare `print()` does not take that lock, so with the channel
bridge on (default) it can also land in the middle of a notification line.

The sibling condition again: the failure branch three lines above correctly
writes to `sys.stderr`; the success message goes to stdout
([[feedback_check_the_sibling_condition]]). And `write()` already has an `out=`
parameter — tests pass it, the one production caller does not.

**Evidence:** the three-line transcript above from a real `serve_stdio`
subprocess; `mcp.py:246`; `handoff.py:249-256`.

**Fix:** `_mi.write(memdir, out=sys.stderr)`. One argument, the one the
parameter exists for.

### BULLSHIT #b-3: the bug-041 poll loop silently discards a half-arrived request {#b-3}

**File:** `src/refmatrix/daemon.py:2864-2877` (`_handle`), with
`_recv_line` at `:547-560`

**What:** the 30 s blocking read became a loop of 1 s slices so the dispatcher
can notice `_shutdown_event`. `_recv_line` accumulates chunks in a **local**
list; a `socket.timeout` raised mid-message destroys them, and the new
`except (socket.timeout, TimeoutError): req_bytes = b""` swallows it and calls
`_recv_line` again on the same socket with a fresh buffer.

**Why it's bullshit:** any request whose bytes do not all arrive inside one poll
slice is truncated, and the daemon answers a protocol error instead of running
the op — on the single request path every op goes through, including writes.
Mutation, same probe, only `_RECV_POLL_S` changed:

```
poll=1.0s  gap=1.5s   ops saw: []
                      reply : {"ok": false, "error": "protocol error:
                               JSONDecodeError('Extra data: line 1 column 4')"}
poll=30.0s gap=1.5s   ops saw: [{'k': 'vvvv…'}]        <- pre-fix behaviour
                      reply : {"ok": true, "result": {"echoed": …}}
```

No log line is written on the loss path, so the daemon cannot report it. The
caller's retry logic does not help: `{"ok": false, ...}` is valid JSON, so
`daemon.call` does not retry — it surfaces "protocol error" for a request that
was well-formed. The window this opens is exactly the one this machine has
documented: a sender descheduled mid-`sendall` under memory pressure
([[project_daemon_ingest_jetsam_diagnosed]]).

`test_a_normal_request_still_works` sends the whole payload in one `sendall` —
the only case that cannot fail. Nothing in the suite sends a request in pieces.

**Evidence:** the two-arm probe above (real `Daemon._handle`, real socketpair,
real pools); `_recv_line:550` `chunks: list[bytes] = []` is function-local.

**Fix:** keep the partial buffer across slices — hoist the accumulator out of
`_recv_line` (or add a `buf=` in/out parameter) so a timeout returns what has
been read so far and the next slice appends to it. Add the split-send test.

### BULLSHIT #b-4: `daemon.py` no longer compiles on the Python the package says it supports {#b-4}

**File:** `src/refmatrix/daemon.py:1323-1327`; `pyproject.toml:10`

**What:** `_final_flush`'s log line puts an implicitly-concatenated string

(github.com/tangentland/refmatrix), so the floor is a promise to someone else.

**Evidence:** `/opt/homebrew/bin/python3.11 -c "compile(open(f).read(), …)"` at
HEAD and at `34aeddf`, transcript above.

**Fix:** either join the two literals onto one line / hoist the message into a

Better: a CI compile check at the declared floor — this is the second

### SKETCHY #s-1: the flush budget tripled and now overruns launchd's kill deadline {#s-1}

**File:** `src/refmatrix/daemon.py:1307-1311` (`RMX_DAEMON_FLUSH_BUDGET_S`,
default 15, was a hard-coded 5.0); `src/refmatrix/launchctl.py:102`
(`EXIT_TIMEOUT_S = 45.0`)

**What:** `_final_flush` waits 15 s for `_store_lock` instead of 5 s.

**Why it's sketchy:** the degraded-stop path is a sum, and nobody added it up
against the supervisor. Worst case is now
`10 + 10 + 10` (three sequential drains) `+ 3 + 3 + 3` (thread joins)
`+ 15` (flush) `+ 5` (bounded close) = **59 s**, against `ExitTimeOut = 45`
(verified in the live plist, `PlistBuddy -c "Print :ExitTimeOut"` → 45).

Replay the two incidents bug-041 reproduces, with the new budget:

| incident | stop → `daemon stopped` | with a 15 s flush | vs ExitTimeOut 45 |
|---|---|---|---|
| 09:50:24 → 09:51:03 | 39 s | 49 s | **over** |
| 11:32:28 → 11:33:06 | 38 s | 48 s | **over** |

Both fitted inside 45 s and now do not. Past `ExitTimeOut`, launchd SIGKILLs —
and a SIGKILL mid-close is the documented cause of the entities ART-index
corruption and the 2026-09-14 crash loop
([[project_refmatrix_entities_index_crashloop_0914]]), the hazard plan-4 r3/r4
spent two rounds closing. The pre-change worst case (49 s) was already over in
theory; what changed is that the two OBSERVED incidents cross the line.

Also stale in the same hunk: the comment left above the call still reads
*"5s budget is generous"* and still explains a 5 s bound that moved.

**Fix:** derive the flush budget from what is left of `EXIT_TIMEOUT_S` after the
drains, or cut `RMX_DAEMON_SHUTDOWN_TIMEOUT_S` so the sum fits; and fix the
comment.

### SKETCHY #s-2: the in-flight registry is keyed by op NAME, so it loses the op it exists to name {#s-2}

**File:** `src/refmatrix/daemon.py:2887-2894` (`self._inflight_ops[op] = time.time()`
/ `.pop(op, None)`), read at `:1317-1327`

**What:** the hunk replaces *"leaked worker likely holds it"* — a hypothesis —
with an in-flight registry, "the evidence".

**Why it's sketchy:** the registry is a `dict` keyed by op name, so two
concurrent calls of the same op share one entry. The second arrival overwrites
the first's timestamp (so the reported age is the YOUNGER call's), and whichever
finishes first pops the key while the other is still running. Reproduced with
the real `_handle` and real pools, on the exact scenario the fix exists for —
an `ingest_path` holding `_store_lock` at shutdown, with a second `ingest_path`
that finished first:

```
A still holds _store_lock; registry: {}
SHUTDOWN LOG: final flush skipped: _store_lock contended (0s timeout);
  in flight: nothing tracked — the holder is not an op, check the watcher
  or a background tick; exiting anyway so the next spawn isn't blocked
```

The guess was replaced by a confident misdirection: the log now sends the reader
to the watcher while an op holds the lock. On a daemon with `disp=20`,
duplicate concurrent op names are the normal case (hub tick `ping`,
`daemon_status`, watcher + queue `ingest_path`).

Third sighting of "a new diagnostic number is structurally incapable of
reporting the thing it names" ([[impression_bsd_counter_read_at_completion]],
[[impression_bsd_right_side_wrong_scope]]).

**Evidence:** two probes against the real dispatcher — timestamp overwritten
(`…939956` → `…940141` with both live), and the pop-while-live transcript above.

**Fix:** key on a unique id (`(op, id(fut))` or a monotonic counter) and render
`op (Ns)` from the values; the log line already formats a list.

### SKETCHY #s-3: bug-043 fixed one operand and left its sibling doing the same thing {#s-3}

**File:** `src/refmatrix/hub.py:702-728`; predicate at `:1108-1129`

**What:** the gate `if hot or pending_refine` became `if hot or new_refine`. The
commit's own comment says the miss was *"the sibling condition in the same
function"*.

**Why it's sketchy:** `hot` was not examined, and `hot` re-publishes the ENTIRE
fleet snapshot every tick for as long as a row stays hot — which is the bug's
own title applied to the operand that did not change. Measured on the live bus,
60 `global:queues` messages:

- **37 of 60** carried a hot row (`stale_files > 0`), so the old gate fired on
  those ticks regardless of the refinement backlog.
- On 2026-09-15 this project's row sat at `stale_files: 37` for **23
  consecutive ticks**, 09:49:47 → 23:37:02 — **13 h 47 m of identical
  30-minute alerts** that the new gate still permits.

The design was argued explicitly ("a hot row is news EVERY tick... suppressing
the repeat would trade alert fatigue for a missed incident"), which is why this
is SKETCHY and not BULLSHIT — but the argument was made without the firing rate,
the same omission [[impression_bsd_gate_firing_rate]] records from plan-12 r2.
A steady, unchanging stale count is not an incident recurring every 30 minutes;
it is one incident, and the hot branch needs the same
announce-on-change-and-on-escalation treatment the refinement branch just got.

Two smaller things in the same row:

- The registry's evidence is wrong for one of the five alerts it names.
  *"13:11, 13:41, 14:11, 14:42, 15:12 ... `stale_files: 0` everywhere and no hot
  flag"* — **13:11:49 carried `refmatrix stale_files: 9`**, and the tick before
  it (12:22:39) carried 3. Four of the five are right
  ([[feedback_read_identifiers_at_write_time]]).
- On a hot tick the code sets `_alerted_refinements = frozenset(pending_ids)`,
  so a candidate that arrives while any store is hot is marked announced and
  never gets its own arrival alert. Defensible (the count rides in the payload),
  but undocumented.

**Evidence:** `rmx bus history global:queues -n 60`, parsed per message; table of
timestamps vs `max(stale_files)` in the audit scratch.

**Fix:** treat a hot row the way the refinement branch is now treated — alert on
transition into hot and on a change of the hot set, with a periodic re-assert at
a much longer interval than the tick.

### SKETCHY #s-4: the "hard cap" is not hard, and the only sign it failed is a line saying nothing happened {#s-4}

**File:** `src/refmatrix/memory_index.py:201-212` (rule 3), `:246-247` (the report)

**What:** the module's one-line summary is *"Generate `MEMORY.md` … under a hard
line cap."* Rule 3 folds only PROJECT notes; feedback and reference are never
folded, by design.

**Why it's sketchy:** when feedback + reference alone exceed the cap, the
generator ships an over-cap index, prints the cap next to the number that
violates it, exits 0, and `--check` calls it in sync. Probe — 250 feedback

write() said : MEMORY.md: 0 -> 251 lines (cap 200; 250 memories on disk)
lines written: 251   MAX_LINES: 200   OVER CAP BY: 51
--check      : MEMORY.md: in sync   (exit 0)
last line    : - 0 older project memories folded — `rmx memory list` … nothing was deleted

`projects[:need]` returns fewer than `need` (here zero) and the code appends the

growth spurt away from being unable to reach the cap — see #b-1, where the real
budget is already exceeded.

**Fix:** after rendering, if the result still exceeds the budget, say so loudly
(non-zero exit for `--check`, a warning from `write()`) and name what could not
be folded. Suppress the fold line when `fold` is empty.

### MEH #m-2: the fold orders by `st_mtime` — the defect the module fixes one function above {#m-2}

**File:** `src/refmatrix/memory_index.py:203` vs `:190-194`

The save-state pointer explicitly does NOT sort by an incidental key: *"By DATE,
not by stem… `created` comes from the frontmatter, mtime is the tiebreak."*
Twelve lines later the fold — the rule that decides which memories DISAPPEAR
from the index — sorts by `e.mtime` alone, although `Entry.created` is already
parsed and sitting in the object. A clone, a `git checkout`, a formatter, or a
bridge run that rewrites files reorders which memories get folded. Same class of
mistake, one function down.

**Fix:** `key=lambda e: (e.created, e.mtime)` — the key the file already uses.

### MEH #m-3: nothing runs `--check`, and `--check` cannot converge on the dir `write()` refuses {#m-3}

**File:** `src/refmatrix/memory_index.py:255-278`

`memory_index` is not a verb, not a CLI command, not in
`CLAUDE.md#before-commit`, and not in any generated hook. The only production
caller is `handoff._ss_update_index`, so index drift is detected only at the next
save-state, and the `--check` the registry cites as proof is a hand-run command.

Second, the guard added for the empty-dir case covers `write()` only: on a

instruction it gives cannot succeed.

**Fix:** make it a verb (the project's own anti-drift rule), add it to the commit
gate next to `rmx install-hooks --check`, and give `check()` the same empty-dir
branch with its own message.

[[#suite]]). Several tests hard-assume the canonical checkout path or the
installed binary's identity — installed-vs-generated hooks, plist renders from
`which rmx` / `sys.argv[0]`, editable-install `code_path` checks — so a detached
`git worktree` at the very sha under test fails 42 tests that pass in-tree
(same three files: 42-failing → 29 passed in 16.95 s in the real checkout).

The practical cost is the one I just paid: once the working tree moves on, a
commit's suite result can no longer be reproduced from its sha, and the only
available number is one taken on a mixed tree. This ledger has filed
"full-suite log ≠ committed tree" twice before; this is why it keeps happening.

**Fix:** let those tests take the repo root from `refmatrix.__file__`'s parents
rather than a fixed path, and skip the installed-hooks/plist identity checks
when `CLAUDE_PROJECT_DIR` (or the discovered root) is not the canonical one.
