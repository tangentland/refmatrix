## Findings {#findings}

### BULLSHIT b-1: the read gate is keyed to `session_id`, which every subagent and teammate shares with the lead {#b-1}

**File:** `src/refmatrix/handoff.py:1370-1465` (`gate_status`, `gate_decision`,
`record_pull`, `remind_line`); `src/refmatrix/cli.py` `_recall_state_handoff`;
`src/refmatrix/hooks.py:507-531` (`_handoff_cmd`).
**What:** the gate, the pull marker and the handoff file are all named by the envelope's
`session_id`. Nothing in the change reads `agent_id`. `grep -n agent_id src/refmatrix/*.py`
finds only `cctree.py`.
**Why it's bullshit:** a subagent's hooks carry the PARENT's `session_id`, with `agent_id` and
`agent_type` added.
- Claude Code 2.1.331's common hook input is `{session_id: e.id, transcript_path: Qh(e.id), …,
  agent_id: g?.agentId, agent_type: h}`. Its PreCompact input is built with
  `{agentId: r.agentId, agentType: r.agentType}`.
- This bsd's own transcript (`…/8adeba5c-…/subagents/agent-absd-cah-….jsonl`, an in-process
  teammate) records `sessionId: 8adeba5c-7501-…`, which is the lead's id.
- A real subagent auto-compaction fired the project's `SessionStart:compact` hooks INSIDE the
  subagent, with the parent's session id. In `070141d0-…/subagents/agent-agreen-216-….jsonl`,
  `compact_boundary` (trigger auto, 968,605 → 13,382 tokens) is followed by four
  `hook_success` records `hookName: SessionStart:compact`, one of them
  `recall-state · session 070141d0-…`.

So in this project's normal mode of work (a lead plus background teammates), the probes show
three failures (`p5`):
1. **The lead's gate denies every teammate.** After the lead's compaction, a teammate's Bash
   call (`session_id=lead01, agent_id=a123`) exits 2 with "read …/handoffs/lead01.txt first".
   Every background agent stalls until the lead reads.
2. **A teammate lifts the lead's gate.** The deny reason tells the teammate to read the lead's
   handoff. When it does, `PostToolUse` `pulled` writes `lead01.pulled` and the lead's own Bash
   is then allowed (`p5-lead-bash-after-subagent-read (0, '')`). The lead was never made to
   read the file, the teammate's context now holds the lead's handoff, and telemetry records
   the lead's pull: `{'event': 'pull', 'session': 'lead01', 'seconds': 0.777}`. The R3b
   compliance figure counts a read that never happened.
3. **A teammate's own compaction gates the whole session.** `SessionStart(compact)` fired with
   `agent_id=a999` writes `handoffs/lead02.txt` and arms the lead's gate. The lead
   (`git status`) and a sibling (`agent_id=a777`) are both denied (`p5-lead-bash-after-subagent-compact`,
   `p5-sibling-bash`: exit 2). The pointer went only to the subagent that compacted.

None of the 21 tests in `tests/test_compaction_handoff.py` fires an envelope with `agent_id`.
**Evidence:** probe `p5` output, quoted above; binary excerpt
`agent_id:g?.agentId,agent_type:h` in the hook-input builder; the transcript records named above.
**Fix:** read `agent_id` from the envelope.
- `gate_decision`, `record_pull` and `remind_line` act only when `agent_id` is absent, i.e. for
  the session's main thread. A subagent's call is allowed, and its Read of the file lifts
  nothing.
- `recall-state --handoff` with `agent_id` set neither writes the file nor arms the gate. It
  prints what that subagent should see (see b-2).
- Add tests with real-shaped subagent envelopes: a gated lead does not block `agent_id` calls; a
  subagent Read does not lift; a subagent `SessionStart(compact)` arms nothing.

This is about 20 `src` lines. The shell fast path can stay, because Python decides.
**Pattern match:** YES. `imp-one-control-point-is-a-census`: one identity key (the session) was
assumed to be one actor.

### BULLSHIT b-2: a subagent's compaction gets the lead's one-line instruction and the lead's handoff {#b-2}

**File:** `src/refmatrix/cli.py` `_precompact_hook` and `_recall_state_handoff`;
`src/refmatrix/hooks.py:484-501`.
**What:** the one PreCompact command prints "Compaction summary: write at most one line … Do not
restate files, decisions or plans", and the handoff it points to is the recall-state of the
envelope's `session_id`.
**Why it's bullshit:** PreCompact fires for subagent compactions. The builder passes
`agentId: r.agentId`, and `070141d0`'s agreen-216 subagent auto-compacted at 968k tokens. With
this change, a long-running teammate's compaction summary shrinks to one line. Its
"authoritative" handoff is then `recall-state` for the LEAD's session: the lead's save-state, the
lead's STM digest, the lead's goal. The teammate's own task, files and findings are dropped
by design. Before C1, a subagent compaction kept Claude Code's normal summary.
R2 and R3 were written for the session's main thread. Nothing in the spec or the tests
considers a subagent compaction.
**Evidence:** the PreCompact input builder above (`agentId` carried); the agreen-216
compaction plus its `SessionStart:compact` hook records; probe `p5`
(`p5-subagent-compact-wrote …/handoffs/lead02.txt`).
**Fix:** when the envelope carries `agent_id`, PreCompact skips the instruction, so the
summary is Claude Code's own. Whether it still saves state is a lead call: saving would
overwrite `savestate_<lead>` from a subagent's turn, as before C1. `recall-state --handoff`
prints nothing, or the pre-C1 budgeted inline report, and arms nothing. AC-3's live probe at
release should include one subagent compaction.
**Pattern match:** YES, the same root as b-1.

### BULLSHIT b-3: the gate traps a session when the handoffs dir cannot be written after arming {#b-3}

**File:** `src/refmatrix/handoff.py:1423-1450` (`record_pull`), `1370-1394` (`gate_status`).
**What:** `record_pull` writes the `.pulled` marker first and only then unlinks the gate. If the
marker write raises, the CLI turns it into `ClickException` (exit 1). The gate file stays,
`gate_status` still finds the file present and readable, and the gate stays `armed`.
**Why it's bullshit:** R3b says the gate "can never trap the session", and the lead's case list
includes "the marker dir unwritable". Probe `p4` arms a `/clear` gate and then makes
`handoffs/` mode 555:
- the Read is allowed (`p4-read (0, '')`);
- `pulled` fails: `(1, "Error: handoff pulled: could not lift the gate: PermissionError: … sessE.pulled")`;
- every later Bash is denied (`p4-bash-0/1/2: exit 2`), and the reminder keeps firing.

The only exit is `GATE_EXPIRY_S` (24 h). For a working session, that is a permanent deny.
**Evidence:** probe `p4` output, quoted above.
**Fix:** a gate that cannot be lifted must stand down.
- In `record_pull`, unlink the gate before writing the marker, and treat a failed marker write
  as a stand-down.
- In `gate_status`, stand down, with its one line, when the handoffs dir is not writable
  (`os.access(dir, W_OK)`): then neither the pull nor the stand-down can persist.
- Add a test that chmods the dir after arming.

The change is a few lines.
**Pattern match:** YES. `imp-fail-closed-per-item` / `imp-clear-on-the-failed-item`.

### SKETCHY s-1: the deny channel is exit 2, which is also click's usage-error exit, so a rollback denies every tool call with no way out {#s-1}

**File:** `src/refmatrix/cli.py` `handoff_gate` (`sys.exit(2)`); `hooks.py` `_handoff_cmd`.
**What:** the gate denies by exiting 2. Claude Code treats any exit 2 from a PreToolUse command
as a block.
**Why it's sketchy:** probe `p7` puts the deployed 0.84.0 `rmx` (no `handoff` group) on the
hook's PATH while a gate file exists. The fast path finds the `.gate`, and the call exits 2 with
"No such command 'handoff'". That blocks every tool, including the Read of the handoff. No rmx
code runs, so nothing can stand down or expire. The only way out is the user deleting the gate
file. The trigger is narrow: a rollback of 0.85.0 while any session holds a gate, or a PATH that
resolves an older `rmx`. Still, the "never trap" property then rests on click's exit code.
**Fix:** deny with exit 0 and `hookSpecificOutput.permissionDecision: "deny"`, which RED's
`denials()` already accepts. In the generated wrapper, map any other non-zero exit to 1: for
example `rmx handoff gate; s=$?; [ $s -eq 2 ] && exit 1; exit $s`. That stays loud, and it is
not `|| true`.
**Pattern match:** NO.

### SKETCHY s-2: PreCompact has no overall time bound, and the bound test became vacuous {#s-2}

**File:** `hooks.py:484-501` (`rmx save-state --precompact --no-sync`, no `--timeout`);
`handoff.finalize_save_state`; `tests/test_plan2_remedy*.py` (amended).
**What:** the promote moved into save-state. Its daemon write is bounded at 30 s with no retries
(`_promote_digest`). But a successful promote then files the digest under the subject through
`_subject_upsert` and `_subject_link`, each `timeout=60, retries=2`. The GMD lint runs with a
20 s timeout. The serial worst case is about 30 + 2×180 + 20 s.
Claude Code 2.1.331's default hook timeout is `bm=600000` ms, so compaction can be held for
minutes. If the hook is killed, no instruction prints at all. Before C1, the PreCompact
`--no-promote` save-state never reached subject filing, and the promote ran as `focus summarize
--promote --timeout 30`.
The amended guard now reads `pre = [...focus summarize --promote...]; assert all("--timeout 30"
in c for c in pre)` over an EMPTY list. The "fails loud before the harness kills it" pin
(bsd-plan2-r3 #m-5) no longer constrains anything. Measured in the sandbox (no daemon): 0.33 s.
**Fix:** give `save-state --precompact` a budget, as the Stop hook has `--timeout 8`. Pass it to
the promote and to subject filing with `retries=0`, and re-pin the bound on the generated
PreCompact command.
**Pattern match:** YES. `feedback_daemon_call_retries_multiply_timeouts`.

### MEH m-1: the shell fast path and Python resolve different stores {#m-1}

`_handoff_cmd` bakes `<refmatrix_root>/handoffs` into the shell test. `rmx handoff gate`,
`pulled` and `remind` then resolve the store with `_root()`, which walks up from the hook's cwd.
With the cwd outside the project (probe `p6-cwd-elsewhere`), the shell sees the gate, Python
consults the global store, and the call is allowed. This fails open rather than trapping, but
the gate silently does nothing there. Fix: export `REFMATRIX_ROOT=<root>` in the generated
handoff commands.

### MEH m-2: stale `--precompact-checkpoint` help {#m-2}

`cli.py` `install-hooks --precompact-checkpoint` still says "PreCompact `rmx save-state
--no-promote --no-sync` checkpoint". It is now `--precompact` with promote, and off means
`rmx handoff precompact`.

### MEH m-3: abandoned gates and handoff files are never reaped {#m-3}

A gate expires only when its own session consults it. A session that ends unread (a `/clear`
and then exit) leaves its `.gate` forever. The `pulled` fast path is `per_session=False` (any
`*.gate`), so from then on every Read in every session on the store starts Python (about 0.12 s
measured). `handoffs/*.txt` (about 45 KB each at the R3 measurement) and `events.jsonl` grow one
file or row per session, unbounded. Fix: reap expired gates and old handoff files when a new
one is written.

### MEH m-4: the `precompact` recall channel and budget have no producer left {#m-4}

R2 removed the generated PreCompact `memory recall --recent`. `hook_budget` still carries
`"precompact": 9_000` and `precompact_recall_cmd`, and `telemetry`'s channel map keeps it.
`test_m2_by_producer…` now feeds a hand-written `_PRECOMPACT_RECALL_ARGV` to keep the channel
counted. Either retire the channel or say why it stays.

## Probed and clean {#clean}

- **Baseline (p1).** `clear` arms the gate. Bash is denied (exit 2) with the reason. A Read with
  offset 5 is allowed but does not lift (ruling `#rr-read`). Another session is untouched. The
  reminder names the path. A Read with no offset lifts.
- **The file deleted after the pointer (p2):** one `systemMessage` stand-down line, then silent
  allow.
- **A symlinked path and a `/tmp` spelling (p3):** both allowed, and both lift (`realpath`).
- **Hub and daemon down:** the sandbox had neither; the gate uses only files.
- **An empty or prose envelope (p6):** exit 0, said on stderr.
- **Two sessions on one store:** the files are per session, and session B's call is allowed.
- **R6 (p8, real transcripts).** A set goal round-trips into `{#active-goal}`, the handoff file
  and the pointer. A goal quoted in a `tool_result`, pasted mid-string in a user message, or
  quoted in assistant text is not taken. The current session's 4 tag-bearing records
  (teammate-message quotes) are not taken. The two real cliquedb `/goal` records parse
  (`sha256[:12] 96ab8d893a6c`, set 2026-11-09T09:25:23Z and 2026-11-10T20:03:51Z). Cost:
  0.04 s on a 21.5 MB transcript.
- **PreCompact output:** 440 B, 2 lines (cap 1,000 B; far under the ~10k cut). Progress and the
  MEMORY.md line go to stderr only. A manual `/compact <text>` prints nothing.
- **Pointer size.** The pointer with a goal line is under 1,024 B (RED contract).
- **`install-hooks --check` on a sandbox install:** `hooks in sync`. The committed repo
  `.claude/settings.json` equals `render_managed` for the dev tree under the recorded flags,
  except for the `$HOME`-derived paths the sandbox HOME changes. The `.refmatrix/CLAUDE.md`
  briefing carries the rule line. This repo's CLAUDE.md does not import it, which is ruling
  `#rr-claude-md`'s release step.
- **Silent failures.** New `except` arms either say the failure on stderr, count it
  (`unreadable_lines`, `skipped`), or turn it into a stand-down. There is no `2>/dev/null` or
  `|| true`. The one quiet fallback is `record_pull`'s `stat` failure, which takes the recorded
  byte count (telemetry only).
- **Deferral sweep on added lines:** none. Achieved and failed goals are not modelled, which
  `#rr-goal` anchors to the L201 live check.
