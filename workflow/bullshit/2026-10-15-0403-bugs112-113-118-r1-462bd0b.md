## Findings {#findings}

### BULLSHIT b-1: `_writer_lost` races graceful shutdown, and the graceful path exits 0, so launchd does not respawn {#b-1}

**File:** `src/refmatrix/daemon.py` (`Daemon._writer_lost`)

**What:** `_writer_lost` sets `_shutdown_event` and `_stop`, then sleeps `RMX_DEGRADE_EXIT_S`
(default 2) before `os._exit(2)`. The serve loop sees `_stop` within 1 s (accept timeout) and runs
the graceful shutdown, which ends in `os._exit(0)`.

**Evidence:** I ran a real `Daemon.serve_forever()` in a child on a tmp root (scratchpad `wl.py`)
and fired `_writer_lost` once ping answered.
- Default 2 s: the process exited 2 at 2.0 s, with no "daemon stopped" line. The exit killed the
  graceful shutdown mid-way, so it won only by a margin of milliseconds.
- `RMX_DEGRADE_EXIT_S=8`: "daemon stopped" appeared about 2 s after the trigger, and the process
  **exited 0**.

An idle fleet daemon whose shutdown beats the timer exits 0. Under `SuccessfulExit=0` launchd
does not respawn it, so the daemon stays down after a log line that says "exiting for respawn".

The body is untested. M-b (no exit) and M-c (exit 0) both survive, because the only test replaces
`_writer_lost` with a lambda. The mock-registry row calls that mock "permanent" because
`os._exit` would kill pytest, but a child-process test (as done here) runs the real body.

**Fix:**
1. Make the exit code deterministic. Either `_writer_lost` sets `self._exit_code = 2` and the
   serve loop's final `os._exit` uses it, or `_writer_lost` exits synchronously like
   `_fast_exit_if_invalidated`, with no `_stop` before the timer.
2. Add a subprocess test that asserts exit status 2 with `RMX_DEGRADE_EXIT_S` both above and
   below the shutdown time.
3. Reclassify the registry row.

**Pattern match:** YES. The shutdown fix is not observable in the process it replaces
(`feedback_shutdown_fix_needs_a_second_restart`), and the guard is tested only through a stub.

### BULLSHIT b-2: the swap-failure exit still returns with the writer closed {#b-2}

**File:** `src/refmatrix/daemon.py` (`_op_replica_merge`, the `except Exception` around step 3
swap)

**What:** The summary says "Every op exit reopens the writer through one helper". The swap branch
does not. It logs, then `return {"ok": False, "error": "swap: ..."}` with `d.store` still the
force-closed Store.

This is the bug-113 failure class: the slot is unlocked until a later op lazily reconnects, and it
may reconnect to the wrong slot. By then `os.replace` may already have installed slot A, while the
`copy2` to B (an 800 MB copy on a full disk is plausible) is partial.

No test covers this exit.

**Fix:**
1. Route the swap failure through `_reopen_writer_after_merge`. Use slot A if A was replaced, else
   `prev_writer`.
2. Add a test that makes `copy2` or `os.replace` raise, then asserts the writer is open and
   locked.

### BULLSHIT b-3: the merge fails on real fleet slots, because the SET list comes from target columns and a stale source slot lacks them {#b-3}

**File:** `src/refmatrix/replica_merge.py` (`_set_all` / `_columns`, the step-5 UPDATE)

**What:** The global store's live shape is writer A current and stale B (2026-06-20) without
`entities.vectors_partition`. Refmatrix's stale A has the same shape.

**Evidence:** `merge_slots(global-snap, gB, dry_run=True)` on copies with duckdb 1.5.3 failed with
`BinderException: Table "be" does not have a column named "vectors_partition"`. The reverse
direction passed (BY NAME INSERT fills NULL). The tests build both slots with the current Store,
so they never meet an older slot.

**Fix:**
1. Build the SET list from the target columns intersected with the columns of the attached source
   (`information_schema.columns WHERE table_catalog='b'`). Do the same for `memory_content`.
2. Add a test with a slot that lacks the newest `ENTITY_COLUMN_UPGRADES` column, as source b and as
   source a.

### SKETCHY s-1: a private DuckDB instance per read-only open costs memory and threads on concurrent reads {#s-1}

**File:** `src/refmatrix/backend.py` (`open_duckdb`, read_only)

**Evidence:** Measured on a copy of the real 828 MB snapshot, opening, running 3 hook-shaped
queries and closing.

| duckdb | Path | Sequential | With 1 holder | 8 concurrent holders |
|--------|------|------------|---------------|----------------------|
| 1.5.3 | old | 20.7 ms | 9.5 ms | +0 MB RSS, +15 threads |
| 1.5.3 | new | 20.2 ms | 20.5 ms | **+699 MB RSS, +120 threads** |
| 1.5.2 | old | 63.7 ms | 37.8 ms | +0 MB RSS |
| 1.5.2 | new | 61.2 ms | 63.0 ms | +397 MB RSS |

The daemon's `context` op (scan-prompt) runs `_read_with_fallback(private=True)`, which opens one
snapshot Store per call. Concurrent sessions therefore each pay a full instance (buffer pool plus
an ncores-sized thread pool), where they used to share one. The mirror and the CLI's
`cached_replica` are unaffected.

**Fix:** Keep one private `:memory:`+ATTACH instance per (realpath, inode) in the backend registry
and return `instance.cursor()`. A new inode gets a new instance, which keeps the bug-112 fix.
Release the instance when the last cursor closes.

### SKETCHY s-2: closing a stale holder mid-statement blocks the writer, gives the reader a misleading error, and behaves differently on 1.5.2 and 1.5.3 {#s-2}

**File:** `src/refmatrix/backend.py` (`_close_stale_holders`)

**Evidence:** Probe T3 in scratchpad `behav.py`. A reader thread runs a 32 s statement on an
open_duckdb read-only connection. The path is then replaced and write-opened.
- **duckdb 1.5.3:** `close()` blocked about 32 s, until the statement finished. The reader then got
  `InvalidInputException('No open result set')`, not "Connection already closed".
- **duckdb 1.5.2:** `close()` returned, the reader got its result, and the write open failed with
  `BinderException: Unique file handle conflict`, not `StaleDuckDBInstanceError`.

Every write open (`Store._connect`, and the merge reopen) runs under the caller's `_store_lock`,
so the stall holds that lock. The raise path is untested (M-j survives).

Reach today is latent: no current daemon write open finds a stale holder, because the merge
releases its writer through `release_duckdb`. Plan-18 task 18.3's in-daemon reclaim makes it live.

**Fix:**
1. Call `con.interrupt()` before `close()`.
2. After closing, verify the path is free. If `connect` raises "Unique file handle conflict",
   re-raise as `StaleDuckDBInstanceError`.
3. Add a mid-statement test, and run the bug-112 file on the deploy interpreter (1.5.3) as well as
   .venv-eval (1.5.2).
