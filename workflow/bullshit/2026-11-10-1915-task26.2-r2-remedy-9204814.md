## Findings {#findings}

### BULLSHIT b2-1: the most frequent sync in the fleet still fails silently {#b2-1}

**Files:** `src/refmatrix/daemon.py:3450-3480` (`_op_flush_queue_async._runner`:
`except Exception as exc: d._log(f"async flush failed: {exc!r}")`); `src/refmatrix/hooks.py:183-195` (`flush_cmd`
and SessionStart `bg_parts`: `rmx sync --flush-queue --async >/dev/null 2>&1 || true`).

**What:**
- The user requirement (2026-11-10, verbatim): "if the sync stops in an error, it needs to fail loudly on the
  commandline or console, not just logs".
- The remedy made 4 surfaces loud: in-process CLI, the daemon reply, the 4 git hooks, and the watcher.
- The Stop / SubagentStop / SessionStart hooks run a fifth one, `rmx sync --flush-queue --async`, on every turn.
  The daemon runs that flush on a background thread whose only failure output is one `rmxd.log` line. The hook
  also discards the CLI's stderr.
- The PostToolUse hook enqueues EVERY edited path with no filter (`hooks.py:133-143`), so memory files under
  `~/.claude/projects/` reach this flush in every project. That puts the remedy's own new raise,
  `MemoryOwnershipError`, on this route.
- The loud test file's docstring claims "Four surfaces carry a sync". That is false.

**Probe** (`26.2-bsd-r2-probe-async-flush.log`): sandbox, throwaway daemon, memdir under
`<base>/.claude/projects/slug/memory` outside the project tree (refmatrix's live layout), x's metadata set to
`'{not json'`, x.md and a project file `docs/d.py` enqueued.
- `rmx sync --flush-queue --async` → exit 0, "flush queued".
- rmxd.log: `async flush failed: MemoryOwnershipError("purge_path(…/a/x.md): memory 'x' has unreadable metadata
  JSON …")`.
- `rmx daemon status` prints nothing about it, because `watch_flush_error` is set only by the watcher's `_flush`.

**Why it's bullshit:** the one async-flush sibling of the watcher fix, 300 lines away, was left out. That is the
requirement's scope shrunk silently. It matches feedback_check_the_sibling_condition and imp-flag-needs-an-anchor.

**Fix:**
- Generalise `last_watch_flush_error` into one daemon `last_sync_error` (`{at, route, error}`).
- Set it in `_runner` (and in any startup or tick drain of the queue).
- Clear it on that route's next good flush.
- Carry it on ping, and print it in `rmx daemon status`.
- Optionally inject it once into the agent's console through the next SessionStart or scan-prompt, since the
  async hook has no terminal.
- **Test:** async flush over a broken x → status names x until a good flush clears it.
- Effort: about the watcher change.

**Pattern match:** YES.

### SKETCHY s2-1: the fail-closed raise aborts the whole sync batch, and the drained queue is gone {#s2-1}

**File:** `src/refmatrix/store.py` (`_memory_owned_anchor_ids` raise) inside `sync._sync_paths`'s
`with s.transaction()`.

**Probe** (same log): after the failed async flush, `dirty.queue` no longer exists and the co-queued project file
`docs/d.py` has **0** entities. In the healthy twin it has 1.
- `drain_queue` unlinks the queue before the sync.
- The raise rolls back every path in the batch, so one memory row with corrupt metadata drops the sync of every
  unrelated file queued with it.
- The watcher batch behaves the same way.
- At 90abc72 this raise did not exist.

**Fix:**

  `memory_ownership_errors: [[path, msg]]` in the report, and continue.
- The CLI still exits 1 after the batch; async/watch record it ([[#b2-1]]).
- Alternatively, re-enqueue the drained paths on any flush failure.
- **Test:** broken x + `d.py` in one batch → `d.py` synced, x refused and named, non-zero exit.
