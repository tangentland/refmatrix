## Findings {#findings}

### SKETCHY s1-r4: the hub-forked daemon still inherits the hub's HTTP listener, so the b1-r3 outage persists through the port (pre-existing) {#s1-r4-forked-daemon-holds-port}

**File:** `src/refmatrix/ui/server.py:263` and `src/refmatrix/bus.py:536`, which still call
`daemon_mod.spawn_daemon` (a bare double fork) inside the hub. The refusal is at
`src/refmatrix/hub.py:946-953`.

**What:** The fork hook closes only hub.lock. Every other hub fd is copied into the daemon,
including uvicorn's LISTEN socket on the hub port. Once the hub stops or crashes, the daemon still
LISTENs on :7777. Any later `Hub.run` then sees `_pid_on_port` return the daemon's pid, logs
"hub port … already in use by pid <daemon> — not starting", and exits 0. Under launchd
`SuccessfulExit:false` that exit is not retried. So b1-r3's user-visible outcome is unchanged:
after a web-UI daemon start or a refinement accept for a stopped project daemon, no hub until
that daemon dies. Only the fd that causes it has changed. In addition, `rmx hub stop` "reaps the
orphan" by sending SIGTERM and then **SIGKILL to the project daemon** holding the port. A DuckDB
writer SIGKILLed mid-write is the 2026-09-14 ART-corruption shape.

**Evidence:** `bsd-bug129-r4-fork-probe.log`. A hub-like process held hub.lock and a LISTEN
socket on 47999, called the real `spawn_daemon(/tmp/rsvr4m)`, and then exited without unlocking.
- `lsof` on the daemon (pid 81691): no hub.lock, and `4u IPv4 TCP 127.0.0.1:47999 (LISTEN)`.
- "new hub can take hub.lock: True", then `_pid_on_port(47999) = 81691`.
- A real `Hub(port=47999).run(serve_http=True)` returned rc 0 and logged "hub port 47999 already
  in use by pid 81691 … not starting".
- After `stop_daemon`, the port was free.

**Not a regression of this branch:** `0518113` `_serve_http` already refused a held port, called
`shutdown()`, and returned 0. So this does not block bug-129. But it undercuts the remedy's
claim that "the fork hook covers every os.fork": the hook covers one fd, and the outage has at
least two.

**Fix (two lines, function already in use twice in hub.py):** move both sites to
`daemon_mod.spawn_daemon_subprocess`, as r3 fix (1) prescribed. That also removes the
fork-in-multithreaded-process deadlock hazard that `hub.py:142`/`:387` already name. If the move
is not made for 0.79.0, log a bug row naming the port leg and the SIGKILL reap.

**Pattern match:** YES. b1-r3 had the same root. It also fits
[[feedback_check_the_sibling_condition]]: one inherited fd was fixed, and its sibling fds were
not checked.

### MEH m1-r4: a stale hub.pid naming a recycled pid makes `rmx hub stop` hang 15 s and report failure {#m1-r4-stale-pid-wait}

**File:** `src/refmatrix/hub.py` `stop_hub`, the new wait loop and the new return clause.
**Evidence:** `bsd-bug129-r4-stale-pid.log`. hub.pid named a live unrelated `sleep`, and no hub
was running. `stop_hub` returned False after 15.3 s, and hub.lock was free throughout. It sends
no wrong signal: the first loop breaks on `not is_running()` before any SIGTERM. So the cost is a
15 s stall and a false "hub did not stop cleanly". A stale file needs an unsupervised hub crash,
and a reused pid is unlikely. **Fix:** stop waiting once the pid is not a hub, for example when
`ps -o command= -p pid` does not contain `hub`, or when a non-blocking lock probe would succeed
with no successor started yet.
