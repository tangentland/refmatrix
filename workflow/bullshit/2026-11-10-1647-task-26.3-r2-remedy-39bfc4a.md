## Findings {#findings}

### SKETCHY s-1: the fail-closed write is not atomic — after a mid-write failure the reader prefers the truncated copy the error says it kept {#s-1}

**File:** src/refmatrix/handoff.py:471 (`target.write_text(doc)` inside the new `try`, :461-478), :480-483
(the comment "a failed write above never costs the only copy of the newest save").

**What:** the remedy writes the save in place with `Path.write_text`, which truncates first. On a
write that fails at the open (EACCES, as RED's chmod test does), both copies survive and the
message is true. On a write that fails PART-WAY (ENOSPC, EIO), `savestates/<id>.md` is left
truncated with a fresh mtime. That breaks the remedy's own rule:

- **fresh-top pair:** the error says "the top-level savestate_sessdup.md is kept; nothing was
  saved". The walk now ranks the truncated folder copy newest (today's mtime), skips the intact
  top-level copy, and recall-state reads a 160-byte stub (probe P4, fresh-top). The kept copy is
  on disk, but no reader reads it.
- **fresh-folder pair:** the newest copy is destroyed, and the message still says nothing was
  saved (P4, fresh-folder).
- **Flat dirs:** this is every live dir today. A re-save of the same session id truncates the
  only copy. The new message says "nothing was saved" where HEAD let the raw OSError through.

**Why it matters here:** r1 recorded the non-atomic write only as a pre-existing note. This remedy
makes the write load-bearing: the delete-after-write order (R2) and the error text both assume a
failed write leaves `target` as it was. It does not.

**Fix (small):** write `doc` to a dot-named temp file in `target.parent` and `os.replace` it onto
`target`.
- The walk already skips and names a leftover dot-file.
- Keep the file mode (see impression `imp-atomic-write-changes-mode`).
- Add a test that fails the write part-way and asserts that the reader still returns the kept
  copy. Register the monkeypatch in `workflow/test_mock_registry.md`.

**Pattern match:** YES. This is `imp-atomic-write-changes-mode`'s family: a write path whose
guarantee was assumed, not probed. The guarantee was also tested only on the easy failure (an
open-time EACCES).

### MEH m-1: in a flat dir with `savestates/`, the save takes `created:` from the copy the walk did not keep {#m-1}

**File:** src/refmatrix/handoff.py:432 (`pair = ... if organised else None`) vs the comment at :428-431.

**What:** the walk resolves the pair in flat dirs too (tested). The writer does not: in a flat
dir, `created_from` is the top-level copy whatever its rank.

**Evidence:** probe P1 used a flat fresh-folder pair. The walk kept `savestates/` (created
2026-11-05). After the save, the top level has `created: 2026-10-01` (the stale copy's), and the
folder copy remains.

The spec's "next save" sentence is scoped to organised dirs, so this is MEH. But the code comment
says "comes from the copy the walk keeps", which is false here. Flat dir + `savestates/` is
exactly the shape the docstring names (a rollback that kept the folder).

**Fix:** drop the `if organised` guard on the `savestate_pair` lookup (it does not depend on the
marker), and add the flat fresh-folder case to the next-save test.

### MEH m-2: the AC-2 move path's error says "nothing was saved" without saying the legacy file was moved {#m-2}

**File:** src/refmatrix/handoff.py:464-478.

**What:** `os.replace(legacy, target)` runs before the write. If the write then fails, `kept` is
empty because `legacy` no longer exists, and the message is only "could not write ...; nothing
was saved".

**Evidence:** probe P2 used a read-only legacy file. The top level is empty, the content is now
at `savestates/`, and the CLI said nothing about the move (`moved_legacy` is set on `result`,
but the raise discards it).

**Fix:** when `result["moved_legacy"]` is set, the message says the legacy file was moved into
`savestates/` with its content intact. With s-1's temp write the content stays intact on every
failure.

### MEH m-3: three remedy behaviours have no killing test {#m-3}

**File:** tests/test_savestate_subfolder.py:650-693.

**What:** M3, M4 and M5 each survive the two save-state files.
- `test_rm_newer_copy_the_next_save_keeps_the_fresh_top_levels_created` asserts only `"removed"`
  and the file name, so either message branch passes it.
- The write-failure test runs through the CLI. With M4, a raw `OSError` still exits non-zero, so
  the `VerbError` contract that MCP relies on is unpinned.
- Nothing makes the unlink fail.

**Fix:**
- (a) a fresh-folder or tie next-save test that asserts the "removed stale top-level ... (kept
  savestates/...)" line, and the fresh-top line on the existing test;
- (b) a verb-level test (`VERBS["rmx_save_state"].run`) that asserts `VerbError` on an
  unwritable `savestates/` (probe P5's shape);
- (c) a `chflags uchg` top-level copy that asserts exit 0, `remove_failed` on the result, and the
  red line (probe P6's shape).
