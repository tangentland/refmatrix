## Findings {#findings}

### SKETCHY S1: "built from the published snapshot, never the writer" has no test that can fail {#s1}

**File:** `task-30.4-daemon-adjacency-ppr-op.md` `#r3` (the builder "never reads the writer"),
plan-30 D6, `#mutations` 1 ("the builder reads the writer store → AC-4's census"), `#ac-4`.

**What:** D6 is the claim the service's correctness rests on. The mutation that should prove it
is aimed at AC-4, and AC-4 checks two things:
1. 20 `ppr_rank` calls succeed while `_store_lock` is held;
2. a census asserts nothing reachable from the op or the service **names `_store_lock`**.

**Why it's sketchy:**
- A builder that reads `daemon.store` (the writer) directly, without the lock, names no
  `_store_lock`, so the census passes.
- The build is asynchronous and not on the op's path, so holding the lock in the test blocks
  nothing.
- Mutation 1 therefore survives. No AC observes which graph the entry was built from.
- This is the shape of [[feedback_clean_corpus_hides_a_dead_gate]]: the gate cannot see the
  breach it is named for.

**Fix:**
- Add an AC: link an edge through the writer with the publish held (no snapshot tick). Wake the
  builder with a first request for the key. The entry must not contain the edge, and its `seq`
  must be the last publish's. After the publish, the next entry contains it.
- Widen the census predicate to writer access in `adjacency_service`: `.store`, `_st(`, or a
  `Store(` open on a slot path. Plant a site that fails it.
- Point mutation 1 at both.

### SKETCHY S2: the replay and the memory band price one key, but the service rebuilds every demanded key on every publish {#s2}

**File:** `task-30.4-daemon-adjacency-ppr-op.md` `#r0` item 3 (the replay prints "builds per
day; build seconds per day" for "30.2's measured build time"), `#r0-policy-bands`, `#r3`
(rebuild "each demanded key whose entry is older than the current sequence"), `#r7` (every
daemon `context` degree walk registers demand through the provider); `task-30.2` `#r0-memory-bands`.

**What:**
- The publish sequence is global: one counter for the whole catalog snapshot.
- So a write to any partition (a session ingest, a memory add, a sync of another tree) makes
  every demanded key behind.
- R3 then rebuilds each one, about 0.5 s apiece at this store's size.
- R7 adds demand from every `context` op that walks a degree, for whichever partition it
  queried. That is not only the hook's project partition, and each key stays live for 30
  minutes.
- The replay, as specified, prices one key's build per publish.
- 30.2's memory band prices one build's peak. It does not price the steady state: about 40 MB
  per live key, plus one being built, plus the open snapshot connection.

**Why it's sketchy:** the 2% CPU band and the in-daemon-or-child decision would both be taken
on a number short by the count of demanded keys. Most rebuilds would recompute a partition that
no write touched.

**Fix:**
- The replay reads the demanded key set from 7 days of `scan` and `context` rows (partition ×
  parameters), and prices builds per key per publish.
- The memory band adds the steady state: live keys × entry bytes, plus one build peak.
- Add a rule that skips a key's rebuild when no write since its sequence touched its partition,
  for example a per-partition dirty mark set where `_request_snapshot` is called. Otherwise
  state why not.

### SKETCHY S3: a publish that fails after `begin` leaves the sequence unknown forever {#s3}

**File:** `task-30.4-daemon-adjacency-ppr-op.md` `#r2` (`begin` "incremented under
`_snapshot_lock` just before the snapshot file is replaced", `end` "just after"; the sequence is
known only "when all four reads are equal"), `#r3` step 1 ("opens it again if the sequence came
back unknown").

**What:**
- `_snapshot_catalog` returns early on an `OSError` from `_copy_out_of_process` or `os.replace`
  (`daemon.py`, base).
- If `begin` has been incremented by then, `end` never catches up.
- From then on every `open_snapshot_store` sees `begin != end`, and the sequence is `None`.

**Why it's sketchy:** three things follow, and none is bounded or loud.
1. R3 step 1 re-opens with no bound, so the `rmxd-adjacency` thread spins.
2. No read store gets a provider (R7).
3. The op ages past `RMX_ADJ_MAX_BEHIND_S` into `unavailable: behind`, which R6 classes as an
   operating state: a row and a counter, no output line.

The daemon would serve every prompt in-process indefinitely, with nothing said.

**Fix:**
- Increment `end` in a `finally` once `begin` has moved, so a failed publish is a completed
  sequence step with no new file. Or restore `begin`.
- Bound the reopen (for example 3 tries). Count the failure, and record it under
  `adjacency:<partition>` as a `build-failed`, which R6 does say.
- Add a mutation: `end` not incremented on a failed replace. It turns a test of an injected
  `os.replace` failure red.
